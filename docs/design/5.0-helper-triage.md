## Verdicts

- **port**: becomes an `hv` verb, or an internal Go package for a Python module, with the same file formats and exit codes.
- **merge**: no verb of its own. It becomes a flag or subcommand of another verb, or part of an internal package.
- **keep**: kept on purpose even though its skill goes away. Only `hv-migrate`, which #44 keeps for future migrations; it ports as `hv migrate`.
- **delete**: no 5.0 equivalent.

## Rules applied

1. **Decision (a), maintainer, 2026-10-02, relayed by the orchestrator:** where #45 and #44 disagree, #44 wins. #45's scope says to drop helpers whose only callers are go, next, init, config or update. #44 makes init, config, update and migrate into `hv` verbs. So helpers used by init, config, update or migrate are **port** and map to `hv init`, `hv config`, `hv update` and `hv migrate`. Only helpers whose sole skill callers are go or next are deleted, except `hv-archive-old`, which the maintainer kept (open question 1).
2. A caller is a skill (`hv-*/`), a shared reference (`references/`), another helper, or the managed blocks that `hv-skills-index`, `hv-map-index` and `hv-qa-index` write into the project's instructions file. Agents read those blocks and call the query helpers they name. Smoke sections are listed but don't count: A2 rewrites them against the new verbs.
3. A helper with no caller from a skill, reference or block, but documented as a user command in `docs/reference/cli-helpers.md`, is ported. `hv` is user-facing in 5.0, so documented commands keep a home. Each one is marked as a deletion candidate in its reason.
4. Thin wrappers and writer/reader twins merge into one verb (`hv-todo-set-field` becomes `hv item field set`, `hv-status-add-multi` becomes `hv status add --repos`).
5. v3 shims (`hv-managed-block-strip-deprecated`) and one-shot backfills (`hv-backfill-since`, `hv-knowledge-migrate`) merge into the verb or package they serve, so they don't become standalone verbs.

Caller columns come from a word-boundary text search over skills, references, `bin/` and `test/` at `c0ec502`. A "helpers" entry can therefore be a comment that names the helper rather than a call. The skill and reference columns were spot-checked for every delete and every reason that depends on them.

## Open questions

The verdicts below follow the rules above but have consequences a user would notice. Each one has a verdict, so A2 is not blocked; flag any of them to change it.

1. **`hv-archive-old` (port, resolved).** Maintainer, 2026-10-02, orchestrator session: ported as `hv backlog archive`, not deleted. Without it nothing moves old `## Completed` items to `ARCHIVE.md` in file-backend projects, and F1 (#71) requires each removed skill's useful behaviour to stay reachable through an `hv` verb.
2. **`hv-reconcile` (delete).** It removes stale `status.json` entries whose branch is gone and reports drift. C2 (#58) `hv round reconcile` rebuilds round state from disk and should absorb this logic in Go rather than port the script.
3. **`hv-codex-verify` (delete, resolved).** Maintainer, 2026-10-03, relayed by the orchestrator: option (c), drop the codex runner in 5.0 (#158). It runs `codex exec` headlessly. #44 decides that 5.0 has no headless sessions. The original verdict merged it into E1 (#68), but E1 is a visible Codex worker with no verdict channel, so it doesn't replace the helper. The other options were waiting for E1 or porting a minimal verb in A9 (brief: `.worktrees/codex-decision.md`, round-local, not tracked). A leftover `ship.secondOpinionRunner: codex` runs the subagent gate in advisory mode, so a FAIL still doesn't block. The `/hv-qa` `codex-verify` runner is gone. S7 deletes the file with the rest of `bin/`. E1 can add a visible-worker second opinion later.
4. **`hv-migrate` v4 body (keep).** #44 keeps `hv-migrate`. Its 678 lines are almost all the v3→v4 codemod. A cheaper reading keeps only the `hv migrate <version>` dispatcher and `issues`, and asks 3.x projects to upgrade through 4.x first. The default here ports the v4 body too.
5. **Phase assignment for groups #44 doesn't name.** Core, config, update and repo resolution go to A3; status, refactor counters and `hv summary` to A4; map, qa and `migrate v4` to A5; debug counter and `plan uncertain` to A6; git guards and worktree helpers to A8. This is my call and nobody has ratified it.
