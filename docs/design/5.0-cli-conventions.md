# 5.0 `rota` CLI conventions

These rules hold for every `rota` verb. Per-verb flags and `--json` data shapes live in the verb contract (A2, #46) and must fit inside them. The command tree comes from the [helper triage](5.0-helper-triage.md). The Go code that enforces these rules is `internal/cli`.

## Invocation

```
rota [global flags] <group> [global flags] <verb> [flags and args, in any order] [-- args]
```

The argument rule, exactly:

1. Before the verb is reached (before and between command words), the only tokens allowed are command words and global flags. Anything else that starts with `-` is a usage error (exit 2).
2. After the verb, one parser reads global and verb flags together, mixed freely with positional args: `rota item show --json 12` and `rota item show 12 --json` are the same call. The verb defines its flags. Global flags are added to every verb, and a verb may not reuse a global flag's name.
3. A token is a flag when it starts with `-` and is not `-` alone, which means stdin. `--name` and `-name` are the same flag. Docs and skills always write two dashes, except for the short globals `-C` and `-h`.
4. A flag that takes a value always takes the next token, even one that starts with `-`. `--title --json` sets the title to `--json`, and does not turn on JSON output. `--name=value` is the same as `--name value`.
5. A boolean flag takes no separate token. `--flag` means true, and `--flag=false` is allowed.
6. Giving the same flag twice keeps the last value, unless the verb contract defines that flag as repeatable (a list).
7. `--` ends flag parsing. Every later token is positional, including ones that look like flags.
8. An unknown flag is a usage error (exit 2) naming the flag.

- Any flag that takes a file path also accepts `-`, which means stdin. Bodies always come in this way (`--body-file -`), never as positional text.
- `rota` never prompts and never reads a TTY. A verb that needs a decision fails with usage (exit 2) and names the missing flag. Asking the human is the skill's job.

## Global flags

| Flag | Meaning |
|---|---|
| `--json` | Machine output: one JSON envelope on stdout (below). |
| `-C <dir>`, `--cwd <dir>` | Run as if started in `<dir>`, like `git -C`. Lets an orchestrator act on a worker's worktree without `cd`. |
| `--repo <name>` | Umbrella mode: scope the verb to the named sub-repo registered in `.rota/repos.json`. On a verb without repo scope it is an unknown flag (exit 2). Outside umbrella mode (no registered sub-repos), or with a name that isn't registered, the verb exits 3 (`resolution`). |
| `-h`, `--help` | Help for the group or verb, on stdout, exit 0. |

`rota --version` (before any command word) is an alias for `rota version`. There are no colour, verbosity or quiet flags: output carries no ANSI codes, and stdout is already the quiet channel.

## Project root

A verb that needs `.rota/` walks up from the working directory (or `--cwd`) to the nearest directory that holds `.rota/`. In umbrella mode that is the umbrella root; `--repo` picks a sub-repo below it but does not move the root. When no `.rota/` is found, the verb exits 3 with the hint `run: rota init`. Only `rota init`, `rota version`, `rota update` and help run without one.

## Output

Without `--json`, stdout carries human text, also on exit 1 and 4 when the verb has an answer to print: plain lines, lists one item per line, no colour, no tables wider than the data needs. Text output is for people and may change between releases. Skills that parse output use `--json`.

With `--json`, stdout carries exactly one JSON document followed by a newline, on success and on failure:

```json
{"ok": true, "data": { … }}
{"ok": true, "data": { … }, "warnings": ["…"]}
{"ok": false, "error": {"code": "resolution", "exit": 3, "message": "item 12 not found", "hint": "…"}}
{"ok": false, "error": {"code": "failed", "exit": 1, "message": "working tree is dirty"}, "data": { … }}
```

- `data` is the verb's result, defined per verb in the contract. A verb with nothing to return sends `{}`. A list verb returns an object (`{"items": […]}`), never a bare array, so fields can be added later.
- A mutating verb reports `"changed": true|false` in `data`. An idempotent no-op is a success (`ok: true`, exit 0, `changed: false`).
- If the arguments themselves don't parse, the usage error comes as an envelope when any token before `--` is exactly `--json`. This is the one place a value token counts, because no parse exists yet.
- `warnings` is present only when non-empty. Each warning also goes to stderr.
- A failure carries `data` beside `error` on exit 1 and exit 4 only. On exit 1, `data` is the verb's answer, so a check verb's result never has to travel inside `error.message`. On exit 4, `data` says what blocked the change and what the verb did change anyway. The verb contract defines the failure `data` per verb. Exits 2, 3, 5, 6, 70 and 71 mean the verb could not produce a result, so they send `error` alone.
- `error.code` is the name from the exit-code table, `error.exit` is the process exit code, and `hint` is optional.
- Field names are camelCase, matching `config.json` (`mergeStrategy`, `loopStartedAt`). Dates are `YYYY-MM-DD` and timestamps are RFC 3339 in UTC. Item IDs are strings (`"B07"`, or `"12"` in issue mode), so the two backends share one shape.
- Shapes change only additively within a major version. Removing or retyping a field is a breaking change.

## stderr

stderr is always text for people, never JSON, with or without `--json`:

```
rota item show: item 12 not found
hint: run rota backlog list to see open items
rota backlog drift: warning: 3 commits reference closed items
```

The first line is `rota <group> <verb>: <message>`, with `warning:` before the message for warnings. An optional next line starts with `hint:`. On failure the stderr line and `error.message` carry the same text.

## Exit codes

| Exit | `error.code` | Meaning |
|---|---|---|
| 0 | | Success, including idempotent no-ops. |
| 1 | `failed` | The verb ran and the answer is no: a guard or check failed (`dirty tree`, `item not ready`, `release blocked`), or a read-only verb's precondition doesn't hold. |
| 2 | `usage` | Bad invocation: unknown group or verb, unknown or missing flag, malformed argument. |
| 3 | `resolution` | Something named or required could not be resolved: item, milestone, plan key, sub-repo, base branch, or the `.rota/` root itself. The name follows #47. |
| 4 | `refused` | A mutating verb refused to break an invariant it enforces. Only mutating verbs exit 4: the target already exists, the operation would run on the base branch, proof is missing, a manual gate is not cleared. |
| 5 | `unavailable` | An external dependency is missing or failing: `git`, `gh`, `glab`, auth, network, or the tracker. |
| 6 | `retry` | A transient condition that a later retry can clear: a rate limit, or a lock held past its timeout. |
| 70 | `internal` | A bug in `rota`: unexpected state or an unhandled error. Report it. |
| 71 | `not_implemented` | The verb is in the tree but not ported yet. Only exists until A9. |

Use 1 when the verb exists to answer a question, and 4 when the verb exists to change something and declines to. A read-only verb never exits 4. When its precondition fails (the branch is the base branch, the requested version is not newer), the answer is no and the exit is 1.

Exits 1 and 4 say that the requested outcome did not happen. They do not say that nothing changed. Some verbs change state on the way to a no: `worker gate` can merge and then fail verification, and `ship pr-merge` records `changes-requested` on an unproven item when it refuses. Such a verb reports `"changed": true` in its failure `data`, plus the fields its contract defines for what changed. Callers read `data.changed` and never infer it from the exit code. A verb that hits a corrupt or unreadable state file exits 70, unless the contract defines a recovery for it.

## Writes

- Every write is atomic: write `<path>.tmp` in the same directory, fsync it, rename it over `<path>`, then fsync the directory. Readers never lock. The two fsyncs keep a crash from leaving an empty or missing file. A directory fsync that fails with EINVAL or ENOTSUP (filesystems without it) is ignored, because the rename has already succeeded.
- A read-modify-write takes an exclusive advisory `flock` on the sibling `<path>.lock`, never on the data file, because the rename swaps the inode. The lock is retried every 50 ms for up to 10 s, then the verb exits 6. The empty `.lock` file stays in place. This matches `hvlib_io.locked`, so `rota` and the old helpers can share a file during the port.
- JSON state files are written the way Python's `json.dumps(data, indent=2)` writes them: two-space indent, key order preserved, `\uXXXX` for non-ASCII, and a trailing newline. A file round-tripped through `rota` produces no diff.

## Config

`.rota/config.json` is read with `.rota/config.local.json` deep-merged on top. Nested objects merge by key. A scalar, an array, or a value whose type differs from the base replaces the base value. A missing or unparseable file counts as absent, and so does a local file holding `null`. A local file that isn't an object replaces the whole config. This matches `hvlib_io.load_config`, and Go tests compare the two byte for byte on shared fixtures in `internal/config/testdata/`.

Two inputs behave differently from Python, on purpose:

- `NaN`, `Infinity` and `-Infinity` are not JSON. Python's `json.loads` accepts them, but `rota` treats a file containing them as unparseable, and so absent.
- Invalid UTF-8 makes Python's `load_config` raise `UnicodeDecodeError`, which crashes the helper. `rota` loads the file and replaces each bad byte with U+FFFD.

`internal/config/divergent/` holds both cases. Its test checks that Go keeps its behaviour and that Python still differs, so this list stays accurate.

## Build and packaging

- The Go module is `github.com/l4ci/rota`, at the repo root. Releases are 0.x, so the path has no `/vN` suffix; Go requires one only from v2 on. Code lives in `cmd/rota` and `internal/`, uses only the standard library, and builds with Go 1.22.
- Users get the binary from `install.sh` (a `curl | sh` script that checks the download against `checksums.txt` and fails closed) or from the Homebrew tap `l4ci/tap`. `go install` works but is not advertised. `rota skills install` then puts the skills in place.
- `.goreleaser.yaml` builds linux and darwin, amd64 and arm64, as bare binaries named `rota_<os>_<arch>`, tarballs, and `checksums.txt`. There is no Windows build, because the sidecar lock uses `flock`.
- The binary carries the skills and the `references/` they cite, and `rota skills install` copies them for Claude Code and Codex (F6a, #230; see the verb contract's "F6a: embedded skills"). The plugin and its `bin/rota` launcher are gone, so nothing downloads a binary at run time.
- A release publishes the GitHub release assets before the version bump reaches the branch, so the branch never announces binaries that are not there. The version lives in two places that must agree: the git tag (what goreleaser stamps into the binary through ldflags) and the root `VERSION` file (what `rota release bump` edits); `release.yml` fails a tag that is not `v$(cat VERSION)`. The order (F4, #74): the human pushes the tag (`rota release push --tag-only`); `.github/workflows/release.yml` runs goreleaser on the `v*` tag and attaches the binaries to a **draft** release (`release.draft` in `.goreleaser.yaml`; a draft's assets do not resolve at `/releases/download/`); `rota release publish` fills in the approved notes and un-drafts that release, so there is one release, and refuses until the four `rota_<os>_<arch>` binaries and `checksums.txt` are attached; then `rota release push --branch-only`, which needs that release published, puts the version bump on the branch. Goreleaser's own changelog is off, since the notes come from `/rota-release`. The same goreleaser run pushes a Homebrew formula to `l4ci/homebrew-tap` (needs `HOMEBREW_TAP_TOKEN`; see `.rota/RELEASE.md`).
