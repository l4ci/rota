# 5.0 `rota` verb contract

This file defines every `rota` verb's arguments, flags, `--json` data and exit codes. The black-box smoke suite (A2, #46) tests against it, and the Go port (A3 to A9) implements it. Verbs come from the command tree in the [helper triage](5.0-helper-triage.md). Global flags, the JSON envelope, stderr format, the exit-code table, write rules and config loading are fixed by the [CLI conventions](5.0-cli-conventions.md) (A3, #47). Nothing here overrides them: failure `data` on exit 1 and 4, exit 4 for mutating verbs only, and `changed` in failure data all come from the conventions.

Status: **reviewed by the maintainer on 2026-10-02, who signed off on the defaults pending the changes now applied** (quote: "Defaults + you verify"). Arguments were redesigned on purpose (maintainer, 2026-10-02: "Redesign arguments now"), so many verbs differ from the helper they replace. During the port, `test/hv-shim` translates each new-shape call into the old helper call. The `old:` line under each verb is the shim's mapping.

## Per-verb rules

These rules fill in what the conventions leave to each verb. Every verb below follows them, and any exception says why.

1. **Positionals are for the thing the verb acts on**: an item ID, a key, a topic, a name. Everything else is a flag. A verb takes at most one kind of positional. A kind is a category, not the target, so `kind` is always the flag `--kind` (`rota id next --kind bugs`, `rota item create --kind bugs`). Setting a state or status is `--to <value>` everywhere (`item state --to`, `milestone status --to`).
2. **Lists.** Several targets of the same kind are variadic positionals (`rota backlog milestones B01 F02`), never one comma-joined argument. A list carried in a flag is comma-separated (`--repos a,b`); no flag is repeatable.
3. **Bodies** come from `--body-file <path|->`, never from positional text or inline flag values. A verb that already takes `--body-file` and needs a second, different file input names it after its content; the only case is `item create --raw-file`, the preformatted bullet. Short single-line values (title, summary, note) are flag values: `--title`, `--summary`, `--note`.
4. **Families share one shape where the verb exists.** milestone, plan, design and spike use `add` (create; refused with exit 4 if the key exists), `list`, `show <key>`, `put <key> --body-file`, `rm <key>`. The key is always the first positional. Not every family has every verb: milestone has no `rm` (it ends as `archived`), spike has neither `put` nor `rm` (`finish` ends it), and `milestone add` mints its key.
5. **Preview before bulk rewrites.** Verbs that rewrite many files, history or several items at once (`migrate hv`, `migrate issues`, `ship undo`, `item rm`) only report what they would do unless `--apply` is given. Every other mutating verb acts directly. No verb uses `--dry-run`, `--force` or `--yes`. A preview that writes nothing adds the warning `preview only; pass --apply` to `warnings`.
6. **Check verbs** answer a question: guards, gates, `has`-style lookups. Exit 0 means the predicate in the verb's name holds (`item ready` is ready, `git guard clean` is clean, `item shipped` found evidence); every other answer is 1. `data` carries the answer (a named boolean or a verdict) on both exits (conventions: failure data). `--json` callers never need the exit code.
7. **Verdict vs check.** A classifier verb (`worker poll`, `update`, `version --drift`, `plan validate-docs`) returns its verdict in `data` and exits 0 whatever the verdict. A check verb exits 0 when the predicate in its name holds and 1 for every other verdict, with the verdict in `data`. The predicate is the one the name asks: `plan uncertain` exits 0 when the item is uncertain, `item shipped` when ship evidence is found, `worker gate` when the gate passes, `worker session check` when inside a managed session, `worker reset --check-only` when the slot holds no work. The check verbs are `config check`, `repo umbrella`, `item ready`, `item shipped`, `plan uncertain`, `knowledge contradiction has`, `worker gate`, `worker session check`, `worker reset --check-only`, `worker account pick`, `git guard clean`, `git guard feature-branch`, `release milestone-check`, `init check` and `doctor`. A mutating verb that declines to act exits 4 (`worker reset` without `--check-only`, `release bump` to a version that is not greater, `ship pr-merge` with an unproven item, `item complete` without proof, any gated verb whose manual gate is not cleared, `ship pr`, `ship merge` or `ship pr-merge` after a recorded FAIL, a debug attempt past the Iron Law), and its failure `data` says what blocked it. `worker gate` is a check verb that still exits 4 on a manual-gate refusal (B1), because it refuses before judging anything. A verb that changed state on the way to exit 1 or 4 (`worker gate` after a merge, `ship pr-merge` recording `changes-requested`) reports `"changed": true` in its failure `data`. A read-only verb never exits 4.
8. **Text output** is one human line per result, or the body of the requested file for `show` verbs. The contract defines only `--json` data. Smoke asserts on `--json` except where it checks that a `show` verb prints the stored body verbatim.
9. **`--repo` is global.** Each verb states whether it is repo-scoped. A verb with no repo scope rejects `--repo` (exit 2), per the conventions. On a repo-scoped verb, a name that is not a registered sub-repo exits 3 (`resolution`) before any check of the verb's own, so an entry's "`--repo` exits 2" means a registered name the verb does not accept.
10. **No test-only flags.** Fixture hooks the old helpers carried as flags (`--fixture`, `--status`) become environment variables named `ROTA_TEST_*`, which the contract lists per verb and which are not part of the CLI.
11. **Item IDs** are strings in `data`. File mode: `"B07"`. Issue mode: the issue number, `"12"`. Umbrella issue mode: `"<repo>:12"`. Every `data` object that names an item by `id` also has `type` (`"B"`, `"F"` or `"T"`) in both modes, so the type letter is never lost; rows inside the `bugs`, `features` and `tasks` lists of `backlog list` are already grouped by kind and omit it. Lists of bare IDs (`ids`, `items` as `[]string`) use the same `id` spelling and carry no types. Inputs accept every form the old helpers accepted (`B7`, `#7`, `7`, `repo:B7`, `repo#7`). A flag that carries a list of item IDs is always `--items <ID>[,<ID>…]`.
12. **Data shapes.** A list verb wraps its list in an object keyed by a domain noun (`{"items": […]}`, `{"plans": […]}`). A verb whose subject is one item names it `id`. Every mutating verb reports `changed`.
13. **Flag names.** No verb flag reuses a global flag's name (`--json`, `-C`/`--cwd`, `--repo`, `-h`/`--help`), as the conventions require.

## Verb entry format

```
### rota <group> <verb>
rota <group> <verb> <positional> [--flag <value>] [--bool]
repo: scoped | none
data: {"field": type, …}
exit: 1 when …; 3 when …; 4 when …
old: hv-helper <args in old order>    (shim mapping)
shim: how the shim builds `data` and maps old exit codes    (optional)
note: …    (optional)
env: ROTA_TEST_* hooks    (optional; rule 10)
```

Field types use JSON names (`string`, `number`, `bool`, `object`, `[]string`). `?` after a field name means it may be absent. Exits 0, 2 and 70 are implied and not listed. `exit: implied only` means the verb adds no other code.

## Shared definitions

Entries use these names instead of restating them.

- **scope S.** A repo-scoped verb's scope. `--repo <name>` selects a registered sub-repo. With no `--repo`, S resolves from the working directory: inside a registered sub-repo it is that sub-repo, otherwise the umbrella, as the old `hv-knowledge-scope.sh` did. To reach umbrella scope from inside a sub-repo, pass `-C <umbrella root>`. Outside umbrella mode S is always the project.
- **text-read data.** `{"text": string, "missing"?: []string}`. `text` is the stdout the old helper printed (also what text mode prints). `missing` lists requested names that matched nothing. The shim cannot compute `missing` for helpers that don't report it, and omits it there.
- **`backend` in an `exit:` line.** The verb works on one backlog backend only (`backlog.backend` `file` or `issues`) and was called under the other. A mutating verb exits 4 `refused`; a read-only verb (no `changed` in its `data`) exits 1 `failed`, because the conventions forbid exit 4 for read-only verbs. Either way the failure data is `{"blockedBy": "backend", "changed": false}`, and the hint names the verb to use instead when one exists. Old backend helpers exited 2 for this.
- **`tracker` in an `exit:` line.** Exit 5 `unavailable` when the tracker or forge CLI is missing or failing, exit 6 `retry` when it rate-limits. Old backend helpers exited 3 and 4 for these.
- **Failure data.** Exit 1 carries the verb's answer in `data`, which is the same shape as its success `data` unless the entry says otherwise. Exit 4 carries `{"blockedBy": string, "changed": bool}` unless the entry defines more: `blockedBy` names the invariant in one word or phrase (`exists`, `base branch`, `proof missing`, `backend`), and `changed` is true only if the verb changed state before refusing. Every other failure sends `error` alone (conventions).
- **Invalid `backlog.backend`.** A value other than `file` or `issues` is a corrupt config: every verb that reads the backend exits 70.
- **Lock timeout.** Every verb that writes a state file exits 6 when the lock times out (conventions). Entries don't repeat it.
- **Old backend rc mapping.** Unless an entry says otherwise, the shim maps an old backend helper's rc 1 to 3 when stderr says `not found` and to 2 for bad arguments, rc 2 to 4 (`backend`), rc 3 to 5 and rc 4 to 6 (`tracker`).
- **Umbrella issue mode IDs.** `<repo>:<ID>` and `<repo>#<n>` always resolve. A bare ID that exactly one sub-repo holds resolves to it, as the old helper did (`_pick` in `bin/hvlib_backend.py`). A bare ID that several sub-repos hold (`F42`, `#42`) is exit 2, and the message lists the qualified candidates in the `data.id` spelling (`ghrepo:42, other:42`). The global `--repo` selects a sub-repo scope for the verb and never rewrites an ID. The shim maps the old TrackerError rc 1 with `ambiguous across sub-repos` to 2.
- **Dual spelling.** The backend still writes the old spelling. `bin/hvlib_backend.py` renders the issue bullet head as `**[{letter}{number}] …**` (line 714) and returns `f"{letter}{number}"` from create (lines 857 to 858, where the `{ID}` placeholder in the issue body is also replaced by it), so commits, PR bodies and issue bodies carry `[B7]`. A caller maps `[B7]` to `id` `"7"` by dropping the type letter; the letter is `type`. This PR does not change the backend's write format. The shim does the mapping when it builds `data`.
- **Checkout verbs under `--repo`.** A repo-scoped verb that reads or writes a git checkout or files in it (`release version|bump|host|changelog|pending`, `release notes --from commits`, `git`, `review` and `ship` verbs) runs in the named sub-repo's checkout, not at the umbrella root.
- **Commands that run without `.rota/`.** The conventions name `rota init` as running without a project root. `init check` and `init umbrella` count as part of it: they act on the working directory after `-C`, with no walk-up.
- **`slot`** (A7 verbs, which all act on `.rota/workers.json` at the project root). `{"name": string, "branch": string, "worktree": string, "base": string, "handle"?: string, "state": string, "task"?: string, "pr"?: string, "relays": [{"round": number, "ts": string, "summary": string}], "configDir"?: string, "account"?: string}`. Null registry fields are absent in `data`.


## A3 and A4: version, update, config, repo

`rota version` ports in A3 (#47). `rota update`, `rota config` and `rota repo` were routed to A4 (#48) after the triage; their shapes stay here.

### rota version
rota version [--drift]
repo: none
data: {"version": string}; with `--drift`: {"version": string, "stamped": string, "installed": string, "status": "match"|"drift"|"unknown", "drift": bool}
exit: 3 when `--drift` and no `.rota/` is found. `status` is `unknown` when `stamped` or `installed` is empty.
old: plain `rota version`: hv-resolve-plugin-root --root-only (no positional or flag maps; prints the plugin root). `--drift`: hv-version-check --json (new `--drift` selects the old `--json` form; no other args).
shim: plain form reads the binary's stamped version; `--drift` wraps the old JSON (`stamped`, `installed`, `status`) and adds `version` (= `installed`) and `drift` (= `status == "drift"`); an old rc 0 with empty output (no `.rota/`) becomes exit 3.
note: `stamped` is `rota.version` from the merged config; `installed` is the running binary's embedded version (old: plugin.json at the resolved plugin root). In 5.0 they are the same source, so `version` and `installed` are equal.
note: old `hv-version-check` exited 0 silently without `.rota/`, where 5.0 exits 3.

### rota update
rota update
repo: none
data: {"installType": "brew"|"script"|"dev"|"unknown", "installRoot": string, "currentVersion": string, "latestVersion": string, "status": "behind"|"current"|"ahead"|"unknown", "updateCommand": string}
exit: implied only. A missing `gh`, a network failure or an unresolved install gives `latestVersion` or `currentVersion` empty and `status: "unknown"`, as old. Read-only: never runs the update.
old: hv-update-check (no args). Env: `HV_INSTALL_ROOT` stays as the real override (`installType: "override"`, not a test hook); `ROTA_TEST_LATEST_VERSION` is the test hook, for old `HV_LATEST_VERSION` (rule 10).
shim: old stdout is already this JSON; pass it through unchanged and export `HV_LATEST_VERSION="$HV_TEST_LATEST_VERSION"` when set.
note: strings may be empty rather than absent, as in the old helper.
note: F6b (#230) replaced the plugin-era detection. `currentVersion` is the running binary's version and `installRoot` is the directory holding the binary (symlinks resolved). `installType` is `brew` for a path under a Homebrew prefix (`/Cellar/`, `/homebrew/`, `/linuxbrew/`), `dev` for an unstamped or `-dev` build, `unknown` when the binary path does not resolve, otherwise `script`. `updateCommand` is `brew update && brew upgrade rota`, the `install.sh` pipe, or a rebuild, each followed by `&& rota skills update`. `HV_INSTALL_ROOT` and `CLAUDE_PLUGIN_ROOT` are no longer read.

### rota config show
rota config show [<key>]
repo: scoped
data: {"entries": [{"key": string, "value": any, "source": "local"|"project"|"default"}]}
exit: 3 when `<key>` is neither a schema key nor present in the merged config; 2 when more than one positional is given. `value` is the raw JSON value (not a JSON string of it). No key: every schema key in schema order. With a key: `entries` holds exactly one element, so both forms share one shape.
old: hv-config-show [<key>] (new `<key>` maps to the old single positional; unchanged).
shim: parse each stdout line with `^(\S+) = (.*)  \(source: (local|project|default)\)$` into `key`, `value` (JSON-parsed), `source`; old rc 1 with `unknown key` on stderr becomes exit 3, rc 1 with `usage:` becomes exit 2.
note: old rejected any key outside the schema table. 5.0 accepts a key that is in the schema or present in the merged config, so a hand-edited key stays readable (`config set` itself is schema-only). The shim cannot do this; it fails with exit 3 as before.

### rota config set
rota config set <key> <value>
repo: scoped
data: {"key": string, "value": any, "previous"?: any, "changed": bool}
exit: 2 when `<key>` is not in the schema that `config check` uses (the shared table in `bin/hvlib_config.py`), is a malformed path (empty segment: `""`, `.a`, `a.`), or an argument is missing; 70 when `.rota/config.json` exists but is not a JSON object, or the write fails.
old: hv-config-set <key> <value> (both map to the old positionals in order). Writes `.rota/config.json` only, never `config.local.json`. `<value>` is parsed as JSON first (`true`, `42`, `"x"`, `[…]`, `{…}`) and falls back to a raw string (`opus`, empty string). `previous` is the stored value before the write and is absent when the key was unset.
shim: old accepts any key, so the shim checks `<key>` against the schema table first and exits 2 without calling the helper when it is absent; old stdout is empty; read `.rota/config.json` before and after the call to fill `value`, `previous` and `changed`; old rc 1 with `malformed key path` on stderr becomes exit 2, rc 1 for missing argv becomes exit 2, any other rc 1 becomes exit 70.
note: the JSON-then-string coercion is kept because `hv-init` and `hv-config` skills depend on it. A string that looks like JSON (`"true"`) still needs shell quoting (`'"true"'`). No `--string` or `--local` flag is added.
note: a key outside the schema is rejected (maintainer decision), where old accepted any key.
note: an empty `<value>` is valid and stores the empty string; the old helper rejected it, so the shim passes `""` as a JSON literal.

### rota config check
rota config check
repo: scoped
data: {"status": "upToDate"|"fresh"|"stale"|"corrupt", "upToDate": bool, "missing": []string}
exit: 1 when `status` is anything but `upToDate` (`fresh`, `stale` or `corrupt`); 3 when no `.rota/` is found. `missing` lists dotted required keys that are absent or null, in schema order, and is non-empty only for `stale`. `fresh` means `config.json` does not exist; `corrupt` means it is invalid JSON or not an object (this is a defined verdict, so it does not use exit 70).
old: hv-config-schema-check (no args).
shim: map stdout `UP_TO_DATE` to `status: upToDate`, `FRESH` to `fresh`, `CORRUPT` to `corrupt`, and `STALE:a,b` to `stale` with `missing` = the split list; exit 0 for `upToDate`, else 1 (old always exited 0).
note: old always exited 0, so skills that branch on the four tokens must read `data.status`.

### rota config fill
rota config fill
repo: scoped
data: {"filled": []string, "changed": bool}
exit: 3 when no `.rota/` is found; 70 when `.rota/config.json` exists but is invalid JSON or not an object (`config check` status `corrupt`), and nothing is written.
old: none (A9 addition, G1; replaces the ~20 default `config set` calls the hv-init skill carried as prose).
note: writes the schema default (`config show`'s `source: default` value) for every required key that `config check` lists in `missing`, so `config check` reports `upToDate` afterwards. `filled` lists those keys in schema order. A missing `config.json` is created holding every required key. Keys already present, keys outside the schema and `config.local.json` are never touched. Nothing missing gives `filled: []`, `changed: false`, and the file is not rewritten.
note: each added key goes in at its schema position among its siblings: before the first existing sibling that comes later in schema order (an object's position is that of its first schema key), so a file that starts in schema order stays in it (G7). Siblings outside the schema keep their place. The file is written as `config set` writes it (two-space indent).
note: `umbrella.enabled` and `rota.version` are required, so `fill` writes their defaults (`false`, `""`) when they are missing. Callers that know better set them with `config set`; `config set` on a present key keeps its position. The init skill runs `rota init`, then `rota config fill`, then `config set` for the answered keys, which keeps the file in schema order.

### rota repo which
rota repo which
repo: none (the answer comes from the working directory)
data: {"name": string, "path": string}
exit: 3 when the working directory is not inside a registered sub-repo, is not in a git repo, there is no umbrella, or a stray `.rota/` inside a registered sub-repo masks the umbrella (`error.message` says which, and the hint names the stray `.rota/`); 5 when `git` is missing. `path` is the absolute realpath of the registered sub-repo root (a Layout B worktree maps to its main repo).
old: hv-resolve-repo (no args; run from the same working directory, `-C` becomes `cd`).
shim: old stdout is the name; fill `path` by running `hv-resolve-repo-path <name>` from the umbrella root printed by hv-resolve-umbrella; old rc 1 maps to 3, including the `masking` case.
note: the triage tree writes name-to-path as `rota repo which --path`. That shape is dropped: `which` now returns both name and path, and the name-to-path lookup is `rota repo resolve <name>`, so hv-resolve-repo-path (merged) needs no flag.

### rota repo resolve
rota repo resolve [<name>…]
repo: none (reads the umbrella registry)
data: {"repos": [{"name": string, "path": string}]}
exit: 3 when any name is not registered, or the project is not an umbrella (empty registry); `error.message` names every unregistered name. No names gives `{"repos": []}` and exit 0, as the old helper did for `""`. Order follows the arguments, duplicates preserved; `path` is the absolute realpath.
old: hv-resolve-repos "<names joined by comma>" (variadic positionals become the one comma-joined old positional; zero names become `""`). Run from the umbrella root.
shim: wrap the old stdout JSON array as `{"repos": [...]}`; old rc 1 becomes exit 3.
note: the triage tree writes `resolve <csv>`; rule 2 makes it variadic. Merged hv-resolve-repo-path (`<name>` to path) is `rota repo resolve <name>` and reads `repos[0].path`.

### rota repo umbrella
rota repo umbrella
repo: none
data: {"umbrella": bool}
exit: 1 when the project is not an umbrella (no `.rota/`, no `.rota/repos.json`, or an empty registry). It never exits 3 for a missing `.rota/`: no root means no.
old: hv-umbrella-on [<dir>] (new `-C <dir>` global flag replaces the old optional positional; no positional remains).
shim: map stdout `yes` to `umbrella: true` and exit 0, `no` to `umbrella: false` and exit 1; pass `-C <dir>` as the old positional.
note: umbrella status is true iff `.rota/repos.json` holds at least one entry, and `umbrella.enabled` is ignored, same as old. The old positional dir is dropped for `-C`; unlike old, discovery walks up to the nearest `.rota/` (conventions).


## A4: backlog, capture, IDs, status

### rota id next
rota id next --kind <bugs|features|tasks|milestones>
repo: scoped
data: {"kind": string, "id": string, "changed": bool}
exit: 2 when `--kind` is missing or not bugs|features|tasks|milestones; backend (file-only: issue mode IDs are issue numbers)
old: hv-next-id <kind>    (`--kind` is the old positional)
shim: `id` is the printed ID, `changed` is always true (the counter is written).
note: `--kind` is a flag, as in `item create` (rule 1). Exception to rule 11: `id` is a fresh counter ID and `kind` already gives the type, so there is no `type` field.

### rota item create
rota item create --kind <bugs|features|tasks> --title <text> [--tag <tag>] [--desc <text>] [--body-file <path|->] [--related <text>] [--milestone <text>] [--repos <csv>] [--subsystem <text>] [--captured <YYYY-MM-DD>] | --kind <kind> --raw-file <path|->
repo: scoped

## B2: verdicts

B2 (#55) replaces "parse the last line" routing in `/rota-review`, `/rota-qa`, `/rota-ship` and `/rota-debug` with typed verdicts: the skill records each verdict through a verb, which validates it, and the routing from verdict to next step is a tested function in code. B3 (#56) builds on the store: `ship pr` and `ship merge` refuse after a recorded FAIL, and the debug Iron Law counts failed fixes per item.

- **Verdict store.** `.rota/verdicts.json`, at the project root (the umbrella root in umbrella mode), gitignored per developer like `status.json` (`rota init` adds the line to its managed `.gitignore` block). Shape: `{"branches": {"<key>": [record, …]}, "items": {"<id>": [record, …]}}`. A branch key is the branch name, or `<repo>:<branch>` for a sub-repo branch (git forbids `:` in ref names, so keys never collide). An item key is the ID as given to the verb. Records are appended oldest first, and each list keeps its latest 20. The file follows the conventions' write rules (atomic, locked read-modify-write).
- **record.** `{"kind": string, "verdict": string, "combined"?: string, "branch"?: string, "repo"?: string, "sha": string, "recordedAt": string, "summary"?: string, "findings": [finding], "items"?: [{"id": string, "verdict": string}]}`. `sha` is the short tip of the branch (HEAD for debug) when the verdict was recorded; `recordedAt` is UTC ISO 8601. Item records carry no `branch` or `repo`. `combined` is stored on `review-quality` records only (see `verdict add`).
- **kinds and their verdicts.** `review-spec`, `review-quality` and `second-opinion` take `PASS`, `CONCERNS` or `FAIL`; `qa` adds `INFRA-FAIL`; `debug-fix` takes `PASS` or `FAIL`. Worst-of order is `PASS` < `CONCERNS` < `FAIL` < `INFRA-FAIL`.
- **body.** `--body-file` is optional and holds a JSON object `{"verdict"?: string, "summary"?: string, "findings"?: [finding], "items"?: [{"id": string, "verdict": string}]}`. A `finding` is `{"severity": "blocker"|"major"|"minor"|"info", "title": string, "file"?: string, "line"?: number, "detail"?: string}`. Validation is strict: an unknown key, a wrong type, an empty `title`, a `line` below 1, a `severity` or `items[].verdict` outside its set, or text that is not one JSON object is exit 2, and the message names the field. `--verdict` is always required; a `verdict` in the body must equal it (exit 2 otherwise), so a reviewer's JSON block can be passed through whole.
- **effective review verdict** of a branch. The latest `review-quality` record's `combined`, unless a `review-spec` record is newer, in which case that record's `verdict` (a spec-only review, or a spec FAIL that skipped Stage 2). `verdict route --for ship-review` and B3's ship refusal read it.
- **stale.** A record is stale when its `sha` differs from the branch's current tip. Routing reports it and does not change `next` because of it.

## B1: manual gates

B1 (#54) moves the manual gates out of skill prose and into the verbs. Orchestrator rulings (round 4, phase B, from the maintainer on 2026-10-03): a gated verb exits non-zero without `--confirm` at every autonomy level; skills pass `--confirm` only after an `AskUserQuestion` yes; every confirmed pass is appended to an audit log under `.rota/` with the gate, the verb, the time and the quoted human answer (`--confirm-note`, required with `--confirm`). Issue close and issue label are not gated in code. Gated: tag push, release publish, public filing (`tracker suggest-upstream`), and merges where config requires human approval (all merges, or merges touching listed paths, per #44 "Merging").

- **Registry.** One table in `internal/gate` names every manual gate the skills describe, enforced or not. `rota gate list` prints it. A gate is `enforced` when a verb refuses without `--confirm`; the rest stay skill judgment (an `AskUserQuestion` the skill must not auto-pick) and are listed so the inventory is complete in one place.

| Gate | Enforced by | State it creates |
|---|---|---|
| `tag-push` | `release push` | the release tag (and branch) on the remote |
| `release-publish` | `release publish` | a GitHub or GitLab release page |
| `public-filing` | `tracker suggest-upstream` | a public issue on the hv-skills repo |
| `merge-approval` | `ship merge`, `ship pr-merge`, `worker gate` (only when `ship.mergeApproval` applies) | a merge into the base branch |
| `debug-reset` | `debug reset` (B3) | a fresh failed-fix count for an item the Iron Law halted |
| `pr-open` | skill only (`/rota-ship`) | a public PR or MR |
| `issue-close` | skill only (`/rota-ship`, `/rota-release`); ruled out of code | closed upstream issues |
| `issue-label` | skill only (`/rota-capture` import and `--remove`); ruled out of code | upstream label added or removed |
| `decision-write` | skill only (`/rota-decide`) | a hard boundary in `DECISIONS.md` |
| `runlog-entry` | skill only (`/rota-learn`) | a signed entry in the public runlog registry |

- **Confirmation flags.** Every enforced verb takes `--confirm` and `--confirm-note <answer>`. `--confirm-note` holds the human's answer, quoted as given. `--confirm` without a non-empty `--confirm-note`, or `--confirm-note` without `--confirm`, is exit 2. `autonomy.level` is never read to clear a gate: `off`, `auto` and `loop` all refuse alike.
- **Refusal.** A gated verb that would cross its gate without `--confirm` exits 4 before it changes anything, with failure data `{"blockedBy": "manual gate", "gate": string, "changed": false}`; `merge-approval` adds `"paths": []string`, the changed paths that matched `ship.mergeApprovalPaths` (empty under `all`). The hint names the flags to pass after asking. The check runs after usage and resolution checks, so a bad call still exits 2 or 3 and a refused one tells the caller exactly what needs approval.
- **Audit.** A cleared gate appends one JSON line to `.rota/gate-audit.jsonl` at the project root, under the `.lock` sidecar, before the gated action runs: `{"ts": string, "gate": string, "verb": string, "target": string, "note": string, "autonomy": string, "escalation"?: string}`. `escalation` is set when the approval came through `--approval` (C5). `ts` is RFC 3339 UTC; `target` is the tag, branch, PR or issue title the verb acts on; `autonomy` is the `autonomy.level` in force, recorded for evidence only. The line is written even when the action then fails, because the human did approve that attempt. The file is per-developer runtime state and is gitignored (`rota init` adds `.rota/gate-audit.jsonl` to the managed block): a tracked log would dirty the base branch on every merge or release push. `--confirm` on a call that crosses no gate (a merge `ship.mergeApproval` does not cover) is accepted and writes nothing.
- **Merge approval config.** `ship.mergeApproval` is `none` (default; the orchestrator merges after the gate passes, per #44), `all` (every merge needs `--confirm`) or `paths` (only merges whose changed files match `ship.mergeApprovalPaths`). `ship.mergeApprovalPaths` is a list of repo-relative entries; a changed file matches an entry when it equals it, lies under it (`rota-release` matches `rota-release/SKILL.md`), or matches it as a `path.Match` glob against the whole path (`*.md` matches top-level files only). Changed files are `git diff --name-only <base>...<branch>` for `ship merge` and `worker gate`, and the PR's file list from the forge for `ship pr-merge`. Neither key is written by `rota init`. Any other `ship.mergeApproval` value is exit 2 on a merge verb, never a silent `none`.
- **Amended entries.** `tracker suggest-upstream`, `ship merge`, `ship pr-merge` and `worker gate` take the confirmation flags and gain the exit-4 refusal; their entries above say where the check runs. `worker gate` is a check verb (rule 7) but exits 4 on this refusal, not 1, because it refuses before it has judged anything: the merge has not been attempted, and `data.verdict` is `approval-required`.

## B3: verdict refusals, the Iron Law, loop-only flags

B3 (#56) moves three prose rules into the verbs. Orchestrator rulings (round 4, phase B, from the maintainer on 2026-10-03): ship refuses after a recorded review or second-opinion FAIL, except under the advisory codex fallback (#158); the Iron Law is a per-item counter, and a 4th attempt is refused until `rota debug reset <ID>`, a B1 gated verb (`--confirm` plus `--confirm-note`, audited, with a reason); `--auto-loop` outside loop mode is a usage error (exit 2).

- **Ship refusal.** `ship pr` and `ship merge` read the branch's records in the B2 store (key as `verdict add` builds it). The branch is blocked when its effective review verdict is `FAIL`, or its latest `second-opinion` record is `FAIL` and `ship.secondOpinionRunner` is not `codex`. A stale FAIL still blocks: only a newer record of the same kind clears it, so a fix is reviewed again before it ships. `CONCERNS` and QA verdicts never block here; their routing stays with `verdict route`. A branch with no records ships as before. The refusal is exit 4 before anything changes, with failure data `{"blockedBy": "verdict", "kind": string, "verdict": "FAIL", "sha": string, "stale": bool, "changed": false}` (`kind` is `review-spec`, `review-quality` or `second-opinion`; review is checked first). The hint names `rota verdict show`. `ship pr-merge` (the `/rota-review --queue` merge path) applies the same refusal to the PR's head branch, read from the forge's open-PR listing the verb already makes; in umbrella mode the key is `<repo>:<branch>` for the `--repo` sub-repo. When the forge reports no head branch, the verb does not refuse and adds the warning `could not resolve the head branch of PR <n>; verdicts not checked`. `worker gate` is not covered.
- **Iron Law.** The count is per item: the item's `debug-fix` FAIL records in the store since its latest `debug-reset` record, the same number `debug verdict` reports as `failedFixes`. A new branch or a cleared session file does not reset it. At 3 or more, `debug counter init <ID>` and `debug counter record-attempt` (which reads the item from the session's `bug_id`) exit 4 with failure data `{"blockedBy": "iron law", "bugId": string, "failedFixes": number, "changed": false}` and the hint `rota debug reset <ID>`. `debug verdict` is never refused: an outcome is always recorded.
- **Loop-only flag.** `--auto-loop` on `design add` and `plan add` marks the artifact as written by a loop run: the verb adds `auto: true` to the frontmatter, after `status:`. It is exit 2 unless `autonomy.level` (config.local.json over config.json) is `loop`, checked before anything is written. These two verbs are where a loop-mode `/rota-brainstorm` or `/rota-plan` run leaves its mark; the skills' own `--auto-loop` argument is not a verb flag.

## C: rounds

The `round` group is the orchestrator layer over the same slot registry (`.rota/workers.json`) and host package as `rota worker`. It adds no second state file. Each verb below owns its entry.

### rota round wait

note: blocks until one watched slot needs attention, then returns that slot. Watched slots are the named ones, or, when none is named, every registered slot that has a `handle` and whose recorded `state` is not `idle`. Pool init seeds every slot `idle` and gives a tmux slot a nominal handle before anything runs in it, and `worker poll` treats a recorded `idle` as already reported, so an idle slot is not watched unless named, or one parked slot would end every wait at once. `worker dispatch` records `busy`, which arms the slot. A slot with no handle is skipped, not an error, unless it was named.
note: "needs attention" is the `rota worker poll` classification, not the host's raw status: `idle`, `blocked`, `done`, `dead`, `limited`, `needs-permission` or `unknown` (UNKNOWN is surfaced, never treated as finished). `busy` keeps waiting. `state` is lowercased, `evidence` is the same line `worker poll` reports.

The orchestrator's context never sees either loop. One exception on herdr (#211): a slot classified `busy` only because its pane moved while herdr's own status was not `working` is re-classified after each settle without waiting for an event (`source: "poll"`), because herdr sends no event when an idle or done agent's pane comes to rest; right after a turn, two of herdr's `recent-unwrapped` reads a moment apart can return different scrollback windows, so the classification right after the last event can see movement (recorded live, #211).
note: read-only. The verb does not write `.rota/workers.json`, so there is no `changed` field; recording a slot's new state stays with `rota worker poll`.
note: a timeout is a normal outcome, not a fault: exit 1 with `timedOut: true`, because the verb exists to answer "which slot needs me" and the answer is "none yet". Exit 6 is not used, since the conventions send it `error` alone and reserve it for faults a retry clears. `--timeout` defaults to 0, meaning wait indefinitely. A caller whose shell cuts commands short raises the cap (`BASH_MAX_TIMEOUT_MS` in Claude Code) or loops on a finite `--timeout`.
note: no `ROTA_TEST_*` hooks. The smoke section drives a fake `herdr` binary plus a fake unix-socket server (`HERDR_SOCKET_PATH`), and `test/fakes/tmux`.

- **Round slot.** The `slot` of A7 plus derived fields. C2 stores nothing new: the issue is the slot's `task` (or, when `task` is not a number, the leading number of the branch `<agent>/<issue>-<slug>`), the PR is `pr`, and the host state is read live. Later C issues (tier, escalations) add optional slot fields with their own entries.
- **Sources.** Rows come from the union of three sources, so a restart works with an empty registry: the registry slots; the git worktrees under `<root>/.worktrees/` (a worktree on `park/<name>` is a parked slot named `<name>`, on `<name>/<issue>-<slug>` a slot working that issue); and the host snapshot, whose agents are matched to a row by `handle` (tab id), else by `cwd` equal to the row's worktree. Open PRs come from the forge by head branch, issue labels from the tracker.
- **Degraded sources.** A source that is unavailable (host not running, forge or tracker CLI missing or failing) is named in `unavailable` and `warnings`, and the drift kinds that need it are skipped. The verbs still exit 0: a restart usually finds herdr down.
- **Drift kinds.** `dead-tab`: slot has a `handle` and the host has no live agent for it. `unclaimed-tab`: a live agent whose `cwd` is inside `.worktrees/` matches no row. `unregistered-worktree`: a worktree under `.worktrees/` has no registry slot. `branch-no-pr`: the slot's branch is neither its parking branch nor the base, has commits ahead of the base, and has no open PR. `pr-unrecorded`: an open PR has the slot's branch as head and `pr` is empty. `pr-stale`: `pr` names a PR that is merged or closed while the slot still holds its task. `label-missing`: the slot holds an issue and the issue lacks the `in-progress` label. `label-orphan`: an issue has `in-progress` and no slot holds it.
- **Safe repairs** (`reconcile --apply` only, each additive or derived): `dead-tab` clears `handle` and sets `state` to `dead`; `unregistered-worktree` registers the slot; `pr-unrecorded` records `pr`; `label-missing` adds `in-progress`. Never repaired: `unclaimed-tab` (a tab may be a live worker), `branch-no-pr` (opening a PR is the worker's act), `pr-stale` and `label-orphan` (resetting a slot and removing the label are the orchestrator's calls, `worker.md`).
- **Host snapshot.** herdr: `herdr api snapshot` (pin 0.9.x), reading `agents[]` (`tab_id`, `cwd`, `agent_status`, `name`). tmux: `tmux list-windows` with the pane's current path. Both sit behind a new optional `host.Snapshotter`, in `internal/host/snapshot.go`; the `Host` interface does not change.

### C3: round start, candidates, assign, wind-down

C3 (#59, absorbing #40 and #41) adds the round lifecycle over the same registry. Orchestrator rulings (round 4, `c-rulings.md`): no second state file unless a need does not fit `workers.json`; the autonomy axis is a new key, not `autonomy.level`; the file-overlap rule is concrete and states what it cannot catch.

- **Round config.** Four keys, all silent defaults (the `ship.mergeApproval` pattern; not seeded by init). `round.scope` is `slate`, `milestone` or `next`, default `milestone`. `round.roster` is a list of agent names, default `["ben","dana","nia","kit"]`. `round.brief` is the path the worker pointer names, default `""` (see **Brief pointer**). `round.sharedPaths` is a list of repo-relative globs the overlap check ignores, default `[]`. `autonomy.level` (off/auto/loop) is untouched: it says how far skills chain on their own, `round.scope` says which issues a round may take.
- **Scope.** The candidate set is the open, unheld items of: `slate` the round's recorded slate and nothing else; `milestone` the active milestones (`rota milestone active`, then `rota backlog ids --milestone`); `next` the same, and when none of those is left to assign, the items of the first `planned` milestone whose dependencies are all shipped (`milestone list`, `ready`). The scope is enforced by `assign`, not advisory: an issue outside it is refused. Choosing `slate` is how the maintainer approves exactly what a round may touch; `milestone` is the #44 default (slate confirmed once, by the orchestrator, from `start`'s candidates); `next` lets an unattended round roll over.
- **Registry fields.** C3 adds optional fields to `.rota/workers.json`, all absent until written. Top level: `scope` (string, the scope the round started with) and `slate` (`[]string`, issue IDs in rule-11 spelling, present only for `slate`). Per slot: `claimId` (string, the `item claim` id `assign` took, released by `wind-down` and by C10's return). The issue a slot holds stays in `task` and its branch in `branch`; the top-level `round` number is the one `worker dispatch --round` already writes.
- **Lease.** One orchestrator per repo, keyed on `git rev-parse --git-common-dir` so every worktree of the repo shares it. It does not fit `workers.json`: that file lives under each worktree's own `.rota/`, so a second worktree sees an empty registry and a lock inside it protects nothing. The lease is `<git-common-dir>/rota/round-lease.json`: `{"pid": number, "start"?: number, "host": string, "pane"?: string, "paneHost"?: "herdr"|"tmux", "root": string, "round": number, "startedAt": string}`. `pid` is the orchestrator process, not the short-lived `rota`: the nearest ancestor that is not a shell, `env`, `timeout` or `rota` (in Claude Code, the `claude` process), else the parent. A herdr or tmux server is a boundary: when the walk reaches one, rota ran from a plain shell in a pane and the holder is that pane's shell, the ancestor just below the server, so two panes on one server never share a holder (#205). `start` is that process's start time (Linux `/proc/<pid>/stat` field 22), read to defeat PID reuse, absent where the platform has none. `pane` is `HERDR_PANE_ID` or `TMUX_PANE`. The lease is `live` when `host` is this host and the pid runs with the same `start`; `stale` when `host` is this host and the pid is gone or its start differs; `foreign` when `host` differs (cannot be checked, treated as live and named). `pid`, `host` and `pane` are overridable by `--holder-pid` for harnesses whose ancestry is not discoverable.
- **Lease seam (C2, C6).** `internal/round` exports `ReadLease(root) (Lease, LeaseState, error)` with `LeaseState` one of `none`, `live`, `stale`, `foreign`, and `ClearStaleLease(root) (Lease, bool, error)`, which removes only a `stale` lease. C3 owns both; `reconcile` and `reap` call them and write nothing of their own. `reconcile` gets one new drift kind, `lease-stale` (a `stale` lease; the finding's `detail` names the holder), never repaired by `--apply`; `rota reap` lists it as a candidate and clears it through `ClearStaleLease`. `rota round start` also reclaims a stale lease itself, since a provably dead holder needs no human, with the warning `reclaimed stale lease held by pid <n>`.
- **Readiness.** `candidates` and `assign` run three checks per item, each reported in `checks` as `{"name": "criteria"|"dependencies"|"overlap", "ok": bool, "detail": []string}`:
  1. `criteria`: the `rota item ready` rule verbatim (acceptance criteria, or a design or plan note); its `reasons` are the detail.
  2. `dependencies`: every reference in the item's `## Depends on` section (issue body, or the detail file in file mode) must be done: closed in issue mode, archived in file mode. A reference in the item's own ID spelling (`#57`, `57`, `B07`) is looked up; any other reference (`owner/repo#N`, a URL) cannot be verified and fails the check (`cannot verify <ref>`). An item with no such section has no dependencies. An open dependency with a PR is not done.
  3. `overlap`: no file overlap with an in-flight item. In flight means a slot in this registry holding a `task` other than this item. The footprint of an item is the `## Files` section when present (one path or glob per bullet), otherwise every token of the body and comments that is a tracked path at the base (`git ls-files`) or a directory prefix of one (two or more segments, so `docs/` alone never counts), minus `round.sharedPaths`. The footprint of an in-flight item is its own footprint plus its slot's real changes (`git diff --name-only <base>...<branch>` and uncommitted paths in the slot's worktree). Two footprints overlap when they share a file or one names a directory holding the other's file. The check cannot catch: files an item will create, paths nobody wrote down, two items editing the same function or file under different names, generated files and registries every item touches (list those in `round.sharedPaths`), renames, work on another machine's round, and a stale issue text. It is a heuristic that fails closed on what it can see, so it stays on only because it is cheap to override (below).
- **Brief pointer.** `assign` hands the worker a short signed brief instead of the pasted contract (#41): its agent name, the round number, the path of the standing contract, the issue to read first with its thread (and the instruction to dispute the ticket before implementing if it is wrong or already decided), the branch, the sibling issues, and the answered decisions verbatim from `--body-file`. The contract is `references/worker-contract.md`, which C3 extends with a *Read the issue and dispute it* step. The path comes from `round.brief` when set, else `references/worker-contract.md` under `CLAUDE_PLUGIN_ROOT` when that is set, else under the project root; if none exists `assign` refuses before touching anything (`blockedBy: "brief missing"`). `/rota-work`'s own dispatch keeps pasting the contract; moving it to the pointer belongs to the orchestrate skill (C7).

### C5: merge policy and approval requests

C5 (#61) is the orchestrator side of the merge policy. Most of #61 shipped with B1 (#54): `ship.mergeApproval` (`none`, `all`, `paths`) and `ship.mergeApprovalPaths`, the `merge-approval` gate on `ship merge`, `ship pr-merge` and `worker gate`, and the path match against the PR's changed files. Under the default `none`, `worker gate` already merges a passing PR without a prompt. C5 adds the two missing pieces: the approval request goes out through the C4 escalation channel, and the human's answer comes back as a recorded B1 approval. It adds no verb and no config key, only two flags on `worker gate` and `ship pr-merge`.

- **Approval thread.** The thread a merge's approval request lives on: the PR (`kind` `pr`, its number) when the merge has one, else for `worker gate` the slot's issue (`kind` `issue`, the round slot's issue number). `ship merge` has no forge thread, so it takes neither flag and keeps `--confirm` from an `AskUserQuestion`.
- **`--escalate`.** When the `merge-approval` gate refuses, the verb also sends the approval request with `round escalate send` on the approval thread (`--slot` set for `worker gate`), then exits 4 as before, with the escalation in `data.escalation`. Title `Merge approval: PR #<n>` (or `Merge approval: <slot> (<branch>)` without a PR). The body names the policy (`all`, or `paths` with the matching files from `data.paths`) and ends: ``Reply `approve`, `approved`, `yes`, `lgtm` or `ship it` to merge. Any other reply holds the merge.`` When an escalation on that thread is already pending, the verb sends nothing and returns the pending one, so a re-gate in a loop never posts twice. With no gate to clear (the policy does not cover the merge), `--escalate` is accepted and does nothing. A send failure is a `warnings` entry; the refusal stands.
- **`--approval <id>`.** Clears the `merge-approval` gate with a recorded answer instead of `--confirm`. It reads escalation `<id>` from `.rota/workers.json` and makes no forge call, so run `round escalate check` first. Checks, in order, all before anything changes:
  - unknown `<id>`: exit 3;
  - the escalation is not on this merge's approval thread: exit 2;
  - `status` is not `answered` (pending, or timed out with no answer): exit 4, `{"blockedBy": "approval pending", "escalation": string, "status": string, "changed": false}`;
  - the answer does not approve: exit 4, `{"blockedBy": "approval declined", "escalation": string, "answer": string, "changed": false}`.
  An answer approves when the first word of its first non-blank line, lowercased with trailing punctuation removed, is in the allowlist `approve`, `approved`, `yes`, `lgtm`; or when that line's first two words, treated the same way, are `ship it`. `Approve.`, `YES, go ahead`, `lgtm!` and `Ship it.` approve; `no`, `yes-ish`, `please approve` and `ok` hold the merge. The allowlist lives in one function (maintainer ruling, relayed by the orchestrator in round 4: "Approve or yes words").
- **Recording.** A cleared `--approval` writes the B1 audit line with `note` set to the answer body verbatim and `escalation` set to `<id>`, exactly as `--confirm --confirm-note` would with the quoted answer. The escalation stays in the registry as the record of what the human said; the same answered escalation can clear a re-gate of the same thread (after a `stale` bounce, say).
- **Flag rules.** `--approval`, `--escalate` and `--confirm` are mutually exclusive (exit 2). `--approval` on a merge the policy does not cover is accepted and writes nothing, the same as `--confirm` (B1).
- **Skill routing.** `/rota-work`'s gate step and `/rota-review --queue` pass `--escalate` when the round is unattended (`autonomy.level` `loop`, or the orchestrator is driving herdr workers), record the escalation id against the slot or PR, keep working other slots, and re-gate with `--approval <id>` once `round escalate check` reports it answered. An `approval declined` refusal is surfaced and the slot is held, never retried. Interactive runs keep the `AskUserQuestion` plus `--confirm` path from B1.
- **Limits.** The approval is tied to the thread, not to a commit: commits pushed to the PR after the answer are covered by it. `worker gate`'s provenance and freshness checks still run on every re-gate, so a moved head is re-verified, but it is not re-approved.

### C9: worker tier and model

C9 (#75) lets the orchestrator choose how heavy a model each worker starts with, and tells the worker how to size its own subagents. Skills and briefs speak in **tiers**; config maps tiers to model names per harness kind, so nothing outside config names a model.

- **Tiers.** `light` (reading, searching, discovery), `standard` (writing code and tests), `heavy` (hard reasoning, design, tricky debugging), in that order. A harness **kind** is `claude` or `codex`.
- **Config.** Eight keys, all silent defaults (not seeded by init). `round.tier` is the default tier, `standard`. `round.tiers.<kind>.<tier>` is the model name: `claude` defaults to `haiku` for light and `opus` for heavy, and `standard` defaults to the value of `models.worker` (itself `sonnet` by default), so one knob governs the standard model and the two cannot drift; an explicit `round.tiers.claude.standard` wins; `codex` defaults to `""` for all three, because codex model names are not ours to fix and a codex worker is E1's. A kind is *configured* when any of its three tiers is non-empty. Validation (read through `internal/roundcfg`, so every verb that reads round config exits 70 on it): `claude` must be configured; a configured kind must have all three tiers non-empty (the error names the missing `round.tiers.<kind>.<tier>`); `round.tier` must be a tier. Unconfigured `codex` is never an error: a codex worker then gets no model and Codex picks its own (#68), unless a custom `work.codexCommand` holds `{model}`, which `assign` refuses with `no tier map` before anything is marked.
- **Choosing.** `rota round assign --tier <t>` picks the tier; omitted, it is `round.tier`. rota does not choose from the issue: size, type, labels and judgment belong to the orchestrate skill (C7). The config tier is a default, not a ceiling: a tier above it needs `--tier-reason <text>` (one line, exit 2 without), and any given reason is recorded. A tier at or below the default needs none. `--kind` is the harness kind of the worker, default the slot's recorded `kind`, else `claude`.
- **Resolving.** `model` is `round.tiers.<kind>.<tier>`. On a `claude` kind the default launch command is `claude --model <model> --dangerously-skip-permissions` (`models.worker` also drives `/rota-work`'s own dispatch, and is the default of the standard tier, above). A custom `work.workerCommand` receives the model only through a `{model}` placeholder in it; without one the tier is recorded but `model` is left out of the slot and `data`, and `assign` adds the warning `tier model not applied: work.workerCommand has no {model} placeholder`, because rewriting a command rota does not own would lie about what ran.
- **Codex.** The tier map, its validation and the resolution above are defined for `codex` and `--check-only` reports the model it would use. Starting a codex worker is E1 (#68), under "E: Codex workers".
- **Registry fields.** Optional per-slot fields, absent until `assign` writes them and cleared when the slot is parked (`wind-down`): `kind` (string), `tier` (string), `model` (string), `tierReason` (string). They are the round state C9 asks for; `round status` rows show them.
- **Brief.** The subagent guidance is split on purpose. The **standing rule**, harness-neutral and with no model names, lives in `references/worker-contract.md`: delegate reading and searching to a `light` subagent, code and tests to `standard`, and keep `heavy` for genuinely hard reasoning, using the tier map the pointer gives. The **resolved facts** for this worker live in the pointer brief `assign` writes: its own tier and model, the tier-to-model table of its kind, the reason when it is above the default, and the instruction to put `Worker tier: <tier> (<model>)` in its PR body, which is how the choice reaches the PR (workers write their own PR bodies, rota cannot).
- **Not in C9.** Picking the tier from the issue (C7), a tier per subagent call (the worker decides, by the rule), and showing `size` or priority in `candidates` to help the choice (the orchestrator reads the backlog).
### C10: round return, transfer, reclaim

C10 (#76) moves an issue that is already assigned. It builds on C3 (`assign` takes the claim, `claimId` on the slot, the lease) and C2 (`reconcile`). Orchestrator rulings (round 4, `c-rulings.md`): the claim lives on the tracker, through the same `item claim`, `item release` and `item state` calls `assign` makes; no local-only claims file; the note transfer hands over is a minimal stand-in for D1's.

- **Premise check.** Four points in #76 do not hold as written, and the entries below follow the code, not the ticket. (1) "Back to ready" is not a state: `item ready` is a property of the text (acceptance criteria or a design note), and the only tracker state `assign` sets is `in-progress`. Return puts the issue back in the candidate set by releasing the claim and clearing `in-progress`; `candidates` then lists it again with its checks. (2) "The branch stays" is false for a slot today: `worker reset` refuses to leave a branch with commits not on the base, and git will not check one branch out in two worktrees, so a slot cannot both keep the branch checked out and be free. The branch has to be pushed and the slot switched off it (**Park**). (3) "Reclaim from a stalled slot" needs a stall signal the registry does not hold: it has no activity time (**Stalled**). (4) "Transfer to the human" cannot be an assignee: the orchestrator and the human usually post as the same account (C4), so an assignee marks nothing; it is a label (**Claim on the tracker**).
- **Claim on the tracker.** The holder is the open claim comment `item claim` posts (`claimId` `<agent>@<round>`, C3) plus the `in-progress` label. `.rota/workers.json` mirrors it: the slot's `task` and `claimId`. A new top-level label role `issues.labels.needsHuman` (default `needs-human`) marks an issue handed to the human: no claim, no `in-progress`, the label on. Each verb below changes the tracker first and the registry second, so a crash between them leaves a mismatch reconcile reports and `--apply` repairs from the tracker, which wins. Return and transfer to a slot release the old claim before claiming anew, so an item is never claimed by two.
- **Park.** Return, transfer and reclaim free a slot with the same sequence, `internal/round.Park(slot)`: salvage the worktree if dirty (stage the dirty paths by name, never `-A`, and commit `wip: parked from <slot> (rota round <verb>)`), push the work branch to `origin` (`git push -u origin <branch>`, no force), and only if the push succeeded switch the worktree to `park/<agent>` at the base. A failed push leaves the slot as found, exit 5; the branch is never the only copy of the work. This is a second guard beside `worker reset`'s, not a change to it: reset still refuses a slot holding unmerged commits, because it cuts a fresh branch for new work; `Park` only moves the checkout off a branch that now exists on the remote. `worker reset` is the one that cuts the next issue's branch afterwards, so `assign` after a return behaves as on any parked slot. The salvage commit is the one thing a verb writes into a worker's branch. A commit that a hook rejects is exit 5 and the slot is left as found.
- **Stalled.** A slot is `stalled` when it holds an issue, its host agent is alive, and nothing has moved for `round.stallMinutes` (default 30, `0` turns the check off; a silent default like `round.scope`, not seeded by init). "Moved" is the newest of: the committer time of the branch tip when the branch has commits past the base; the newest mtime among the worktree's dirty paths (`git status --porcelain`, `stat`); and the slot's `activeAt`, a new optional registry field (RFC 3339 UTC) that `worker dispatch` stamps and `worker poll` re-stamps whenever the state it classifies differs from the recorded one. A worker editing without committing is therefore not stalled. A slot whose host agent is not alive is `dead`, not `stalled` (`dead-tab`, C2), and a slot waiting on an open escalation (C4) is never stalled. The signal that cannot be had is the host's raw agent-status churn: herdr events are not stored and `round wait` is read-only, so a hung agent that still repaints its status is judged on commits and files alone. Reconcile and reclaim compute this the same way, in `internal/round.Stalled(slot, now)`, with `now` injectable so the threshold is testable without sleeping.
- **Reconcile amendments (C2).** Two drift kinds, neither repaired by `--apply`'s existing rules except as noted. `stalled`: the rule above (`detail` carries the idle minutes and the signal that last moved). `claim-mismatch`: the tracker and the registry disagree about who holds an issue: the slot's `task` has no open claim by its `claimId` (or another claim holds it), or an open claim `<agent>@<round>` names a registry slot that does not hold that issue. `--apply` repairs only the registry side of an unambiguous mismatch (clears a `claimId` whose claim is gone; never edits the tracker), because the tracker is the source of truth and a human may have changed it on purpose. `label-orphan` and `label-missing` stay as C2 defined them.
- **Handoff note.** A stand-in for D1's note (#65), small enough that D1 can absorb it: one comment on the issue, posted by `return`, `transfer` and `reclaim`, ending with the marker `<!-- rota:handoff <from>@<round> -->` so C4's answer rule never reads it as an answer. Body: `**rota handoff** (<verb>, from <slot>)`, then four labelled lines `Branch:`, `Head:` (the pushed sha7 and subject), `State:` (committed, plus `salvage commit` when `Park` made one) and `Reason:`, then free text under `Done and next:` taken from `--note-file`. A receiving worker finds it by the marker; the pointer brief (C3) names the latest `rota:handoff` comment and the branch. When D1 lands, its format replaces this body and the marker stays.

## E: Codex workers

E1 (#68) runs OpenAI's Codex CLI as a round or pool worker beside Claude Code. It adds no verb: `worker dispatch` and `round assign` take `--kind codex`, `doctor` gains a `codex` check. A codex worker is a visible TUI session in a herdr tab, like a claude one; headless `codex exec` stays out (#44).

- **Kind.** `--kind` picks the harness; the default is the slot's recorded `kind`, else `claude`. `assign` records it on the slot (C9) and passes it to dispatch. The kind selects the launch command, and under herdr the command's binary must match the kind (`claude` or `codex`, by basename after any leading `KEY=VALUE` tokens), so `herdr agent start --kind` is derived from the command, never assumed.
- **Launch command.** New key `work.codexCommand`, a silent default (not seeded by init): `codex --model {model} --dangerously-bypass-approvals-and-sandbox --dangerously-bypass-hook-trust --no-daemon --no-alt-screen`. `{model}` takes the tier's model, as in `work.workerCommand` (C9); with no model chosen (a bare `worker dispatch`, or `round assign` with `round.tiers.codex` unset) the default drops `--model {model}` and Codex uses its own default, while a custom command that still holds `{model}` exits 2. The bypass flag is the codex twin of `--dangerously-skip-permissions`, for the same reason (nobody answers prompts in a worker pane; scope, not gating, bounds it). `--no-daemon` keeps the session in the pane's own process tree: a session hosted by Codex's background app-server would outlive `tab close`, and dispatch's kill must be provable. `--no-alt-screen` keeps the pane's scrollback readable: herdr refuses `agent read --source recent-unwrapped` while a Codex agent in the alternate screen is working, which would leave `worker poll` blind mid-turn (seen live, #70 spike). `--dangerously-bypass-hook-trust` is there because Codex opens a hook-review screen on the first prompt for any untrusted hook, including herdr's own integration hook in every slot home; the screen swallows the prompt and herdr reports `idle` or `working`, never `blocked`, so no dialog handler sees it (seen live, #70 spike). The worker already bypasses the sandbox and approvals, so trusting hooks unread adds little; the Claude-worker parity is `--dangerously-skip-permissions` (maintainer ruling, round 4). The resume guard also refuses codex's `resume` and `fork` subcommands.
- **Codex home.** Each slot has its own `CODEX_HOME` at `<git-common-dir>/rota/codex/<slot>`, never `~/.codex`. It holds the slot's login, sessions, history and herdr integration, so two slots share no auth or session state. It lives beside the round lease rather than inside the worktree: inside, it would dirty `git status`, trip the reset guard and sit in the worker's own tree. It is outside `.worktrees/`, so `reap` never sees it, and it survives `wind-down` and resets, which keeps the login. rota creates it (0700) on the first codex dispatch to the slot and never deletes it.
- **Seeding.** On creation rota writes `config.toml` into the home, and only when the file is absent: the slot's worktree trusted (`[projects."<worktree>"] trust_level = "trusted"`) and `check_for_update_on_startup = false`, so neither dialog opens in an unattended pane. Under herdr, when `CODEX_HOME=<home> herdr integration status` does not report codex `current`, rota runs `CODEX_HOME=<home> herdr integration install codex`, the codex counterpart of the claude integration the `hook` check asks for. rota never writes `auth.json` and never copies one.
- **Login.** rota does not log a slot in. Before anything is marked, `assign` and `dispatch` run `CODEX_HOME=<home> codex login status`; a non-zero exit is exit 5 with the hint `CODEX_HOME=<home> codex login`, which the maintainer runs once per slot. Copying an existing `auth.json` into a slot home is not a shortcut: a ChatGPT login carries a rotating refresh token, so two copies refresh independently and can invalidate each other, including the maintainer's own login in `~/.codex`.
- **Version.** The supported Codex CLI range is pinned in rota: `>= 0.159.0, < 0.160.0` (the version tested, 0.159.2, as herdr is pinned to 0.9.x). It is read from `codex --version` (`codex-cli X.Y.Z`; anything else counts as unsupported). Outside the range, `assign` and `dispatch` refuse with exit 4, `blockedBy: "codex version"`, before anything is marked; `--accept-codex-version` lets one call through and adds the warning `codex X.Y.Z is outside the supported range <range>`. The flag is not `--force` (rule 5). `doctor` reports the same check.
- **Host.** herdr only: `tab create` passes `--env CODEX_HOME=<home>` (the account is fixed at tab creation, as `CLAUDE_CONFIG_DIR` is) and `agent start --kind codex`. `work.accounts` and its usage meter are Anthropic's and are skipped for a codex slot: the slot's home is its account, so there is nothing to rotate until Codex has a meter. Under tmux a codex dispatch exits 5 (`codex workers need work.dispatch=herdr`): the tmux host detects a booted session from Claude Code's screen text and has no codex equivalent.
- **Startup dialogs.** herdr reports Codex's folder-trust, update and hook-review screens as `idle` or `working`, never `blocked`, so the herdr dialog handler (`agent_not_ready` at start) cannot see them. They are prevented instead: the seeded `config.toml` covers folder trust and the update check, and `--dangerously-bypass-hook-trust` covers hooks. The texts are recorded in the #70 spike.
- **Classification.** Unchanged code: herdr reports the codex agent's state natively, and `worker poll` and `round wait` apply the same sentinels (`ROTA-DONE`, `ROTA-BLOCKED`) on top. `limited` gains Codex's usage-limit text once recorded live. The working, idle and blocked check on the Codex TUI is manual and recorded in the PR (#68).
- **`rota doctor` `codex` check.** Placed after `hook`. `skip` when codex is not on PATH and no slot has a codex home. Otherwise `fail` when codex is missing (a slot has a home), its version is unreadable or outside the range (hint: install codex-cli 0.159.x), or a slot home is not logged in (hint `CODEX_HOME=<home> codex login`) or, under herdr, lacks the integration (hint `CODEX_HOME=<home> herdr integration install codex`). `detail` names the version and the homes checked, and on a pass with `round.tiers.codex` unset notes that the tiers are optional (workers use Codex's default model, #68). `codex --version` runs with `CODEX_HOME` set to a slot home when one exists, so the check never needs `~/.codex`.
- **Not in E1.** Codex subagents and solo mode (E3, #70, then C8), a Codex usage meter, codex under tmux, a second-opinion runner (#158 retired it).

### D1: statusline dump, Stop hook and handoff

D1 (#65) lets a long-running Claude orchestrator hand off and exit before its context or usage runs out. Three small pieces: a **state dump** fed by the statusline, a **Stop hook** that blocks above a context threshold, and a **SessionStart hook** that injects the handoff into the next session. It acts only on the orchestrator. Restarting the pane after the exit is D2 (#66), and what to do about a usage limit is D3 (#67); D1 writes the state they read and starts nothing.

Status: **ratified by the maintainer, round 4** (AskUserQuestion, relayed by the orchestrator). Statusline: "Wrapper", so `--wrap-statusline`, record the original, uninstall restores it exactly, and `dump` swallows its own errors. Hook scope: "Project-local", `.claude/settings.local.json`. Handoff file: `.rota/handoff/<base>.md`, delivered by the SessionStart hook. The 75% threshold default is ratified as configurable. The context fallback from `current_usage` and `context_window_size` is accepted; `used_percentage` stays unverified. If a plugin cannot register a `statusLine`, the wrapper does not need it to. Still my own calls, unratified: the verb names (`rota hook install`, not `rota statusline install`, since one command installs the hooks and the statusline together), the three other config defaults, the loop-prevention counts and the lease-based orchestrator test.

- **The session state file.** `<git-common-dir>/rota/session/<session_id>.json`, written atomically (`fsio`) on every statusline refresh. It sits next to the round lease for the same reason: per repo, shared by every worktree, never tracked, and no new `.rota/.gitignore` entry. Fields: `sessionId`, `cwd`, `updatedAt` (RFC 3339), `contextPct` (number or absent), `rateLimits` (the statusline's `rate_limits` object verbatim, absent when the session has none), and `raw` (the whole input JSON, so D3 and later phases read fields D1 did not anticipate). `contextPct` is `context_window.used_percentage` when present; otherwise it is derived from `context_window.current_usage` (input, cache-creation and cache-read tokens) over `context_window.context_window_size`; absent when neither exists. Files for a session untouched for 24 h are removed by the next dump.
- **"The orchestrator."** The session whose Claude process holds the round lease (`internal/roundlease`, C3), matched with `Holder.SameAs` on the nearest non-shell ancestor, as `rota round start` records it. No lease, or a lease held by another process, means the hook is a no-op and exits 0 with no output. This is how the plugin or settings registration can be wide without touching workers, which also run Claude but never hold the lease. The dump itself is written for every session, because the statusline cannot know which it is.

#### The handoff file

### D2: keepalive supervisor

D2 (#66) restarts the orchestrator in the same pane after it exits, but only when it left a fresh handoff (D1). It stacks on D1: the handoff path, its freshness rule and the SessionStart injection are D1's, unchanged.

Status: **ratified by the maintainer, round 4** (AskUserQuestion, relayed by the orchestrator; answers in `.worktrees/finn-q.md`). The supervisor holds the lease via `ROTA_ROUND_HOLDER_PID`, with the small C3 edits (`roundlease.Discover`, `round start` numbering) and tests. The supervisor shape, `rota keepalive run -- claude …`, departs from the issue's wording and is ratified as such. `orchestrator.escalateIssue` is unset by default and this repo sets nothing for now: the breaker's notification is a host notification only. The restart prompt is appended as the last argument, with the default text below. Still my own calls, unratified: the defaults 10, 3 and 5 s, progress by handoff SHA, and the state file's shape.

- **A supervisor, not a watcher.** `rota keepalive run -- <command…>` is the pane's foreground process and runs the orchestrator (`claude …`) as its child. It gets the child's real exit status from `wait`, so it needs neither herdr's process-info PID nor `agent_status_changed`, works the same under tmux, and "the same pane" is simply the pane it already owns. The issue's "watch for the process to exit" is satisfied by being its parent.
- **The lock is the round lease.** No second lock. `run` takes the C3 lease (`internal/roundlease`) as the holder, with its own PID and start time (and the pane from the environment, as `Discover` reads it), and holds it for its whole lifetime, across restarts. It sets `ROTA_ROUND_HOLDER_PID=<its pid>` in the child's environment, and `roundlease.Discover` returns that PID as the holder whenever the variable is set and no explicit `--holder-pid` was given. So every `rota round start`, `wind-down` and D1 hook the orchestrator runs sees the supervisor as the lease holder and treats the session as the orchestrator, without any change to `Holder.SameAs`. Consequences: a second `run`, or a second orchestrator started by hand while the supervisor lives, is refused by the lease it already enforces; the round number survives a restart, because `rota round start` in the restarted session renews the lease instead of reclaiming a stale one; and D1's SessionStart hook injects the handoff immediately, with no `rota round start` first (this removes the lease-timing caveat of D1's `session-start`).
- **Round numbering.** `run` takes the lease unnumbered (`round` 0). The first `rota round start` under it numbers it (registry `round` plus one, written to the lease and the registry); a renewal under the same holder keeps the number. A lease the supervisor finds already numbered, with itself as holder, is reused.
- **State.** `<git-common-dir>/rota/keepalive.json`, next to the lease, rewritten under its own `fsio` lock on every transition: `{"pid": number, "startedAt": string, "command": []string, "status": "running" | "stopped", "restarts": number, "noProgress": number, "runStartedAt": string, "lastHandoffSha"?: string, "lastExit"?: {"code": number, "signal"?: string, "at": string}, "stopReason"?: string, "escalation"?: string}`. D3 does not write here: its usage-limit log is `limits` in `.rota/workers.json`, the round state (see D3), so this file stays the supervisor's own.

### rota keepalive run
rota keepalive run [--max-restarts <n>] [--breaker <n>] [--backoff <seconds>] [--prompt <text>] [--no-limits] -- <command> [<arg>…]
repo: none
data: {"stopReason": "no-handoff" | "interrupted" | "max-restarts" | "breaker", "restarts": number, "noProgress": number, "lastExit": {"code": number, "signal"?: string}, "escalation"?: string, "changed": bool}
exit: 0 when it stopped because the orchestrator exited without a fresh handoff or the supervisor was interrupted (`no-handoff`, `interrupted`); 1 when it stopped on `max-restarts` or `breaker` (same `data`); 2 when `<command>` is missing, a number flag is invalid, or `--` is absent; 70 when a `limits.*` key is out of range (not checked with `--no-limits`); 3 when there is no project root; 4 when the lease is held by another live or foreign holder (`blockedBy`: `lease held`, `changed` false, nothing started); 5 when the command cannot be executed or `git` fails (the lease is released and the state file records `stopReason` `spawn-failed`, a value `data.stopReason` never has)
old: none (new in D2)
note: not a query. It blocks for the life of the orchestrator and its restarts, so `--json` prints one envelope at the very end; the child owns the terminal until then. Flags override config for this run: `--max-restarts` `orchestrator.keepaliveMaxRestarts`, `--breaker` `orchestrator.keepaliveBreaker`, `--backoff` `orchestrator.keepaliveBackoffSeconds`, `--prompt` `orchestrator.restartPrompt`. `--no-limits` (D3) does not run the usage-limit watcher beside the command; it is a flag, not a key.
note: loop. (1) Refuse unless the lease is free, stale or this supervisor's. Take it. (2) Start the command with the current directory, stdio and process group unchanged, plus `ROTA_ROUND_HOLDER_PID`. (3) On the child's exit, record `lastExit` and decide from the handoff file (`.rota/handoff/<base>.md`, D1): **fresh** is D1's rule (it exists and its mtime is within `orchestrator.handoffMaxAgeSeconds`; a consumed handoff, renamed `.consumed`, is not fresh). No fresh handoff: stop, `no-handoff`; this is also how a deliberate `/exit` ends the loop. A fresh one: continue. (4) Progress check, below. (5) If `restarts` has reached the maximum, stop `max-restarts`; if `noProgress` has reached the breaker, stop `breaker`. (6) Wait the backoff, start the command again with the restart prompt appended as its last argument, increment `restarts`, go to 3. The first start never gets the prompt.
note: **progress.** A run made progress when the handoff it ended with was written when or after the run started (mtime not earlier than `runStartedAt`, which is taken just before the spawn, so a coarse filesystem timestamp cannot hide a handoff written at once) and its SHA-256 differs from `lastHandoffSha`, the handoff the run began with. For the first run that is the handoff present when `run` started, if any. Progress resets `noProgress` to 0 and stores the new sha; anything else adds one. This is what the circuit breaker counts: a restarted orchestrator that dies before consuming the handoff (bad auth, a hook error, a crash on boot) leaves the same fresh file behind, and without this check the loop would restart it until `max-restarts`. `noProgress` is therefore not "restarts without a handoff" (those stop at step 3) but "restarts that left no new handoff".
note: **signals.** SIGINT and SIGTERM to the supervisor are forwarded to the child and set `interrupted`; the supervisor then waits for the child, does not restart, and stops. A Ctrl-C in the pane reaches both (same process group), so the supervisor ignores SIGINT for itself and relies on the forward. SIGKILL cannot be handled: the lease then goes stale (the holder is gone) and `rota reap --kind lease` clears it, as for any dead orchestrator.
note: `changed` is true once a child was started. A `--json` run raises its warnings (escalation not sent, no `escalateIssue`, a reclaimed stale lease) in the envelope and on stderr.
note: **on stop** the supervisor releases the lease it holds (a stopped round needs no orphan lease, and a human can start an orchestrator at once), writes `status: "stopped"` and `stopReason`, and on `max-restarts` or `breaker` sends the escalation below. Releasing is skipped when the lease is no longer this supervisor's.
note: **breaker notification (C4).** On `max-restarts` and `breaker`, `run` calls `round escalate send` (the library entry, not a subprocess) on the issue `orchestrator.escalateIssue`: title `Orchestrator keepalive stopped: <stopReason>`, body with the restart and no-progress counts, `lastExit`, the handoff path and age, the state file path, and the line `Run rota keepalive run again after fixing the cause; the handoff is kept.` The escalation id goes in `data.escalation` and the state file. With `orchestrator.escalateIssue` unset (0) there is no thread to post on: `run` raises the host notification alone (`Notify`, herdr only), records `escalation` absent, and adds a `warnings` entry saying why. A pending escalation already on that thread (`send` exits 4) is a warning too; the stop stands. `no-handoff` and `interrupted` send nothing: they are the human's own act.
note: **the handoff is never deleted by the supervisor.** Only D1's SessionStart hook consumes it (rename), which is the one place that knows the injection happened.

### C8: solo mode

C8 (#64) lets a round run with no terminal host: the orchestrator runs each worker as an in-harness subagent (the Claude `Agent` tool) inside the slot's own `.worktrees/<agent>` checkout. Rulings (round 4): the round detects its host (maintainer, via AskUserQuestion: "Detect host"); detection applies to round verbs, and the existing worker verbs keep their behavior outside a round (orchestrator); `.rota/workers.json` holds what tab mode writes, so `round reconcile` accepts it; gates and the merge policy apply unchanged. The judgment (when to assign, how to read a result) stays in `rota-orchestrate` (C7); C8 is the host and state side.

- **Premise.** `work.dispatch` already exists with `subagent` as its silent default, and `internal/host` maps every value except `herdr` to tmux. Outside a round that stays as it is.
- **Round host.** Resolved once, by `round start`, and recorded as a top-level `host` (`"herdr"`, `"tmux"` or `"solo"`) in `.rota/workers.json`:
  - `work.dispatch` `herdr`: herdr; `tmux`: tmux. Unavailable is exit 5, as today. Solo is never a silent fallback from an explicit host.
  - `work.dispatch` unset or `subagent`: herdr when the session runs inside a herdr pane (`HERDR_ENV=1` and `herdr` on `PATH`), else tmux when inside tmux (`TMUX` set), else solo.
  - A later `round start` of the same round keeps the recorded host, so a round never changes mode mid-flight; a new round resolves again. `round wind-down` on `clean` clears it with the lease.
- **Which verbs read it.** Every round verb uses the recorded `host`; with none recorded (no round started), `round status` and `round reconcile` keep their pre-C8 guess (herdr when `work.dispatch` is `herdr` or `HERDR_ENV=1`, else tmux), so their output does not change outside a round. So do the worker verbs a round drives (`worker dispatch` and its `--relay`, `worker poll`, `worker wait`, `worker session check`/`ensure`) when the registry has a `host`; with none (no round started) they select from `work.dispatch` exactly as before. This keeps one host per round: without it, a round on the default config that detected herdr would spawn herdr panes from `round assign` while `worker poll` and `worker dispatch --relay` looked for tmux. Before `round start`, or after a clean wind-down, nothing changes for the worker verbs and no existing behavior or frozen record moves.
- **Slot state under solo.** The A7 slot with no host fields: `handle` null, no `session`, no `window`, no `configDir`, no `account` (every subagent runs on the orchestrator's own account). `worktree`, `branch` (`<agent>/<issue>-<slug>`), `base`, `task`, `claimId`, `pr` and `state` are written by the same verbs as in tab mode; `state` is set by `round report` instead of a pane poll. `round reconcile` already skips the host findings (`dead-tab`, `unclaimed-tab`) for a slot with no handle; every forge and git finding runs unchanged.
- **Assign under solo.** `round assign` runs steps 1 to 8 as in tab mode (lease, scope, readiness, claim, in-progress state and comment, reset onto the issue branch), skips the account pick, and replaces `worker dispatch` with setting the slot `busy` and returning the pointer brief it would have sent. Data adds `"host": "solo"`, `"brief": string` (the brief text, the same text tab mode pastes into the pane) and `"worktree": string` (absolute); `dispatched` is false. Nothing new is written under `.rota/`. The orchestrator launches the subagent with the brief as its prompt and `worktree` as its working directory. A failure before the slot is marked `busy` undoes the claim and state, as in tab mode.
- **Pane verbs under solo.** With the recorded `host` `solo`, `worker dispatch` (and `--relay`), `worker poll`, `worker wait`, `worker session check`/`ensure` and `worker account pick`/`assign` exit 2 with `solo round: workers are subagents, there are no panes` and the solo equivalent in the hint. `round wait` never blocks under solo: it returns the first watched slot whose recorded `state` is not `busy` (`source: "registry"`), or exits 1 with `timedOut: true` at once when every watched slot is `busy`, because only `round report` changes a solo slot. The orchestrator waits on the `Agent` tool's completion instead.
- **Transfer and reclaim under solo.** `round transfer` to a slot of a solo round mirrors `assign`: no account pick, the receiver set `busy`, and `host`, `brief`, `worktree` with `dispatched: false` in the data. `round reclaim` skips the kill (there is no pane), so a stalled or forced reclaim does not refuse on a live agent.
- **Unchanged.** `worker gate`, `worker reset`, `round wind-down`, the merge-approval gate and the C5 flags need no host and behave identically. `round status` and `round reconcile` report the round's `host`. `rota doctor` resolves the host the same way (#236), so a herdr pane with `work.dispatch` unset or `subagent` gets the herdr host and hook checks; only solo skips. `--escalate` notifies through herdr only when herdr is the host; under solo the PR comment is the only channel.
- **Session limit.** Every solo worker is a subagent of the orchestrator's session: they share its account, its rate window and its context budget for results. A `limited` hit stops every slot at once, and the orchestrator with them. `docs/usage/parallel-rounds.md` says so in its solo section.
- **Claude only.** Solo workers are Claude `Agent`-tool subagents. A Codex subagent cannot be given a working directory (E3, #70), so it would edit the orchestrator's own checkout instead of the slot's worktree; solo mode does not run Codex workers: `round assign --kind codex` (or a slot whose kind is codex) exits 2 under solo, before anything is marked. Supporting them would need a clean-tree guard on the orchestrator checkout after each one.

### D3: usage-limit handling

D3 (#67) keeps a round from stalling on a 5-hour or weekly usage limit: it sleeps until the reset and then resumes, or moves a worker's issue onto another account. It stacks on D2 (#66) and assumes the ratified D2 design: the supervisor (`rota keepalive run`) is a long-running process that holds the lease and owns the orchestrator's pane.

Status: **ratified by the maintainer, round 4** (AskUserQuestion, relayed by the orchestrator; answers to `.worktrees/finn-d3-q.md`). "Sleep until reset": the orchestrator sleeps and only workers can switch; the proactive orchestrator handoff and switch is a separate follow-up issue (filed, linked from the D3 PR). "Switch" is the default for `limits.mode`. The account policy is `round assign`'s rule (keep the slot's account unless it is cooling, else pick by headroom, else exit 5) on top of A7's `account pick`, nothing more. `pane.output_matched` exists in herdr 0.9.3 (schema in `.worktrees/herdr-0.9.3-schema.json`) and D3 builds on it, with the capture poll as the stated fallback. Questions 5 to 8 of the list (resume by typing a prompt, the log in `.rota/workers.json`, the reset time parsed from text, the defaults) stand as my calls.

- **One loop, two homes.** The watcher is a library loop (`internal/limits`), run (a) as a goroutine inside `rota keepalive run`, unless `--no-limits` is given, and (b) standalone as `rota limit watch` for an orchestrator not started under `run`. Both watch the orchestrator's own pane and every registered slot that has a session. The orchestrator's context never sees it, as with `round wait`.
- **Detection, data first.** *Orchestrator:* the D1 session file's `rateLimits` (`five_hour`, `seven_day`, each `used_percentage` and `resets_at`, epoch seconds): a window at 100 or more is a limit, `resetsAt` its `resets_at`; if both are, the later one. It is a local file read, so it is checked on every pass of the loop (every `--settle` seconds, 5 by default, and at once on a pane event), not by watching the file. *Slot:* the A7 meter of the slot's account (`worker account list`: `verdict` `cooling` with `resetsAt`). The meter calls the OAuth usage endpoint, so it is read only when text suggests a limit, never on a timer.
- **Detection, text fallback.** A limit message in a pane is `pane.output_matched` on herdr 0.9.x, over the C1 socket client (`internal/host`): one subscription per watched pane, `{"type": "pane.output_matched", "pane_id": …, "source": "recent", "match": {"type": "regex", "value": …}}` with `strip_ansi` left at its default true, where the regex is the alternation of the limit phrases that `worker poll` already uses (`limitPatterns` in `internal/worker`, which D3 exports so there is one list; Go's `(?i)` is written as the regex's own case-insensitive flag, and a phrase herdr's regex dialect rejects fails the subscription, which falls back to the poll). The event is `{"event": "pane.output_matched", "data": {"pane_id", "matched_line", "read": {"text", "revision", …}}}`; the subscribe reply can itself be an `output_matched` result when the pane already matches, and counts as a match. `matched_line` and `read.text` feed the reset-time parse. On tmux, which has no such event, the loop re-captures the pane every `--settle` seconds as `round wait` does and applies the same patterns. A match alone makes a limit with `source: "text"`: for a slot it then reads the account meter once; with data the limit takes the meter's `resetsAt` and `source` becomes `data`. With none, the reset time is parsed from the text when it has one (`resets at 3pm`, read in the local zone, and only when it parses to a time in the next 8 days) and otherwise the limit sleeps `limits.fallbackSleepSeconds`.
- **Decision.** `limits.mode` is `switch` (the default) or `sleep`. `sleep`: wait for the reset. `switch`, for a slot only: the account is chosen by the policy `round assign` already applies, on top of A7's `account pick`: keep the slot's account unless it is `cooling`, otherwise `rota worker account pick --exclude <the slot's account>` takes the account with the most headroom (`unknown` is "rotate", as A7 has it, and counts), and with none usable the switch is impossible (the exit-5 case of `assign`). With an account named and an idle slot on it: the slot's issue moves there with `rota round transfer` (C10), so the work continues from its pushed branch and a handoff comment. No usable account, or no idle slot on it, falls back to `sleep`, and the entry says why. **The orchestrator never switches**: a limited session cannot write a handoff, and a restarted one with no handoff has nothing to continue from, so it always sleeps.
- **Resume.** At `resetsAt` plus `limits.resumeMarginSeconds` the loop types `limits.resumePrompt` into the pane through the host's send (the same path `worker dispatch` uses for a brief; the supervisor addresses its own pane by `HERDR_PANE_ID` or `TMUX_PANE`, which needs a pane-addressed send beside `Host.Send`'s slot-addressed one). It then watches for the limit text again. A pane still limited after the prompt starts a new cycle, at most `limits.maxResumes` of them for one limit; past that the entry is `failed` and the loop sends the C4 escalation on `orchestrator.escalateIssue` as the D2 breaker does, or a host notification when it is unset.
- **Round state.** A top-level `limits` list in `.rota/workers.json`, beside `slots` and `escalations`, written under the registry lock. An entry is `{"id": string, "session": "orchestrator" | <slot name>, "window": "five_hour" | "seven_day" | "unknown", "source": "data" | "text", "detectedAt": string, "resetsAt"?: string, "action": "sleep" | "switch", "account"?: string, "to"?: string, "status": "waiting" | "resumed" | "switched" | "failed", "cycles": number, "resolvedAt"?: string, "note"?: string}`. `id` is `l<N>`, N one more than the highest in the list. Times are RFC 3339 UTC. Every transition rewrites the entry, so the log shows what the watcher did and when. Resolved entries stay as the record, as escalations do; nothing prunes them in D3. `rota round status` and `reconcile` list the entries still `waiting` the way C4 amended them for escalations: read from the registry, no new drift kind.

### D4: proactive orchestrator switch on usage

D4 (#206) lets a limited orchestrator move to another account by handing off before the limit. D3 keeps the orchestrator on its own account and sleeps at the reset, because a session at 100% cannot write a handoff. D4 acts earlier, while it still can. It touches D1's Stop hook, D2's supervisor and D3's log, adds no verb and no flag, and is off by default: with it off, every line below is inert and D3's sleep is the behavior.

Status: **ratified by the maintainer, round 5**, in part. "#206 D4 now"; with no usable account, "Restart, same account" (AskUserQuestion, relayed by the orchestrator), which replaces the issue's "wait for the reset"; the account rule (point 1 under "Rulings") and the undiscounted figure (point 3) are ratified, and so is excluding accounts without a `configDir` for 5.0. The key names and defaults are still my own calls.

- **Opt-in, two keys.** `orchestrator.switchOnUsage` (boolean, default `false`) and `orchestrator.usageThreshold` (integer 1 to 100, default **90**). With `switchOnUsage` false, the Stop hook ignores `rateLimits`, the supervisor never reads a usage marker, and `rota doctor` skips its `switch` check.
- **D1, the Stop hook.** When `switchOnUsage` is true and the session is supervised, a `rateLimits` window at or above `usageThreshold` blocks the way a context reading does. The figure is the larger of `five_hour.used_percentage` and `seven_day.used_percentage` from the session file, under the same freshness rule (`stateMaxAgeSeconds`). **A hold passes it:** while `keepalive.json` carries a `switchHold` whose `until` is still ahead (see below), the hook ignores usage, so a session that has no account to move to is not asked for a handoff again. *Supervised* means `keepalive.json` says `running` and its `pid` is alive, the test `rota keepalive status` applies: with no supervisor nothing would restart the orchestrator under another account, so the hook passes and D3's sleep applies. A session with no `rateLimits` (API billing, no subscription meter) passes. The block reason names the window, the percentage, the threshold and the reset time when there is one, then gives the same handoff instruction as the context reason (path, marker line, `## Round state`, `/exit`). When context and usage both trip, the usage reason is used. Loop prevention is unchanged and shared: `handoffMaxBlocks`, `handoffFailed`, and a fresh handoff newer than the block passes.
- **The marker.** On a usage block the hook records `usageHandoff` in the session file next to `blockedAt`: `{"window": "five_hour" | "seven_day", "usedPct": number, "resetsAt"?: string (RFC 3339 UTC, from `resets_at` epoch seconds), "at": string}`. It survives statusline refreshes as `blockedAt` does. A context-only block writes none. It is how the supervisor tells a usage handoff from a context one.
- **D2, the supervisor.** After a child exits with a fresh handoff, the supervisor looks for a `usageHandoff` whose `at` is not before `runStartedAt` in the session files whose `cwd` is the project root (the lookup D3 uses for the orchestrator). None: the restart is as today. One: it decides the account before the restart, then applies D2's progress check, `max-restarts` and breaker unchanged (a switch is a restart and counts as one).
  1. **Current account.** The `work.accounts` entry whose `configDir` equals `CLAUDE_CONFIG_DIR` in the child's environment (the supervisor's own at the first start, then the last one it chose). Paths are compared after `filepath.Clean`, and an empty value is `~/.claude`. No match leaves the current account unnamed; it is still excluded from the candidates by directory.
  2. **Candidates.** Every other `work.accounts` entry that has a `configDir`, whose A7 meter says `free` and whose headroom is known and above `100 - usageThreshold`. `unknown` is not a candidate (A7 counts it as "rotate" for a worker; here a wrong guess costs a whole handoff cycle, so it does not). The one with the most headroom wins, ties by config order.
  3. **A candidate exists.** The restart adds `CLAUDE_CONFIG_DIR=<its configDir>` to the child's environment, here and for every later restart of this run, and appends the restart prompt as D2 does. The restarted session reads its handoff through D1's SessionStart hook, as after any restart.
  4. **None exists.** The supervisor restarts at once on the same account (after D2's backoff, with the restart prompt) and records a hold in `keepalive.json`: `switchHold` `{"until": string, "window": string}`, `until` being `usageHandoff.resetsAt`, or now plus `limits.fallbackSleepSeconds` when the marker has none. Until then the Stop hook passes on usage, so the restarted session works on, and D3's in-session sleep handles the real limit at 100%. A hold ends when `until` passes, or when a later decision finds a candidate and switches (the hold is cleared then). It does not stop a context handoff.
- **D3, the log.** One `limits` entry per decision, in the shape D3 defined, no new field: `session` `orchestrator`, `window` and `resetsAt` from the marker, `source` `data`, `detectedAt` the marker's `at`, `action` `switch` with `status` `switched`, or `action` `restart` (new value, D3's `action` is `"sleep" | "switch" | "restart"` from here) with `status` `resumed`, the same-account restart; `resolvedAt` is set at once for both. `account` is the account left (absent when unnamed), `to` stays empty (it names a slot) and the account switched to is in `note`, as D3 puts it for a worker. `note` also carries the percentage and threshold and, for a restart, why: `no usable account` plus each other account's verdict and headroom, and the hold's `until`. `rota limit status` and `rota round status` read it unchanged.
- **D3 and the gap.** Between the old child's exit and the new child's start there is no orchestrator pane to act on. The embedded loop skips the orchestrator session for as long as the supervisor holds no child (a flag the supervisor sets and clears around the gap). Without it a limit seen in the last session file would type a resume prompt at a supervisor with no child, and the keystrokes would reach the next `claude`. The standalone `rota limit watch` is never under a supervisor, so the hook passes there and no gap exists.
- **State.** `keepalive.json` gains `account` (name of the current account, absent when unnamed), `switches` (number) and `switchHold` (absent when none). `rota keepalive run`'s `data` gains `switches`. `keepalive status` shows the stored file as before.
- **`rota doctor`.** One check, `switch`, after `stop-hook`: `skip` unless `orchestrator.switchOnUsage` is true; otherwise `fail` when fewer than two accounts have a `configDir` (hint: add a second account to `work.accounts`) or when the `stop-hook` check would fail (hint `rota hook install`). It reads config and settings files only and never calls the usage endpoint.

#### Config
Two keys under `orchestrator`, silent defaults like D1's, validated where read (out of range exits 70 for verbs that read them; the hook treats it as a pass): `switchOnUsage` (boolean, default `false`) and `usageThreshold` (integer 1 to 100, default `90`). - **A usage figure is not a limit** (ratified; documented in the usage guide). Rulings (maintainer, 2026-10-04, relayed in round 5): skills ship "Embedded in rota", before the 5.0 tag; the verb names are open to argument. The version lives in the binary's ldflags, set from the tag (lea, F6b, agreed in round 5); F6a reads only `version.Get()`. F6b's root `VERSION` file is only the input to `release bump`, and nothing at runtime reads it.

- **Embedding.** `embed.go` at the module root (`package rota`, the only Go package at the root, since `go:embed` cannot reach a parent directory) embeds `rota-*/*.md` and `references/*.md`. `internal/skills` owns everything else. The **set digest** is the sha256 of the sorted `path NUL sha256(content) NL` lines over the files one install writes. It identifies a skill set without a version, so a dev build (`version` empty) still compares.
- **Install layout.** Each skill is installed as a self-contained directory: `<root>/<skill>/SKILL.md`, its other `*.md` files, and `<root>/<skill>/references/` holding only the references the skill cites, closed transitively over references that cite references. A skill's `references/x.md` therefore resolves relative to its own directory, which is the Agent Skills convention and the base directory both harnesses hand the model. No shared directory sits beside the skills, nothing is rewritten at install time, and installed bytes equal embedded bytes. To get there, the source changes once: links in `SKILL.md` drop the `../` (`](../references/x.md)` becomes `](references/x.md)`, the form the inline citations already use), and `test/validate-skills.py` resolves a skill's `references/` links against the repo's `references/`. A test installs into a temp root and fails if any `references/<name>.md` cited by an installed file is missing from that skill's directory.
- **Roots.** `--scope user` (default): `~/.claude/skills` and `~/.agents/skills`. The Claude root follows `CLAUDE_CONFIG_DIR` when it is set (`$CLAUDE_CONFIG_DIR/skills`, where Claude Code reads user skills), so a machine with several Claude accounts installs once per config dir. A user scope with no HOME (and, for Claude, no `CLAUDE_CONFIG_DIR`) exits 3. Manifest keys that are not local paths under an `rota-*` directory are ignored, and rota never writes or deletes through a symlinked parent directory. `--scope project`: `<git toplevel>/.claude/skills` and `<git toplevel>/.agents/skills`, for the toplevel of the working directory after `-C`, so it needs no `.rota/`. `--agent claude|codex|all` (default `all`) selects which of the two. `~/.agents/skills` is the user directory Codex scans (and other Agent Skills tools share); `CODEX_HOME` does not move it. A copied skill lists in Codex as `rota-pause`, not `hv-skills:rota-pause` (E2's probe), and `$rota-pause` invokes it.
- **Manifest.** `<root>/.rota-manifest.json`, one per root, so a project install carries its own: `{"schema": 1, "version": string, "digest": string, "agent": "claude"|"codex", "files": {"<skill>/<path>": "<sha256>"}}`. It lists exactly what rota wrote, and rota never touches a path outside it except to create one. It is written under the sidecar lock `.rota-manifest.json.lock`, with an atomic rename, after the files.
- **File states.** For each path the embedded set wants: `absent` (written: `created`); in the manifest, on-disk hash equal to the manifest's (`unchanged` when the content is the same, else rewritten: `updated`); in the manifest, on-disk hash different (`edited`: kept); on disk but not in the manifest (`unmanaged`: kept). A manifest path the new set no longer has is removed when unedited (`removed`), else kept (`edited`). Empty skill directories left behind are removed. A legacy `rota init --codex` symlink (`.agents/skills/rota-*` pointing at a directory with `SKILL.md`) holds no user content, so it is replaced (`replaced`) and not reported as unmanaged.
- **No `--force`.** Rule 5 forbids `--force`. `--overwrite` replaces `edited` and `unmanaged` paths. Without it, the verb still does all the other work, then exits 4 with `blockedBy: "edited"` or `"unmanaged"`, listing the paths in `kept`.

- **Built as** (worker calls, accepted by kit; unratified): `references/README.md` is copied when a file cites it, but its own links are not followed, since it links every reference and would put all of them in every skill (each skill gets 15 to 23 references, 308 files per root). The `CLAUDE_CONFIG_DIR` root, the manifest-key and symlinked-parent guards came out of review. A path on disk that is not in the manifest but has the embedded bytes is adopted as `unchanged`, so a lost manifest does not cause a false exit 4. `replaced` also covers an `--overwrite` of an `edited` or `unmanaged` path. `install` and `uninstall` default to `--scope user`; `update` and `status` default to both scopes. `uninstall` leaves the root directories and removes the lock sidecar. The text output gives one line per root with a count for each status, then the kept paths and warnings; `--json` lists every file.
- **Frontmatter must be strict YAML.** Codex 0.159.2 silently dropped `rota-capture`, whose unquoted description held `GH: #N`. Claude Code reads it leniently. `test/validate-skills.py` now fails an unquoted single-line value that holds `': '` or `' #'` or starts with a YAML indicator. `rota-capture` and `rota-orchestrate` use `description: >-`.
- **Proof** (`codex debug prompt-input`, Codex 0.159.2, CODEX_HOME unset, no model session): with the real HOME, Codex lists `~/.agents/skills` as skill root `r0`. After `rota skills install --agent codex` into a temp HOME, it lists all 16 rota skills from `<HOME>/.agents/skills`.

### rota skills install
rota skills install [--scope user|project] [--agent claude|codex|all] [--overwrite]
repo: none
data: {"roots": [{"root": string, "agent": "claude"|"codex", "scope": "user"|"project", "version": string, "digest": string, "files": [{"path": string, "status": "created"|"updated"|"unchanged"|"removed"|"replaced"|"edited"|"unmanaged"}]}], "kept"?: []string, "warnings"?: []string, "changed": bool}
exit: 4 when a path was kept (`blockedBy` `edited` or `unmanaged`, `changed` true when anything else was written); 3 when `--scope project` and the working directory is not in a git work tree; 5 when a root cannot be created or written
note: runs without `.rota/`. Idempotent: on a root that already has a manifest it does what `update` does there. `files` lists only paths whose status is not `unchanged`, unless `--json` is given, where every path is listed.

### rota skills update
rota skills update [--scope user|project] [--agent claude|codex|all] [--overwrite]
repo: none
data: as `skills install`
exit: 1 when no root in scope has a manifest (`roots` empty; hint `run: rota skills install`); otherwise as `skills install`
note: refreshes only roots that already have a manifest. With no flags, it covers every root in both scopes for the current directory, so `rota skills update` after an upgrade refreshes whatever was installed. It never creates a root.

### rota skills uninstall
rota skills uninstall [--scope user|project] [--agent claude|codex|all] [--overwrite]
repo: none
data: {"roots": [{"root": string, "agent": string, "scope": string, "removed": []string, "kept": []string}], "changed": bool}
exit: 4 when an `edited` path was kept (`blockedBy: "edited"`); the manifest then keeps only the kept paths
note: removes manifest paths whose hash matches, then the empty directories, then the manifest. Unmanaged paths are never removed, even with `--overwrite`. A root with no manifest is skipped silently.

### rota skills status
rota skills status [--scope user|project] [--agent claude|codex|all]
repo: none
data: {"version": string, "digest": string, "roots": [{"root": string, "agent": string, "scope": string, "installed": bool, "version"?: string, "digest"?: string, "current": bool, "edited": []string, "missing": []string}]}
exit: implied only (classifier, rule 7)
note: read-only. `version` and `digest` at the top are the binary's. `current` is the root's manifest digest equal to the binary's. `missing` are manifest paths absent from disk.

### Changes to existing verbs

- **`rota init`**: `--codex` and `--skills-dir` are removed. Either flag exits 2 with the hint `run: rota skills install --scope project --agent codex`. `internal/initproj/codex.go` and its `codex` data go. `.agents/skills/rota-*` lines that earlier inits wrote to `.gitignore` are left alone.
- **`rota doctor`**: the `rota` check (binary against `.claude-plugin/plugin.json`) becomes a `skills` check in the same position. It reads the manifests in both scopes. With no manifest anywhere it is `skip` with the hint `run: rota skills install` (the repo's opt-in doctor rule: skip until installed, fail only on a broken install; orchestrator, round 5). It fails when an installed root's digest differs from the binary's (`skills 4.5.0, rota 5.0.0`, hint `run: rota skills update`), when an installed root has missing or edited files.
- **`rota round assign`**: the brief lookup drops `CLAUDE_PLUGIN_ROOT`. The order becomes `round.brief`, then `<project>/references/worker-contract.md` (a source checkout), then `rota-orchestrate/references/worker-contract.md` under the first installed Claude root (project, then user). Exit 4 `brief missing` is unchanged.
