## A9: init

A9 amendments (orchestrator rulings G1 to G7, round 3): `rota init` runs the managed blocks and returns `blocks` (G2), `rota init umbrella --list` (G3), the new `rota config fill` (G1, under `config`), schema key order for the seed `config.json` (G7), `rota version --drift` (G6, entry above), and two decisions recorded here:

- **Parity exception (G4).** Seed and generated block text name `rota` verbs instead of `.hv/bin/hv-*` paths: the `MAP.md` seed, `rota block skills` and the `milestone index` block. This is the one deliberate break from byte parity with the old helpers. Parity tests exclude exactly that text; everything else stays byte-identical.
- **`.rota/bin/` (G5).** Dropped with the rest of the hv-skills v3/v4 compatibility (#236): `rota init` neither writes a `.rota/bin/` line nor removes a 4.x mirror.

### rota init
rota init [--no-blocks] [--force]
repo: none
data: {"root": string, "created": []string, "configFilled": []string, "versionStamped": string, "projectRegistered": bool, "noVerify": bool, "blocks"?: [{"key": string, "status": string, "changed": bool}], "instructions"?: [{"action": string, "file": string, "keys"?: []string}], "warnings"?: []string, "changed": bool}
exit: 2 when `--codex` or `--skills-dir` is given (F6a removed both; hint `run: rota skills install --scope project --agent codex`; nothing is written); 4 in the home directory (see note); 70 when a seed file exists but is unreadable or corrupt, or `.rota/config.json` is not a valid JSON object. Acts on the working directory after `-C`, with no walk-up, so it runs without a `.rota/` root.
old: hv-bootstrap (no args).
shim: `created` is the diff of `find .rota .gitignore` before and after (paths relative to the root), and `changed` is `created` non-empty. The shim does not run the block steps and omits `blocks` and `instructions`.
note: steps, in order: seed `.rota/` and `.gitignore` (bootstrap); `instructions init`; strip the deprecated managed blocks; then the six blocks `block skills`, `block knowledge`, `milestone index`, `block decisions`, `map index`, `qa index` (G2). `instructions` is `instructions init`'s `actions`. `blocks` has one entry per block in that order, keyed `skills`, `knowledge`, `milestones`, `decisions`, `map`, `qa`, with the status the verb reports (`created`, `updated`, `appended`, `unchanged`); `milestones` reports only `changed`, so its status is `updated` or `unchanged`. A deprecated block that was stripped adds an entry `{"key": "<key>", "status": "removed", "changed": true}` before the six; a project without one gets no entry. `changed` is true when anything was created, migrated or written, blocks included.
note: config step (#71, replaces the removed init skill's fill and stamp), after seeding and before the blocks, runs on every `rota init`, `--no-blocks` included: it does what `config fill` does (writes the schema default of every missing required key, never touching a present one; required keys are project-scope keys only, so no machine or taste key is written (#1786); `configFilled` lists them, empty when none) and then sets `rota.version` to the binary's version (`versionStamped` is that version when the stamp changed, else `""`), which clears the drift nudge. An unreleased `dev` binary stamps nothing, and a stamp that would lower a gated version is left alone. The step also migrates the legacy `backlog.backend` and `issues.provider` keys to `issues.source` and moves the round-only `work.*` keys to `round.*` (each adds a `warnings` entry), and writes an explicit `issues.source` when the project has none: the origin's provider for a backlog already on the tracker (`.rota/issue-map.json` exists), else `file`. The global config is not copied into a new project; it applies at runtime. A re-run on a current project fills and stamps nothing and `changed` is false. Text mode adds `config filled: <keys>` and `stamped rota.version: <v>`.
note: `.gitignore` merge: the managed header and ignore lines (per-developer state: `status.json`, `repos.json`, `config.local.json`, `verdicts.json`, `gate-audit.jsonl`, `ledger.jsonl`, `flakes.jsonl`, `bugreports.jsonl`, `train-cache.json`, `handoff/`, `debug/`, the ledger, audit and bugreport logs, `workers.json`, `receipts.json`, `**/knowledge-hits.jsonl*`, `**/*.proof`, `**/*.lock`, `.codex/` and more) are written when the file is missing. In an existing file only the missing lines are added, directly under the managed header when it is present, else appended with a new header, so an older block picks up new lines on the next `rota init`. `.worktrees/` is added unless an equivalent line exists.
note: a block step that fails (a tracker error from `milestone index` in issue mode, say) does not fail `rota init`: its entry gets `status: "failed"`, `changed: false`, and `warnings` names it. Seeding has already happened, and a re-run retries it. Exit 70 still applies to the seed step.
note: closing line (#493): when `test.full` and `test.e2e` are both empty under a local verify, `noVerify` is true and text mode ends with `test.full is empty: the merge gate will refuse to merge until it is set (rota config set test.full '[...]')`. No prompt; it does not affect `changed`.
note: registry step (#24), last, on every `rota init` (`rota setup` runs it too): adds the directory (realpath) to `projects.json` in the rota state dir, `$XDG_STATE_HOME/rota` when that is an absolute path, else `~/.local/state/rota`. A registry an older rota left in `<global config dir>/projects.json` is moved there on first use; a state file already there wins and the old copy is removed. `projectRegistered` is true when the entry is new; a re-init only refreshes its `lastSeen`. The registry is machine state, not the project's, so it never makes `changed` true. A registry that cannot be written adds an entry to `warnings` and does not fail init.

note: temporary storage (#2107): paths under `$TMPDIR`, `/tmp`, `/var/folders` or `/private/var/folders` are excluded after resolving symlinks on the project and temp roots. Matching uses whole directory components. Init still seeds the project, sets `projectRegistered` false and prints one line: `project not registered: temporary directory`. A skipped registration neither creates nor updates the registry.
note: `--no-blocks` seeds only: no `instructions init`, no strip, no blocks, and `blocks` and `instructions` are absent. Sections that test seeding use it; a user who manages `AGENTS.md` by hand can too, so it is a real flag, not a test hook (rule 10).
note: seed `config.json` content stays the issues-only defaults (`issues.labels.inProgress` and `issues.autoCreateLabel`), written in schema key order, so it differs from the old helper's byte order (G7). `rota config fill` completes it, and `rota.version` is stamped with `rota config set`. The `MAP.md` seed names `rota map query <name>` and `rota map index` (G4).
note: home guard (#1183): when the working directory is `$HOME` (symlinks resolved) with no `.rota/` there or in a parent, `rota init` and `rota setup` exit 4 and hint `run: rota projects to pick a project, or pass --force to init here`; nothing is written. `--force` skips the guard. A `$HOME` that already holds `.rota/` is a project and is not guarded. `init umbrella` is not guarded: an umbrella over the git repos in `$HOME` is a legitimate use.
note: `--codex` and `--skills-dir` were removed by F6a (#230). They stay parseable only to exit 2 with the hint above; Codex discovery is `rota skills install --scope project --agent codex`, which copies the skills. `.agents/skills/rota-*` lines that earlier inits wrote to `.gitignore` are left alone.

### rota init check
rota init check
repo: none
data: {"initialized": bool, "missing": []string}
exit: 1 when not initialized. Like `rota init`, it acts on the working directory after `-C`, with no walk-up, and runs without a `.rota/` root (see shared definitions).
old: hv-preflight (no args).
shim: old rc 0 and rc 3 give `initialized: true` (rc 3 is the old helper-mirror check, dropped in 5.0); rc 2 gives `initialized: false` and exit 1, and the shim lists every missing core path itself in `missing` (the old helper names only the first); stderr `warn:` and drift lines go to `warnings`.
note: split from `init --check` because its `data` shape differs from `init`. It verifies `.rota/` and its seven core files only (DECISIONS.md, BACKLOG.md, KNOWLEDGE.md, MILESTONES.md, counters.json, config.json, status.json). It reports every missing path, where old stopped at the first. The old helper-mirror check goes away because the `rota` binary is on PATH. The advisory umbrella-flag mismatch and the version-drift line (`rota version --drift`) become entries in `warnings`.

### rota init umbrella
rota init umbrella (--repos <csv> | --all | --list)
repo: none
data: {"root": string, "created": []string, "registered": []string, "umbrellaIsGitRepo": bool, "configFilled": []string, "versionStamped": string, "umbrellaEnabled": bool, "changed": bool}; with `--list`: {"root": string, "candidates": []string, "isGitRepo": bool}
exit: 2 when not exactly one of `--repos`, `--all` and `--list` is given; 3 when the directory has no immediate child with a `.git` entry (checked before any seeding, so exit 3 leaves nothing behind); 70 when a seed file exists but is unreadable or corrupt. Like `rota init`, it acts on the working directory after `-C`, with no walk-up, and runs without a `.rota/` root (see shared definitions).
old: hv-bootstrap, then `printf '%s\n' <value> | hv-umbrella-init` where `--repos a,b` becomes stdin `a,b`, `--repos ""` becomes `none`, and `--all` becomes `all`.
shim: `created` is the diff of `find .rota .gitignore` before and after (paths relative to the root), `registered` and `umbrellaIsGitRepo` come from hv-umbrella-init's stdout JSON, and `changed` is `created` non-empty or a registry change.
note: after registering, it runs the same config fill and version stamp as `rota init` and, when at least one sub-repo is registered and `umbrella.enabled` is not already true, sets `umbrella.enabled` to true (`umbrellaEnabled` says whether it did). `changed` includes those config writes.
note: it also runs the base seeding that plain `init` does, since the init skill always runs hv-bootstrap first and a registry cannot exist without `.rota/`. Re-running is idempotent and never overwrites.
note: the old helper read one line from stdin, which `rota` never does (conventions: no prompts). `--repos` takes comma-separated names (empty value means none registered) or `--all`. Unknown names are ignored with a warning, and prior registrations still on disk as git children are kept with a warning, same as old.
note: `--list` is read-only (G3): it writes nothing, never seeds and never exits 3. `candidates` are the names of the immediate children with a `.git` entry (directory or file), sorted, the same scan `--all` registers; an empty list is exit 0. `isGitRepo` is whether the working directory itself is a git repo, the same test as `umbrellaIsGitRepo`. The init skill reads it to ask its umbrella question before anything is written. No `--list` old mapping exists; the shim runs the scan itself.

### rota projects
rota projects
repo: none
data: {"dir": string, "projects": [{"name": string, "path": string, "lastSeen": string, "missing": bool}]}
exit: 70 when the state dir cannot be located (neither `XDG_STATE_HOME` nor `HOME` is set). Read-only; runs without a `.rota/` root and ignores the working directory.
old: none.
note: the machine-wide registry `rota init` fills (#24): `<state dir>/projects.json`, `{"projects": [{"path", "name", "lastSeen"}]}`, `path` absolute and realpath-resolved, `name` its directory name, `lastSeen` the UTC RFC 3339 time of the last `rota init` there. Rows are sorted by name, then path. `missing` is true when the path no longer exists; such an entry is flagged, never pruned by this verb (`rota projects cleanup` does), so a project on an unmounted drive returns with it. Text mode prints `name<TAB>path` per row, plus `(missing)`. An absent or unreadable registry lists nothing and exits 0. This is not `.rota/repos.json`, the per-project umbrella sub-repo registry.

### rota projects cleanup
rota projects cleanup
repo: none
data: {"removed": [{"name": string, "path": string, "lastSeen": string, "reason": "temporary"|"stale"}], "changed": bool}
exit: 70 as `rota projects`. Runs without a `.rota/` root and ignores the working directory.
old: none.
note: deletes at once, no preview (#195, #2107): every registry entry in temporary storage (the same resolved-path rule as init), whose directory is gone or no longer holds `.rota/`, under the registry's lock. Text mode prints `removed<TAB>name<TAB>path` per entry, appending `<TAB>(temporary)` for temporary entries, or `noop: no stale or temporary projects` when nothing is removed. Each JSON row keeps `name`, `path` and `lastSeen`, and adds `reason`: `temporary` for temporary paths (even if also stale), otherwise `stale`. An absent registry removes nothing and is not created. Plain `rota projects` still never prunes.

### rota projects remove
rota projects remove <dir>
repo: none
data: {"removed": [{"name": string, "path": string, "lastSeen": string}], "changed": bool}
exit: 2 unless exactly one directory is given; 70 as `rota projects`. Runs without a `.rota/` root and ignores the working directory.
old: none.
note: drops the one registry entry for `<dir>` (#543), under the registry's lock, and never touches the directory. `<dir>` matches as given (made absolute) or by realpath, so a symlinked path and a directory that is already gone both find their entry. Text mode prints `removed<TAB>name<TAB>path`, or `noop: not registered: <dir>` (exit 0, `changed` false). An absent registry removes nothing and is not created. `rota projects --ui` calls this verb for its `d` key.

### rota projects --ui
note: the only `--ui` view on the projects verbs (#543): the registry from `rota projects` Data, each row with a status (`ok`, `missing directory`, `no .rota/`), and a detail pane with path, last round and round lease. Keys: Enter opens the palette in that project (`rota -C <path>`), `c` runs `projects cleanup`, `d` runs `projects remove` after a confirm, `n` asks for a directory and runs `rota -C <dir> init`, `/` filters, `q`/Esc go back. `cleanup` and `remove` have no view. Terminal only; the palette's Projects entry opens it.

### rota setup
rota setup [--force] [--yes] [--set <key>=<value>]... [--save-global] | --list
repo: none
data: init's `data` plus `"answers": {<key>: value}` and, when answers were saved globally, `"savedGlobal": [key]`; on the support path: {"role": "support", "file": ".rota/config.local.json", "answers": {<key>: value}, "doctor": {"ok": bool, "check"?: string, "hint"?: string}}; with `--list`: {"questions": [{"key": string, "title": string, "default": string, "choices": [{"value": string, "description": string}], "roles": ["main"|"support"], "if"?: "<key>=<value>", "free"?: true, "suggestion"?: string, "evidence"?: string}]}
exit: 2 when there is no terminal (or `--json`) and neither `--yes` nor `--set` was given, when `--set` names a key that is not a setup question, gives a value outside its choices, names a conditional question whose condition fails, or names a question the chosen role does not ask, and when terminal input ends before the last question (nothing is written in any of these); 4 when `.rota/` already exists here on the main path, with `blockedBy` `role` on the main path when the working directory is in a support project (here or a parent; before anything is written), or in `$HOME` without `--force` (home guard, see `rota init`), and on the support path with `blockedBy` `config` (`key` `round.support`) when the tracked `.rota/config.json` has no `round.support`, or `blockedBy` `backend` when `issues.source` is `file` (nothing is written); 70 as `rota init`. Acts on the working directory after `-C`, like `rota init`.
old: none (the init skill asked Q1 to Q5 in chat).
note: `rota init` plus the main config choices, asked first and written after init has seeded `.rota/`. This is the one verb that reads a terminal (#25, a maintainer ruling; the "never prompts" convention has this exception). Questions, choices, descriptions and defaults are `config.Prompts` in `internal/config/schema.go`, defaults being the schema's. Interactive means stdin is a terminal and neither `--yes` nor `--json` is given: prompts go to stderr, one numbered list per question, Enter takes the default, a number or a choice value answers. `--yes` takes the default for every question `--set` did not answer; `--set` alone suffices and skips prompting for the keys it names. `issues.source` is the one issue-tracking question (`file`, `github`, `gitlab`, `jira` or `linear`); `forge.provider` is not asked and stays `auto`. Each answer goes where its key's scope says (#1786): a project answer to `.rota/config.json`, defaults included; a machine answer (`round.dispatch`, `round.harnesses`, `orchestrator.harness`) to `.rota/config.local.json`, and a taste answer (`work.isolation`, `work.mergeStrategy`, `autonomy.level`, `ship.review`, `ship.qa`) to `.rota/config.json`, each only when it differs from the value the project would inherit (the global value, else the schema default). A taste answer is further written only as a deliberate pin: a `--set` value, or a typed answer other than the offered suggestion; a default or project signal taken by `--yes` or Enter (`.worktrees/` suggesting `work.isolation: worktree`) is never written. So `--yes` pins neither; text adds ` (config.local.json, this machine only)` to a local `set` line. An answer equal to the global value is never written. All validation happens before init runs. `--list` is read-only and answers with the questions and how to pass them.
note: signals (#1782): setup reads the project in the working directory for a suggested answer per question, and the starting value of a question is, in order: `--set`, the global config's value, the project signal, the schema default (`--yes` writes it; interactive prompts show `suggested: <value> (<evidence>)` and Enter takes it). When the global holds a value and the signal differs, the global stays and the evidence says `global config; project suggests <value>: <evidence>`; a question the global or `--set` already answers is not probed. A question with no signal keeps its default, and `--list` omits `suggestion` and `evidence` for it; `default` equals the suggestion when one exists. Signals: `git.baseBranch` (the shared `Repo.Base` fallback: main, master, trunk, then origin/HEAD), `issues.source` (`github`/`gitlab` when origin is github.com, gitlab.com or a `gitlab.*` host and `gh`/`glab` is installed and `auth status --hostname <host>` exits 0, else `file` with the reason; a probe that times out (5 s) or cannot run gives no signal; no signal for another host or no origin), `test.fast` and `test.full` (`go.mod`, a `package.json` test script, pyproject pytest, `Cargo.toml`, a Makefile test target; `test.full` prefers a test command a CI file runs; values are one-element JSON lists), `round.harnesses` (first harness kind on PATH), `work.isolation` (`worktree` when linked worktrees or `.worktrees/` exist), `round.dispatch` (`herdr` on PATH, else `tmux` on PATH with `$TMUX` set). Reading signals runs no project or test command; the only process started is the `auth status` probe. `git.baseBranch`, `test.fast`, `test.full`, `round.envSetup` and `round.sharedDirs` are free-text questions (`"free": true`, empty `choices`, unset when left empty): a bare command typed or passed with `--set` for a list key becomes a one-element list, and a JSON list is taken as is. They are project-owned, so the save-global offer skips them. (`round.harnesses` is also free text, but a machine key.)
note: roles (#1774): the first question is `round.role`, `main` (the default) or `support`; `--set round.role=support` answers it off a terminal. `main` is the flow above and writes no `round.role` (main is the default, and the tracked config may not hold the key). `support` is the support path, for a clone of a project whose main machine already ran `rota round support enable <name>`: it acts on the project enclosing the working directory (a subdirectory reads and writes the root's `.rota/`), does not run `rota init`, and refuses before asking anything else when the clone's tracked `.rota/config.json` has no `round.support` or `issues.source` is `file`. It asks only the questions whose `roles` include `support` (`round.dispatch`, `autonomy.level`, `round.harnesses`, `orchestrator.harness`; tracker, isolation, merge, review, QA, base branch and test commands arrive with the tracked config) and writes `round.role: support` plus every answer to `.rota/config.local.json` in one write, creating it when missing and keeping the keys already there; it never writes `.rota/config.json` or the global config, and makes no save-global offer. Each question there starts from the value the clone already holds, `.rota/config.local.json` first, then the tracked `.rota/config.json`, before the global config, the signal and the schema default, so a rerun keeps its answers and `--yes` never overrides main's tracked value with a schema default. The path ends by running `rota doctor` and prints `doctor: <check>: <hint>` for the first failing check, or `doctor: pass`; `data.doctor` is {"ok": bool, "check"?: string, "hint"?: string}, and a failing doctor does not fail setup. `rota setup` is not in the support fence: on a support machine the support path writes only `config.local.json`, and the main path refuses the initialized clone. `--list` prints `roles: both` or `roles: main` per question. The save-global offer never includes `round.role`.
note: bare `rota` in a directory without `.rota/` is meant to run this verb; the routing lives in `cmd/rota` (#19), not here.
