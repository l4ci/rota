## A3 and A4: version, update, config, repo

`rota version` ports in A3 (#47). `rota update`, `rota config` and `rota repo` were routed to A4 (#48) after the triage; their shapes stay here.

### rota version
rota version [--drift]
repo: none
data: {"version": string}; with `--drift`: {"version": string, "stamped": string, "installed": string, "status": "match"|"drift"|"unknown", "drift": bool}
exit: 3 when `--drift` and no `.rota/` is found. `status` is `unknown` when `stamped` or `installed` is empty.
old: plain `rota version`: hv-resolve-plugin-root --root-only (no positional or flag maps; prints the plugin root). `--drift`: hv-version-check --json (new `--drift` selects the old `--json` form; no other args).
shim: plain form reads the binary's stamped version; `--drift` wraps the old JSON (`stamped`, `installed`, `status`) and adds `version` (= `installed`) and `drift` (= `status == "drift"`); an old rc 0 with empty output (no `.rota/`) becomes exit 3.
note: `stamped` is `rota.version` from the merged config; `installed` is the running binary's embedded version (old: plugin.json at the resolved plugin root). In 5.0 they are the same source, so `version` and `installed` are equal.
note: old `hv-version-check` exited 0 silently without `.rota/`, where 5.0 exits 3.

### rota update
rota update
repo: none
data: {"installType": "brew"|"script"|"dev"|"unknown", "installRoot": string, "currentVersion": string, "latestVersion": string, "status": "behind"|"current"|"ahead"|"unknown", "updateCommand": string}
exit: implied only. A missing `gh`, a network failure or an unresolved install gives `latestVersion` or `currentVersion` empty and `status: "unknown"`, as old; an unstamped build (version empty, `dev` or `(devel)`) also reports `status: "unknown"`. Read-only: never runs the update.
old: hv-update-check (no args). Env: `HV_INSTALL_ROOT` stays as the real override (`installType: "override"`, not a test hook); `ROTA_TEST_LATEST_VERSION` is the test hook, for old `HV_LATEST_VERSION` (rule 10).
shim: old stdout is already this JSON; pass it through unchanged and export `HV_LATEST_VERSION="$HV_TEST_LATEST_VERSION"` when set.
note: strings may be empty rather than absent, as in the old helper.
note: allowed on a support machine (`round.role support`): the support fence permits this read-only check, with the same version report and update command as on main.
note: F6b (#230) replaced the plugin-era detection. `currentVersion` is the running binary's version and `installRoot` is the directory holding the binary (symlinks resolved). `installType` is `brew` for a path under a Homebrew prefix (`/Cellar/`, `/homebrew/`, `/linuxbrew/`), `dev` for an unstamped or `-dev` build or one stamped with a full-length (40-char) commit SHA, which only a checkout rebuild writes (goreleaser stamps a short abbreviation), `unknown` when the binary path does not resolve, otherwise `script`. `updateCommand` is `brew update && brew upgrade rota`, the `install.sh` pipe, or a rebuild, each followed by `&& rota skills update`. `HV_INSTALL_ROOT` and `CLAUDE_PLUGIN_ROOT` are no longer read.

### rota config show
rota config show [--global|--local] [<key>]
repo: scoped (not with `--global`)
data: {"entries": [{"key": string, "value": any, "source": "local"|"project"|"global"|"default", "global"?: any, "scope"?: "project"|"machine"|"taste", "default"?: any, "type"?: "bool"|"int"|"string"|"list"|"path"|"enum"|"object", "group"?: string, "desc"?: string, "choices"?: [string], "effective"?: string, "effectiveSource"?: "explicit"|"profile"|"default"|"harness default"}]}
exit: 3 when `<key>` is neither a schema key nor present in the merged config; 2 when more than one positional is given. `value` is the raw JSON value (not a JSON string of it). No key: every schema key in schema order. With a key: `entries` holds exactly one element, so both forms share one shape.
note: `scope`, `default`, `type`, `group`, `desc` and (enum keys only) `choices` are the schema row's metadata (#541). They are absent for a hand-edited key outside the schema. `scope` (#1786) is the layer the key belongs in: `project` (the repo: tracked `.rota/config.json`), `machine` (one developer's machine: `.rota/config.local.json` or the global config) or `taste` (a working preference a team may pin in the tracked file). The text line of a schema key ends `(source: <source>, scope: <scope>)`; a hand-edited key keeps `(source: <source>)`.
note: `--local` lists `.rota/config.local.json`'s own values instead of the merged ones, as `--global` does for the global config: `data` gains `"scope": "local"`, `source` is `local` or `default`. `--global` with `--local` is exit 2.
old: hv-config-show [<key>] (new `<key>` maps to the old single positional; unchanged).
shim: parse each stdout line with `^(\S+) = (.*)  \(source: (local|project|default)(, scope: \w+)?\)$` into `key`, `value` (JSON-parsed), `source`; old rc 1 with `unknown key` on stderr becomes exit 3, rc 1 with `usage:` becomes exit 2.
note: old rejected any key outside the schema table. 5.0 accepts a key that is in the schema or present in the merged config, so a hand-edited key stays readable (`config set` itself is schema-only). The shim cannot do this; it fails with exit 3 as before.
note: `effective` and `effectiveSource` appear on the nine `round.tiers.<kind>.<tier>` rows only (#932): the model a worker of that kind and tier launches with after `round.profile` and the default, `""` when the harness picks, and where it came from. `round.profile` fills Claude tiers only. The text line gains a suffix `  effective <model|-> (<source>)` after `(source: ...)`, so the shim's end-anchored regex does not match those nine lines.
note: `global` is what the global config holds for the key, present only when it holds one, so a project value that overrides it still shows what dropping the override would inherit. `--global` lists the global config's own values instead of the merged ones (no `.rota/` needed; `data` gains `"scope": "global"`, `source` is `global` or `default`, project-owned keys are unknown keys; exit 2 with `--repo`). A global file that does not parse is exit 70 with the message naming its path, on `show`, `set` and `edit --global` and on `save-global`; no write ever replaces such a file, so repair or remove it by hand.
note: `--ui` (global flag) opens the config screen over these entries instead of printing them; it exits 2 off a terminal or with `--json`, and the screen's writes are described under `config edit`.
note: schema values resolve from the same merged configuration as runtime reads. A local null or non-object parent replaces the project value; an absent or null key after merging uses its schema default and reports `source: default`. Otherwise the source is `local` when that layer supplies the key, or `project`. The machine-specific list key `round.accounts` treats an empty list in the project or local file as unset when the global config holds a non-empty list: the global value shows and the source is `global` (#1766). With two or more non-empty lists across the global, project and local files, the value is them merged by kind: a layer listing a kind replaces the lower layers' entries of that kind and inherits the rest.

### rota config edit
rota config edit [--global]
repo: scoped (not with `--global`)
data: {"changed": [string]}
exit: 4 when `--json` is given, TERM is `dumb`, or stdin or stdout is not a terminal (hint: `run: rota config set <key> <value>`); 3 when no `.rota/` is found; 70 when a config file holds JSON that is not an object.
old: none (added in #193; the screen is #542).
note: opens the config screen, the same one `rota config show --ui` and `rota config --ui` open. Keys are grouped by section, with a detail pane built from `config show`'s `default`, `type`, `group`, `desc` and `choices`. A value is checked by the code `config set` runs (`config.Validate`), so the screen rejects exactly what `config set` rejects. Enter edits the value where `config set` writes it: the local override for a machine-scope key, else the project value (`.rota/config.json`); `l` edits the local override (`.rota/config.local.json`), `g` switches a key between inheriting the global value (the project value is dropped) and overriding it (the global value is written into `.rota/config.json`); `r` resets a key: it drops the local override, then restores the schema default for a required key or removes the key for an optional one. Every change is written at once, so quitting loses nothing. `changed` lists the keys written, in order; the text is `changed: <keys>` or `no changes`. `--global` edits the global config instead: no `l`, no `g`, `r` removes the key from it, and no `.rota/` is needed. The earlier numbered prompt loop is gone, with no fallback: its type check was stricter than `config set`'s.

### rota config set
rota config set [--global|--local|--project] <key> <value>
repo: scoped (not with `--global`)
data: {"key": string, "value": any, "previous"?: any, "changed": bool, "scope"?: "global"|"local", "keyScope": "project"|"machine"|"taste", "autonomy"?: {"rewrote": true}}
exit: 2 when `<key>` is not in the schema that `config check` uses (the shared `Keys` table in `internal/config/keys.go`), is a malformed path (empty segment: `""`, `.a`, `a.`), an argument is missing, or `<value>` is one the key cannot hold (`invalid value`: `release.versionFile` takes a project-relative path string that stays inside the project, or `""` to clear it; `ship.review` takes `true`, `false`, `full`, `light`, `none` or a `{default, lightBelow, labels, paths, scopeDrift, supportPaths}` object, anything else is `invalid value`; `round.support` takes any name but `main`, reserved for the main machine; `review.lenses` takes an object keyed by `security`, `perf` or `ux`, each `{paths: [globs], labels: [names]}`, a glob using `*` within a segment or a trailing `/**` only; `issues.labels.extra` takes an object of label names to non-empty descriptions); 70 when `.rota/config.json` exists but is not a JSON object, or the write fails.
old: hv-config-set <key> <value> (both map to the old positionals in order). Writes `.rota/config.json` only, never `config.local.json`. `<value>` is parsed as JSON first (`true`, `42`, `"x"`, `[…]`, `{…}`) and falls back to a raw string (`opus`, empty string). `previous` is the stored value before the write and is absent when the key was unset.
shim: old accepts any key, so the shim checks `<key>` against the schema table first and exits 2 without calling the helper when it is absent; old stdout is empty; read `.rota/config.json` before and after the call to fill `value`, `previous` and `changed`; old rc 1 with `malformed key path` on stderr becomes exit 2, rc 1 for missing argv becomes exit 2, any other rc 1 becomes exit 70.
note: the JSON-then-string coercion is kept because `hv-init` and `hv-config` skills depend on it. A string that looks like JSON (`"true"`) still needs shell quoting (`'"true"'`). `--global` writes the global config (same validation, no `.rota/` needed; a project-owned key is exit 2) instead of `.rota/config.json`. In `$HOME` with no `.rota/` there or above, `config show`, `set` and `edit` act on the global config without `--global` (#1183). A global write adds `"scope": "global"` to `data` and text mode prints `global: <key> = <value> (global config, ...)`. `--repo` is refused with the global config (exit 3). No `--string` flag is added. `round.commands` is an object key holding one worker command per harness kind; `config show` and `set` also take `round.commands.<kind>` (`claude`, `codex` or `opencode`) as a machine-scope key: the value must be a command string, `show` of an unset one reports `""` with source `default`, and setting `""` unsets it.
note: (#1786) the target follows the key's `scope`, which `data.keyScope` names. A `machine` key writes `.rota/config.local.json` (`"scope": "local"`, one text line `local: <key> = <value> (.rota/config.local.json: a machine key, this machine only; --project writes the tracked config)`; `--local` keeps `(.rota/config.local.json, this machine only)`); a `project` or `taste` key writes `.rota/config.json`. `--local` writes `config.local.json` for any key; `--project` writes `.rota/config.json` for any key, and on a machine key warns on stderr, once the write succeeded, that the tracked value shadows every developer's global config; `--global` writes the global config. More than one of the three is exit 2, and so is `--project` on `round.role`, which stays in `config.local.json`. A support machine's refusal of tracked writes applies only when the write targets `.rota/config.json`.
note: a key outside the schema is rejected (maintainer decision), where old accepted any key.
note: an empty `<value>` is valid and stores the empty string; the old helper rejected it, so the shim passes `""` as a JSON literal.
note: (#1101) `autonomy.level` takes `off`, `roundtrip` or `auto`. A project file stamped before the split may still hold the old one-hop `auto`; `config set autonomy.level` first rewrites it to `roundtrip` in `config.json` and `config.local.json` (with `--global`, in the global config), applies the value, then raises the stamp, so a deliberate `rota config set autonomy.level auto` is kept. A rewrite adds `autonomy: {"rewrote": true}` to `data` and a `rewrote: autonomy.level auto -> roundtrip in <files> ...` line to the text; when the set itself then fails, the same lines go to stderr as warnings.

### rota config save-global
rota config save-global
repo: scoped
data: {"path": string, "saved": []string, "changed": bool, "autonomy"?: {"rewrote": true}}
exit: 3 when no `.rota/` is found; 70 when `.rota/config.json` is missing or is not a JSON object, when the global config exists but is not a JSON object (it is left as it is), or the write fails.
old: none (added with the global config, #194).
note: merges the schema keys `.rota/config.json` sets (never `config.local.json`, and never `rota.version`, `git.baseBranch` or `umbrella.enabled`) into the global config in the rota config dir, keeping the global keys the project does not set. `path` is the global file and `saved` lists the keys merged, in schema order.
note: `changed` is true when at least one saved key was absent from the global config or held a different value there before the write, so a repeat run reports `false` although `saved` is the same list. The verb takes no arguments.
note: an old one-hop `autonomy.level auto` in a project stamped before the split is copied as `roundtrip`; that adds `autonomy: {"rewrote": true}` to `data` and a `rewrote: ...` line to the text (#1511). Text mode prints `saved <n> keys to <path>`.

### rota config check
rota config check
repo: scoped
data: {"status": "upToDate"|"fresh"|"stale"|"corrupt", "upToDate": bool, "missing": []string, "removed": []string, "warnings": []string, "unknown"?: []string, "legacy"?: []string, "retired"?: []string, "globalCorrupt"?: string}
exit: 1 when `status` is anything but `upToDate` (`fresh`, `stale` or `corrupt`), or when it is `upToDate` but `unknown` names a key the schema does not know; 3 when no `.rota/` is found; 4 with `blockedBy: "config"` and `changed: false` when `round.role` is not `main` or `support`, `round.support` is empty on a support role, is `main`, or is not a lowercase branch-safe name (checked after the retired check, before the status verdict). Required keys are project-scope keys only (#1786), so a machine or taste key is never `missing`. `missing` lists dotted required keys that are absent or null in the project file and that neither `config.local.json` nor the global config supplies (the layers `config show` resolves; an empty list for the three machine-specific list keys still counts as a value here, #1765), in schema order, then `refactor.verifyCommands` when it still holds commands and `test.full` holds none (the deprecated key `config fill` moves), and is non-empty only for `stale`. `fresh` means `config.json` does not exist; `corrupt` means it is invalid JSON or not an object (this is a defined verdict, so it does not use exit 70).
old: hv-config-schema-check (no args).
shim: map stdout `UP_TO_DATE` to `status: upToDate`, `FRESH` to `fresh`, `CORRUPT` to `corrupt`, and `STALE:a,b` to `stale` with `missing` = the split list; exit 0 for `upToDate`, else 1 (old always exited 0).
note: old always exited 0, so skills that branch on the four tokens must read `data.status`.
note: `removed` lists keys older `rota init` runs seeded, or that a later release dropped, that nothing reads any more and the file still holds (`issues.filterMineOnly`, `issues.providers.github`, `issues.providers.gitlab`, `round.autopilot`, `debug.competingHypotheses`, and since #1824 `round.codexAccounts` and `round.opencodeAccounts`, which `config fill` migrates into `round.accounts` before deleting, in `config.json` and `config.local.json` only; the global config is left to `rota migrate config`), in that order, then the ones only `config.local.json` holds, each suffixed ` (config.local.json)`; `[]` when none. They are inert: they never change `status` or the exit, and text mode adds a `REMOVED: <keys> (nothing reads them; run: rota config fill)` line (when `issues.labels.support` is listed: `run: rota migrate labels --apply for issues.labels.support; rota config fill for other removed keys`). `config fill` deletes them from both files.
note: (#1973) `issues.labels.support` is removed from live routing. `config check` names `rota migrate labels --apply` as its replacement. `config fill` preserves this key so migration can use its custom value; only a fully successful label migration removes it. A support role without `round.support` fails `config check` and is reported as a config error.
note: `unknown` (present only when non-empty) lists the old `work.*` round keys the merged config still holds (they moved to `round.*`; text `UNKNOWN: <old> (now <new>), ...`, fix with `rota migrate config --apply` or `config fill`): nothing reads the old names and a round verb refuses to run while one is set. `legacy` lists the `backlog.backend` and `issues.provider` keys `.rota/config.json` still holds (replaced by `issues.source` and `forge.provider`; text `LEGACY: ...`, fix with `rota migrate source --apply` or `config fill`). Neither changes `status` or the exit. `unknown` then lists every other key `.rota/config.json` or `config.local.json` holds that the schema does not know and rota does not recognise (not a schema key, below one or a parent of one, nor a removed, legacy or old round key), as dotted leaf paths, a local one suffixed ` (config.local.json)`; each prints `unknown: <key> (not a config key; nothing reads it)` and fails an otherwise `upToDate` check with exit 1 (#1786). `warnings` lists, in schema order, each machine-scope key `.rota/config.json` holds (`<key> is a machine key in .rota/config.json`) and each taste-scope key it pins at the schema default (`<key> is pinned at its default in .rota/config.json`), then each key the global config file holds that the schema does not know (`<key> in the global config is not a config key (nothing reads it)`; an unknown key in the global file warns, one in the tracked or local file fails); text adds a `warn: <warning>` line each. They never change `status` or the exit: `rota migrate config --apply` moves them. `globalCorrupt` is the read error of an unparseable global config, present only when `status` is `stale`; the inherited keys then read as missing, and the text adds `GLOBAL CORRUPT: ...` (repair the global config, do not run `fill`).

note: a malformed `ship.review` value (it would read as the default), a `review.lenses` value `ParseLenses` rejects, or an `autonomy.level` outside `off`, `roundtrip` and `auto` (the retired `loop` included) fails the check like a retired value: exit 1, listed in `data.retired` and as `RETIRED: …` in text, when `status` is `upToDate` or `stale`.

### rota config fill
rota config fill
repo: scoped
data: {"filled": []string, "removed": []string, "changed": bool, "autonomy": {"rewrote": bool, "autopilotWasOn": bool}, "renamed"?: {"config": [{"from": string, "to": string}], "local": [{"from": string, "to": string}]}, "migrated"?: {"source": string, "forge": string, "removed": []string}}
exit: 3 when no `.rota/` is found; 4 with `blockedBy: "config conflict"` when an old `work.*` round key and its `round.*` replacement hold different values (`data.conflicts` names both, nothing is written); 4 with `blockedBy: "account conflict"` when one file holds two `round.accounts` entries with one name and different dirs (`data.conflicts` lists file, name and dirs; nothing is written); 70 when `.rota/config.json` exists but is invalid JSON or not an object (`config check` status `corrupt`), and nothing is written.
old: none (A9 addition, G1; replaces the ~20 default `config set` calls the hv-init skill carried as prose).
note: writes the schema default (`config show`'s `source: default` value) for every required key that `config check` lists in `missing` (project-scope keys only: fill never writes a machine or taste key, #1786), so `config check` reports `upToDate` afterwards. `filled` lists those keys in schema order. A missing `config.json` is created holding every required key. Keys already present, keys outside the schema and `config.local.json` are never touched. Nothing missing and nothing to remove gives `filled: []`, `removed: []`, `changed: false`, and the file is not rewritten.
note: `removed` lists the inert keys `config check` names under `removed`; `fill` deletes them (except `issues.labels.support`, retained for `migrate labels`) and drops `issues.providers` or `debug` when that leaves it empty. `changed` is true when anything was filled, removed, renamed, migrated or rewritten. Text mode prints `filled: <keys>` and a `removed: <keys>` line. When the global config is unparseable and the project is `stale`, the text adds `GLOBAL CORRUPT: ...` (inherited keys read as missing: repair the global config first).
note: `fill` also runs the migrations `config check` reports. `renamed` (present when non-empty) moves the old `work.*` round keys to `round.*` in `config.json` and `config.local.json` (`renamed: old -> new, ...`). `migrated` (present when it changed something) turns `backlog.backend` and `issues.provider` into `issues.source` and `forge.provider`, reading the `origin` remote when `issues.provider` was `auto` (`migrated: <removed keys> -> issues.source <source>, forge.provider <forge>`); with `auto` and an origin naming neither github nor gitlab nothing is migrated and a warning asks for `issues.source` by hand. `autonomy.rewrote` is true when an old one-hop `autonomy.level auto` became `roundtrip` in `config.json`, `config.local.json` or the global config (text `rewrote: ...`), a deliberate `auto` set under the current stamp being kept; `autopilotWasOn` is true when `round.autopilot` was true, a removed key that no longer turns anything on: the autopilot now runs only under `autonomy.level auto`.
note: each added key goes in at its schema position among its siblings: before the first existing sibling that comes later in schema order (an object's position is that of its first schema key), so a file that starts in schema order stays in it (G7). Siblings outside the schema keep their place. The file is written as `config set` writes it (two-space indent).
note: `umbrella.enabled` and `rota.version` are required, so `fill` writes their defaults (`false`, `""`) when they are missing. Callers that know better set them with `config set`; `config set` on a present key keeps its position. The init skill runs `rota init`, then `rota config fill`, then `config set` for the answered keys, which keeps the file in schema order.

### rota migrate config
rota migrate config [--apply] [--keep <key>]...
repo: scoped
data: {"applied": bool, "planned": bool, "changed": bool, "config": [{"from": string, "to": string}], "local": [{"from": string, "to": string}], "accounts": [{"file": string, "from": []string, "entries": number}], "merges": [{"file": string, "from": []string}], "scope": [{"key": string, "action": "delete"|"move", "reason": string, "before": any, "after": any}]}
exit: 3 when no `.rota/` is found; 4 with `blockedBy: "config conflict"` when an old `work.*` round key and its `round.*` replacement hold different values (`data.conflicts` names both, nothing is written); 4 with `blockedBy: "merge conflict"` when the merges step finds `round.workerKind` and `round.harnesses[0]`, or `models.worker` and `round.tiers.claude.standard`, set to different values in one file (`data.conflicts` lists `{file, old, new}`, nothing is written); 70 when `.rota/config.json` or `config.local.json` is invalid JSON or not an object, and nothing is written.
old: none (#1097 rename; #1786 scope step)
note: four steps, in order. First the old `work.*` round keys move to their `round.*` names in `config.json` (`config`) and `config.local.json` (`local`), value unchanged. Then the accounts step (#1824): over the global config, `.rota/config.json` and `.rota/config.local.json`, lowest layer first, `round.codexAccounts` (`{name, codexHome}`) and `round.opencodeAccounts` (`{name, configDir}`) fold into `round.accounts` as `{kind, name, dir}` and legacy claude entries (`{name, configDir}`, no kind) are rewritten to that shape; each file keeps only its own entries, since layers merge `round.accounts` by kind when read. `accounts` lists one `{file, from, entries}` per rewritten file (`from` the keys folded in). Then the merges step (#1825): over the same three files, lowest layer first, read and planned in full before any write, the merged and renamed keys move with their value unchanged: `models.orchestrator` to `orchestrator.model`, `round.operatorCommand` to `orchestrator.command`, `models.worker` to `round.tiers.claude.standard`, `round.workerCommand`, `round.codexCommand` and `round.opencodeCommand` to `round.commands.claude`, `.codex` and `.opencode`, and `round.workerKind` into the head of `round.harnesses`. A file with `workerKind` and no `harnesses` gets `harnesses = [workerKind] + (the harnesses of the layers below, minus workerKind)`; with both set and `harnesses[0] == workerKind` the old key is dropped. An old key and its new key set to different values in one file (`workerKind` against `harnesses[0]`, `models.worker` against `round.tiers.claude.standard`) is a conflict: nothing is written and the verb exits 4. `issues.label` is a special case, never a conflict: it moves to `issues.labels.inProgress` when that key is unset in the same file and is dropped when it is set. Emptied parents (`models`) are removed. `merges` lists one `{file, from}` per rewritten file (`from` the old keys). The dropped and demoted keys (`ship.secondOpinionRunner`, `gate.smokeShards`, the eleven fixed constants) have no migration; `config check` names them as removed and `config fill` deletes them. Then the scope step (#1786) runs on the files as the rename leaves them, so a preview plans exactly what `--apply` writes: a tracked machine key is deleted when `config.local.json` already holds it (`reason: "config.local.json already holds it"`), when it equals the global value (`"equals global"`) or the default (`"equals default"`), and otherwise moves to `config.local.json` (`action: "move"`, `reason: "machine key"`); a tracked taste key at its schema default is deleted (`"pinned at its default"`). `before` and `after` are the key's effective value before and after the change. A tracked `round.accounts` list moves its kinds the local list lacks into `config.local.json`. `--keep` (repeatable or comma-separated) leaves the named keys, and keys under a named object key (`round.commands`), in place.
note: without `--apply` it only reports (`planned` true, `changed` false; text `would change:` and a warning `preview only; pass --apply`); with it, `config.local.json` is written first (created when missing), then `config.json` (text `changed:`). ### rota migrate labels
rota migrate labels [--apply]

data: {"applied": bool, "issues": [{"id": string, "changed": bool}], "changed": bool}

note: main only. Preview writes nothing. ### rota repo umbrella
rota repo umbrella
repo: none
data: {"umbrella": bool}
exit: 1 when the project is not an umbrella (no `.rota/`, no `.rota/repos.json`, or an empty registry). It never exits 3 for a missing `.rota/`: no root means no.

### rota repo add
rota repo add <path> [--name <name>]
repo: none (edits the umbrella registry)
data: {"name": string, "path": string, "changed": bool}
exit: 3 when `<path>` is missing, is not a directory, has no `.git` entry, or is not strictly below the umbrella root; 4 when the name is already registered for another directory or the directory under another name; 2 without exactly one `<path>`. Adding an entry that is already registered (same name, same directory) is exit 0 with `changed: false` and does not rewrite the file.
note: `<path>` is relative to the working directory. `name` defaults to the directory's basename. The entry is written as `./<path relative to the root>`, the file stays sorted by name, and entries `repos.json` holds that `add` does not know are kept. A new entry also gets `.rota/knowledge/<name>/` and a `/<path>/` line in the umbrella's `.gitignore` when that is a git repo, as `rota init umbrella` leaves them. The sub-repo is never touched. `umbrella.enabled` is not changed.

### rota repo rm
rota repo rm <name>
repo: none (edits the umbrella registry)
data: {"name": string, "path": string, "changed": true, "openItems": [string], "activeStreams": [string]}
exit: 3 when `<name>` is not registered (so a second `rm` of the same name exits 3, not 0); 2 without exactly one `<name>`.
note: only the registry entry goes. The sub-repo, its `.rota/knowledge/<name>/` and its `.gitignore` line stay. Before removing, `rm` lists the open items whose `Repos:` field names the repo (`openItems`, item IDs) and the active streams in `status.json` whose `repo` is the name (`activeStreams`, branches), and warns for each non-empty list; neither blocks. A backlog that cannot be read gives a warning and an empty `openItems`.
