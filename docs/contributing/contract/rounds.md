## C: rounds

The `round` group is the orchestrator layer over the same slot registry (`.rota/workers.json`) and host package as `rota worker`. Landing freezes live under the git common directory; each verb below owns its entry.

### rota round wait
rota round wait [<slot>...] [--timeout <seconds>] [--settle <seconds>] [--lines <n>]
repo: none
data: {"slot": string, "state": string, "evidence": string, "source": "herdr-event" | "snapshot" | "poll" | "registry", "waited": number}
exit: 1 when `--timeout` passes with every watched slot still `busy` (failure `data` is `{"timedOut": true, "waited": number, "slots": [{"name": string, "state": string}]}`); 2 when `--timeout` or `--settle` is not a number or `--timeout` is negative (an invalid `round.stallMinutes` does not fail a wait: the unverifiable-slot report stays off, and `round status` names the key); 3 when a named slot is not in the pool, or the pool has no slot with a session handle to watch; 5 when the host is unavailable, or herdr is not 0.9.x
old: none (new in C1)
note: blocks until one watched slot needs attention, then returns that slot. Watched slots are the named ones, or, when none is named, every registered slot that has a `handle` and whose recorded `state` is not `idle`. Pool init seeds every slot `idle` and gives a tmux slot a nominal handle before anything runs in it, and `worker poll` treats a recorded `idle` as already reported, so an idle slot is not watched unless named, or one parked slot would end every wait at once. `worker dispatch` records `busy`, which arms the slot. A slot with no handle is skipped, not an error, unless it was named.
note: "needs attention" is the `rota worker poll` classification, not the host's raw status: `idle`, `blocked`, `done`, `dead`, `limited`, `needs-permission`, `unknown` (UNKNOWN is surfaced, never treated as finished) or `unverifiable`. `busy` keeps waiting, and so does `unverifiable`: the host could not be asked or the pane could not be read, which is not news on its own (see `workers.md`, #820). The wait still records the state and its reason (slot field `reason`, written only when it changes, dropped when the state changes), so `round status` shows it, and records the slot's return to `busy`. After `round.stallMinutes` of continuous `unverifiable` (from the `activeAt` its state change stamped; 0 turns it off) the wait returns the slot once, with the reason as evidence (on herdr the event wait is bounded by the earliest such deadline, since an unverifiable slot emits no event; tmux re-classifies every pass) and the usual `seen` dedupe; `round watch` forwards that, and the prompt digest shows `unverifiable:<reason>` for the slot. `state` is lowercased, `evidence` is the same line `worker poll` reports.
note: the host only wakes the verb, it never decides. On herdr a status event for a watched pane, on tmux a change in a watched pane's text, triggers a re-classification through the `worker poll` code, so sentinels (`ROTA-DONE`, `ROTA-BLOCKED`), `limited` and `dead` outrank the host's native state exactly as in `worker poll`.
note: a slot that already needs attention when the verb starts is returned at once, `source: "snapshot"`, so an event that fired before the call is never lost. When several slots qualify, the first in registry order wins.
note: (#29) a slot comes back once per change. The returned slot is recorded with `seen` = its state and evidence, and a slot whose classification (state and evidence) equals its `seen` is treated as `busy`, so the next call waits on the others instead of returning a done slot whose PR the orchestrator is holding. A new `ROTA-BLOCKED` question or limit line differs in evidence and comes back. `needs-permission` and `dead` are never remembered and come back on every call: they are answered in the pane or by a reclaim, which re-arms nothing, and a permission prompt's evidence cannot tell two prompts apart. A watched slot classified any other way (`busy` included) has `seen` cleared and is armed again; `worker dispatch` (and so every `--relay`), `worker poll` recording a different state, `round report` and solo `assign` clear it too. Under solo, the recorded state is compared with `seen` the same way.
note: herdr (0.9.x, pinned; any other minor exits 5): wakes on `pane.agent_status_changed` over one socket subscription for all watched panes (`source: "herdr-event"`). tmux has no agent status and no event stream, so the verb re-captures the watched panes every `--settle` seconds (default 5) inside the process and re-classifies on change (`source: "poll"`). The orchestrator's context never sees either loop. One exception on herdr (#211): a slot classified `busy` only because its pane moved while herdr's own status was not `working` is re-classified after each settle without waiting for an event (`source: "poll"`), because herdr sends no event when an idle or done agent's pane comes to rest; right after a turn, two of herdr's `recent-unwrapped` reads a moment apart can return different scrollback windows, so the classification right after the last event can see movement (recorded live, #211). That re-check is not needed for a slot whose agent reports a finished turn past its dispatch baseline (`completion_seq` greater than `turnSeq`, #511): it is read once at the event, with no movement check, as `worker poll` does. A lost herdr event stream (an `events_lost` frame, a socket close, a herdr restart; herdr replays nothing) does not end the wait: it re-subscribes first, then re-classifies every slot from current state, so a transition during the gap is reported once (the per-slot seen dedupe). After 3 losses or failed re-subscribes in a row (a delivered event resets the count) it prints one line on stderr and falls back to the `source: "poll"` loop it uses on tmux; it never spins on the socket. (#510)
note: (#819) a slot's recorded event (`worker send`, `worker done`, `worker reply`; field `event` in `.rota/workers.json`) is read before the pane (`worker.Decide`). The event is the worker's newer word, so it decides the row over a static pane whatever sentinel its scrollback still shows (an old `ROTA-DONE`, a relay, a rest, then `--blocked` reads `blocked`): `blocked` and `question` read as `blocked` with the text as evidence, `done` and `review-reply` as `done` with the PR (a `ROTA-DONE` row keeps its own PR evidence). What the pane shows as happening now still wins: movement (`busy`: the question was answered, work resumed; the event is then dropped, only the one the row was read against), `dead`, `limited`, `needs-permission`. An event is live only while its `ts` is not older than the slot's `activeAt`, which a state change and every dispatch stamp, so an event from before a brief never classifies the new session. The event and `activeAt` are re-read on every pass of `round wait`; a row read before a newer event arrived is not recorded (it would stamp `activeAt` past the event) and is read again. A done event carries no PR when `worker done` ran first, so its row takes the same open-PR lookup by branch head as an idle pane. The `seen` key of an event-decided row ends in `\t#<seq>`: the next event is news even when it reads the same, and the same event is returned once. That includes a `done` event whose pane still shows the same `ROTA-DONE`: a second done for the same PR after a bounce wakes the wait. Under solo, where no pane exists, the recorded state carries the same suffix. `worker poll` raises the herdr notification for a `blocked` event once per event (`event.notified`). Known gap: an old session's `worker send` after a redispatch is only guarded by the dispatch clearing the event (#707).
note: (#29) the verb writes only the slot it returns, the way `worker poll` records a row (`state`, `activeAt` on a change, `pr` from a URL-shaped `ROTA-DONE`), plus `seen`, and clears `seen` on slots that moved on. A timeout writes nothing. There is still no `changed` field: the data answers "which slot", and the write is bookkeeping, so the round's `assign` can see a slot is done with a PR without a separate `poll`.
note: (#1843) a `done` or `idle` slot whose recorded PR the forge shows merged is not returned: it waits on nothing. A PR lookup that fails, or that the `--timeout` deadline cuts, holds the slot back for that pass and is asked again on the next, so no wake rests on a guess.
note: a timeout is a normal outcome, not a fault: exit 1 with `timedOut: true`, because the verb exists to answer "which slot needs me" and the answer is "none yet". Exit 6 is not used, since the conventions send it `error` alone and reserve it for faults a retry clears. `--timeout` defaults to 0, meaning wait indefinitely. A caller whose shell cuts commands short raises the cap (`BASH_MAX_TIMEOUT_MS` in Claude Code) or loops on a finite `--timeout`.
note: no `ROTA_TEST_*` hooks. The smoke section drives a fake `herdr` binary plus a fake unix-socket server (`HERDR_SOCKET_PATH`), and `test/fakes/tmux`.
note: (#1526, #1554) `round wait`, `round watch` and `round tick` add `trainNudge`, `[{"base": string, "prs": []string, "command": string}]`, and a text line `nudge\ttrain\t...`, by default when two or more reviewed PRs wait on one base: one `rota worker train <PRs> --base <base>` verifies them once where a gate per PR would verify each. A PR waits when it is a `done` slot's recorded PR or a review-list record, and the forge still lists it open (a forge that cannot answer keeps the row). It counts as reviewed when a review verdict is recorded at its head and no verdict blocks it: a FAIL review, cross-harness review, lens review or second opinion, a blocking finding, or a failed item keeps it out, as does a PR sent back by `round bounce` and not pushed to since. By default a base with one such PR makes no nudge; a PR with no recorded base groups under the default base. Advice only: an unreadable registry or branch reads as nothing waiting, and `round wait` carries it on a timeout too (`timedOut` data).
note: (#2173) `round.trainMax` and `round.trainFillMinutes` (nonnegative integers, both default `0`) control when the tick and nudge build a train per base. A nonzero count threshold fires when that many ready PRs wait; a nonzero age threshold fires when the oldest ready PR reaches that many minutes since its latest current-head review prerequisite. Either enabled rule suffices. A due lone PR gets a `worker gate` nudge. Configured nudges name the fired key in text and optional JSON `reason`. `trainMax` also bounds the proposed train size, retaining the oldest-ready members without changing their relative order; the tick still respects `round.autopilotCap`, evaluating readiness before the cap. With review disabled the clock uses worker done time; a ready record missing that time is gated immediately. A count-only policy can starve a lone PR. The nudge text reports observed wait and selected versus ready counts. Persisted Held/FailedHeads are excluded by the same head-aware predicate as the tick. The tick adds optional `holding: []string` only for changed per-base fill status, without making it a NeedsYou item; base/count/maximum keys persist across restarts, without rendered elapsed time. Optional `fillStatus: []string` carries current progress for explicit tick output and heartbeat rendering; `round status` exposes current `holding` progress. Holding notices alone never wake the watch; a completed merge or new attention item does. Known PR-state refusals bypass fill and reach an individual gate. Both thresholds zero preserve immediate tick merges and the two-PR nudge. Explicit gate/train commands retain their behavior.
note: (#2049) when a free active slot has a ready candidate, each train nudge also has `assignFirst: {"slot": string, "issue": string, "title": string, "command": string}`. The text names `assign first: rota round assign <id> --agent <slot>` before the train command. Slot selection and readiness use the round's existing checks. With no free slot or ready candidate, the nudge is unchanged; unreadable advisory state suppresses this extra step.
note: `round wait` and `round watch` (with no autopilot running) also add `assignNudge`, `{"slot": string, "issue": string, "title": string, "command": string}`, and a `nudge\tassign\t...` text line, when the returned slot is `done` with a PR and a candidate is ready: a done slot with a PR is free to take work before its PR is gated (`round assign`, #29), so the orchestrator assigns first. Unreadable config or backlog reads as no candidate.

- **Round slot.** The `slot` of A7 plus derived fields. C2 stores nothing new: the issue is the slot's `task` (or, when `task` is not a number, the leading number of the branch `<agent>/<issue>-<slug>`), the PR is `pr`, and the host state is read live. Later C issues (tier, escalations) add optional slot fields with their own entries.
- **Sources.** Rows come from the union of three sources, so a restart works with an empty registry: the registry slots; the git worktrees under `<root>/.worktrees/` (a worktree on `park/<name>` is a parked slot named `<name>`, on `<name>/<issue>-<slug>` a slot working that issue); and the host snapshot, whose agents are matched to a row by `handle` (tab id), else by `cwd` equal to the row's worktree. Open PRs come from the forge by head branch, issue labels from the tracker.
- **Degraded sources.** A source that is unavailable (host not running, forge or tracker CLI missing or failing) is named in `unavailable` and `warnings`, and the drift kinds that need it are skipped. The verbs still exit 0: a restart usually finds herdr down.
- **Drift kinds.** `dead-tab`: slot has a `handle` and the host has no live agent for it (matched by herdr agent name `rota-<slot>-<handle>`, then recorded tab, then worktree, so a pane `rota layout` moved is still found). `tab-moved`: the agent is found by its herdr name (checked before the recorded tab, since folded panes share one) but under another handle than the recorded one: its pane moved to another tab, or other panes joined its tab. The handle it would record is the pane id when the tab holds other panes or the count is unknown, else the tab id. `unclaimed-tab`: a live agent whose `cwd` is inside `.worktrees/` matches no row. `unregistered-worktree`: a worktree under `.worktrees/` has no registry slot. `branch-no-pr`: a done or idle slot's branch is neither its parking branch nor the base, has commits ahead of the base, and has no open PR. The live host state wins; without one, the recorded slot state is used. A working slot is still producing its PR and is not reported. `pr-unrecorded`: an open PR has the slot's branch as head and `pr` is empty, or, for a registered done or idle slot holding an issue, a merged PR the branch owns (its head commit is the branch tip or is on the branch and not yet in the base) was never recorded. The merged lookup runs only for such a slot; a forge failure there is a warning (`merged PRs of <branch>: …`) and no finding. `pr-superseded`: `pr` names a closed unmerged PR while another open PR heads the slot's branch (a merged record is never superseded; an unreadable PR state is a warning, no finding). `pr-stale`: `pr` names a PR that is merged or closed while the slot still holds its task. `label-missing`: the slot holds an issue and the issue lacks the `in-progress` label. `label-orphan`: an issue has `in-progress` and no slot holds it. `label-stale`: a closed issue still has `in-progress` or a `claimed:` label (including issues closed outside rota). `claim-label-drift`: visible `claimed:<agent>@<machine>` labels disagree with open comment claims on a held or in-progress issue, or any open issue carrying a `claimed:` label; the comments win.
- **Safe repairs** (`reconcile --apply` only, each additive or derived): `tab-moved` (the agent is found by its herdr name but its handle is not the recorded one) renames the agent for the new handle and records it: the pane id when the tab holds other panes, else the tab id; `dead-tab` clears `handle` and sets `state` to `dead` (the host answered and lists no agent for the tab: positive absence; a host that could not answer is `unverifiable`, never `dead`); `unregistered-worktree` registers the slot; `pr-superseded` records the open PR in place of the closed one; `pr-unrecorded` records `pr` (the open PR, else the merged one, so `round assign` and `round transfer` stop refusing with `no PR recorded for branch`); `label-missing` adds `in-progress`; `pr-stale` on a slot whose PR is merged parks the slot as `assign` would (worktree to `park/<agent>` at the base, no push, issue, claim and PR cleared; refused while the slot is busy or its worktree is dirty; a `blocked` slot is freed too, since a relay can leave one blocked after its PR merged, and `round transfer` frees it the same way); `merged-external` (an adopted slot whose PR merged outside the gate) releases the slot, keeping its worktree and branch (an adopted slot that records no PR and has none open is matched to the merged PR its branch headed, only when that PR's head commit is the branch tip or is on the branch and not yet in the base, so a reused branch name is not mistaken for it); `label-stale` removes in-progress and all `claimed:` labels from the closed issue, even when in-progress was already removed. The post-merge gate does the same for closed issues named by the PR. Status, watch and the autopilot tick read closed issues filtered by in-progress; only the `round reconcile` command sweeps closed issues for claim labels without in-progress (`Env.SweepClosedClaims`). A failed sweep list is a warning and leaves the forge available. `claim-label-drift` recomputes and syncs only the `claimed:` labels from open comment claims; it never edits claims or other labels. Label-write errors leave the finding in drift with a warning. Never repaired: `unclaimed-tab` (a tab may be a live worker), `branch-no-pr` (opening a PR is the worker's act), `pr-stale` on a slot whose PR is closed unmerged, and `label-orphan` (resetting a slot and removing the label are the orchestrator's calls, `worker.md`). `base-drift` (a done slot whose issue's milestone tag changed since assign routed it; a milestone going active under an unchanged tag is not drift, and an active milestone with no origin branch warns and is skipped) is repaired by `reconcile --apply`: the PR is retargeted (`gh pr edit --base`, `glab mr update --target-branch`), the slot is routed to the new base (back to its registered base when the issue left every active milestone) and a `BASE` relay, also written to the slot's inbox, tells the worker to merge the new base before the PR merges, and the slot is marked busy so the tick does not gate it before its next `worker done`; queued PRs whose slot moved on are not judged. `round assign` routes an issue tagged to an active milestone whose `milestone/<id>` branch exists on origin to that branch: the slot records it as its base (`Slot.RouteBase` remembers the registered one), the branch is cut from `origin/milestone/<id>`, the brief says `Your base branch is …`, and a worker's `rota git base` and `rota ship` read it. An untagged issue, one of a milestone that is not active, a project with no `origin`, or an active milestone whose branch is not on origin (a warning names it) keeps the round base. `queued-branch-mismatch` (a queued record whose branch does not head the PR it names, so `worker gate <PR>` would read the wrong branch) is reported only: drop the record with `rota round` tooling and re-queue it. `round assign` onto a slot whose recorded PR another record already holds is refused as `slot-busy`, and `worker poll` / `round wait` do not record such a PR on a slot, since the pane's last `ROTA-DONE` is the previous issue's.
- **Host snapshot.** herdr: `herdr api snapshot` (pin 0.9.x), reading `agents[]` (`tab_id`, `pane_id`, `cwd`, `agent_status`, `name`) and `tabs[]` (`tab_id`, `pane_count`, which with the pane id gives `Agent.Handle()`). tmux: `tmux list-windows` with the pane's current path. Both sit behind a new optional `host.Snapshotter`, in `internal/host/snapshot.go`; the `Host` interface does not change.

### rota round watch
rota round watch [--heartbeat <seconds>] [--poll <seconds>] [--forge-poll <seconds>] [--settle <seconds>] [--lines <n>] [--autopilot [--base <branch>] [--holder-pid <n>]]
repo: none
data: {"reason": "slot" | "change" | "heartbeat" | "interrupt", "waited": number, "round": number, "slot"?: string, "state"?: string, "evidence"?: string, "source"?: string, "changes": [{"key": string, "from": string, "to": string}], "digest": string}
exit: 2 when a `round.*` key is invalid (checked at start; if one goes bad while the watch runs, the polls that need it are skipped and a warning is printed once), or `--heartbeat` or `--poll` is not positive, `--forge-poll` or `--settle` is negative, or a positional argument is given; 4 when another watch is already running for this repo (`rota round watch` keeps exactly one); 5 under a solo round (no panes to watch) or when the host is unavailable
old: none (new in #81)
note: `round wait` for a session that must stay free. It is written to run as a background command: the harness wakes the orchestrator when the process exits, and the orchestrator re-arms it. It exits 0 with what happened: `slot` (a watched slot needs attention, the `round wait` verdict, same `seen` bookkeeping), `change` (a registry or forge entry moved, see below), `heartbeat` (nothing happened for `--heartbeat` seconds, default 600) or `interrupt` (SIGINT/SIGTERM). The heartbeat is what keeps an orchestrator from going quiet for good: it wakes however little happened. Every exit's `digest` ends with the hint to re-arm `rota round watch` (the prompt hook's digest says whether a watch is armed instead), and a heartbeat exit prints it in text mode even beside warnings.
note: `change` entries are the snapshot keys that differ from the start of the watch: `pr/<slot>` (the slot's recorded PR), `escalation/<id>` (the stored status), `gate/land` (present while a gate or train holds the land lock, valued with its holder; its disappearing is the "gate cleared" change that says refused assigns can be retried), and, from the forge every `--forge-poll` seconds (default 120, `0` never asks), `pr/state/<slot>` (PR state from `round status`), `escalation/status/<id>` (derived status after `round escalate check` has stored any answer) and `review/<slot>` (review input waiting on a `done` slot's PR, valued `<n> from <authors> <pr-url>`; see `round review-relay`; a hand-sent relay clears it with `worker dispatch --relay --review-through <time>`). A slot's own state is reported through `slot` only, so the orchestrator's `assign` does not wake the watch it just armed. Checks and review status of a PR are not in `round status` and are not watched (follow-up).
note: one at a time. The process writes `<git-common-dir>/rota/round-watch.json` (`pid`, `start`, `host`, `startedAt`, `heartbeatSeconds`) under a lock and removes it on exit; a marker whose process is gone is replaced. A second `round watch` exits 4. The Stop and prompt hooks read the marker.
note: (#1843, #1927) the forge poll also writes the registry: on each `done` slot it sets or clears the slot field `prMerged` (boolean, absent when false) from the PR state `round status` reads, and only a slot whose PR the forge answered for is touched. A `done` slot with `prMerged` set is not asked for in the prompt digest (`(needs you)`) or the Stop hook's attention list, since it waits on nothing. Without a running watch nothing sets it, so a merged `done` slot still reads `(needs you)` until `round reconcile --apply` parks it or `worker reset` ends it. A failed registry write is warned once per watch (`merged-PR mark skipped: …`). `unbind` (park, free, reset) drops the field.
note: (#1827, #1911) with `round.support` set the forge poll also reads support entries, which wake the watch as `change` entries `support/<id>/<kind>` and print as `support: <id> <kind> <value>`. On the support machine (`round.role support`) two changes are new in #1911: `comment`, the newest `rota:from main` comment of a writer-trusted author on the issue of a PR parked on the review list, read like the issues its slots hold; and `conflict`, valued with the PR's head sha, for an open PR of this machine, held by a slot or queued, that the forge reports as conflicting with its base. A conflict wakes once per PR head: a push while it still conflicts wakes again, a mergeable PR adds nothing. A failed or unknown read, or a forge without the mergeability read, is no news. With `round.support` unset the watch makes none of these reads.
note: with no slot to watch (all idle) the verb still runs: it waits out the interval on the registry and the forge, so an answered escalation wakes an orchestrator whose workers are all parked. Each wait covers one classification (`--poll` plus `--settle` plus 2s), so a heartbeat can run a few seconds past its interval.
note: no `ROTA_TEST_*` hooks. The smoke section (108) uses `test/fakes/tmux` with a churning pane.
note: (#93) `--autopilot` makes the watch the autopilot's heartbeat: it runs `round tick` first, then waits, and ticks again on every wake. It returns only for a `needsYou` item no earlier tick reported (`reason` `change`), the heartbeat, an interrupt, or a stop (`reason` `stopped`, `autopilotStopped` says why, exit 0). The result gains `autopilot` (the tick's `{did, needsYou, new}`) and, on a stop, `autopilotStopped`. In watch output (text and JSON), `branch-no-pr` appears in `needsYou` only when new: once per slot state or held-issue change, or when the finding returns after disappearing. Repeated heartbeats omit it; explicit `round tick`, `round status` and `round reconcile` keep reporting the finding while it remains. Exit 4 when `autonomy.level` is not `auto`. A round running it still has its watch armed, so the Stop hook is satisfied.
note: when the installed `rota` is behind the rota source checkout the watch runs in, the first wake of a round (once per round, kept by a `stale-binary-round` marker under `<git-common-dir>/rota/`) adds `staleBinary`, `{"commit": string, "head": string, "behind": number, "rebuild": string}`, and a `warning` text line; a marker that cannot be written adds `staleBinaryError` and the warning is still shown.

### rota round tick
rota round tick [--base <branch>] [--holder-pid <n>]
repo: none
data: {"did": [{"action": "reconcile" | "merge" | "assign" | "review-relay", "target": string, "detail"?: string}], "needsYou": [{"kind": string, "target": string, "why": string}], "new": [{"kind": string, "target": string, "why": string}], "capped"?: string, "batchFull"?: true, "deferred"?: string, "changed": boolean} (on a stop: {"stopped": true, "changed": false})
exit: 2 on a positional argument; 4 when `autonomy.level` is not `auto`, or this process holds no live round lease, or a wind-down has stopped the round's autopilot (`stopped: true`); 3 when there is no project root or the round config is invalid (the message names the key)
old: none (new in #93)
note: one pass of the round autopilot, in order: (1) `reconcile --apply` (the safe repair kinds; drift it does not repair goes to `needsYou`); (1b) review loop (`round.reviewLoop`): every `done` slot with a PR is checked for new review input (see `round review-relay`); under `auto` the input is relayed to the worker (`did` `review-relay`), under `manual` it only comes back in `needsYou` as kind `review` and the slot is gated as before (a poll failure is a `review` item too); under `auto` a slot whose input was relayed is not merged this tick, and one that could not be relayed (the bounce cap, a refused relay, a failed poll) stays in `needsYou` and is held; (2) merge: every slot that is `done` with a recorded PR (and not relayed or held by the review loop), and every queued PR, goes through `worker gate` (one target) or `worker train` (several, grouped by the base each merges into), at most `round.autopilotCap` per tick; (3) assign: the first ready candidate of the round's scope to each idle slot, at most `round.autopilotCap`, with the default tier and kind and never `--accept-overlap`. The merge runs before the assign so the next assignment branches from the gated base.
note: (#578) `capped` is set when step (3) and the review mint were skipped because every account a worker could run under is cooling down (`round assign` refuses with `blockedBy` `quota` for the same reason); its text is the reason, and text mode adds a `capped <reason>` line. The merge and repair steps still run, and the next tick after the reset fills slots again. It is not `needsYou` and does not set `changed`. (#1917) `deferred` is set (and text mode adds a `deferred` line reading `gate running, deferred: <refusal>`) when an assignment inside the tick was refused with `blockedBy` `gate-running`: the tick stops assigning, and the next one after the lock clears tries again. Like `batchFull` it is not `needsYou`. The cap reads `round.accounts` through their usage meters and the `codex` entries of `round.accounts` through the waiting entries of the limit log; a pool with no configured account is never cooling, and the Claude pool does not count when `round.harnesses` is `codex`.
note: (#936) `batchFull` is `true` when `round.batch` items are open: step (3) and the review mint are skipped (or stop when an assignment inside the tick fills the batch, `round assign` having refused with `blockedBy` `batch`), and text mode adds a `batch-full` line. note: every action is appended to `.rota/gate-audit.jsonl` as `{"gate": "autopilot", "verb": "round tick <action>", "target", "note"}`. These are not human approvals.
note: no `ROTA_TEST_*` hooks. The smoke section (114) uses the gh and tmux fakes of section 104.
note: (#2176) the tick's merge runs yield while any gate or train is running or queued for the land lock. - **Escalation** (C4, #60). A question the orchestrator puts to the human on an issue or PR thread, with a herdr notification alongside. Open escalations live in a top-level `escalations` list in `.rota/workers.json`, beside `slots`, because an escalation need not belong to a slot. An entry is `{"id": string, "kind": "issue" | "pr", "number": number, "slot"?: string, "title": string, "commentId": string, "sentAt": string, "deadline"?: string, "notified": bool, "options"?: [string], "recommend"?: number, "cost"?: string, "status": "pending" | "answered", "answer"?: answer}`, with `answer` `{"commentId": string, "author": string, "body": string, "seenAt": string, "option"?: number}`. `options`, `recommend` (1-based) and `cost` are present when `send` was given options (#962); `answer.option` is the 1-based option a bare reply resolved to, absent when it named none. `id` is `e<N>`, N one more than the highest in the list. - **Marker.** Every comment rota posts for an escalation ends with the line `<!-- rota:escalation <id> -->`, invisible once rendered. Any comment carrying a `<!-- rota:` marker is rota's own and is never an answer.
- **Answer rule.** The orchestrator, the workers and the human usually post as the same account, so the author decides nothing. The answer to an escalation is the first comment on its thread that comes after the escalation comment in the forge's oldest-first order and carries no `<!-- rota:` marker (maintainer ruling, 2026-10-03, relayed by the orchestrator in round 4). The rule therefore relies on rota marking every comment it posts; a comment posted outside rota (raw `gh`, a bot) on a thread with a pending escalation reads as its answer, so `check` returns the answer's body for the orchestrator to read before acting on it.
- **One per thread.** At most one pending escalation per issue or PR, so a single answer can never be read as answering two questions.

### C3: round start, candidates, assign, wind-down

C3 (#59, absorbing #40 and #41) adds the round lifecycle over the same registry. Orchestrator rulings (round 4, `c-rulings.md`): no second state file unless a need does not fit `workers.json`; rounds read `autonomy.level` (#1101); the file-overlap rule is concrete and states what it cannot catch.

- **Round config.** Four keys, all silent defaults (the `ship.mergeApproval` pattern; not seeded by init). `round.scope` is `slate`, `milestone` or `next`, default `milestone`. `round.roster` is a list of agent names, default `["ben","dana","nia","kit"]`. `round.brief` is the path the worker pointer names, default `""` (see **Brief pointer**). `round.sharedPaths` is a list of repo-relative globs the overlap check ignores, default `[]`. The orchestrator reads `autonomy.level` (off/roundtrip/auto): `auto` turns on the autopilot tick, `off` and `roundtrip` run without it, and `round.scope` says which issues a round may take.
- **Scope.** The candidate set is the open, unheld items of: `slate` the round's recorded slate and nothing else; `milestone` the active milestones (`rota milestone active`, then `rota backlog ids --milestone`); `next` the same, and when none of those is left to assign, the items of the first `planned` milestone whose dependencies are all shipped (`milestone list`, `ready`). The scope is enforced by `assign`, not advisory: an issue outside it is refused. Choosing `slate` is how the maintainer approves exactly what a round may touch; `milestone` is the #44 default (slate confirmed once, by the orchestrator, from `start`'s candidates); `next` lets an unattended round roll over.
- **Registry fields.** C3 adds optional fields to `.rota/workers.json`, all absent until written. Top level: `scope` (string, the scope the round started with) and `slate` (`[]string`, issue IDs in rule-11 spelling, present only for `slate`). Per slot: `claimId` (string, the `item claim` id `assign` took, released by `wind-down` and by C10's return). The issue a slot holds stays in `task` and its branch in `branch`; the top-level `round` number is the one `worker dispatch --round` already writes.
- **Lease.** One orchestrator per repo, keyed on `git rev-parse --git-common-dir` so every worktree of the repo shares it. It does not fit `workers.json`: that file lives under each worktree's own `.rota/`, so a second worktree sees an empty registry and a lock inside it protects nothing. The lease is `<git-common-dir>/rota/round-lease.json`: `{"pid": number, "start"?: number, "host": string, "pane"?: string, "paneHost"?: "herdr"|"tmux", "root": string, "round": number, "startedAt": string}`. `pid` is the orchestrator process, not the short-lived `rota`: the nearest ancestor that is not a shell, `env`, `timeout` or `rota` (in Claude Code, the `claude` process), else the parent. A herdr or tmux server is a boundary: when the walk reaches one, rota ran from a plain shell in a pane and the holder is that pane's shell, the ancestor just below the server, so two panes on one server never share a holder (#205). `start` is that process's start time (Linux `/proc/<pid>/stat` field 22), read to defeat PID reuse, absent where the platform has none. `pane` is `HERDR_PANE_ID` or `TMUX_PANE`. The lease is `live` when `host` is this host and the pid runs with the same `start`; `stale` when `host` is this host and the pid is gone or its start differs; `foreign` when `host` differs (cannot be checked, treated as live and named). `pid`, `host` and `pane` are overridable by `--holder-pid` for harnesses whose ancestry is not discoverable.
- **Lease seam (C2, C6).** `internal/round` exports `ReadLease(root) (Lease, LeaseState, error)` with `LeaseState` one of `none`, `live`, `stale`, `foreign`, and `ClearStaleLease(root) (Lease, bool, error)`, which removes only a `stale` lease. C3 owns both; `reconcile` and `reap` call them and write nothing of their own. `reconcile` gets one new drift kind, `lease-stale` (a `stale` lease; the finding's `detail` names the holder), never repaired by `--apply`; `rota reap` lists it as a candidate and clears it through `ClearStaleLease`. `rota round start` also reclaims a stale lease itself, since a provably dead holder needs no human, with the warning `reclaimed stale lease held by pid <n>`.
- **Readiness.** `candidates` and `assign` run four checks per item, each reported in `checks` as `{"name": "criteria"|"dependencies"|"overlap"|"template", "ok": bool, "detail": []string}`:
  1. `criteria`: the acceptance-criteria part of `rota item ready` (acceptance criteria, or a design or plan note); its criterion reasons are the detail. The separate `template` check below reports required headings.
  2. `dependencies`: every reference in the item's `## Depends on` section (issue body, or the detail file in file mode) must be done: closed in issue mode, archived in file mode. A reference in the item's own ID spelling (`#57`, `57`, `B07`) is looked up; any other reference (`owner/repo#N`, a URL) cannot be verified and fails the check (`cannot verify <ref>`). An item with no such section has no dependencies. An open dependency with a PR is not done.
  3. `overlap`: no file overlap with an in-flight item. In flight means a slot in this registry holding a `task` other than this item. A slot whose issue is already closed (its PR merged) is skipped. The footprint of an item is the `## Files` section of the body when present (one path or glob per `- ` or `* ` bullet; other lines are ignored, and comments never feed it), otherwise every token of the body and comments that is a tracked path at the base (`git ls-files`) or a directory prefix of one (two or more segments, so `docs/` alone never counts), minus `round.sharedPaths`. The footprint of an in-flight item is its own footprint plus its slot's real changes (`git diff --name-only <base>...<branch>` and uncommitted paths in the slot's worktree). Two footprints overlap when they share a file or one names a directory holding the other's file. The check cannot catch: files an item will create, paths nobody wrote down, two items editing the same function or file under different names, generated files and registries every item touches (list those in `round.sharedPaths`), renames, work on another machine's round, and a stale issue text. Scopes are compared next to paths: an item's `## Touches` bullets (a symbol, endpoint, schema, migration or config key), trimmed, lower-cased and compared exactly, else `subsystem:<name>` from its `Subsystem:` field when neither side declares `## Touches`. A shared scope joins the same overlap entry as `scopes`, and fails the check only under `round.scopeOverlap: block` (default `warn`: listed, item still ready); `--accept-overlap` skips both. `candidates` and a successful `assign` also report `overlaps`. It is a heuristic that fails closed on what it can see, so it stays on only because it is cheap to override (below).
  4. `template`: a fresh feature assignment, including Cosmetic, needs Acceptance and Out of scope headings in its body or the assign brief (`--settled-file`). Missing required sections are named and cause `not ready`; empty headings count, and content quality is not checked. Resuming a slot's own issue or deliberately redoing an existing open PR does not enforce this check again. A design/plan note or checkbox alone cannot replace these headings. Research and decision items are exempt. Bugs and tasks have no required template sections. The shared per-kind table also drives create-time warnings and `item template`; existing items become assignable when the missing headings are added, without a migration.
- **Brief pointer.** `assign` hands the worker a short signed brief instead of the pasted contract (#41): its agent name, the round number, the path of the standing contract, the issue to read first with its thread (and the instruction to dispute the ticket before implementing if it is wrong or already decided), the branch, the sibling issues, and the settled answers verbatim from `--settled-file`. The contract is `skills/references/worker-contract.md`, which C3 extends with a *Read the issue and dispute it* step. The path comes from `round.brief` when set, else `references/worker-contract.md` under `CLAUDE_PLUGIN_ROOT` when that is set, else under the project root, else under the first installed skills root; with `round.brief` unset and none of those present (#1778) it falls back to the copy in the skills cache (`<user cache>/rota/skills/<version>/references/worker-contract.md`, extracted from the binary when missing). If none exists, or a set `round.brief` is missing, `assign` refuses before touching anything (`blockedBy: "brief missing"`). `/rota-work`'s own dispatch keeps pasting the contract; moving it to the pointer belongs to the orchestrate skill (C7).

### C5: merge policy and approval requests

C5 (#61) is the orchestrator side of the merge policy. Most of #61 shipped with B1 (#54): `ship.mergeApproval` (`none`, `all`, `paths`) and `ship.mergeApprovalPaths`, the `merge-approval` gate on `ship merge`, `ship pr-merge` and `worker gate`, and the path match against the PR's changed files. Under the default `none`, `worker gate` already merges a passing PR without a prompt. C5 adds the two missing pieces: the approval request goes out through the C4 escalation channel, and the human's answer comes back as a recorded B1 approval. It adds no verb and no config key, only two flags on `worker gate` and `ship pr-merge`.

- **Approval thread.** The thread a merge's approval request lives on: the PR (`kind` `pr`, its number) when the merge has one, else for `worker gate` the slot's issue (`kind` `issue`, the round slot's issue number). `ship merge` has no forge thread, so it takes neither flag and keeps `--confirm` from an `AskUserQuestion`.
- **`--escalate`.** When the `merge-approval` gate refuses, the verb also sends the approval request with `round escalate send` on the approval thread (`--slot` set for `worker gate`), then exits 4 as before, with the escalation in `data.escalation`. Title `Merge approval: PR #<n>` (or `Merge approval: <slot> (<branch>)` without a PR). The body names the policy (`all`, or `paths` with the matching files from `data.paths`) and ends: ``Reply `approve`, `approved`, `yes`, `lgtm` or `ship it` to merge. Any other reply holds the merge.`` When an escalation on that thread is already pending, the verb sends nothing and returns the pending one, so a re-gate in a loop never posts twice. With no gate to clear (the policy does not cover the merge), `--escalate` is accepted and does nothing. A send failure is a `warnings` entry; the refusal stands.
- **`--approval <id>`.** Clears the `merge-approval` gate with a recorded answer instead of `--confirm`. It reads escalation `<id>` from `.rota/workers.json` and makes no forge call, so run `round escalate check` first. Checks, in order, all before anything changes:
  - unknown `<id>`: exit 3;
  - the escalation is not on this merge's approval thread: exit 2;
  - `status` is not `answered` (pending, or timed out with no answer): exit 4, `{"blockedBy": "approval pending", "escalation": string, "status": string, "changed": false}`;
  - the answer does not approve: exit 4, `{"blockedBy": "approval declined", "escalation": string, "answer": string, "changed": false}`.
  An answer approves when the first word of its first non-blank line, lowercased with trailing punctuation removed, is in the allowlist `approve`, `approved`, `yes`, `lgtm`; or when that line's first two words, treated the same way, are `ship it`. `Approve.`, `YES, go ahead`, `lgtm!` and `Ship it.` approve; `no`, `yes-ish`, `please approve` and `ok` hold the merge. The allowlist lives in one function (maintainer ruling, relayed by the orchestrator in round 4: "Approve or yes words").
- **Recording.** A cleared `--approval` writes the B1 audit line with `note` set to the answer body verbatim and `escalation` set to `<id>`, exactly as `--confirm --confirm-note` would with the quoted answer. The escalation stays in the registry as the record of what the human said; the same answered escalation can clear a re-gate of the same thread (after a `stale` bounce, say).
- **Flag rules.** `--approval`, `--escalate` and `--confirm` are mutually exclusive (exit 2). `--approval` on a merge the policy does not cover is accepted and writes nothing, the same as `--confirm` (B1).
- **Skill routing.** `/rota-work`'s gate step and `/rota-review --queue` pass `--escalate` when the round is unattended (the orchestrator is driving herdr workers), record the escalation id against the slot or PR, keep working other slots, and re-gate with `--approval <id>` once `round escalate check` reports it answered. An `approval declined` refusal is surfaced and the slot is held, never retried. Interactive runs keep the `AskUserQuestion` plus `--confirm` path from B1.
- **Limits.** The approval is tied to the thread, not to a commit: commits pushed to the PR after the answer are covered by it. `worker gate`'s provenance and freshness checks still run on every re-gate, so a moved head is re-verified, but it is not re-approved.

### C9: worker tier and model

C9 (#75) lets the orchestrator choose how heavy a model each worker starts with, and tells the worker how to size its own subagents. Skills and briefs speak in **tiers**; config maps tiers to model names per harness kind, so nothing outside config names a model.

- **Tiers.** `light` (reading, searching, discovery), `standard` (writing code and tests), `heavy` (hard reasoning, design, tricky debugging), in that order. A harness **kind** is `claude`, `codex` or `opencode`.
- **Config.** Eight keys, all silent defaults (not seeded by init). `round.tier` is the default tier, `standard`. `round.tiers.<kind>.<tier>` is the model name: `claude` defaults to `haiku` for light and `opus` for heavy, and `standard` defaults to `sonnet` (the old `models.worker` knob is merged into `round.tiers.claude.standard`; precedence is the explicit tier key, then `round.profile`, then the default); `codex` defaults to `gpt-6-luna`, `gpt-6.1-sol` and `gpt-6-astra` (light, standard, heavy) and `opencode` to `opencode/claude-haiku-5-5`, `opencode/claude-sonnet-5-5` and `opencode/claude-opus-5-5`; setting all three of a kind to `""` hands the model choice to that harness. `round.profile` (`quality`, `balanced`, `budget` or `inherit`, default empty) fills the three Claude tiers, and an explicit `round.tiers.claude.<tier>` wins over it; Codex and OpenCode tiers are not touched. A kind is *configured* when any of its three tiers is non-empty. Validation (read through `internal/roundcfg`, so every verb that reads round config exits 70 on it): `claude` must be configured; a configured kind must have all three tiers non-empty (the error names the missing `round.tiers.<kind>.<tier>`); `round.tier` must be a tier. Unconfigured `codex` is never an error: a codex worker then gets no model and Codex picks its own (#68), unless a custom `round.commands.codex` holds `{model}`, which `assign` refuses with `no tier map` before anything is marked.
- **Choosing.** `rota round assign --tier <t>` picks the tier; omitted, it is `round.tier`. rota does not choose from the issue: size, type, labels and judgment belong to the orchestrate skill (C7). The config tier is a default, not a ceiling: a tier above it needs `--tier-reason <text>` (one line, exit 2 without), and any given reason is recorded. A tier at or below the default needs none. `--kind` is the harness kind of the worker, default the slot's recorded `kind`, else `claude`.
- **Resolving.** `model` is `round.tiers.<kind>.<tier>`. On a `claude` kind the default launch command is `claude --model <model> --dangerously-skip-permissions` (`round.tiers.claude.standard` also drives `/rota-work`'s own dispatch). A custom `round.commands.claude` receives the model only through a `{model}` placeholder in it; without one the tier is recorded but `model` is left out of the slot and `data`, and `assign` adds the warning `tier model not applied: round.commands.claude has no {model} placeholder`, because rewriting a command rota does not own would lie about what ran.
- **Codex.** The tier map, its validation and the resolution above are defined for `codex` and `--check-only` reports the model it would use. Starting a codex worker is E1 (#68), under "E: Codex workers".
- **Registry fields.** Optional per-slot fields, absent until `assign` writes them and cleared when the slot is parked (`wind-down`): `kind` (string), `kindSource` (string: `--kind`, `harness label`, `round.harnesses`, `slot`, `slot (resume)` or `default`), `tier` (string), `model` (string), `tierReason` (string). They are the round state C9 asks for; `round status` rows show them.
- **Brief.** The subagent guidance is split on purpose. The **standing rule**, harness-neutral and with no model names, lives in `references/worker-contract.md`: delegate reading and searching to a `light` subagent, code and tests to `standard`, and keep `heavy` for genuinely hard reasoning, using the tier map the pointer gives. The **resolved facts** for this worker live in the pointer brief `assign` writes: its own tier and model, the tier-to-model table of its kind, the reason when it is above the default, and the instruction to put `Worker tier: <tier> (<model>)` in its PR body, which is how the choice reaches the PR (workers write their own PR bodies, rota cannot). A non-research brief also carries the pre-flight (#1919): run the tier the brief assigns (`rota test run fast`, or `full` when `test.fast` is empty), measure every numeric acceptance criterion on base and branch and paste both values in the PR, and report `--outcome partial` naming the criterion when one cannot be measured or a check fails, still printing `ROTA-DONE` last.
- **Not in C9.** Picking the tier from the issue (C7), a tier per subagent call (the worker decides, by the rule), and showing `size` or priority in `candidates` to help the choice (the orchestrator reads the backlog).
### C13: request ids and receipts

Added by #822. `round assign`, `round transfer`, `round reclaim`, `round pick`, `round return`, `round report`, `round tick`, `round escalate send`, `worker gate` and `worker train` take `--request-id <id>`; worker-side verbs (`worker done`, `worker reply`) do not. The lockfiles guard concurrent writers and are unchanged; the receipt guards a repeated caller.

- **Receipts file.** `.rota/receipts.json` (gitignored, per developer): `{"receipts": [...]}`, one entry per id with `verb`, `fingerprint`, `status` (`done` or `failed`), `attempts`, the stored `text` and `data`, and for a failure `exit`, `message`, `failedStage` and `residualResources`. An unreadable file is exit 5. `round wind-down` removes it once it releases the lease; a refused wind-down keeps it. Between those, each write keeps the newest 20 receipts per verb, so an autopilot's gate ticks do not grow it.
- **Id.** `--request-id` or a minted `req-<hex>`; the result carries `requestId`. The fingerprint is the verb, `--repo`, the positional arguments and every flag the caller set except `--request-id`; a `*-file` flag counts by the sha-256 of its content (stdin is read once and handed on to the verb), and `worker gate` / `worker train` add the head of the branch each argument resolves to by the gate's own target resolution (`Registry.GateTargetAny`: a slot, a queued PR whose slot moved on, an adopted slot, or a PR number; local refs, except a bare external PR, whose head the forge answers), so a new push or a changed brief under the same id is a different call. The file is read before the verb runs on every call, minted id or not; a corrupt one is exit 5.
- **Claim.** `receipt.Store.Do` holds a lock on the id (`receipts.json.<hash>.lock`) across the verb's run, so two concurrent calls under one id run the mutation once: the second waits, then replays the first's receipt. The verb list is `receiptedVerbs` in `internal/cli/receipt.go`. `round bounce` stays out: it counts one bounce per issue and review head, a dedupe across callers that a retry id (minted fresh per call) cannot express. `round escalate check` only reads.
- **Replay.** A `done` receipt with the same fingerprint returns the stored data and text with `replayed: true` and `changed: false`; the verb does not run. A different fingerprint or verb under the same id is exit 4, `blockedBy: request-id`, `changed: false`.
- **Partial failure.** A call that ends in exit 1, 5, 6, 70 or 71 records a `failed` receipt. `failedStage` is the saga step that failed (`claim`, `dispatch`, ...) and `residualResources` the stages still in place: those whose undo failed, or, for a `keep` step such as `dispatch`, every stage that ran. The error hint names both and the id. The retry runs the verb again under the same id; the saga skip checks resume it, and the result carries `resumedFrom`. An exit-1 call that returns a `verdict` in its data and no stage (a gate or train verdict such as `verify-failed`) is a finished run: it records a `done` receipt with its `exit` and `message`, a rerun does not warn, and a replay returns the verdict with exit 1. This includes environmental verdicts (`base-moved`, `verify-timeout`, `check-broke`, `merge-failed`, `ci-not-run`): a retry under the same id replays the stored failure, it does not rerun. After a push the same id is refused (exit 4, `blockedBy: request-id`), since the head is part of the fingerprint. To rerun, make a fresh call without `--request-id` (it mints a new id), after a push if the head should change.
- **No receipt** for exits 2, 3 and 4 (nothing was written, a retry must judge afresh) or for `--check-only`.

### C10: round return, transfer, reclaim

C10 (#76) moves an issue that is already assigned. It builds on C3 (`assign` takes the claim, `claimId` on the slot, the lease) and C2 (`reconcile`). Orchestrator rulings (round 4, `c-rulings.md`): the claim lives on the tracker, through the same `item claim`, `item release` and `item state` calls `assign` makes; no local-only claims file; the note transfer hands over is a minimal stand-in for D1's.

- **Premise check.** Four points in #76 do not hold as written, and the entries below follow the code, not the ticket. (1) "Back to ready" is not a state: `item ready` is a property of the text (acceptance criteria or a design note), and the only tracker state `assign` sets is `in-progress`. Return puts the issue back in the candidate set by releasing the claim and clearing `in-progress`; `candidates` then lists it again with its checks. (2) "The branch stays" is false for a slot today: `worker reset` refuses to leave a branch with commits not on the base, and git will not check one branch out in two worktrees, so a slot cannot both keep the branch checked out and be free. The branch has to be pushed and the slot switched off it (**Park**). (3) "Reclaim from a stalled slot" needs a stall signal the registry does not hold: it has no activity time (**Stalled**). (4) "Transfer to the human" cannot be an assignee: the orchestrator and the human usually post as the same account (C4), so an assignee marks nothing; it is a label (**Claim on the tracker**).
- **Claim on the tracker.** The holder is the open claim comment `item claim` posts (`claimId` `<agent>@<round>`, C3); `in-progress` and `claimed:<agent>@<machine>` are derived labels. A main claim `ben@3` adds `claimed:ben@main`; a support claim `mac-ben@3` with committed `round.support: mac` adds `claimed:ben@mac`. Labels are created on demand unless `issues.autoCreateLabel` is false. A failed label write warns and leaves the comment claim intact. `.rota/workers.json` mirrors it: the slot's `task` and `claimId`. A new top-level label role `issues.labels.needsHuman` (default `needs-human`) marks an issue handed to the human: no claim, no `in-progress`, the label on. Each verb below changes the tracker first and the registry second, so a crash between them leaves a mismatch reconcile reports and `--apply` repairs from the tracker, which wins. Return and transfer to a slot release the old claim before claiming anew, so an item is never claimed by two.
- **Park.** Return, transfer and reclaim free a slot with the same sequence, `internal/round.Park(slot)`: salvage the worktree if dirty (stage the dirty paths by name, never `-A`, and commit `wip: parked from <slot> (rota round <verb>)`), push the work branch to `origin` (`git push -u origin <branch>`, no force), and only if the push succeeded switch the worktree to `park/<agent>` at the base and clear the pane's host label (best-effort, no effect without a host or handle). A failed push leaves the slot as found, exit 5; the branch is never the only copy of the work. This is a second guard beside `worker reset`'s, not a change to it: reset still refuses a slot holding unmerged commits, because it cuts a fresh branch for new work; `Park` only moves the checkout off a branch that now exists on the remote. `worker reset` is the one that cuts the next issue's branch afterwards, so `assign` after a return behaves as on any parked slot. The salvage commit is the one thing a verb writes into a worker's branch. A commit that a hook rejects is exit 5 and the slot is left as found.
- **Stalled.** A slot is `stalled` when it holds an issue, its host agent is alive, and nothing has moved for `round.stallMinutes` (default 30, `0` turns the check off; a silent default like `round.scope`, not seeded by init). "Moved" is the newest of: the committer time of the branch tip when the branch has commits past the base; the newest mtime among the worktree's dirty paths (`git status --porcelain`, `stat`); and the slot's `activeAt`, a new optional registry field (RFC 3339 UTC) that `worker dispatch` stamps and `worker poll` re-stamps whenever the state it classifies differs from the recorded one. A worker editing without committing is therefore not stalled. A slot whose host agent is not alive is `dead`, not `stalled` (`dead-tab`, C2), a slot waiting on an open escalation (C4) is never stalled, and neither is one whose standing event is `done` and not older than its `activeAt` (it waits on the orchestrator). The signal that cannot be had is the host's raw agent-status churn: herdr events are not stored and `round wait` is read-only, so a hung agent that still repaints its status is judged on commits and files alone. Reconcile and reclaim compute this the same way, in `internal/round.Stalled(slot, now)`, with `now` injectable so the threshold is testable without sleeping.
- **Reconcile amendments (C2).** Two drift kinds, neither repaired by `--apply`'s existing rules except as noted. `stalled`: the rule above (`detail` carries the idle minutes and the signal that last moved). `claim-mismatch`: the tracker and the registry disagree about who holds an issue: the slot's `task` has no open claim by its `claimId` (or another claim holds it), or an open claim `<agent>@<round>` names a registry slot that does not hold that issue. `--apply` repairs only the registry side of an unambiguous mismatch (clears a `claimId` whose claim is gone; never edits the tracker), because the tracker is the source of truth and a human may have changed it on purpose. `label-orphan` and `label-missing` stay as C2 defined them.
- **Handoff note.** A stand-in for D1's note (#65), small enough that D1 can absorb it: one comment on the issue, posted by `return`, `transfer` and `reclaim`, ending with the marker `<!-- rota:handoff <from>@<round> -->` so C4's answer rule never reads it as an answer. Body: `**rota handoff** (<verb>, from <slot>)`, then four labelled lines `Branch:`, `Head:` (the pushed sha7 and subject), `State:` (committed, plus `salvage commit` when `Park` made one) and `Reason:`, then free text under `Done and next:` taken from `--note-file`. A receiving worker finds it by the marker; the pointer brief (C3) names the latest `rota:handoff` comment and the branch. When D1 lands, its format replaces this body and the marker stays.

rota orchestrate [--dry-run]
repo: none
data: {"harness": "claude" | "codex", "host": "herdr" | "tmux" | "solo", "mode": "tab" | "session" | "inplace", "cwd": string, "session"?: string, "command": [string], "tab"?: string, "dryRun"?: true, "changed": bool}
exit: 1 when `rota doctor` reports a failure (its checks print, no session starts); 3 when there is no project root; 4 when `round.dispatch` is `herdr` and the caller is outside herdr (`blockedBy` the reason, `changed` false); 5 when tmux is required and missing, a host call fails, or the exec fails; 70 when `orchestrator.harness` or `orchestrator.command` is unusable
old: none (new in #19; replaces typing herdr, then claude, then /rota-orchestrate)
note: not a query. Steps: (1) run `rota doctor` in-process and stop on a `fail` before anything starts. (2) Resolve the harness from `orchestrator.harness` (default `claude`) in the launch table of `internal/orchestrate`: the agent argv and its first prompt (`/rota-orchestrate` for claude, `$rota-orchestrate` for codex). (3) Resolve the host from where the caller is: inside a herdr pane, a new focused tab in that workspace; inside tmux, a new window; outside both, `exec tmux new-session -A -s rota-<dir> -c <root>` with the supervisor as the window's command, or, with no tmux, `exec` the supervisor in this terminal (`solo`). (4) The process every mode starts is `rota keepalive run --first-prompt <prompt> [--config-dir <dir>] -- <agent argv>` (`--config-dir` for a claude orchestrator: the caller's `CLAUDE_CONFIG_DIR`, else the `round.accounts` entry with the most headroom, else the first; the plan reports it as `account`/`configDir`): the first prompt is a CLI argument, nothing is typed into a pane, and a restart gets `orchestrator.restartPrompt` instead.
note: the claude argv is `orchestrator.command` when set, else `claude --model <orchestrator.model, default opus> --permission-mode auto`; a fresh session, not `--continue`. The codex argv is `codex`.
note: `--dry-run` runs doctor, prints the plan and starts nothing (`changed` false). `mode: tab` returns after the tab opened and its command was typed: acked on start, not on the agent's first turn. `session` and `inplace` replace this process, so `--json` prints no envelope for them. The lease is `keepalive run`'s: a second orchestrator is refused there (exit 4 `lease held`), in the tab, where a person sees it.
note: **Outside a multiplexer, herdr first (maintainer via orchestrator relay round 1).** herdr 0.9.3 has no startup-command flag (`workspace create` and `tab create` take `--cwd`, `--label`, `--env`, `--focus`), and its guide forbids driving the user's own session from outside. A named session of rota's own is not that session: `herdr --session rota-<dir> server` starts it headless, `herdr --session rota-<dir> workspace create --cwd <root> --label orchestrator` makes the workspace, `pane run` types the supervisor into its root pane and `herdr session attach rota-<dir>` replaces the caller's terminal. Checked on 0.9.3 in a throwaway session (`rota-probe`, no agent): the server came up, `pane run` ran `echo` and `pane read` showed the output, and `workspace close`, `session stop` and `session delete` removed it; the default session was untouched throughout. A session that already runs is only attached (the keepalive lease refuses a second orchestrator). Order: inside herdr, inside tmux, `round.dispatch: tmux` forces tmux, herdr installed, tmux installed, else in place. The tab opens with `tab create` and `pane run`, not `agent start`, because the command is the supervisor and not the agent binary; a first-run trust dialog is answered by the person in the focused tab. maestro's herdr notes: `pane run` retries five times on a pane-not-found race; its orphan sweep is not ported (a dead orchestrator tab holds a shell, and `rota reap` closes agentless tabs).
note: **bare `rota`.** With no arguments in a terminal (stdin and stdout are ttys, no `--json`): no `.rota/` here or above runs the interactive setup (#25); an initialized project opens the palette (#181, `internal/palette`), whose preselected Orchestrate entry runs this verb. A pipe, `--json` or any other word keeps the usage error (exit 2, `missing command` or `unknown command`), so a script never opens a session.
note: **Config.** `orchestrator.harness` (`claude` or `codex`, silent default `claude`), documented in `docs/reference/config-options.md`, `docs/usage/configuration.md` and `internal/config/schema.go`. #33 adds harnesses by adding rows to the launch table. The codex prompt syntax is #33's to verify; it is taken from that issue.

### C12: arrange a round's panes

#180: a purely visual verb. It moves live herdr panes between one split view and tabs; no process restarts, nothing is typed, no pane content changes.

### rota layout
rota layout [--project <dir>]
rota layout split [--project <dir>]
rota layout tabs [--project <dir>]
repo: none
data: {"projects": [{"project": string, "name": string, "layout"?: "split" | "tabs" | "mixed", "before"?: "split" | "tabs" | "mixed", "moves"?: int, "changed"?: bool, "orchestrator"?: {"pane": string, "tab": string}, "workers"?: [{"slot": string, "pane": string, "tab": string}], "foreign"?: [{"pane": string}], "skipped"?: string}]}
exit: 3 when `--project` names a directory without `.rota/`, and, for `split` and `tabs`, when no project has an orchestrator pane open in the herdr it runs against; 5 for `split` and `tabs` when nothing was arranged because herdr is missing or failing, or the round is on tmux or solo (the `skipped` text says which), and when a `pane move` fails part-way; the bare form exits 0 in all of these cases. `split` and `tabs` exit 0 when at least one project was arranged, even if another was skipped.
old: none (new in #180)
note: `layout` and `before` are `split` when every live worker pane sits in the orchestrator's tab, `tabs` when none does (also: no live worker), `mixed` otherwise. `moves` and `changed` are in the `split` and `tabs` answers only; `layout` there is the state after the run. Bare `rota layout` is read-only. `foreign` lists the other panes of the orchestrator's tab (a shell the person opened); they are never moved, and each one is also a warning.
note: **The split layout.** The orchestrator is the left column at full height. Live workers, in registry (slot) order, fill columns two panes high, column-major; an odd count leaves the last column one pane at full height. Every column, the orchestrator's included, gets the same width: 1/(1+ceil(n/2)). Two panes in a column split 50/50. Panes are built columns first (`pane move <head> --tab <orch-tab> --split right --target-pane <previous column> --ratio <r> --no-focus`), then each two-pane column splits down (`--split down --ratio 0.5`). n=3: p1 right of the orchestrator at 0.3333, p3 right of p1 at 0.5, p2 down from p1 at 0.5.
note: **herdr 0.9.3 semantics (probed in a throwaway session).** `--ratio` is the share the TARGET pane keeps; the moved pane gets the rest, so a column with c columns of room still to fill (itself included) passes `1/c`. `--label` is accepted by `--new-tab` only, not on a split move (the pane keeps its own label). A move keeps the pane id, the agent name and every process; the moved-from tab closes when that was its last pane, and `--new-tab` makes a tab with a new id at the end of the tab bar. A move into the tab the pane is already in changes nothing (`reason: same_tab`), so a re-split cannot move panes inside the tab. `--no-focus` keeps focus where it was. Command order is pinned by `internal/layout/layout_test.go`.
note: **Idempotence.** `split` on a view whose panes already sit in the grid (same column order and same order inside each column, read from `pane layout`) does nothing; widths a person dragged stay. Otherwise (a worker assigned since, a different order) it sends every worker already in the tab out to a tab of its own, in slot order, and builds the grid again. `tabs` moves only the workers that are in the orchestrator's tab, in slot order, labelled with the slot name. Running either twice in a row is a no-op the second time.
note: **Finding the panes.** The workers' panes are the live slots' agents: the agent named for the slot and its recorded `handle` (`rota-<slot>-<tab id>`), whose name survives a move; a slot with no handle (parked) or no agent (dead) is skipped. The `handle` is not rewritten: after a move it names the tab the slot started in, which may be gone. The orchestrator is the pane working in the project root that no slot owns, preferring one in a tab or workspace labelled `orchestrator` (`orchestrate.Label`) and one running an agent. No pane id is recorded at launch: the label and cwd lookup also covers an orchestrator started by hand.
note: **Which projects.** Without `--project`: every project in `rota projects` that exists on disk, plus the one the caller is in, that has an orchestrator pane in the herdr the command talks to (the one the shell is in; the default session otherwise). A project whose registry records a tmux or solo round is skipped with `host is tmux: layout needs herdr` (listed only when `--project` names it or the registry still holds a handle). `round assign` keeps opening workers as tabs; run `rota layout split` again to fold them in.

### rota round freeze
rota round freeze [--repair-issue <id> | --repair-pr <number-or-url> | --verify | --clear --reason <text>]
repo: none
data: {"freeze": object | null, "changed": bool}
exit: 1 when recovery verification fails (freeze kept); 2 for incompatible flags, invalid repair IDs/URLs or a clear without a non-empty reason; 3 when no freeze exists for a mutation; 4 when recovery is attempted off the frozen base, against a dirty or outdated checkout, with no verification commands, or when the freeze record is unreadable
old: none (#2170)
note: without flags, shows the latest freeze, including its clearance record. State lives under `<git-common-dir>/rota/freeze.json`, shared by all worktrees and outside the source tree. A failed post-landing gate verification freezes further gate, train and assign calls (`exit 4`, `blockedBy: "freeze"`). A scratch verification failure before landing does not freeze. CI verification that times out or never runs stops without freezing. Unreadable records refuse landing/assignment with the same freeze classification and name the audited clear command; status and the prompt warn and remain available. The record names the base, full landed SHA, landed PRs and failing checks. `round status` adds an active `freeze` object and the prompt digest says `FROZEN`.
note: designate the repair by positive issue number or backlog item ID such as `B07` (allowing assignment and its gate/train) or PR number/URL (allowing its gate/train). All members of a train must be repairs while frozen. Designation replaces the previous repair. A repair must target the frozen base and still passes the normal gate checks; it cannot bypass verification. A verified repair landing clears the matching base's freeze. A train clears only after the complete verified tree lands. Skipped verification never clears.
note: `--verify` runs the configured full tier (local or CI), followed by `test.e2e`, on the frozen base checked out at the current origin SHA; without an origin it checks the local base. It clears only when verification passes and HEAD stays at that SHA. The record retains who cleared it, when, and the full SHA. Use this after an external repair or a transient failure.
note: `--clear --reason <text>` clears without verification and writes a `freeze-clear` gate-audit entry with the reason. Clearance records the frozen base SHA when it resolves, otherwise the operator's current HEAD; a deleted base does not prevent a clear. An unreadable record is replaced with an inactive record and the audit names the damaged path and read error. Missing reasons are rejected, with a hint to supply one. Clearance and repair designation use the landing lock, so a concurrent failing landing cannot be cleared accidentally.
