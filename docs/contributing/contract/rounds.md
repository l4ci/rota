## C: rounds

The `round` group is the orchestrator layer over the same slot registry (`.rota/workers.json`) and host package as `rota worker`. It adds no second state file. Each verb below owns its entry.

### rota round wait
rota round wait [<slot>...] [--timeout <seconds>] [--settle <seconds>] [--lines <n>]
repo: none
data: {"slot": string, "state": string, "evidence": string, "source": "herdr-event" | "snapshot" | "poll" | "registry", "waited": number}
exit: 1 when `--timeout` passes with every watched slot still `busy` (failure `data` is `{"timedOut": true, "waited": number, "slots": [{"name": string, "state": string}]}`); 2 when `--timeout` or `--settle` is not a number or `--timeout` is negative; 3 when a named slot is not in the pool, or the pool has no slot with a session handle to watch; 5 when the host is unavailable, or herdr is not 0.9.x
old: none (new in C1)
note: blocks until one watched slot needs attention, then returns that slot. Watched slots are the named ones, or, when none is named, every registered slot that has a `handle` and whose recorded `state` is not `idle`. Pool init seeds every slot `idle` and gives a tmux slot a nominal handle before anything runs in it, and `worker poll` treats a recorded `idle` as already reported, so an idle slot is not watched unless named, or one parked slot would end every wait at once. `worker dispatch` records `busy`, which arms the slot. A slot with no handle is skipped, not an error, unless it was named.
note: "needs attention" is the `rota worker poll` classification, not the host's raw status: `idle`, `blocked`, `done`, `dead`, `limited`, `needs-permission` or `unknown` (UNKNOWN is surfaced, never treated as finished). `busy` keeps waiting. `state` is lowercased, `evidence` is the same line `worker poll` reports.
note: the host only wakes the verb, it never decides. On herdr a status event for a watched pane, on tmux a change in a watched pane's text, triggers a re-classification through the `worker poll` code, so sentinels (`ROTA-DONE`, `ROTA-BLOCKED`), `limited` and `dead` outrank the host's native state exactly as in `worker poll`.
note: a slot that already needs attention when the verb starts is returned at once, `source: "snapshot"`, so an event that fired before the call is never lost. When several slots qualify, the first in registry order wins.
note: (#29) a slot comes back once per change. The returned slot is recorded with `seen` = its state and evidence, and a slot whose classification (state and evidence) equals its `seen` is treated as `busy`, so the next call waits on the others instead of returning a done slot whose PR the orchestrator is holding. A new `ROTA-BLOCKED` question or limit line differs in evidence and comes back. `needs-permission` and `dead` are never remembered and come back on every call: they are answered in the pane or by a reclaim, which re-arms nothing, and a permission prompt's evidence cannot tell two prompts apart. A watched slot classified any other way (`busy` included) has `seen` cleared and is armed again; `worker dispatch` (and so every `--relay`), `worker poll` recording a different state, `round report` and solo `assign` clear it too. Under solo, the recorded state is compared with `seen` the same way.
note: herdr (0.9.x, pinned; any other minor exits 5): wakes on `pane.agent_status_changed` over one socket subscription for all watched panes (`source: "herdr-event"`). tmux has no agent status and no event stream, so the verb re-captures the watched panes every `--settle` seconds (default 5) inside the process and re-classifies on change (`source: "poll"`). The orchestrator's context never sees either loop. One exception on herdr (#211): a slot classified `busy` only because its pane moved while herdr's own status was not `working` is re-classified after each settle without waiting for an event (`source: "poll"`), because herdr sends no event when an idle or done agent's pane comes to rest; right after a turn, two of herdr's `recent-unwrapped` reads a moment apart can return different scrollback windows, so the classification right after the last event can see movement (recorded live, #211). That re-check is not needed for a slot whose agent reports a finished turn past its dispatch baseline (`completion_seq` greater than `turnSeq`, #511): it is read once at the event, with no movement check, as `worker poll` does. A lost herdr event stream (an `events_lost` frame, a socket close, a herdr restart; herdr replays nothing) does not end the wait: it re-subscribes first, then re-classifies every slot from current state, so a transition during the gap is reported once (the per-slot seen dedupe). After 3 losses or failed re-subscribes in a row (a delivered event resets the count) it prints one line on stderr and falls back to the `source: "poll"` loop it uses on tmux; it never spins on the socket. (#510)
note: (#29) the verb writes only the slot it returns, the way `worker poll` records a row (`state`, `activeAt` on a change, `pr` from a URL-shaped `ROTA-DONE`), plus `seen`, and clears `seen` on slots that moved on. A timeout writes nothing. There is still no `changed` field: the data answers "which slot", and the write is bookkeeping, so the round's `assign` can see a slot is done with a PR without a separate `poll`.
note: a timeout is a normal outcome, not a fault: exit 1 with `timedOut: true`, because the verb exists to answer "which slot needs me" and the answer is "none yet". Exit 6 is not used, since the conventions send it `error` alone and reserve it for faults a retry clears. `--timeout` defaults to 0, meaning wait indefinitely. A caller whose shell cuts commands short raises the cap (`BASH_MAX_TIMEOUT_MS` in Claude Code) or loops on a finite `--timeout`.
note: no `ROTA_TEST_*` hooks. The smoke section drives a fake `herdr` binary plus a fake unix-socket server (`HERDR_SOCKET_PATH`), and `test/fakes/tmux`.

- **Round slot.** The `slot` of A7 plus derived fields. C2 stores nothing new: the issue is the slot's `task` (or, when `task` is not a number, the leading number of the branch `<agent>/<issue>-<slug>`), the PR is `pr`, and the host state is read live. Later C issues (tier, escalations) add optional slot fields with their own entries.
- **Sources.** Rows come from the union of three sources, so a restart works with an empty registry: the registry slots; the git worktrees under `<root>/.worktrees/` (a worktree on `park/<name>` is a parked slot named `<name>`, on `<name>/<issue>-<slug>` a slot working that issue); and the host snapshot, whose agents are matched to a row by `handle` (tab id), else by `cwd` equal to the row's worktree. Open PRs come from the forge by head branch, issue labels from the tracker.
- **Degraded sources.** A source that is unavailable (host not running, forge or tracker CLI missing or failing) is named in `unavailable` and `warnings`, and the drift kinds that need it are skipped. The verbs still exit 0: a restart usually finds herdr down.
- **Drift kinds.** `dead-tab`: slot has a `handle` and the host has no live agent for it (matched by recorded tab, then herdr agent name `rota-<slot>-<handle>`, then worktree, so a pane `rota layout` moved is still found). `unclaimed-tab`: a live agent whose `cwd` is inside `.worktrees/` matches no row. `unregistered-worktree`: a worktree under `.worktrees/` has no registry slot. `branch-no-pr`: the slot's branch is neither its parking branch nor the base, has commits ahead of the base, and has no open PR. `pr-unrecorded`: an open PR has the slot's branch as head and `pr` is empty. `pr-stale`: `pr` names a PR that is merged or closed while the slot still holds its task. `label-missing`: the slot holds an issue and the issue lacks the `in-progress` label. `label-orphan`: an issue has `in-progress` and no slot holds it. `label-stale`: a closed issue still has `in-progress` (a merged `Closes #N` PR closes the issue and leaves the label).
- **Safe repairs** (`reconcile --apply` only, each additive or derived): `dead-tab` clears `handle` and sets `state` to `dead`; `unregistered-worktree` registers the slot; `pr-unrecorded` records `pr`; `label-missing` adds `in-progress`; `pr-stale` on a slot whose PR is merged parks the slot as `assign` would (worktree to `park/<agent>` at the base, no push, issue, claim and PR cleared; refused while the slot is busy or its worktree is dirty); `merged-external` (an adopted slot whose PR merged outside the gate) releases the slot, keeping its worktree and branch; `label-stale` removes it from the closed issue (this is also the one-time cleanup of issues closed before the gate released the label itself). Never repaired: `unclaimed-tab` (a tab may be a live worker), `branch-no-pr` (opening a PR is the worker's act), `pr-stale` on a slot whose PR is closed unmerged, and `label-orphan` (resetting a slot and removing the label are the orchestrator's calls, `worker.md`).
- **Host snapshot.** herdr: `herdr api snapshot` (pin 0.9.x), reading `agents[]` (`tab_id`, `cwd`, `agent_status`, `name`). tmux: `tmux list-windows` with the pane's current path. Both sit behind a new optional `host.Snapshotter`, in `internal/host/snapshot.go`; the `Host` interface does not change.

### rota round watch
rota round watch [--heartbeat <seconds>] [--poll <seconds>] [--forge-poll <seconds>] [--settle <seconds>] [--lines <n>] [--autopilot [--base <branch>] [--holder-pid <n>]]
repo: none
data: {"reason": "slot" | "change" | "heartbeat" | "interrupt", "waited": number, "round": number, "slot"?: string, "state"?: string, "evidence"?: string, "source"?: string, "changes": [{"key": string, "from": string, "to": string}], "digest": string}
exit: 2 when `--heartbeat` or `--poll` is not positive, `--forge-poll` or `--settle` is negative, or a positional argument is given; 4 when another watch is already running for this repo (`rota round watch` keeps exactly one); 5 under a solo round (no panes to watch) or when the host is unavailable
old: none (new in #81)
note: `round wait` for a session that must stay free. It is written to run as a background command: the harness wakes the orchestrator when the process exits, and the orchestrator re-arms it. It exits 0 with what happened: `slot` (a watched slot needs attention, the `round wait` verdict, same `seen` bookkeeping), `change` (a registry or forge entry moved, see below), `heartbeat` (nothing happened for `--heartbeat` seconds, default 600) or `interrupt` (SIGINT/SIGTERM). The heartbeat is what keeps an orchestrator from going quiet for good: it wakes however little happened.
note: `change` entries are the snapshot keys that differ from the start of the watch: `pr/<slot>` (the slot's recorded PR), `escalation/<id>` (the stored status), and, from the forge every `--forge-poll` seconds (default 120, `0` never asks), `pr/state/<slot>` (PR state from `round status`), `escalation/status/<id>` (derived status after `round escalate check` has stored any answer) and `review/<slot>` (review input waiting on a `done` slot's PR, valued `<n> from <authors> <pr-url>`; see `round review-relay`). A slot's own state is reported through `slot` only, so the orchestrator's `assign` does not wake the watch it just armed. Checks and review status of a PR are not in `round status` and are not watched (follow-up).
note: one at a time. The process writes `<git-common-dir>/rota/round-watch.json` (`pid`, `start`, `host`, `startedAt`, `heartbeatSeconds`) under a lock and removes it on exit; a marker whose process is gone is replaced. A second `round watch` exits 4. The Stop and prompt hooks read the marker.
note: with no slot to watch (all idle) the verb still runs: it waits out the interval on the registry and the forge, so an answered escalation wakes an orchestrator whose workers are all parked. Each wait covers one classification (`--poll` plus `--settle` plus 2s), so a heartbeat can run a few seconds past its interval.
note: no `ROTA_TEST_*` hooks. The smoke section (108) uses `test/fakes/tmux` with a churning pane.
note: (#93) `--autopilot` makes the watch the autopilot's heartbeat: it runs `round tick` first, then waits, and ticks again on every wake. It returns only for a `needsYou` item no earlier tick reported (`reason` `change`), the heartbeat, an interrupt, or a stop (`reason` `stopped`, `autopilotStopped` says why, exit 0). The result gains `autopilot` (the tick's `{did, needsYou, new}`) and, on a stop, `autopilotStopped`. Exit 4 when `round.autopilot` is off. A round running it still has its watch armed, so the Stop hook is satisfied.

### rota round tick
rota round tick [--base <branch>] [--holder-pid <n>]
repo: none
data: {"did": [{"action": "reconcile" | "merge" | "assign" | "review-relay", "target": string, "detail"?: string}], "needsYou": [{"kind": string, "target": string, "why": string}], "new": [{"kind": string, "target": string, "why": string}], "changed": boolean} (on a stop: {"stopped": true, "changed": false})
exit: 2 on a positional argument; 4 when `round.autopilot` is off, or this process holds no live round lease, or a wind-down has stopped the round's autopilot (`stopped: true`); 3 when there is no project root
old: none (new in #93)
note: one pass of the round autopilot, in order: (1) `reconcile --apply` (the safe repair kinds; drift it does not repair goes to `needsYou`); (1b) review loop (`round.reviewLoop`): every `done` slot with a PR is checked for new review input (see `round review-relay`); under `auto` the input is relayed to the worker (`did` `review-relay`), under `manual` it only comes back in `needsYou` as kind `review` and the slot is gated as before (a poll failure is a `review` item too); under `auto` a slot whose input was relayed is not merged this tick, and one that could not be relayed (the bounce cap, a refused relay, a failed poll) stays in `needsYou` and is held; (2) merge: every slot that is `done` with a recorded PR (and not relayed or held by the review loop), and every queued PR, goes through `worker gate` (one target) or `worker train` (several, grouped by the base each merges into), at most `round.autopilotCap` per tick; (3) assign: the first ready candidate of the round's scope to each idle slot, at most `round.autopilotCap`, with the default tier and kind and never `--accept-overlap`. The merge runs before the assign so the next assignment branches from the gated base.
note: the autopilot never answers a worker, approves a permission, picks a tier above the default, accepts overlap, reclaims a stalled slot or merges without a passing gate. A slot that is `blocked`, `needs-permission`, `limited`, `dead` or `unknown`, drift it does not repair, a gate that did not pass and a `ship.mergeApproval` other than `none` (the autopilot then merges nothing) all come back in `needsYou`. A gate that failed for a reason only a person can clear (anything but a `stale` or `provenance-fail` bounce, which the gate sends back to the worker and which returns when the worker does) is held: the next tick lists it but does not re-run the checks, until the slot leaves `done`.
note: `new` is the `needsYou` items no earlier tick reported. State lives in `<git-common-dir>/rota/round-autopilot.json` (`round`, `held`, `reported`, `stopped`), per round. `round wind-down` sets `stopped` before it re-verifies, so no tick assigns or merges meanwhile, clears it when the lease is kept and removes the file when the round ends.
note: every action is appended to `.rota/gate-audit.jsonl` as `{"gate": "autopilot", "verb": "round tick <action>", "target", "note"}`. These are not human approvals.
note: no `ROTA_TEST_*` hooks. The smoke section (114) uses the gh and tmux fakes of section 104.

### rota round status
rota round status
repo: none
data: {"slots": []row, "drift": number, "unavailable": []string, "host"?: string, "escalations": []escalationRow, "limits": []limit, "review": []reviewRow}
exit: 3 when there is no project root; 5 when git fails
old: none (new in C2)
note: `row` is `{"name": string, "agent"?: string, "issue"?: string, "branch": string, "pr"?: string, "prState"?: string, "hostState"?: string, "state"?: string, "tab"?: string, "registered": bool, "drift": []string, "escalations": []string, "kind"?: string, "kindSource"?: string, "tier"?: string, "model"?: string, "tierReason"?: string, "bounces": number}`; `bounces` is how often the slot's issue was sent back (0 when never; see `round bounce`); `kind`, `tier`, `model` and `tierReason` are the slot's C9 fields, absent on a slot that was never assigned; `escalations` holds the ids of the slot's open escalations (C4). `agent` is the host agent's name, `hostState` its `agent_status` (absent when the host is unavailable or the row has no live agent), `drift` the kinds above. Unclaimed tabs are rows with `registered: false` and no `name` match, listed after the slots.
note: (#580) `state` is set only for an adopted slot, whose `hostState` is `external`: `done` (PR open), `busy` (branch ahead of the base, no PR), `idle`, or `unknown` while the forge cannot answer. Text and `--ui` show it as `external/<state>`.
note: read-only: writes nothing and has no `changed`. Text mode prints one line per row: `name issue branch pr hostState drift`, plus `bounces <n>` when the count is above 0. `rota round status --ui` opens the round screen over the same slots and review list. It also shows each open PR's title and the last evidence line `round wait` stored for the slot; neither is in `data`. Each refresh starts with an empty forge read cache.
note: `review` (#29) lists the PRs on the round's review list, `{"issue": string, "pr": string, "branch": string, "from": string}`; text mode adds one `review #<issue> <pr> <branch> from <slot>` line each. A record counts as holding its issue for `label-orphan`, `claim-mismatch` (its `claimId` against the issue's claim, no repair) and `pr-stale` (its PR merged or closed; repair: drop the record).
note: `unregistered-branch` (#580) is a finding kind for a local or remote branch that matches `round.adoptPattern`, that no slot holds and that is not merged into the base. The pattern is a `path.Match` glob over the branch name (`codex/*`, `claude/*`): `*` stops at `/`, and an empty pattern (the default) turns the check off. A bad pattern is a warning. `issue` is set when the name yields a number (`<agent>/<issue>-<slug>`, `issue-N` or `#N`); `repair` is then `adopt as an external slot` and the finding has no `slot`. A name with no number is listed with `needs --issue` and is never repaired. `--apply` adopts the numbered ones as `rota worker adopt` does, creating a local branch from `origin/<branch>` first when only the remote exists; a blocking overlap or a held issue becomes a warning and the finding stays in `drift`. The tick of `round watch --autopilot` runs `reconcile --apply`, so it adopts too. Only `round reconcile` (and so the tick) scans branches; plain `round status` does not, and its `drift` count leaves them out.
note: external (adopted) slots are skipped by the `dead-tab`, `unclaimed-tab`, `stalled` and `item-timeout` findings: they have no host.
note: `limits` (D3 amendment) lists the usage-limit entries still `waiting`, as `rota limit status` stores them, read from the registry only. A waiting limit is not drift. Text mode adds one `limit <id> waiting <session> <window> <resetsAt> <action> <note>` line each.

### rota round reconcile
rota round reconcile [--apply]
repo: none
data: {"drift": []finding, "repaired": []finding, "clean": bool, "unavailable": []string, "changed": bool, "escalations": []escalationRow, "limits": []limit}
exit: 3 when there is no project root; 5 when git fails
old: none (new in C2)
note: `finding` is `{"kind": string, "slot"?: string, "issue"?: string, "detail": string, "repair"?: string}`; `repair` is the action `--apply` would take and is absent for kinds that are never repaired. Without `--apply` the verb reports and writes nothing (rule 5), `repaired` is `[]` and `changed` false. With `--apply`, `drift` holds what remains and `repaired` what was fixed.
note: the host is herdr when `work.dispatch` is `herdr` or the process runs inside herdr (`HERDR_ENV=1`), else tmux. `branch-no-pr` counts commits against `origin/<base>` when it exists, so a stale local base can overstate it until the next fetch.
note: `item-timeout` (#399) is a finding kind for an item whose wall-clock time since its first assignment is at least `work.itemTimeoutMinutes` (integer 0 or more, silent default `0` = off; no finding, no park). The start is stamped once, at the first `round assign`, in `itemStarts` of `.rota/workers.json` (issue to RFC 3339 UTC time), beside `bounces`; it is per item, so a `round transfer` to another slot keeps the clock running, and it is dropped when the item is parked for a human or its merged slot is parked. `detail` carries the elapsed minutes and the limit. `--apply` repairs it like `round transfer --to human`, the path `round.maxBounces` uses: slot freed, `needs-human` label, a comment naming the limit, the PR left open. It needs the round lease and the tracker; without them the repair fails, a warning says why, and the finding stays in `drift`.
note: `limits` (D3 amendment) is the same list of `waiting` usage-limit entries as in `round status`, with the same text lines; it adds no finding and leaves `clean` alone.
note: a classifier (rule 7): exit 0 whatever the drift, `clean` is true when `drift` and `repaired` are both empty. A repair that fails on one slot is a `warnings` entry and leaves that finding in `drift`; the rest still run.

- **Escalation** (C4, #60). A question the orchestrator puts to the human on an issue or PR thread, with a herdr notification alongside. Open escalations live in a top-level `escalations` list in `.rota/workers.json`, beside `slots`, because an escalation need not belong to a slot. An entry is `{"id": string, "kind": "issue" | "pr", "number": number, "slot"?: string, "title": string, "commentId": string, "sentAt": string, "deadline"?: string, "notified": bool, "status": "pending" | "answered", "answer"?: answer}`, with `answer` `{"commentId": string, "author": string, "body": string, "seenAt": string}`. `id` is `e<N>`, N one more than the highest in the list. Times are RFC 3339 UTC. `timed-out` is derived on read (`pending` past `deadline`) and never stored, so a late answer still lands.
- **Marker.** Every comment rota posts for an escalation ends with the line `<!-- rota:escalation <id> -->`, invisible once rendered. Any comment carrying a `<!-- rota:` marker is rota's own and is never an answer.
- **Answer rule.** The orchestrator, the workers and the human usually post as the same account, so the author decides nothing. The answer to an escalation is the first comment on its thread that comes after the escalation comment in the forge's oldest-first order and carries no `<!-- rota:` marker (maintainer ruling, 2026-10-03, relayed by the orchestrator in round 4). The rule therefore relies on rota marking every comment it posts; a comment posted outside rota (raw `gh`, a bot) on a thread with a pending escalation reads as its answer, so `check` returns the answer's body for the orchestrator to read before acting on it.
- **One per thread.** At most one pending escalation per issue or PR, so a single answer can never be read as answering two questions.

### rota round escalate send
rota round escalate send <number> [--pr] [--slot <name>] --title <text> --body-file <path|-> [--timeout <seconds>]
repo: none
data: {"escalation": escalation, "url": string, "notified": bool, "changed": bool}
exit: 2 when `<number>` is not a positive integer, --title or --body-file is missing or the body is empty, or `--timeout` is not a non-negative number; 3 when there is no project root, `--slot` names no registered slot, or the forge reports no such issue or PR; 4 when an escalation on the same thread is still pending (failure `data` is `{"pending": string, "changed": false}`, the id of the pending one); 5 when the forge CLI is missing, unauthenticated or fails
old: none (new in C4)
note: posts one comment on issue `<number>`, or on PR/MR `<number>` with `--pr`: `**rota escalation <id>**: <title>`, the body, a line asking for an answer in a new comment on the thread, and the marker. Then raises a herdr notification (`rota escalation <id>` / `<title> (#<number>)`) and records the entry under the registry lock. On GitHub a PR thread is the issue-comments API of the same number; on GitLab it is the MR notes.
note: the notification goes through `internal/host` Notify when the host is herdr: `work.dispatch` is `herdr` or the process runs inside herdr (`HERDR_ENV=1`), and the `herdr` binary is installed. Otherwise the comment alone is the channel, `notified` is false and `warnings` says why. Notify returns nothing, so `notified: true` means the notification was raised, not that a human saw it. When herdr answers anything but `shown` or `disabled` (`rate_limited`, `no_foreground_client`, `busy`), or the call errors, the host prints one line on stderr naming the notification title (it carries the slot) and the reason, with no retry; the same holds for the `worker poll` blocked/needs-permission alert. A herdr problem never fails the verb.
note: `--timeout` (default 0, no deadline) sets `deadline` to `sentAt` plus that many seconds. The verb returns as soon as the comment is posted; it never waits for the answer, so the orchestrator keeps working other slots.
note: the comment is posted before the record is written. If the write then fails, the verb exits 1 with the comment's `url` in the failure `data`, so the orchestrator can delete or record it by hand; a retry would post a second comment.

### rota round escalate check
rota round escalate check [<id>...]
repo: none
data: {"escalations": [{"id": string, "kind": string, "number": number, "slot"?: string, "title": string, "status": "pending" | "answered" | "timed-out", "sentAt": string, "deadline"?: string, "answer"?: answer}], "pending": number, "answered": number, "timedOut": number, "changed": bool}
exit: 3 when there is no project root or a named `<id>` is not in the list; 5 when the forge CLI is missing
old: none (new in C4)
note: a classifier (rule 7): exit 0 whatever the statuses. With no `<id>`, reports every entry whose stored status is `pending`; named ids are reported whatever their status. For each pending entry it reads the thread's comments once and applies the answer rule. A found answer is stored (`status: "answered"`, `answer`) under the registry lock, `changed` true; an entry already answered is reported from the registry without a forge call.
note: a forge failure on one thread is a `warnings` entry and that escalation is reported with its stored status; the rest still run. A deleted escalation comment is a warning too (the thread can no longer be ordered against it), and the entry stays pending.
note: answered entries stay in the list as the record of what the human said; nothing in C4 prunes them.
note: `round status` and `round reconcile` (C4 amendment) list the open escalations, stored `pending` ones with the derived status `pending` or `timed-out`, as `escalationRow`: the row shape `check` reports. They read the registry only and make no forge call, so they never see an answer `check` has not stored. An open escalation is not drift: it adds no finding, leaves `clean` alone and is never repaired. Text mode adds one `escalation <id> <status> <kind> #<number> <title>` line each.
note: no `ROTA_TEST_*` hooks. Tests inject a fake forge exec and a fake host; the smoke section (84) drives the fake `gh` under `test/fakes` and a fake `herdr`.

### rota round summary
rota round summary [--round N]
repo: none
data: {"round": number, "issues": []issueRow, "slots": []total, "accounts": []total, "audit": []auditRow}

### C3: round start, candidates, assign, wind-down

C3 (#59, absorbing #40 and #41) adds the round lifecycle over the same registry. Orchestrator rulings (round 4, `c-rulings.md`): no second state file unless a need does not fit `workers.json`; the autonomy axis is a new key, not `autonomy.level`; the file-overlap rule is concrete and states what it cannot catch.

- **Round config.** Four keys, all silent defaults (the `ship.mergeApproval` pattern; not seeded by init). `round.scope` is `slate`, `milestone` or `next`, default `milestone`. `round.roster` is a list of agent names, default `["ben","dana","nia","kit"]`. `round.brief` is the path the worker pointer names, default `""` (see **Brief pointer**). `round.sharedPaths` is a list of repo-relative globs the overlap check ignores, default `[]`. `autonomy.level` (off/auto) is untouched: it says how far skills chain on their own, `round.scope` says which issues a round may take.
- **Scope.** The candidate set is the open, unheld items of: `slate` the round's recorded slate and nothing else; `milestone` the active milestones (`rota milestone active`, then `rota backlog ids --milestone`); `next` the same, and when none of those is left to assign, the items of the first `planned` milestone whose dependencies are all shipped (`milestone list`, `ready`). The scope is enforced by `assign`, not advisory: an issue outside it is refused. Choosing `slate` is how the maintainer approves exactly what a round may touch; `milestone` is the #44 default (slate confirmed once, by the orchestrator, from `start`'s candidates); `next` lets an unattended round roll over.
- **Registry fields.** C3 adds optional fields to `.rota/workers.json`, all absent until written. Top level: `scope` (string, the scope the round started with) and `slate` (`[]string`, issue IDs in rule-11 spelling, present only for `slate`). Per slot: `claimId` (string, the `item claim` id `assign` took, released by `wind-down` and by C10's return). The issue a slot holds stays in `task` and its branch in `branch`; the top-level `round` number is the one `worker dispatch --round` already writes.
- **Lease.** One orchestrator per repo, keyed on `git rev-parse --git-common-dir` so every worktree of the repo shares it. It does not fit `workers.json`: that file lives under each worktree's own `.rota/`, so a second worktree sees an empty registry and a lock inside it protects nothing. The lease is `<git-common-dir>/rota/round-lease.json`: `{"pid": number, "start"?: number, "host": string, "pane"?: string, "paneHost"?: "herdr"|"tmux", "root": string, "round": number, "startedAt": string}`. `pid` is the orchestrator process, not the short-lived `rota`: the nearest ancestor that is not a shell, `env`, `timeout` or `rota` (in Claude Code, the `claude` process), else the parent. A herdr or tmux server is a boundary: when the walk reaches one, rota ran from a plain shell in a pane and the holder is that pane's shell, the ancestor just below the server, so two panes on one server never share a holder (#205). `start` is that process's start time (Linux `/proc/<pid>/stat` field 22), read to defeat PID reuse, absent where the platform has none. `pane` is `HERDR_PANE_ID` or `TMUX_PANE`. The lease is `live` when `host` is this host and the pid runs with the same `start`; `stale` when `host` is this host and the pid is gone or its start differs; `foreign` when `host` differs (cannot be checked, treated as live and named). `pid`, `host` and `pane` are overridable by `--holder-pid` for harnesses whose ancestry is not discoverable.
- **Lease seam (C2, C6).** `internal/round` exports `ReadLease(root) (Lease, LeaseState, error)` with `LeaseState` one of `none`, `live`, `stale`, `foreign`, and `ClearStaleLease(root) (Lease, bool, error)`, which removes only a `stale` lease. C3 owns both; `reconcile` and `reap` call them and write nothing of their own. `reconcile` gets one new drift kind, `lease-stale` (a `stale` lease; the finding's `detail` names the holder), never repaired by `--apply`; `rota reap` lists it as a candidate and clears it through `ClearStaleLease`. `rota round start` also reclaims a stale lease itself, since a provably dead holder needs no human, with the warning `reclaimed stale lease held by pid <n>`.
- **Readiness.** `candidates` and `assign` run three checks per item, each reported in `checks` as `{"name": "criteria"|"dependencies"|"overlap", "ok": bool, "detail": []string}`:
  1. `criteria`: the `rota item ready` rule verbatim (acceptance criteria, or a design or plan note); its `reasons` are the detail.
  2. `dependencies`: every reference in the item's `## Depends on` section (issue body, or the detail file in file mode) must be done: closed in issue mode, archived in file mode. A reference in the item's own ID spelling (`#57`, `57`, `B07`) is looked up; any other reference (`owner/repo#N`, a URL) cannot be verified and fails the check (`cannot verify <ref>`). An item with no such section has no dependencies. An open dependency with a PR is not done.
  3. `overlap`: no file overlap with an in-flight item. In flight means a slot in this registry holding a `task` other than this item. A slot whose issue is already closed (its PR merged) is skipped. The footprint of an item is the `## Files` section of the body when present (one path or glob per `- ` or `* ` bullet; other lines are ignored, and comments never feed it), otherwise every token of the body and comments that is a tracked path at the base (`git ls-files`) or a directory prefix of one (two or more segments, so `docs/` alone never counts), minus `round.sharedPaths`. The footprint of an in-flight item is its own footprint plus its slot's real changes (`git diff --name-only <base>...<branch>` and uncommitted paths in the slot's worktree). Two footprints overlap when they share a file or one names a directory holding the other's file. The check cannot catch: files an item will create, paths nobody wrote down, two items editing the same function or file under different names, generated files and registries every item touches (list those in `round.sharedPaths`), renames, work on another machine's round, and a stale issue text. Scopes are compared next to paths: an item's `## Touches` bullets (a symbol, endpoint, schema, migration or config key), trimmed, lower-cased and compared exactly, else `subsystem:<name>` from its `Subsystem:` field when neither side declares `## Touches`. A shared scope joins the same overlap entry as `scopes`, and fails the check only under `round.scopeOverlap: block` (default `warn`: listed, item still ready); `--accept-overlap` skips both. `candidates` and a successful `assign` also report `overlaps`. It is a heuristic that fails closed on what it can see, so it stays on only because it is cheap to override (below).
- **Brief pointer.** `assign` hands the worker a short signed brief instead of the pasted contract (#41): its agent name, the round number, the path of the standing contract, the issue to read first with its thread (and the instruction to dispute the ticket before implementing if it is wrong or already decided), the branch, the sibling issues, and the answered decisions verbatim from `--body-file`. The contract is `skills/references/worker-contract.md`, which C3 extends with a *Read the issue and dispute it* step. The path comes from `round.brief` when set, else `references/worker-contract.md` under `CLAUDE_PLUGIN_ROOT` when that is set, else under the project root; if none exists `assign` refuses before touching anything (`blockedBy: "brief missing"`). `/rota-work`'s own dispatch keeps pasting the contract; moving it to the pointer belongs to the orchestrate skill (C7).

The order is: re-verify the base, then park, then release the lease, so a failed verify never frees the repo for a second orchestrator.
note: re-verify runs the same commands the gate does (`test.full`, `verified` lists them) on the base branch checked out in the project root, which must be clean and on the base (3 otherwise, with the hint). An empty list is `verifySkipped: true` with the `NO-VERIFY` warning `worker gate` gives. `--no-verify` skips it.
note: parking uses `worker reset <slot>` for each registered roster slot onto `park/<agent>` at the base, so the work-holding guard is the one reset already has: a slot with uncommitted changes or commits not on the base is `retained` with `dirty` and `unmerged` and the verb exits 4. Nothing is discarded, which is why "leaves no slot unparked" is true of a clean wind-down and a refusal otherwise; fix the slot and run it again. A slot already parked is `unchanged`. `claimId` is released for each slot that held an item, and the item's `in-progress` state is left to the merge or to C10's return, not cleared here.
note: (#580) an adopted (external) slot is never parked. One whose PR merged is unregistered and reported `released`, with its worktree and branch kept; any other is `open` and stays registered. `--prune` also removes a released slot's worktree and branch, leaving a dirty worktree (and its branch) in place with a warning. Neither outcome makes `holds-work`.
note: every slot wind-down parks (or finds already parked) has its `handle` cleared, as `round reclaim` does: a parked slot has no pane, and a handle left behind reads as a `dead-tab` to `round reconcile` once the tab closes. A `retained` slot keeps its handle. `session` is pool-level and is left alone.
note: **session end (#212, ratified round 4).** For each slot it parks or finds parked that has a `handle`, wind-down ends the slot's session with the host's provable `Kill` (the one `round reclaim` uses) before clearing the handle, so no worker keeps drawing quota after the round. A `retained` slot keeps its session and handle. When the host cannot be asked or the kill is not proved, the slot is still parked, its handle is kept, and the warning `SESSION-KEPT <slot>: session still running` is added; verdict and exit are unchanged. A slot with no handle is skipped.
note: wind-down reports, and does not delete: branch hygiene (merged `<agent>/…` branches) and the label sweep belong to `reconcile` (`label-orphan`, never auto-repaired) and `rota reap` (#62). `drift` is the count a read-only reconcile finds after the parking, so the summary says what is left for them.
note: `merged` is true when the slot's PR is merged, and `issue` and `pr` come from the slot before it was parked. The lease is released only on `clean`; `lease` is present on the other verdicts.

### C5: merge policy and approval requests

C5 (#61) is the orchestrator side of the merge policy. Most of #61 shipped with B1 (#54): `ship.mergeApproval` (`none`, `all`, `paths`) and `ship.mergeApprovalPaths`, the `merge-approval` gate on `ship merge`, `ship pr-merge` and `worker gate`, and the path match against the PR's changed files. Under the default `none`, `worker gate` already merges a passing PR without a prompt. C5 adds the two missing pieces: the approval request goes out through the C4 escalation channel, and the human's answer comes back as a recorded B1 approval. It adds no verb and no config key, only two flags on `worker gate` and `ship pr-merge`.

- **Approval thread.** The thread a merge's approval request lives on: the PR (`kind` `pr`, its number) when the merge has one, else for `worker gate` the slot's issue (`kind` `issue`, the round slot's issue number). `ship merge` has no forge thread, so it takes neither flag and keeps `--confirm` from an `AskUserQuestion`.
- **`--escalate`.** When the `merge-approval` gate refuses, the verb also sends the approval request with `round escalate send` on the approval thread (`--slot` set for `worker gate`), then exits 4 as before, with the escalation in `data.escalation`. Title `Merge approval: PR #<n>` (or `Merge approval: <slot> (<branch>)` without a PR). The body names the policy (`all`, or `paths` with the matching files from `data.paths`) and ends: ``Reply `approve`, `approved`, `yes`, `lgtm` or `ship it` to merge. Any other reply holds the merge.`` When an escalation on that thread is already pending, the verb sends nothing and returns the pending one, so a re-gate in a loop never posts twice. With no gate to clear (the policy does not cover the merge), `--escalate` is accepted and does nothing. A send failure is a `warnings` entry; the refusal stands.
- **`--approval <id>`.** Clears the `merge-approval` gate with a recorded answer instead of `--confirm`. It reads escalation `<id>` from `.rota/workers.json` and makes no forge call, so run `round escalate check` first. Checks, in order, all before anything changes:
  - unknown `<id>`: exit 3;
  - the escalation is not on this merge's approval thread: exit 2;
  - `status` is not `answered` (pending, or timed out with no answer): exit 4, `{"blockedBy": "approval pending", "escalation": string, "status": string, "changed": false}`;
  - the answer does not approve: exit 4, `{"blockedBy": "approval declined", "escalation": string, "answer": string, "changed": false}`.
  An answer approves when the first word of its first non-blank line, lowercased with trailing punctuation removed, is in the allowlist `approve`, `approved`, `yes`, `lgtm`; or when that line's first two words, treated the same way, are `ship it`. `Approve.`, `YES, go ahead`, `lgtm!` and `Ship it.` approve; `no`, `yes-ish`, `please approve` and `ok` hold the merge. The allowlist lives in one function (maintainer ruling, relayed by the orchestrator in round 4: "Approve or yes words").
- **Recording.** A cleared `--approval` writes the B1 audit line with `note` set to the answer body verbatim and `escalation` set to `<id>`, exactly as `--confirm --confirm-note` would with the quoted answer. The escalation stays in the registry as the record of what the human said; the same answered escalation can clear a re-gate of the same thread (after a `stale` bounce, say).
- **Flag rules.** `--approval`, `--escalate` and `--confirm` are mutually exclusive (exit 2). `--approval` on a merge the policy does not cover is accepted and writes nothing, the same as `--confirm` (B1).
- **Skill routing.** `/rota-work`'s gate step and `/rota-review --queue` pass `--escalate` when the round is unattended (the orchestrator is driving herdr workers), record the escalation id against the slot or PR, keep working other slots, and re-gate with `--approval <id>` once `round escalate check` reports it answered. An `approval declined` refusal is surfaced and the slot is held, never retried. Interactive runs keep the `AskUserQuestion` plus `--confirm` path from B1.
- **Limits.** The approval is tied to the thread, not to a commit: commits pushed to the PR after the answer are covered by it. `worker gate`'s provenance and freshness checks still run on every re-gate, so a moved head is re-verified, but it is not re-approved.

### C9: worker tier and model

C9 (#75) lets the orchestrator choose how heavy a model each worker starts with, and tells the worker how to size its own subagents. Skills and briefs speak in **tiers**; config maps tiers to model names per harness kind, so nothing outside config names a model.

- **Tiers.** `light` (reading, searching, discovery), `standard` (writing code and tests), `heavy` (hard reasoning, design, tricky debugging), in that order. A harness **kind** is `claude` or `codex`.
- **Config.** Eight keys, all silent defaults (not seeded by init). `round.tier` is the default tier, `standard`. `round.tiers.<kind>.<tier>` is the model name: `claude` defaults to `haiku` for light and `opus` for heavy, and `standard` defaults to the value of `models.worker` (itself `sonnet` by default), so one knob governs the standard model and the two cannot drift; an explicit `round.tiers.claude.standard` wins; `codex` defaults to `""` for all three, because codex model names are not ours to fix and a codex worker is E1's. A kind is *configured* when any of its three tiers is non-empty. Validation (read through `internal/roundcfg`, so every verb that reads round config exits 70 on it): `claude` must be configured; a configured kind must have all three tiers non-empty (the error names the missing `round.tiers.<kind>.<tier>`); `round.tier` must be a tier. Unconfigured `codex` is never an error: a codex worker then gets no model and Codex picks its own (#68), unless a custom `work.codexCommand` holds `{model}`, which `assign` refuses with `no tier map` before anything is marked.
- **Choosing.** `rota round assign --tier <t>` picks the tier; omitted, it is `round.tier`. rota does not choose from the issue: size, type, labels and judgment belong to the orchestrate skill (C7). The config tier is a default, not a ceiling: a tier above it needs `--tier-reason <text>` (one line, exit 2 without), and any given reason is recorded. A tier at or below the default needs none. `--kind` is the harness kind of the worker, default the slot's recorded `kind`, else `claude`.
- **Resolving.** `model` is `round.tiers.<kind>.<tier>`. On a `claude` kind the default launch command is `claude --model <model> --dangerously-skip-permissions` (`models.worker` also drives `/rota-work`'s own dispatch, and is the default of the standard tier, above). A custom `work.workerCommand` receives the model only through a `{model}` placeholder in it; without one the tier is recorded but `model` is left out of the slot and `data`, and `assign` adds the warning `tier model not applied: work.workerCommand has no {model} placeholder`, because rewriting a command rota does not own would lie about what ran.
- **Codex.** The tier map, its validation and the resolution above are defined for `codex` and `--check-only` reports the model it would use. Starting a codex worker is E1 (#68), under "E: Codex workers".
- **Registry fields.** Optional per-slot fields, absent until `assign` writes them and cleared when the slot is parked (`wind-down`): `kind` (string), `kindSource` (string: `--kind`, `harness label`, `round.workerKind`, `slot` or `default`), `tier` (string), `model` (string), `tierReason` (string). They are the round state C9 asks for; `round status` rows show them.
- **Brief.** The subagent guidance is split on purpose. The **standing rule**, harness-neutral and with no model names, lives in `references/worker-contract.md`: delegate reading and searching to a `light` subagent, code and tests to `standard`, and keep `heavy` for genuinely hard reasoning, using the tier map the pointer gives. The **resolved facts** for this worker live in the pointer brief `assign` writes: its own tier and model, the tier-to-model table of its kind, the reason when it is above the default, and the instruction to put `Worker tier: <tier> (<model>)` in its PR body, which is how the choice reaches the PR (workers write their own PR bodies, rota cannot).
- **Not in C9.** Picking the tier from the issue (C7), a tier per subagent call (the worker decides, by the rule), and showing `size` or priority in `candidates` to help the choice (the orchestrator reads the backlog).
### C10: round return, transfer, reclaim

C10 (#76) moves an issue that is already assigned. It builds on C3 (`assign` takes the claim, `claimId` on the slot, the lease) and C2 (`reconcile`). Orchestrator rulings (round 4, `c-rulings.md`): the claim lives on the tracker, through the same `item claim`, `item release` and `item state` calls `assign` makes; no local-only claims file; the note transfer hands over is a minimal stand-in for D1's.

- **Premise check.** Four points in #76 do not hold as written, and the entries below follow the code, not the ticket. (1) "Back to ready" is not a state: `item ready` is a property of the text (acceptance criteria or a design note), and the only tracker state `assign` sets is `in-progress`. Return puts the issue back in the candidate set by releasing the claim and clearing `in-progress`; `candidates` then lists it again with its checks. (2) "The branch stays" is false for a slot today: `worker reset` refuses to leave a branch with commits not on the base, and git will not check one branch out in two worktrees, so a slot cannot both keep the branch checked out and be free. The branch has to be pushed and the slot switched off it (**Park**). (3) "Reclaim from a stalled slot" needs a stall signal the registry does not hold: it has no activity time (**Stalled**). (4) "Transfer to the human" cannot be an assignee: the orchestrator and the human usually post as the same account (C4), so an assignee marks nothing; it is a label (**Claim on the tracker**).
- **Claim on the tracker.** The holder is the open claim comment `item claim` posts (`claimId` `<agent>@<round>`, C3) plus the `in-progress` label. `.rota/workers.json` mirrors it: the slot's `task` and `claimId`. A new top-level label role `issues.labels.needsHuman` (default `needs-human`) marks an issue handed to the human: no claim, no `in-progress`, the label on. Each verb below changes the tracker first and the registry second, so a crash between them leaves a mismatch reconcile reports and `--apply` repairs from the tracker, which wins. Return and transfer to a slot release the old claim before claiming anew, so an item is never claimed by two.
- **Park.** Return, transfer and reclaim free a slot with the same sequence, `internal/round.Park(slot)`: salvage the worktree if dirty (stage the dirty paths by name, never `-A`, and commit `wip: parked from <slot> (rota round <verb>)`), push the work branch to `origin` (`git push -u origin <branch>`, no force), and only if the push succeeded switch the worktree to `park/<agent>` at the base and clear the pane's host label (best-effort, no effect without a host or handle). A failed push leaves the slot as found, exit 5; the branch is never the only copy of the work. This is a second guard beside `worker reset`'s, not a change to it: reset still refuses a slot holding unmerged commits, because it cuts a fresh branch for new work; `Park` only moves the checkout off a branch that now exists on the remote. `worker reset` is the one that cuts the next issue's branch afterwards, so `assign` after a return behaves as on any parked slot. The salvage commit is the one thing a verb writes into a worker's branch. A commit that a hook rejects is exit 5 and the slot is left as found.
- **Stalled.** A slot is `stalled` when it holds an issue, its host agent is alive, and nothing has moved for `round.stallMinutes` (default 30, `0` turns the check off; a silent default like `round.scope`, not seeded by init). "Moved" is the newest of: the committer time of the branch tip when the branch has commits past the base; the newest mtime among the worktree's dirty paths (`git status --porcelain`, `stat`); and the slot's `activeAt`, a new optional registry field (RFC 3339 UTC) that `worker dispatch` stamps and `worker poll` re-stamps whenever the state it classifies differs from the recorded one. A worker editing without committing is therefore not stalled. A slot whose host agent is not alive is `dead`, not `stalled` (`dead-tab`, C2), and a slot waiting on an open escalation (C4) is never stalled. The signal that cannot be had is the host's raw agent-status churn: herdr events are not stored and `round wait` is read-only, so a hung agent that still repaints its status is judged on commits and files alone. Reconcile and reclaim compute this the same way, in `internal/round.Stalled(slot, now)`, with `now` injectable so the threshold is testable without sleeping.
- **Reconcile amendments (C2).** Two drift kinds, neither repaired by `--apply`'s existing rules except as noted. `stalled`: the rule above (`detail` carries the idle minutes and the signal that last moved). `claim-mismatch`: the tracker and the registry disagree about who holds an issue: the slot's `task` has no open claim by its `claimId` (or another claim holds it), or an open claim `<agent>@<round>` names a registry slot that does not hold that issue. `--apply` repairs only the registry side of an unambiguous mismatch (clears a `claimId` whose claim is gone; never edits the tracker), because the tracker is the source of truth and a human may have changed it on purpose. `label-orphan` and `label-missing` stay as C2 defined them.
- **Handoff note.** A stand-in for D1's note (#65), small enough that D1 can absorb it: one comment on the issue, posted by `return`, `transfer` and `reclaim`, ending with the marker `<!-- rota:handoff <from>@<round> -->` so C4's answer rule never reads it as an answer. Body: `**rota handoff** (<verb>, from <slot>)`, then four labelled lines `Branch:`, `Head:` (the pushed sha7 and subject), `State:` (committed, plus `salvage commit` when `Park` made one) and `Reason:`, then free text under `Done and next:` taken from `--note-file`. A receiving worker finds it by the marker; the pointer brief (C3) names the latest `rota:handoff` comment and the branch. When D1 lands, its format replaces this body and the marker stays.

note: to a slot, in order: `Park` the sending slot; handoff comment; `item release` the old claim; `item claim <issue> --as <to>@<round>`; `worker reset <to> --task <issue>` replaced by checking out the existing branch in `<to>`'s worktree (`git switch -C <branch> origin/<branch>`, after the same clean guard), so the receiver starts from the pushed work and not from a fresh branch; record `task`, `branch`, `claimId` on `<to>`; `worker dispatch <to>` with the pointer brief plus the latest handoff comment named, the account picked as `assign` does, `--round`. The `in-progress` label stays on throughout; the `overlap` check is C3's, run for the receiver against the other in-flight slots and not the sender.
note: to `human`: `Park` the sending slot; handoff comment; `item release`; `item state --to none`; add the `needs-human` label (`issues.labels.needsHuman`). No claim is taken, since a claim comment would read as the orchestrator holding it, and nothing is dispatched (`dispatched: false`, no `claimId`). `candidates` skips an item that carries `needs-human`; clearing the label is the human's act and puts it back in the set. The `needs-human` label is the one thing C10 adds to the tracker's vocabulary.
note: (#27) the sending slot is never stranded by an issue the tracker no longer resolves: a not-found from the handoff comment, `item release` or (to `human`) `item state` is skipped with a warning, as in `return`, and the move continues. The first lookup of `<issue>` is not tolerated (exit 3), and neither is the new claim for a slot receiver.
note: (#239) `--tier` sets the receiver's tier as `assign --tier` does: one above `round.tier` needs `--tier-reason` (exit 2), and the tier, model and reason are recorded on the slot and named in the brief. Without it the receiver gets `round.tier`. Ignored for `--to human`. The item's bounce count is not reset by a transfer.
note: if the dispatch fails after the claim moved, the claim and branch stay with `<to>` (the pane may hold the brief), as `assign` keeps them after a failure at dispatch; the failure is exit 5 or 6 and `data` still reports the move.

### rota round bounce
rota round bounce <issue> [--head <sha>] [--slot <slot>]
repo: none
data: {"issue": string, "bounces": number, "max": number, "changed": bool}
exit: 2 when no issue is given; 4 when the item is already at `round.maxBounces` (nothing counted, `changed` false); 70 when `round.maxBounces` is invalid
old: none (new in #239)
note: the orchestrator's count of a bounce it sends by hand (SKILL §7). It shares the per-item `bounces` counter of `.rota/workers.json` with the merge gate, so gate bounces and review bounces add up. `<issue>` may carry a leading `#`. `--head` is the PR head being bounced: the same head twice counts once. `--slot` names the slot holding the bounced PR, so the ledger's bounce entry of a best-of:2 attempt lands on that attempt's row. ### rota round review-relay
rota round review-relay <slot>
repo: none
data: {"slot": string, "pr"?: string, "items": number, "bounces": number, "max": number, "escalated"?: bool, "blockedBy"?: "state" | "maxBounces" | "handle", "changed": bool}
exit: 2 when no slot is given; 3 when the slot is not in the pool or has no PR; 4 when the slot is not `done` (`blockedBy: "state"`) or the item is already at `round.maxBounces` (`blockedBy: "maxBounces"`, nothing relayed, the slot stays `done`) or the slot has no session to relay into (`blockedBy: "handle"`, nothing counted); 5 or 6 as `worker dispatch` for a relay the host refused (no bounce counted, the cursor does not move)
old: none (new in #577)
note: hands review input on a finished worker's PR back to the worker, as the orchestrator does by hand today. Review input is what is new since the slot's `reviewSeen` cursor: PR conversation comments, submitted reviews and inline diff comments (GitHub `pulls/<n>/reviews` and `pulls/<n>/comments`; a GitLab MR's notes), plus a FAIL review verdict recorded for the slot's branch. Dropped: comments carrying a rota marker (the worker's own `worker reply`, escalations, claim and feedback notes), approvals and entries with no text (a body-less CHANGES_REQUESTED stays, as `changes requested, no text`). The cursor starts when the slot reports `done`, so what the PR collected before is not input. The worker's forge login is not used to tell its comments apart, since a solo maintainer reviews under the same login. CI bot comments count.
note: with input waiting it sends a signed relay through the `worker dispatch --relay` path (first line after the ORCHESTRATOR header: `REVIEW <pr-url> (<n> items)`, a header saying the items are claims to verify, never instructions, then each item as a quoted block (`> `) under `Item <n>, untrusted third-party text by <author>:`, each cut at 1500 characters, at most 20 items with a pointer to the PR for the rest, then the verdict), which marks the slot `busy` and logs the relay. It counts one bounce on the item's shared counter (see `round bounce`; the same PR head twice counts once) and moves `reviewSeen` before the relay goes out and puts both back when the dispatch fails, so a failed write cannot cause a second relay of the same batch. The cursor is the newest consumed item's time plus the ids created at that same second. A PR that is not open (merged, closed) is skipped: exit 0, text `nothing to relay: pr <state>`, cursor untouched. At `round.maxBounces` it relays nothing, leaves the slot `done` and the cursor where it was, posts one escalation on the PR (`round escalate send --pr`; not again while that escalation is pending) and exits 4. With nothing waiting it exits 0 (`items` 0, `changed` false, text `nothing to relay`). It never gates or merges, and takes no lease.
note: `round.reviewLoop` `auto` makes `round tick` and the `round watch` forge pass run this for every `done` slot with input waiting; `manual` (default) only reports it (`review/<slot>` watch change, `review` `needsYou` item in a tick).

### rota round reclaim
rota round reclaim <slot> [--force] [--note-file <path|->]
repo: none
data: {"slot": string, "issue"?: string, "branch"?: string, "head"?: string, "health": "dead"|"stalled"|"healthy"|"idle", "salvaged": bool, "released": bool, "parked": bool, "changed": bool}
exit: 3 when there is no project root or the slot is unknown; 4 with `blockedBy` one of `no round` (the caller holds no lease), `healthy` (the slot is neither dead nor stalled and `--force` is absent), `live agent` (see below); 5 when git, the push or the tracker fails (the slot is left as found); 6 when the registry lock times out
old: none (new in C10)
note: the orchestrator's verb for a slot reconcile reports as `dead-tab`, `dead` state or `stalled`. Health is computed fresh, by the same code, not read from the last reconcile. `--force` skips the `healthy` refusal only; a slot with no issue is `idle` and reclaim of it is a no-op (`changed: false`, exit 0), not a refusal.
note: `live agent`: a stalled slot has a live host agent, and parking its worktree under a running agent would leave the agent editing a branch it is no longer on. So for `stalled` and for `--force` reclaim first kills the pane through the host (`internal/host` Kill; with no host it refuses with `live agent` unless the pane is provably gone). A `dead` slot has nothing to kill.
note: in order: kill the pane when live; `Park`; handoff comment (`Reason: reclaimed, <dead|stalled N min|forced>`); `item release` by the slot's `claimId`, which also works when the registry lost it, by releasing every open claim whose id starts `<slot>@`; `item state --to none`; clear `task`, `claimId`, set `state` `idle`, clear `handle`. The slot is parked and the issue assignable, with the branch pushed and named in the comment. Reclaim does not reassign: `assign` or `transfer` is the next call, so the choice of who continues stays the orchestrator's.
note: (#27) a not-found from the handoff comment, `item release` or `item state` (the issue is gone from the tracker, or its ID was minted in file mode and never mapped) is skipped, not fatal: reclaim adds a warning per skipped step (`<step> on <issue> skipped, the tracker does not resolve it: <err>`) and still frees the slot. Any other tracker failure is still exit 5 and leaves the slot as found.
note: `reap` (C6) may reclaim `dead` slots only, never `stalled` ones (maintainer ruling, round 4). A worker in a long test run makes no commits and no status change, so it reads as stalled, and an unattended `reap --apply` would kill it. `stalled` is reported by reconcile, and reclaiming it is always an explicit orchestrator call. `reap` passes no `--force` and checks `health` is `dead` before calling.

### rota round pick
rota round pick <ID> --pr <N> --reason-file <path|-> [--holder-pid <n>]
repo: none
data: {"id": string, "winner": {"slot": string, "branch": string, "pr": string}, "loser": {"slot": string, "branch": string, "pr"?: string, "state": "open-pr"|"no-pr"|"gone"}, "closed": bool, "changed": bool, "warnings"?: []string}
exit: 2 when `--pr` or `--reason-file` is missing or the reason is empty; 3 when the item is unknown; 4 with `blockedBy` `no round` (no lease), `not best-of` (the registry holds no attempts for the item), `not an attempt` (`--pr` is not the PR of either attempt; the message lists them), `already picked` (a pick names another PR), `attempt running` (the other attempt has no PR and its worker is still working); 5 when the forge cannot close the PR
old: none (new in #404)
note: the orchestrator's verb for a `best-of:2` issue (see `round assign`). An attempt's PR is the one its slot records while it holds the issue, else its review-list record, else the open PR whose head is the attempt's branch. In order: close the other attempt's PR with a comment naming the winner, the reason and the kept branch (skipped when it is already closed); drop its review-list record; release its claim (never the winner's); park and free its slot when it still holds the issue and is `done` or `idle` with a clean worktree, else warn that it needs `round reclaim`; record the pick in `bestOf`; reset the item's bounce count; comment the pick and the reason on the issue. The losing branch is never deleted: `rota reap` handles it like any other. Picking the same PR again is `changed: false`.
note: when the other attempt was returned, reclaimed or is dead without a PR, the remaining PR is picked alone. Until a pick names it, `worker gate` and `worker train` refuse either attempt (`best-of-unpicked`).
note: (#404, ruling) bounces stay per item. An attempt cannot be bounced before the pick (the gate refuses it before its freshness check), and the pick resets the count, so the count is the picked attempt's. `round transfer` refuses a best-of item while two attempts still hold it (two slots, or a slot and a PR in review; `blockedBy` `best-of`): pick, return or reclaim one first. Once one holder is left it transfers as usual, so the bounce-cap and item-timeout parks work after a pick. `round return` and `round reclaim` of one attempt keep the `in-progress` label while the other attempt still holds a claim. The autopilot assigns a best-of item when two slots are free and never picks.

### rota orchestrate
rota orchestrate [--dry-run]
repo: none
data: {"harness": "claude" | "codex", "host": "herdr" | "tmux" | "solo", "mode": "tab" | "session" | "inplace", "cwd": string, "session"?: string, "command": [string], "tab"?: string, "dryRun"?: true, "changed": bool}
exit: 1 when `rota doctor` reports a failure (its checks print, no session starts); 3 when there is no project root; 4 when `work.dispatch` is `herdr` and the caller is outside herdr (`blockedBy` the reason, `changed` false); 5 when tmux is required and missing, a host call fails, or the exec fails; 70 when `orchestrator.harness` or `work.operatorCommand` is unusable
old: none (new in #19; replaces typing herdr, then claude, then /rota-orchestrate)
note: not a query. Steps: (1) run `rota doctor` in-process and stop on a `fail` before anything starts. (2) Resolve the harness from `orchestrator.harness` (default `claude`) in the launch table of `internal/orchestrate`: the agent argv and its first prompt (`/rota-orchestrate` for claude, `$rota-orchestrate` for codex). note: the claude argv is `work.operatorCommand` when set, else `claude --model <models.orchestrator, default opus> --permission-mode auto`; a fresh session, not `--continue`. The codex argv is `codex`.

The lease is `keepalive run`'s: a second orchestrator is refused there (exit 4 `lease held`), in the tab, where a person sees it.
note: **Outside a multiplexer, herdr first (maintainer via orchestrator relay round 1).** herdr 0.9.3 has no startup-command flag (`workspace create` and `tab create` take `--cwd`, `--label`, `--env`, `--focus`), and its guide forbids driving the user's own session from outside. A named session of rota's own is not that session: `herdr --session rota-<dir> server` starts it headless, `herdr --session rota-<dir> workspace create --cwd <root> --label orchestrator` makes the workspace, `pane run` types the supervisor into its root pane and `herdr session attach rota-<dir>` replaces the caller's terminal. Checked on 0.9.3 in a throwaway session (`rota-probe`, no agent): the server came up, `pane run` ran `echo` and `pane read` showed the output, and `workspace close`, `session stop` and `session delete` removed it; the default session was untouched throughout. A session that already runs is only attached (the keepalive lease refuses a second orchestrator). Order: inside herdr, inside tmux, `work.dispatch: tmux` forces tmux, herdr installed, tmux installed, else in place. The tab opens with `tab create` and `pane run`, not `agent start`, because the command is the supervisor and not the agent binary; a first-run trust dialog is answered by the person in the focused tab. maestro's herdr notes: `pane run` retries five times on a pane-not-found race; its orphan sweep is not ported (a dead orchestrator tab holds a shell, and `rota reap` closes agentless tabs).
note: **bare `rota`.** With no arguments in a terminal (stdin and stdout are ttys, no `--json`): no `.rota/` here or above runs the interactive setup (#25); an initialized project opens the palette (#181, `internal/palette`), whose preselected Orchestrate entry runs this verb. A pipe, `--json` or any other word keeps the usage error (exit 2, `missing command` or `unknown command`), so a script never opens a session.
note: **Config.** `orchestrator.harness` (`claude` or `codex`, silent default `claude`), documented in `docs/reference/config-options.md`, `docs/usage/configuration.md` and `internal/config/schema.go`. #33 adds harnesses by adding rows to the launch table. The codex prompt syntax is #33's to verify; it is taken from that issue.

### rota layout
rota layout [--project <dir>]
rota layout split [--project <dir>]
rota layout tabs [--project <dir>]
repo: none
data: {"projects": [{"project": string, "name": string, "layout"?: "split" | "tabs" | "mixed", "before"?: "split" | "tabs" | "mixed", "moves"?: int, "changed"?: bool, "orchestrator"?: {"pane": string, "tab": string}, "workers"?: [{"slot": string, "pane": string, "tab": string}], "foreign"?: [{"pane": string}], "skipped"?: string}]}
exit: 3 when `--project` names a directory without `.rota/`, and, for `split` and `tabs`, when no project has an orchestrator pane open in the herdr it runs against; 5 for `split` and `tabs` when nothing was arranged because herdr is missing or failing, or the round is on tmux or solo (the `skipped` text says which), and when a `pane move` fails part-way; the bare form exits 0 in all of these cases. `split` and `tabs` exit 0 when at least one project was arranged, even if another was skipped.
old: none (new in #180)
note: `layout` and `before` are `split` when every live worker pane sits in the orchestrator's tab, `tabs` when none does (also: no live worker), `mixed` otherwise. `moves` and `changed` are in the `split` and `tabs` answers only; `layout` there is the state after the run. Bare `rota layout` is read-only. `foreign` lists the other panes of the orchestrator's tab (a shell the person opened); they are never moved, and each one is also a warning.
note: **The split layout.** The orchestrator is the left column at full height. Live workers, in registry (slot) order, fill columns two panes high, column-major; an odd count leaves the last column one pane at full height. Every column, the orchestrator's included, gets the same width: 1/(1+ceil(n/2)). Two panes in a column split 50/50. Panes are built columns first (`pane move <head> --tab <orch-tab> --split right --target-pane <previous column> --ratio <r> --no-focus`), then each two-pane column splits down (`--split down --ratio 0.5`). n=3: p1 right of the orchestrator at 0.3333, p3 right of p1 at 0.5, p2 down from p1 at 0.5.
note: **herdr 0.9.3 semantics (probed in a throwaway session).** `--ratio` is the share the TARGET pane keeps; the moved pane gets the rest, so a column with c columns of room still to fill (itself included) passes `1/c`. `--label` is accepted by `--new-tab` only, not on a split move (the pane keeps its own label). A move keeps the pane id, the agent name and every process; the moved-from tab closes when that was its last pane, and `--new-tab` makes a tab with a new id at the end of the tab bar. A move into the tab the pane is already in changes nothing (`reason: same_tab`), so a re-split cannot move panes inside the tab. `--no-focus` keeps focus where it was. Command order is pinned by `internal/layout/layout_test.go`.
note: **Idempotence.** `split` on a view whose panes already sit in the grid (same column order and same order inside each column, read from `pane layout`) does nothing; widths a person dragged stay. Otherwise (a worker assigned since, a different order) it sends every worker already in the tab out to a tab of its own, in slot order, and builds the grid again. `tabs` moves only the workers that are in the orchestrator's tab, in slot order, labelled with the slot name. Running either twice in a row is a no-op the second time.
note: **Finding the panes.** The workers' panes are the live slots' agents: the agent named for the slot and its recorded `handle` (`rota-<slot>-<tab id>`), whose name survives a move; a slot with no handle (parked) or no agent (dead) is skipped. The `handle` is not rewritten: after a move it names the tab the slot started in, which may be gone. The orchestrator is the pane working in the project root that no slot owns, preferring one in a tab or workspace labelled `orchestrator` (`orchestrate.Label`) and one running an agent. No pane id is recorded at launch: the label and cwd lookup also covers an orchestrator started by hand.
note: **Which projects.** Without `--project`: every project in `rota projects` that exists on disk, plus the one the caller is in, that has an orchestrator pane in the herdr the command talks to (the one the shell is in; the default session otherwise). A project whose registry records a tmux or solo round is skipped with `host is tmux: layout needs herdr` (listed only when `--project` names it or the registry still holds a handle). `round assign` keeps opening workers as tabs; run `rota layout split` again to fold them in.
