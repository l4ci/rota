## A7: workers, hosts, accounts

**Corrupt registry (#712).** Every verb that writes `.rota/workers.json` refuses when the file exists but does not parse as a JSON object (exit 5, `fix or remove it, rota will not overwrite it`), before it changes anything, instead of starting from an empty pool. `worker pool reap` below states the same for its own exit list.

### rota worker pool init
rota worker pool init --slots <n> [--base <branch>] [--session <name>]
repo: none
data: {"session": string, "base": string, "slots": []slot, "changed": bool}
exit: 1 when `round.envSetup` exits non-zero; 2 when --slots is missing or not a positive integer; 3 when the base branch cannot be resolved or does not exist, or a registered slot's worktree belongs to another repository; 5 when git fails
old: hv-worker-pool init --slots <n> [--base <branch>] [--session <name>]
shim: runs the old helper, then reads `.rota/workers.json` for `data`; `changed` is true when this invocation's registry updates altered the registry content (a no-op or same-value write, or a write by another process, does not count).
note: --base defaults to the current branch and --session to `rota`, as the old helper does.
note: `warnings` gets one entry when `.worktrees/` is not gitignored, and one per registered slot outside `.worktrees/` that is kept in place (old `warning:` and `note:` stderr lines).
note: `round.envSetup` (#398, silent default empty = no-op) is a shell command run in each slot worktree after the slot is registered, with that worktree as cwd. It runs when the hash of the command and the root lockfiles (package-lock.json, pnpm-lock.yaml, yarn.lock, uv.lock, poetry.lock, requirements*.txt, go.sum) differs from `rota-env-setup` in the worktree's git dir (so: on a new slot, and on an existing one whose lockfiles or command changed), and writes that hash only after a zero exit. A non-zero exit stops the verb at that slot with exit 1 and a message naming the slot, the exit code, the command and its output; later slots are not set up, and the failed slot stays registered so the next `pool init` retries it.

note: `round.sharedDirs` (#1832, silent default empty = no-op) is a list of repo-relative directories symlinked from the main checkout into each slot worktree after the slot is registered, and listed in the repo's `info/exclude`. It is all or nothing per slot: when a lockfile (the `round.envSetup` ones plus `Cargo.lock` and `bun.lockb`) differs from main's, a directory is missing in main, a path leaves the repo or the slot holds a real directory, no link is made, the links rota made are removed and `round.envSetup` runs instead; when every directory is shared, `envSetup` does not run. `data` gets `shared` (only when non-empty): one `{slot, dir, action, reason?}` per slot and directory, `action` one of `linked`, `kept`, `unlinked`, `skipped`.

note: (#576) each slot also reserves a port block: `pool init` records `portBase` on the slot, the lowest `round.portBase` (default 20000) plus a multiple of `round.portBlock` (default 100) that no other registered slot holds, picked under the registry lock. A slot that has one keeps it; `pool reap` frees it with the slot. `round.envSetup` runs with `ROTA_SLOT`, `ROTA_PORT_BASE`, `ROTA_PORT_BLOCK` (the width the slot holds) and `ROTA_DB_SUFFIX` (`_` plus the slot name, non-alphanumerics as `_`) exported ahead of the command. `rota doctor` adds a `ports` check (`warn`, never `fail`): for each live slot with a block it reads the TCP listeners (`ss -ltnpH`, else `lsof -nP -iTCP -sTCP:LISTEN -Fpn`) and warns on one inside the block whose process working directory is outside the slot's worktree or unreadable. No `ss` and no `lsof`, or no live slot, adds no line.

### rota worker reset
rota worker reset <slot> [--task <id>] [--check-only]
repo: none
data: {"slot": string, "clean": bool, "retained": bool, "branch"?: string, "base"?: string, "sha"?: string, "dirty"?: []string, "unmerged"?: []string, "changed": bool}
exit: 1 with --check-only when the slot holds work (`clean: false`); 3 when the pool, the slot, its worktree or its base is missing; 4 without --check-only when the slot holds work (uncommitted changes or commits not on the slot's base) and the reset is refused (`blockedBy: "slot holds work"`); 5 when git cannot cut the new branch
old: hv-worker-reset --slot <slot> [--task <id>] [--check-only]
shim: `clean` is true when the old helper exits 0 without a `retry:` line. `retained` is true on the `retry: <slot> keeps its work ...` line (same task on its own branch; exit 0, nothing reset). `branch`, `base`, `sha` come from `reset: <slot> on <branch> at <sha7>` and are absent with --check-only and on retention. `dirty` and `unmerged` come from the `REFUSED` stderr block, and the failure `data` carries them on exit 1 and on exit 4 (what blocked the reset). `changed` is true only after a real reset. Old exit 3 is split by its message: work held becomes 1 or 4, the rest stay 3 or become 5.
note: `--check-only` makes this a check verb (1); without it the verb mutates and declines with 4 (rule 7).
note: each `dirty` entry is one `git status --porcelain` line (`?? scratch.txt`); each `unmerged` entry is `<sha7> <subject>` for a commit not on the slot's base.

### rota worker dispatch
rota worker dispatch <slot> --body-file <path|-> [--task <id>] [--relay [--review-through <rfc3339>]] [--round <n>] [--boot-timeout <s>] [--kind <claude|codex|opencode>]
repo: none
data: {"slot": string, "handle": string, "task"?: string, "round"?: number, "relay": bool, "kind": string, "changed": bool}
exit: 2 when --body-file is missing, --round is not a number, --review-through is not an RFC 3339 time, is in the future or comes without --relay, --kind is not a kind, or the launch command (round.commands.claude, or round.commands.codex for codex) cannot be parsed; 3 when the pool, the slot, its worktree or the body file is missing, or `--review-through` finds the slot without a PR, or --relay finds no running session; 4 when the reset guard finds the slot holding work (`blockedBy: "reset guard"`), the launch command carries a resume flag (-c, -r, --continue, --resume, or codex's `resume`/`fork` subcommands; `blockedBy: "resume flag"`), or `codex --help` lacks a flag the launch line uses (`blockedBy: "codex flags"`, E1); 5 when the host is unavailable or not usable (herdr outside a pane, a launch command whose binary is not the kind's under herdr, a codex worker under tmux, codex not on PATH, the slot's Codex home not logged in, an unrecognised startup dialog), the old session will not close, a dialog refused input (`blockedBy: "dialog"`, the message naming the dialog's first line; inspect the pane before resending), or the slot's prompt line holds a human draft (nothing was typed; resend once it is submitted or cleared); 6 when the brief was never submitted (safe to resend)
old: hv-worker-dispatch --slot <slot> --brief-file <path> [--task <id>] [--relay] [--round <n>] [--boot-timeout <s>]
shim: `--body-file` is passed as the old `--brief-file`; `-` is spooled to a temp file first. `data` is built from the `dispatched: <slot> (<handle>)` line plus the flags. `changed` is always true on success. Old exit 3 is split by its message (slot holds work becomes 4, host failure becomes 5, missing pool/slot/session stays 3); old exit 4 (brief never submitted) becomes 6 and old exit 5 (dialog open) becomes 5.
note: (#1827) on a support machine (`round.role` support, `round.support` set) a `--relay` dispatch also posts the brief on the slot's issue as a `relay` comment (`<!-- rota:relay round=<n> -->`), because the main gate cannot read this machine's `relays`; a failed post is a warning, the relay was already sent. Main keeps its local log only.
note: (#1866) `--relay --review-through <time>` marks a hand-sent review relay as consumed: once the relay is sent, the slot's `reviewSeen` cursor moves past the review input of its PR dated before `<time>` (the moment the orchestrator read the comments, truncated to the second; the second it falls in stays pending), so `round watch` stops reporting `review/<slot>` for comments the worker already has. Input dated at or after it, and undated input (a zero-dated item or verdict), stays pending and is reported once. It counts no bounce (that is `round review-relay`'s) and, without the flag, a relay never touches the cursor, whatever its text. A failure to move the cursor is a warning: the relay was sent.
note: `<slot>` replaces the old `--slot`. Fresh-session dispatch is the default; `--relay` injects into the running session and appends to `relays`.
note: (#1800) `--task` matching the slot’s assigned issue rebuilds the full assignment brief from the issue and binding (contract pointer, issue sections, attempt and `ROTA-DONE` line); `--body-file` is appended as notes. It preserves the assigned `<agent>/<issue>-<slug>` branch and resolves the issue’s `model:` label before launching. A standalone slot still sends the file as its whole brief. An unacknowledged task sets `unsent: true` and stays idle; polling reports blocked until a successful dispatch clears it. A successful herdr RPC at Codex’s empty startup prompt is not acknowledgement.
note: (#1800) the reset guard fetches an existing `origin/<base>` before comparing commits. When the local base is behind it, the comparison and fresh branch use that fetched ref; without an origin the local base remains the comparison. A failed fetch refuses before the old session is killed.
note: (#820) `unverifiable`: the host could not be asked (`host-unreachable`: no herdr server, a socket error, a binary that cannot run), the slot's tab or pane handle no longer exists (`stale-handle`: herdr `tab_not_found` or `pane_not_found`, e.g. after a layout split) or the pane read failed while the host answered (`pane-unreadable`, through the optional `host.PaneReader`, so a failed read is not an empty pane; a native `working` or `blocked` status still wins over it). tmux has no native status: a capture that fails with `can't find window`, `can't find pane`, `can't find session`, `no server running` or `error connecting to` is `host.ErrPaneGone` and reads `dead`; any other failed capture is `pane-unreadable`. The reason is the row's `evidence`. Only herdr's `agent_not_found` (host `Status` `gone`) is positive proof of exit and stays `dead`: absence of a session proves death, absence of an answer does not. A printed sentinel still outranks it, as it outranks every host state, and a recorded worker event (`worker.Decide`) still decides over it. The registry keeps the reason in the slot's `reason` field (an unchanged reason is not rewritten) so `round status` (`hostState: unverifiable` and `evidence`, JSON for this state only; the text column reads `unverifiable:<reason>`) and `round reclaim` can show it; `round wait` writes it and keeps waiting, and writes the `busy` row that ends it.
note: (#511) on herdr, task and relay dispatch read the agent's `state_change_seq` (`herdr agent get`) just before the brief goes out and record it as the slot's `turnSeq` in `.rota/workers.json` (an optional number). A turn finished after the brief carries a `completion_seq` past it, which `worker poll` and `round wait` read as finished. The baseline is the state number, not `completion_seq`: herdr omits `completion_seq` while the agent works and after startup, so a fresh session has none to record. A failing read, a herdr without the field, or tmux records none and clears an old one.
note: (#391) before typing, both hosts read the prompt line and wait about 4s (3 reads, 2s apart) for a human draft to clear; if text that is not rota's own unsent brief or a placeholder is still there, dispatch exits 5 (`unavailable`, same as a dialog) and types nothing. A refused relay is not logged in `relays`. The read keeps styling (`herdr agent read --format ansi`, `tmux capture-pane -e`) and drops faint (SGR 2) and gray-foreground runs first, so Claude Code's dim ghost suggestion is not a draft; if the styled read fails, plain text is used.
note: "never submitted" (safe to resend) and "dialog open" (inspect first) get distinct `error.code` values. The conventions fix `error.code` to the exit-table name, so per-verb codes are not allowed, and the verb uses two exits instead: `retry` (6) for a brief that was never submitted, `unavailable` (5) for an open dialog. The message and hint still say which.
note: (#576) a task dispatch reserves the slot's port block if it has none, then starts the session with `ROTA_SLOT`, `ROTA_PORT_BASE`, `ROTA_PORT_BLOCK` and `ROTA_DB_SUFFIX` in its environment: herdr passes them as `--env KEY=VALUE` on `tab create` (verified against `herdr tab create --help`, which lists `--env <KEY=VALUE>`), tmux prefixes them to the launch line typed into the window. A relay changes nothing.
note: (#1757, #1777, #1791) account dirs are expanded once, before the launch env is built: a leading `~` or `~/` in `round.accounts[].dir`, whatever the entry's `kind`, becomes the home dir (#1824: one expansion for all kinds; the old `round.codexAccounts` and `round.opencodeAccounts` keys are folded into `round.accounts` by `rota migrate config`), and the path is cleaned (`$HOME` is not expanded). `CLAUDE_CONFIG_DIR`, `CODEX_HOME` and `OPENCODE_CONFIG_DIR` carry the absolute path, and a slot whose cached `configDir` still holds `~` launches under the expanded one. `rota config check` and `rota doctor` refuse a dir that is neither absolute nor `~`-prefixed ("dir must be absolute or start with ~"). On herdr, a startup screen is one of: the folder-trust or bypass dialog (answered), Claude Code's first-run theme picker ("Choose the text style", `Dark mode` / `Light mode` rows; answered with Enter, and not read as a human draft), or a booted session idle at its empty prompt (the banner plus the `❯ Try "` hint or the status line; treated as booted, so the brief is pasted). Anything else is the unrecognised startup dialog (exit 5). A spawn that fails with its tab still open records that tab as the slot's `handle`, so the retry's kill reaps it and no second tab opens beside it.
note: (#1029) on herdr, a just-created tab's shell may not be ready when `agent start` runs and herdr answers `agent_pane_busy`; the start is polled inside the boot timeout, in the same tab, instead of failing the dispatch.
note: Claude Code's autocompact picker (`Want to autocompact at ...`, footer `esc not now`) is dismissed once with Escape before the send, on both hosts; if it is still open, or any other dialog is, the dispatch is refused as above and, for a relay, nothing is logged in `relays`.
note: (#824) on herdr with `round.herdrGroupSlots` (default `true`) a task dispatch opens the slot's worktree as a workspace linked to the orchestrator's instead of a tab in it, and records the workspace as `workspaceId` on the slot; it is closed when the slot's session is killed, and `rota layout` moves the pane out and back. A herdr that cannot link (`unknown_method` or an unknown flag) leaves the slot a plain tab with one warning and no `workspaceId`; any other error fails the dispatch. tmux has no workspaces and records none.
note: (#1792) a task dispatch refuses (exit 4, `blockedBy: "limited"`) before anything is killed or marked when the slot's recorded `round.accounts` account is cooling down (its usage meter reads a weekly or session window at 100% with a future reset, the verdict the quota fallback uses); the message names the account and its reset. A slot with no recorded account, one whose `configDir` is not in `round.accounts`, a harness with no config-dir account and a run with no meter reader pass.
note: `--kind` (E1, #68) defaults to the slot's recorded `kind`, else `claude`; a relay ignores it. A codex dispatch is specified under "E: Codex workers". hv-codex-verify is not absorbed: #158 retired it.

### rota worker inbox
rota worker inbox <slot> [--ack [--upto <seq>]]
repo: none
data: {"slot": string, "mail": [{"seq": number, "round": number, "ts": string, "kind": string, "text": string}], "unread": number, "acked": number, "changed": bool}
exit: 2 when no slot is given, or `--upto` is given without `--ack` or is negative; 3 when the slot is not in the pool
old: none (new in #964)
note: a worker reads the relays the orchestrator wrote to its durable inbox (`inbox` in `.rota/workers.json`: `{seq, round, ts, kind, text, read?}`). Today the only writer is `round review-relay`, which stores the same text it injects into the pane (`kind` `review`, `round` the one the relay is signed with). Without `--ack` the verb lists the unread mail and changes nothing (`unread` counts it, `changed` false). With `--ack` it lists the unread mail and marks it read in the same registry update (`acked` counts it, `unread` counts what is left). `--upto <seq>` bounds the ack to mail up to that sequence number: the unread listing prints the exact command with the highest `seq` it showed, so a relay posted after the listing stays unread and `worker done` still refuses it. Read mail stays in the file until the slot's next task dispatch or an unbind drops the inbox; a relay dispatch (no task) keeps it. It runs from the slot's worktree or the main checkout, like `worker done`. The text is the orchestrator's relay, so it carries the same untrusted-third-party framing as the pane copy and is cited as `orchestrator relay round <round>`. `worker done` refuses while mail is unread (exit 4, `data.unread`).

rota worker reply <slot> --body-file <path|->
repo: none
data: {"slot": string, "pr": string, "commentId": string, "url": string, "changed": true}
exit: 2 when `--body-file` is missing or the body is empty; 3 when the slot is not in the pool or has no PR; 5 or 6 as the tracker verbs (forge unavailable, rate limited)
old: none (new in #577)
note: a worker answers a reviewer on its slot's PR after a `REVIEW` relay (see `round review-relay`). ### rota worker send
rota worker send <slot> (--blocked <question> | --question <text> | --heartbeat)
repo: none
data: {"slot": string, "event": "blocked" | "question" | "heartbeat", "state": string, "previous": string, "seq": number, "changed": bool}
exit: 2 when none or more than one of the three flags is given, the text is empty or the slot is missing; 3 when the slot is not in the pool; 5 when `.rota/workers.json` cannot be read or written (a corrupt registry fails closed, nothing is rewritten)
old: none (new in #819)
note: a worker's typed event on its own slot, written through `round.ReportSlot` on every host (herdr, tmux, solo): a plain `round report` stays solo-only because it would race the pane poll, an event does not, since `round wait` and `worker poll` read it before the pane. It runs from the slot's worktree or the main checkout, like `worker done`. The slot record gains `event` `{"seq": number, "kind": "blocked" | "question" | "done" | "review-reply", "ts": string, "body"?: string, "notified"?: bool}`, the latest event only, and `eventSeq`, the slot's monotonic event id (it survives a cleared event, so an acknowledged event never shares an id with the next).
note: `--blocked` and `--question` move the slot to `blocked`, clear `seen` (so `round wait` returns it) and append a `blocked` ledger row whose `detail` carries `event`, `body` and `seq` (the slot record's event id); every event is a row, not only the first. `--heartbeat` stamps `heartbeatAt` and nothing else: the standing event, state, `activeAt`, `seen` and the ledger are untouched, so a question not yet answered is not lost. `round reconcile` reads the later of `activeAt` and `heartbeatAt` as the stall clock. It proves the worker alive, not that it progressed. `worker done` and `worker reply` record `done` and `review-reply` events through the same writer; the reply also appends a `review-reply` ledger row (`detail.seq`), does not move the review cursor and does not change the slot's state: a reply posted mid-fix leaves a busy slot busy. A task dispatch or a relay clears `event`: a brief answers whatever the worker last sent.
note: the sentinel stays the fallback for a harness that cannot run the verb, and the worker still prints `ROTA-BLOCKED` or `ROTA-DONE` last. `round status` shows the standing event of a slot as `event` and uses its body as the slot's evidence.

### rota worker adopt
rota worker adopt <branch|worktree-path> --issue <id> [--name <slot>] [--pr <url>] [--accept-overlap]
repo: none
data: {"slot": string, "branch": string, "worktree"?: string, "issue": string, "pr"?: string, "overlaps"?: []overlap, "changed": bool}; on exit 4 `blockedBy` plus, for `overlap`, `checks` and `overlaps`, and `changed` false
exit: 2 when `--issue` or the argument is missing, the path is not a worktree of this repo, or the branch does not exist; 3 when there is no project root, the issue is not found, or the round config is invalid (the message names the key); 4 with `blockedBy: "overlap"` (a blocking file clash with an in-flight slot or a queued PR), `"registered"` (a slot already holds the branch) or `"held"` (a slot already holds the issue). Also 3 when `git.baseBranch` is set and does not resolve (the message names the key; never replaced by a conventional name).
old: none (new in #580)
note: registers work another tool started (a Codex managed worktree, a Claude Code agent-team branch, a cloud session's branch) as a slot of `kind: external`: no `handle`, no session, `task` the issue, `pr` when given. Rota never launches, relays to or reads a pane for it. The name is `--name`, else the next free `ext-<n>`.
note: the argument is a local branch or a path from `git worktree list` for this repo; the worktree is recorded when the path is one. It runs the same overlap pass as `round assign` (`round.sharedPaths` left out), and `--accept-overlap` skips only that check; `registered` and `held` cannot be overridden, so a `best-of:2` issue never gets a second holder.
note: an external slot refuses `worker dispatch` (task or relay) with exit 4, `blockedBy: "host"`, `external slot has no host`. `round status` shows it with `hostState` `external` and a `state` derived from the forge and git, since no pane reports one: `done` when its PR is open, `busy` when the branch is ahead of the base with no PR, `idle` otherwise, `unknown` while the forge cannot answer (or fails to read this slot's PR), `merged` once its PR merged. A merged slot stays listed, with a `merged-external` finding, until the gate or `round reconcile --apply` releases it. `worker poll` and `round wait` skip it, and `round reconcile` reports no `dead-tab`, `unclaimed-tab`, `stalled` or `item-timeout` for it.
note: `worker gate <slot>` and `worker train` gate its PR through the normal steps. The provenance step expects no relays and an Approvals line of `None`, as for an unregistered PR. After a pass the slot is released: the registry entry goes, the worktree and branch stay (rota did not create them). `worker gate --prune` also removes the worktree and branch, but leaves a dirty worktree, and with it the branch, in place. `round wind-down` parks no external slot; it reports each under `slots` with outcome `released` (its PR merged) or `open`, and `--prune` applies to the released ones.
note: without `--pr`, adopt records the open PR headed by the branch (`pr` in `data`), so `worker gate` and `worker train` read it at once and `round reconcile` reports no `pr-unrecorded`. When the forge cannot answer or no PR is open, the slot is registered with no PR and `round reconcile --apply` (or the next tick) records it later.
note: `round reconcile` adopts the same way for branches matching `round.adoptPattern` (see there).

### rota worker poll
rota worker poll [<slot>] [--settle <seconds>] [--lines <n>]
repo: none
data: {"slots": [{"name": string, "state": string, "evidence": string}], "changed": bool}
exit: 3 when the named slot is not in the pool, including when there is no registry; 5 when the host is unavailable
old: hv-worker-poll [--slot <slot>] [--settle <seconds>] [--lines <n>]
shim: wraps the old array as `slots` and lowercases `state`. `changed` is true when this invocation's registry updates altered its content (slot state or PR recorded); a no-op or same-value write, or a write by another process, does not count. A poll with no slot and no registry gives `{"slots": [], "changed": false}`. Old exit 3 (host failure) becomes 5.
env: `ROTA_TEST_POLL_FIXTURE=<file>` classifies the file as a static pane, no host, writes nothing (old `--fixture`). `ROTA_TEST_POLL_STATUS=<idle|working|blocked|done|unknown|gone>` sets the host status in fixture mode (old `--status`). `ROTA_TEST_POLL_KIND=<kind>` reads the file as a pane of that harness kind (default: no kind-specific wording). None is part of the CLI. In fixture mode the slot name is `<slot>` or `fixture`, and a missing fixture file exits 2. A failing step is `verify-failed`, exit 1, nothing landed: the message names the step, its issue line and the exit code or the missing line, then the last 20 lines of its output and the transcript path; the hint is `send <slot> back to fix it, then re-gate`. The full transcript is written to `.rota/qa-runs/behaviour/<branch>-<sha7>.txt` (gitignored), a `behaviour` verdict (PASS or FAIL, with `transcript`) is recorded for the branch at the PR head, and a gate with a PR on a forge posts a `### Behaviour run: PASS|FAIL at <sha7>` comment holding the transcript (cut to 200 lines or 20000 bytes, with a pointer to the file); a store or comment failure is a `Warnings` line (`BEHAVIOUR-COMMENT`), never a failed gate. `--check-only`, `--no-verify` and the merge train's landing steps run none of it; the train runs it itself, before landing (see `rota worker train`).
note: `merged-remotely` must never be retried (the PR is on origin but the local base diverged), which is why it is a verdict on exit 1 and not 6.
note: (#466) a PR whose body does not close the slot's issue is refused: exit 4, verdict `closes`, `blockedBy` `closes`, `changed` false, nothing landed. The issue is the one the slot holds (its task, else the number leading `<agent>/<issue>-<slug>`; a queued PR record's issue); a slot with no numeric issue or no recorded PR is not checked. A closing keyword is what the forge's `ClosedNumbers` reads (`Closes`, `Fixes`, `Resolves`, ...). An issue labelled `partial-slice` is exempt from this keyword check, but not from the next one: a PR the forge says closes a `partial-slice` issue (a closing keyword in prose counts) is refused the same way (exit 4, `blockedBy` `closes`, hint naming the keyword to drop), unless `--final-slice` marks it the last slice. `rota worker train` takes `--final-slice <member>`, repeatable, and exempts only the members it names, matched against the token the train was given (slot or PR). A forge that cannot report closing references, or fails the read, skips that check and notes `CLOSING-REFS-UNKNOWN` (once per member per train, not once per stage). A bundled slot's PR must close the lead and every member: each one the body leaves open is named in one refusal (a closed member is skipped, the lead never is), and after the merge each member the PR closes is closed or released as the lead is. Checked after provenance and before the verdict and approval gates, also under `--check-only`, so a train refuses the member (`culprit`). The hint shows the `Closes #N` line to add.

The issue is found as for `closes`; it is best-of when `.rota/workers.json` holds a `bestOf` record for it (written by `round assign`). The check runs before the fetch and the freshness check, so an unpicked attempt is never bounced, and under `--check-only` too, so `worker train` refuses such a member the same way. The picked PR gates normally; when it lands (gate pass or train member) the record is dropped. The autopilot does not hold this verdict for a person: it reports it once and the next tick after the pick gates the winner.
note: (#961) a slot whose worker reported `partial` or `failed` through `worker done --outcome` is refused: exit 4, verdict `outcome-open`, `blockedBy` `outcome-open`, `changed` false, nothing landed. A partial PR goes to review or relay, never straight to the gate: relay the slot to finish the rest, or `round transfer` it. Either is a new brief and clears the outcome; so does the worker's next `worker done --outcome done`. The check reads the slot, so a queued PR and an external PR are not checked, and it runs after the stale-attempt check and before freshness (the PR is never bounced), and under `--check-only` too, so `worker train` refuses such a member the same way. `done` and no outcome pass. Automatic relay on partial is out of scope: the orchestrator decides.
note: (#993) a PR with a commit stamped by a superseded attempt is refused: exit 4, verdict `stale-attempt`, `blockedBy` `stale-attempt`, `changed` false, nothing landed. Workers stamp each commit with a `Rota-Attempt: <id>` trailer (the brief and `worker-contract.md` say so). The gate reads the slot's `attempt` and `attemptBase` (the branch tip the attempt inherited, recorded at `round assign` and `round transfer` after fetching the branch, and only when work already existed: the branch itself, or for a handed-back issue the branch its latest handoff names; absent when the attempt minted the branch) and judges the commits reachable from the head but not from `attemptBase` nor from the gate's base ref (so commits merged in from the base, which keep other workers' trailers, are never judged): any trailer naming another attempt refuses. Commits up to `attemptBase` keep their earlier trailers, so a transfer, a failed dispatch or a resumed one never refuses the receiver's PR; the check reads the slot, never the queued PR record, so a queued PR (gated by number) and an external PR are not checked. Unstamped commits, a slot with no `attempt` (assigned before #958) and an `attemptBase` that is no longer an ancestor of the head pass (a rebase rewrote the inherited tip, so inherited trailers cannot be told from stale ones; this is fail-open on purpose): the gate refuses only what it can attribute. It runs after the refs are read and before the freshness check, so the PR is never bounced, and under `--check-only` too, so `worker train` refuses such a member the same way. The message names the commit and the stamped attempt, not the slot's current one.
note: (#1095) a second gate for a PR some other `worker gate` is running or queued on is refused before the land lock: exit 4, verdict `gate-running`, `blockedBy` `gate-running`, `changed` false, the message naming the other run's pid (a marker `gate-<pr>.pid` under the repo's rota state dir, replaced when its process is gone). A gate that did queue on the land lock (behind a train or a gate for another PR) re-reads the PR once it holds the lock; a PR that merged meanwhile exits 0 with verdict `already-merged` and changes nothing. The `no 'origin' remote` CHECK-BROKE now needs `git remote get-url origin` to exit 2; a git that cannot run, or fails otherwise, is reported as that.
note: (#1480) `round assign` and `round transfer` refuse (exit 4, `blockedBy` `gate-running`) while a gate or train holds the land lock, before they mark, claim or move anything: switching a slot worktree's branch under the gate trips its checkout guard. The probe is non-blocking. (#1917) The message names what the lock is held for (the PR, slot or train targets the gate was given, read from `land.holder` beside the lock) and says nothing was changed and it is safe to retry once the gate exits; `round watch` returns a `gate/land` change when the lock clears. `worker dispatch --relay` never moves a branch (it skips the reset), so it is not refused.
note: (#581) `worker gate` and `worker train` apply `ship.review`: the depth is resolved from the diff size against the base and the labels of the slot's issue (both read before it can pass), raised, never lowered, by a `Door: one-way` line in the PR body, a diff outside the issue's declared files and `paths` globs (see `rota review depth`); a bundled slot resolves each bundled issue on its own and the highest depth wins ( a failed diff or label read is `check-broke`, a malformed policy too), and the branch must have the verdicts that depth needs on record at its current head (a verdict recorded on another commit is stale and does not count; a failed `git rev-parse` of the head is `check-broke`): `full` a `review-spec` and a `review-quality`, `light` a `review-quality`, `none` none. A branch lacking them is exit 4, verdict `review-missing`, `blockedBy` `review-missing`, `changed` false. A recorded FAIL still refuses first as `verdict-blocked`. The depth is also noted as `REVIEW-DEPTH <slot> — <depth> (<why>)`.
note: (#1612) when `rota review depth` would resolve `cross` to a harness (see there; the author is the slot's harness; for a queued PR whose slot moved on, the harness of the latest `assign` ledger entry for its issue, else the label or default order) and the depth is not `none`, the gate and the train also need a `review-cross` record at the current head whose `harness` is that harness. Without one it is exit 4, verdict and `blockedBy` `review-missing`, naming `review-cross verdict from <harness> (<why>)` and hinting at the `review:none` label; a malformed `review.crossLabels`, or `round.harnesses` is `check-broke`. The issue read is fail-closed: while `round.harnesses` is set and `review.crossLabels` is non-empty, every gate and train step reads each bundled issue even when `ship.review` needs none, and a read error is `check-broke` (guessing could skip a Major PR's cross review). note: (#461) an empty `test.full` (read from the base before the merge, like the rest) is refused instead of merged unverified: exit 4, verdict `no-verify`, before the approval gate and the merge. A set `test.e2e` still counts as verification. `--no-verify` merges anyway, with `verifySkipped` true and a `NO-VERIFY` line on stderr. `test.fullWhere` `ci` does not read `test.full`, so it is not refused.
note: `merge-failed` covers both a forge CLI merge that fails and a local `git merge` that conflicts when no PR is recorded.
note: `test.fullWhere` `ci` (default `local`; any other value exits 70) moves the gate's verify before the merge: the merge result (base plus PR head, `--no-ff`) is built in a scratch worktree, pushed to `origin` as `rota/ci/<slot>`, and its forge checks polled (GitHub check suites, check runs and commit statuses, GitLab the jobs of the newest pipeline per ref by job name, plus the pipeline as `pipeline #<id> (<ref>)`); `test.ciChecks` (array, default `[]`, read from the base's config) lists the required check names, and an empty list is refused up front with exit 70 (hint names `test.ciChecks`), never a local fallback. Green needs every listed check finished with success and no check on the commit failed, held over two polls in a row. Unlisted pending checks do not block; an unlisted failure is red. A listed check that finished skipped or neutral counts as failed, and same-name checks must all succeed. A GitLab job failed with `allow_failure: true`, or `manual` and not run, counts as skipped. A merge that changes `.github/workflows/`, `.github/actions/`, `.gitlab-ci.yml` or `.gitlab/ci/` is `ci-config-changed` before any push (the pushed tree's CI definition would choose its own verification). `test.full` is not run locally. Verdicts: `pass`; `verify-failed` on the first red check (nothing landed, `changed` false, so the slot goes back); `verify-timeout` when a listed check is still pending or missing after `test.ciTimeoutMinutes` (default 60, 1-1440; names them); `ci-not-run` when a listed check never appears, decided once the start window (5 minutes) has passed and no check on the commit is pending (the project's CI must run on `rota/ci/**` pushes; the message names the missing checks). A missing `origin` is `check-broke`. Before merging, the base is re-checked (`base-moved`, nothing landed); after merging, the landed tree must equal the CI-verified tree (else `base-moved`). The `rota/ci/` branch is deleted after each run. `--no-verify` skips CI too. Env, in seconds: `ROTA_CI_POLL` (20), `ROTA_CI_START_WAIT` (300), `ROTA_CI_TIMEOUT` (overrides the config).
note: `sha` is always 7 characters, whatever `core.abbrev` says. It is present on `fresh` (the tip of the checked worker branch, `origin/<branch>` when a PR is recorded), on `pass` and `verify-failed` (the merge commit), and on `merged-remotely` (the merge commit on `origin/<base>`, or the verified head for a fast-forward merge).

### rota worker train

repo: none

note: targets are slot names or PRs as `rota worker gate` takes them. The train chooses the merge order itself (#583): each member's footprint is read with the overlap check's reader (`git diff --name-only <base>...<head>`); members sharing no path with another go first in PR-number order, then the rest by ascending changed-line count (ties by PR number). One `ORDER <pr>: no shared paths` or `ORDER <pr>: shares <n> paths with #x, #y` line per member goes to stderr before the scratch merge (also `data.order`). `--order 12,15,9` (PR numbers, `#N`, or slot names, comma-separated) replaces the computed order and must name every member exactly once, else exit 2; a conflict under a given order is `merge-failed` as before. Under the computed order a shared-path member that conflicts with the members before it ends the train with verdict `order`, exit 4, `blockedBy: "order"`: the message names the conflicting pair, nothing pushed (git's pairwise conflicts do not depend on merge order, so no other order is retried). Argument order is ignored unless `--order` is passed. A conflict of the first member with the base alone stays `merge-failed`. Each is first checked as `gate --check-only` does (freshness, PR identity, provenance, recorded verdict), in the order given; the first refusal ends the train with that member's verdict and `culprit` set, nothing merged.
note: (#1916) `--plan` previews the train: each member is checked as above, then every pair sharing a path is merge-tried with `git merge-tree --write-tree`. The plan lists the pairs that really conflict (`plan.conflicts`), the largest conflict-free subset in merge order (`plan.landable`), each remaining member with the landable members it conflicts with (`plan.orderBlocked`), and `plan.command`, a `rota worker train --base <b> --order <subset> <subset>` line that lands exactly that subset (with `--no-verify` appended, and `plan.noVerify` true, exactly when the train would refuse without `--no-verify`: `test.fullWhere` is `local` and both `test.full` and `test.e2e` are empty; passing `--no-verify` to the preview does not change that flag). The lists are `[]` when empty. `--plan` with `--order` exits 2, and a plan run leaves no `--request-id` receipt. It runs no tests, pushes nothing, asks no approval and takes no land lock; a member whose check fails ends it with that member's verdict as without `--plan`. Interactions among three or more members are not looked for. Without `--plan` an order conflict still ends the train with `order`.
note: the members are merged in the chosen order onto the base (`origin/<base>` when any has a PR) in a scratch worktree, and `test.full` run on that tree once. On a pass each member lands through the gate in order (forge merge pinned to its head, no second verify; a branch behind the base only because an earlier member landed is not `stale`). Before the first landing the base and every head must be what the scratch tree was built from, else `base-moved` and nothing lands. Before each later landing the base tree must equal the scratch tree after the members landed so far, and after the last one the landed tree must equal the verified tree; a mismatch (a foreign commit on the base, or a forge that merged differently than git) stops the train with `base-moved`, `landed` listing what already went in and the hint saying `landed k of n`. Under `test.fullWhere` `ci` the scratch tree is pushed as `rota/ci/train` and verified by CI instead of `test.full`, each bisect prefix likewise (one CI run per step); `ci-not-run`, `verify-timeout` and `ci-config-changed` (any member touching the CI definition) end the train with nothing landed. All members must be PRs or all slots without one: a mix is exit 2.
note: a member that conflicts in the scratch tree is `merge-failed` with `culprit` set. When verification fails the train bisects prefixes of the order and names the first member whose merge breaks the tree as `culprit` (`verify-failed`); it may break only with the members before it. Bisect assumes a green base, so when the first member is named the bare base is verified once more; if that is red the verdict is `verify-failed` with no `culprit`. A red train costs up to ceil(log2 n) extra verifies. Nothing lands unless `--land-green`, which lands the verified prefix before the culprit (`landed` lists them, `changed` is true, the exit is still 1).
note: (#915) after `test.full` and `test.e2e` pass on the scratch tree and before anything lands, the train runs each member's `## Try it` steps (see `rota worker gate`) in that tree, member by member in merge order, each in the scratch tree with the members up to it merged. Each member goes through a `--check-only` gate that carries the scratch directory, so the collaborator trust check, the scrubbed environment, the `BEHAVIOUR` / `BEHAVIOUR-SKIP` notes, the transcript, the `behaviour` verdict at the member's PR head and the PR comment are the gate's own. A member whose steps fail is the `culprit` (`verify-failed`, the gate's message naming the step); the members after it do not run. Nothing lands, or under `--land-green` the members before it do. `--no-verify` does not skip the run: it only permits an empty `test.full`.
note: (#461) `--no-verify` lets a train run with an empty `test.full` (and no `test.e2e`), which is refused otherwise (see `rota worker gate`); it does not skip a `test.full` that is set. The `NO-VERIFY train` note stays on stderr.
note: verdict cache (#400): every passing verify the train runs (each tier, each bisect prefix) is recorded in `.rota/train-cache.json` (gitignored, per-developer) under the key tier + base sha + the ordered head shas of the members merged so far, and a train that meets the same key reuses the pass instead of running `test.full` / `test.e2e` again. Failures are never cached: a red can be the machine's (a killed compiler, a load flake), so it always re-verifies and a re-run is a real retry. A moved base or any changed or reordered head is a different key and verifies fresh. A run with nothing to run is never recorded; verdicts of an older base are dropped when the file is next written. Reused passes are listed in `cacheHits` (JSON) and as `CACHE-HIT` lines on stderr.
note: transient culprits: a member the bisect names as culprit is also recorded (branch, head sha). When a later train carrying that member at the same head passes verification, the result lists it in `transient` (JSON; per-member `transient`) with a `TRANSIENT` note, and the record is cleared: the failure did not reproduce on another combination, so it is treated as flaky, not blamed again. A train with an empty `test.full` proves nothing and clears nothing.
note: a gate (not `--check-only`) and a train on one repository serialize on `<git-common-dir>/rota/land.lock`, held from before the first write (the scratch worktree, the merge) through landing; the train's own landing steps run under it. The lock is taken outside `test/gate.sh`'s machine-wide lock, never inside.
note: one approval covers the train: `ship.mergeApproval` is judged over the union of the files the members change, before the scratch merge. `--approval` and `--escalate` use the first target's thread. A culprit whose verdict is `stale` or `provenance-fail` counts a bounce and is parked at `round.maxBounces`, as the gate does (the train's JSON carries no `bounces`); a landed member forgets its count.
note: (#387) the train reads the exclusion ledger exactly as `rota worker gate` does (see there): once from the base before the scratch merge, excusing a failing `test.full` or `test.e2e` command whose failing tests all have an unexpired entry (`data.excluded`), and failing as `verify-failed` with nothing landed, naming test, owner and receipt in the message and `data.expired`, when any entry has expired. ### rota test run

data: {"tier": string, "commands": []string, "verified": []string, "failed": []string, "logPath"?: string}

When every slot is held the run prints one stderr line, `waiting for the test lock (held by <pid> <verb>)`, and waits with no timeout; it never fails on the lock. A run started inside a held lock (`ROTA_TEST_LOCK_HELD` set, as the commands of `rota proof record` and `rota test lock` are) does not queue again. The tier's own commands inherit `ROTA_TEST_LOCK_HELD=1` (#1844), so a nested `rota test lock` or `bash test/gate.sh` does not queue behind the run.

The gate checks open issue claims after reading origin refs and the PR's closing keywords,
including under `--check-only`. A recorded slot or queued `claimId` must remain open;
legacy slots match the branch agent against open claim holders. Another holder causes
exit 4, `blockedBy: claim-lost`, and nothing lands. No open claims, no remote PR, or an
unreadable claim source skips this check (read errors add a `CLAIMS-UNKNOWN` note).
Bundle members are checked with their lead. This fences PRs from holders whose stale
claim was reclaimed on another machine.
