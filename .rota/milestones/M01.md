# M01 — v4.0: The Loop, simplified

## Goal

Cut 8 redundant commands (28 → 20), ship migration codemod, write announcement. The cut is the marketing.

## Acceptance criteria

**Commands removed** (gone from `plugin.json` + `marketplace.json`, no aliases, no stubs):

- `hv-c`, `hv-assume`, `hv-rm`, `hv-undo`, `hv-issues`, `hv-context`, `hv-map`, `hv-docs`

**Surviving commands gain replacements:**

| Removed | Replaced by |
|---|---|
| `/hv-capture` | (gone — type `/hv-capture`) |
| `/hv-work --preview` | `/hv-work --preview` |
| `/hv-capture --remove` | `/hv-capture --remove <ID>` |
| `/hv-ship --undo` | `/hv-ship --undo` |
| `/hv-issues` | `/hv-capture --from-github` / `--from-gitlab` |
| `/hv-learn --term` | `/hv-learn --term <name>` |
| `/hv-map` | auto-only; first-run folded into `/hv-init` |
| `/hv-ship --docs` | `/hv-ship --docs` + auto-trigger when `docs/` exists |

**Migration tooling:**

- `/hv-migrate v4` skill ships. Scans `.hv/BACKLOG.md`, `.hv/plans/*`, `.hv/designs/*`, `.hv/handoffs/*`, `.hv/qa/*`, and project `CLAUDE.md` for the 8 old command names; rewrites to new shape.
- `--dry-run` is default; requires `--apply` to write.
- Idempotent (re-runnable).
- Writes a backup of every touched file to `.hv/migrate-backup/<timestamp>/`.

**Marketing artifacts (all in repo, all merged before tag):**

- `CHANGELOG.md` v4.0 section with two-column `removed | replaced by` table.
- `docs/announcements/v4-0.md` — long-form post. Leads with user-facing outcome ("20 commands, you know what they all do"), not the count. Frames cut as a complexity-budget decision. Receipts table near the bottom. No bare-courage claims — every cut has a "so you can…" clause.
- `README.md` rewritten to the new 20-command surface. Five-lanes section updated. Feature table trimmed.

**Cleanup (no orphans left behind):**

- `docs/usage/` pages for cut commands removed or merged into the successor's page.
- `test/smoke.sh` sections for cut commands removed or rewritten against the new flag surface; the full suite passes.
- `bin/` helpers for cut commands removed or folded into the surviving command's helpers (no orphan binaries).
- `/hv-init` interactive questions reduced — drops any settings that referenced cut commands (e.g., no `hv-map first-run` prompt).
- `SKILL.md` cross-references in surviving skills updated to the new command names. Grep for the 8 old names returns nothing in the canonical sources.
- `plugin.json` and `marketplace.json` entries removed for the 8 cuts; entry added for `/hv-migrate`.

**Definition of done:** version bumped to `4.0.0` via `/hv-release`, tag pushed, GitHub release created from `docs/announcements/v4-0.md`.

## Rationale

28 commands is the project's largest adoption headwind. README reads as a wall of features. Mental model is heavy — even the FAQ comparing hv-skills to GSD and Octo lists features rather than telling a story. Surface-area-to-value ratio favors rebuilding around the "Loop that learns" wedge, but that rebuild needs less surface to land coherently.

The cut isn't an apology — it's the marketing. A v4.0 that *removes* 8 commands and tells that story credibly is more adoptable than a v3.5 that adds more. "Less is harder, more credible." Per Tailwind v4's playbook: frame the removal as the feature itself, not as a loss list.

Hard-cut chosen (vs. aliases or deprecation window) because soft cuts defeat the surface-area win — README still has to list the old commands, mental model stays at 28. Migration codemod chosen as the safety net instead, because a one-shot rewrite is cleaner than per-command stub errors shipping forever.

## Open risks

- **Discovery hole.** User types `/hv-learn --term` post-upgrade and gets a bare "skill not found" with no hint that `/hv-migrate` exists. Mitigation: README upgrade banner, `/hv-update` post-upgrade notice that detects v3.x → v4.0 and prints the migrate command, and pinned release notes in the plugin marketplace listing. Resolve in plan.
- **Codemod safety on project `CLAUDE.md`.** Rewriting user-authored files is destructive. Mitigation: `--dry-run` is the default; `--apply` required to write; every touched file backed up to `.hv/migrate-backup/<timestamp>/`. Plan must define the rewrite rules as a tested regex/AST table, not ad-hoc edits.
- **Semantic snags in folds.** `/hv-learn --term` → `/hv-learn --term <name>` requires a data migration if `.hv/CONTEXT.md` and `.hv/KNOWLEDGE.md` have shape mismatch (different frontmatter, different topic-grouping). Same risk for `/hv-map` auto-only — what does `/hv-init` do if a project already has `.hv/MAP.md` from v3.x? Investigate in plan before execute.
- **"All 8 in one ship" constraint.** If one fold proves disproportionately hard (likely candidate: the CONTEXT.md → KNOWLEDGE.md migration), the whole milestone slips. Acceptance bar holds — no partial ship. Brainstorm should sequence the hardest folds first.
- **Announcement-locks-framing.** `docs/announcements/v4-0.md` must be drafted *before* the engineering merges so the framing is locked in early. Writing it after invites compromise. Plan should make the announcement an early-not-late task.
- **Cross-skill reference rot.** Many `SKILL.md` files reference cut commands in their handoff prose ("then hand off to `/hv-learn --term`"). Easy to miss. Grep-driven sweep needs to be part of acceptance, not afterthought.

## Research findings

**Framing playbook (Tailwind v4, Rails Doctrine, Next.js 13, htmx Complexity Budget):**

- Lead with the user's experience, not the count. Tailwind sold config removal as "CSS-first configuration." Open the v4 post with what a user experiences ("20 commands, you know what they all do"), not "we removed 8 commands."
- Enumerate cuts exactly once, late in the post, as receipts — not as the headline. Next.js 13's removal list lives in a compact block after the thesis sentence.
- Frame as a complexity budget decision (htmx essay): "8 commands users rarely reached for were a tax we kept collecting. We stopped." Matter-of-fact, no apology.
- Every cut needs a "so you can…" clause. Apple's "courage" iPhone-headphone-jack framing is the cautionary tale — virtue named, user benefit absent. Don't repeat it.

**Migration UX playbook (Docker Compose v2, git, Rust editions, Next codemod, Cobra):**

- Even hard cuts in successful tools ship helpful errors with the replacement copy-pasteable on the same line. *We chose harder than that:* no stubs, bare "skill not found." The codemod is the safety net instead.
- Rust edition migration auto-runs `cargo fix --edition` at the version boundary. `/hv-migrate v4` is the analog — one command rewrites the project.
- Next.js codemods are named, versioned, idempotent (`npx @next/codemod@latest`). `/hv-migrate` follows the same shape: explicit version arg, re-runnable, `--dry-run`.

**Successor-naming discipline (React 19):** Every removal in the React 19 upgrade post has a paired "use X instead" line. No removal announced without a named successor. Adopt this for the v4.0 CHANGELOG — two-column `removed | replaced by` table is non-negotiable. Where the answer is "omit, no replacement needed" (e.g., `/hv-capture` alias), say so explicitly.

**Scope-permanence trust signal (esbuild):** esbuild's docs name what the tool will never do (CSS modules, HMR opinions). Sets trust, prevents recurring feature requests. *Consider* a `SCOPE.md` or "what hv-skills v4.0 will not become" section — out of milestone scope, candidate for adoption-track follow-up.

## Notes

- **Brainstorm before plan.** This milestone is large enough to warrant `/hv-brainstorm` on the Major feature items, especially the codemod and the announcement draft. The Major-feature design-nudge in `/hv-capture` should fire automatically.
- **Sequencing hint.** Cheapest cuts first (`/hv-capture`, `/hv-map` auto-only) to land a fast green CI and build momentum. CONTEXT→KNOWLEDGE migration last because it's the highest-risk fold.
- **The codemod is also dogfooding.** It tests `/hv-migrate` against this very repo's `.hv/` state during development. If it can't rewrite hv-skills's own `.hv/`, it won't work for users.
- **Adjacent milestones deferred to a later vision pass:** rebrand or dual-brand the project, hero demo (Loom of capture → ship → learn → next session reads back), content surface, stability promise (SemVer policy on top N commands), cross-project KNOWLEDGE federation. Run `/hv-vision` again after v4 ships to scope the adoption track.
