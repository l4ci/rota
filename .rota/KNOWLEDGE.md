## Architecture: Module extraction & migration safety

- **Golden harness proves byte-identical helper moves** — To prove a helper refactor is a pure move, run `git archive HEAD bin | tar -x -C <scratch>` before editing. Then run one invocation matrix (every flag, error paths, completed/archived IDs) against the old and new bin dirs into separate output trees (stdout, stderr, exit code, resulting .hv files) and `diff -r` them, normalizing only path prefixes. M07-S01 used this to show FileBackend changed nothing across 95 + 64 invocations. Smoke alone would not have caught output drift. <!-- 2026-10-01 -->
- **Shim re-exports preserve private module-level names across extractions** — When decomposing a single-file Python module into flat siblings, private module-level names (underscore-prefixed: `_TODO_FIELD_NAMES`, `_DONE_LINE_RE`) can be re-exported through the shim — `from hvlib_bullet import _TODO_FIELD_NAMES` puts the name in `hvlib`'s module namespace where any shim-defined function resolves it via standard module-namespace lookup. This matters for single-source-of-truth tuples consumed across multiple now-separate modules: co-locate the constant with its primary consumer (`_TODO_FIELD_NAMES` lives with `parse_todo_fields` in `hvlib_bullet`); other consumers reach it via direct `from hvlib_<name> import _NAME` (preferred for inter-module), with the shim re-export as a fallback for stragglers. Both routes preserve "exactly one definition site" — the underscore prefix is a convention, not an export gate. <!-- 2026-05-18 -->
- **Flat-module extractions place functions by import-DAG, not nominal category** — When decomposing a god-module into flat `hvlib_<name>.py` siblings, place each function in the module that owns its DIRECT in-module caller chain — not the module suggested by its nominal category. F25's `iter_topics` looked glossary-shaped (a section/heading scanner) but its only direct caller `print_matching_sections` lived in `hvlib_section`; placing `iter_topics` in `hvlib_glossary` per the original plan would have forced `hvlib_section` to import from `hvlib_glossary` (or worse, route through the shim — circular). The dependency principle "inter-module imports use direct paths, never through the shim" wins decisively: a function belongs with its closest in-DAG caller. The nominal category goes in the docstring, not the file path. <!-- 2026-05-18 -->
- **Deprecated-managed-block strip uses explicit allowlist, not heuristic 'not in v4 set'** — B09 added a strip-orphan-block mode to `bin/hv-managed-block`. Tempting alternative: strip any block whose key isn't in the v4 regenerator set (skills, knowledge, decisions, vision, map, qa). That heuristic would silently sweep user-added custom managed blocks. Instead: hardcoded `DEPRECATED_KEYS = ["context"]` allowlist — one entry today, documented growth point for future cuts. The strip regex also tolerates both delimiter shapes (canonical `<!-- hv-<key>-start/-end -->` and legacy `<!-- hv:<key>:start/:end -->`) by mirroring `hvlib.upsert_block`'s alternation. Pattern: removal lists are explicit and reviewable; never compute 'what should NOT exist' by inversion of a positive set unless every key is system-owned. <!-- 2026-05-17 -->
- **Codemod mention/usage safety: code spans + helper-path tokens + structural block deletes** — F19's hv-migrate `rewrite_text` was a blind line-regex `pattern.sub()` that corrupted self-documenting mentions, substring-matched live helper paths (`/hv-map\\b` inside `hv-map-query`), and word-substituted v3 orphan managed blocks instead of deleting them. B09 fix: three concentric guards — (a) skip fenced code blocks (``` DOTALL), (b) skip inline code spans (single-backtick no-newline), (c) skip helper-path tokens via regex `(?:[\\w./]+/)?\\bhv-\\w+(?:-\\w+)+` which requires at least TWO hyphens after `hv-` so it catches `hv-map-query` but leaves bare slash-commands like `/hv-context` (one segment) untouched. Plus orphan-block stripping moved to `hv-managed-block --strip-deprecated` (structural delete, not word-substitute). Mask must be RECOMPUTED between rules — earlier substitutions shift byte offsets within one rewrite_text call. <!-- 2026-05-17 -->

## Architecture: Helper conventions & invariants

- **Wrappers read stdin only when an argument takes it** — A helper that slurps stdin whenever it is not a TTY hangs under agent shells, which can hand children an inherited pipe that never closes. bin/hv-tracker-call reads stdin only when an argument takes it (`-`, `=-`, `@-`, as in `gh issue create -F -`) and otherwise gives the CLI /dev/null; test/sections/54_tracker_call.sh pins this with a held-open FIFO. <!-- 2026-10-01 -->
- **Umbrella scope as the degenerate 1-element case of hybrid `file_pairs`** — When a helper has two scope paths (umbrella-only single-file reader vs hybrid umbrella+sub-repo reader) that share the same per-file parser, model umbrella as the degenerate 1-element case of the hybrid `file_pairs` list rather than carrying two parallel code paths. Two collapse shapes:

(a) **Full collapse** when both scopes emit the same provenance header — e.g. `hv-glossary-read` prints `> from: <label> (## Glossary)` in both umbrella and hybrid, so a single outer loop iterating `file_pairs` of length 1 or 2 covers both shapes. The whole umbrella branch goes away.

(b) **Inner-only collapse** when output formats differ across scopes (e.g. `hv-knowledge-query`: umbrella suppresses `> from:` and preserves doc-order; hybrid emits `> from:` per file and uses argv-order). Keep the outer loop scope-gated but lift the shared parser (`collect_bullets()` / `extract_entries()`) to module scope so both branches call one function. T104 used shape (a) for glossary-read and shape (b) for knowledge-query; full smoke + byte-identical diff across single/multi-topic, reversed-argv, and all three tier filters confirmed the contract.

Hard rule: single-repo (umbrella-only) projects must remain byte-identical pre/post — gate the commit on `diff <(old) <(new)` across the input matrix, not on smoke alone. <!-- 2026-05-19 -->
- **Optional-value flags use `${PARAM:?$USAGE}` to reject bare trailing flag values** — When a helper takes an optional flag whose value is required ONLY when the flag is present (e.g. `--repo umbrella|<name>`), the parser MUST use `FLAG="${2:?$USAGE}"; shift 2` against a per-helper `USAGE=` constant — not the compact `FLAG="$2"; shift 2` form. The latter silently coerces a bare trailing `--repo` to `""` and downstream callers auto-resolve to a default scope, masking the user's intent. T103 surfaced this across `hv-glossary-{write,read,import}` where bare `--repo` previously fell through to umbrella; the three `hv-knowledge-{merge,tier,amend}` helpers already used the canonical idiom. All 7 knowledge/glossary helpers now match. Smoke section 43 locks the contract by asserting non-zero exit + usage line on bare trailing `--repo` in every helper. Future helpers gaining `--repo` (or any value-bearing optional flag) inherit this guard. <!-- 2026-05-19 -->
- **Scope-axis additions keep the default path byte-identical via literal legacy resolution** — When adding a new dispatch axis (e.g. F21's --repo umbrella|<name>) to a family of single-mode helpers, keep single-mode output byte-identical by making the default scope resolve to the EXACT legacy literal, not a generalized code path: resolve_knowledge_target("umbrella") returns the string ".hv/KNOWLEDGE.md" verbatim and the umbrella branch reproduces the original heredoc unchanged, so single-repo projects diff clean against the pre-feature version. Verify this with a literal `diff <(old) <(new)` across several inputs, not just "looks the same" — it is the cheapest regression guard for a wide helper rewire and the acceptance bar for umbrella-aware work. <!-- 2026-05-19 -->
- **Sourced libs needing caller cwd must restore HV_ORIG_PWD (hv-preamble.sh cds first)** — A sourceable lib that needs the caller's original cwd (e.g. to run a cwd-relative resolver like hv-resolve-repo) must restore HV_ORIG_PWD before invoking it: helpers source hv-preamble.sh, whose hv_self_locate cds to the project/umbrella root BEFORE any later-sourced lib function runs, so a naive cwd probe always resolves to root. F21's bin/hv-knowledge-scope.sh is the reference — it does `if [ -n "${HV_ORIG_PWD:-}" ]; then cd "$HV_ORIG_PWD" || exit 0; fi` inside a subshell before calling the sibling resolver. Without this, sub-repo cwd auto-resolution silently degrades to the umbrella/default scope with no error. <!-- 2026-05-19 -->
- **Field writers co-locate with the read-grammar SoT; order-agnostic parse allows append-at-end** — When adding a writer for a grammar shared with a reader (e.g. `set_todo_field` next to `parse_todo_fields`), co-locate it in the same module beside the single-source-of-truth field tuple (`_TODO_FIELD_NAMES`) so the read and write paths cannot desync as fields are added. Because `parse_todo_fields` delimits each value by a next-field/EOL lookahead, it is order-agnostic — so a writer may append an absent field at end-of-line rather than reordering the bullet (round-trip proven: `Since` still parses with a `Milestone` appended after it). Backlog field writers must restrict mutation to open `- **[ID]` bullets in `.hv/BACKLOG.md` (not strikethrough/archived lines) and stay idempotent — no-op + exit 0 on unchanged value, mirroring `hv-complete`. Reference: `bin/hv-todo-set-field` + `hvlib_bullet.set_todo_field` (T102). <!-- 2026-05-19 -->
- **Sourceable artifact libs (hv-artifact-VERB.sh) are per-verb, not per-kind** — `bin/hv-artifact-rm.sh` and `bin/hv-artifact-show.sh` are sourceable libraries each owning ONE verb across all artifact kinds (design/plan/spike/vision). Each lib's function takes `(kind, id, dir)`; key-shape validation stays in the calling helper where the family-specific regex lives (`[BFT]\d{2,}` for design, `M\d{2,}` for vision, slug `[a-z0-9][a-z0-9-]*` for spike, milestone+unit composite for plan). Caller files shrink to ~5 non-comment lines: preamble, source lib, fetch arg, delegate. The lib never gains a switch on `kind` — kind is an opaque label the lib doesn't introspect; the directory parameter carries the routing. Adding a fifth artifact kind = one new ~5-line wrapper per verb, zero lib changes. <!-- 2026-05-18 -->
- **Helper preamble naming convention: *-preamble.sh auto-invokes; *-locate.sh stays library** — Files in bin/ with intentional source-time side effects (auto-cd, env-var export, function invocation) must be named `*-preamble.sh`. Files named `*-locate.sh`, `*-types.sh`, `*-common.sh` stay pure libraries — they DEFINE state and functions but do NOT INVOKE them. Sourceable files are read by humans much more often than they're written; the filename suffix tells the reader at a glance whether sourcing runs code. F24 introduced `bin/hv-preamble.sh` (the only auto-invoker) and kept `hv-self-locate.sh` library-shaped — sourcing self-locate alone is a no-op and only `hv_self_locate()` runs anything. Smoke test/sections/39_preamble.sh enforces the invariant. <!-- 2026-05-16 --> (Round-6 renumbering: now test/sections/42_preamble.sh.)
- **Use load_repos() for umbrella detection — never truthy-test raw repos.json** — hv-bootstrap writes `{"repos":[]}` as the single-repo default, which is a truthy Python dict. Any code branching on "is this umbrella?" must call `hvlib.load_repos()` (returns `{}` when no sub-repos are registered) instead of `bool(json.loads(repos_json))`. Caught in F19 hv-migrate's umbrella refusal — naive truthy-test fired refusal on fresh-bootstrap single-repo projects. <!-- 2026-05-16 -->
- **Atomic-batch helpers validate the whole batch before any write** — When a writer helper supports atomic multi-entry import (e.g. for codemod consumers), the validation pass MUST be whole-batch up-front, not per-entry inline. The pattern: (1) parse the manifest into N candidates; (2) load existing state once; (3) build two conflict maps — existing-alias-owner (alias→existing-term-name) and batch-alias-owner (alias→(new-term, lineno)) — then walk all candidates collecting all conflicts (don't fail on first); (4) if conflicts non-empty, emit one error line per conflict and exit non-zero WITHOUT writing; (5) only after a clean validation, apply all candidates in memory and write the target file once. Two-direction conflicts to catch: same-batch (term-B alias collides with term-A alias on earlier line) and pre-existing (term-N alias collides with an existing entry not in the batch). Reference impl: bin/hv-glossary-write --batch (F18 T9). F19's /hv-migrate v4 consumes this pattern to import legacy .hv/CONTEXT.md atomically. The cost of upfront validation is one extra parse pass; the benefit is no half-written state to recover from on collision. <!-- 2026-05-16 -->
- **ID-based drift detection must anchor in commit-graph state** — `.hv/` is gitignored, so each machine mints IDs from a local counter and ID collisions across machine syncs are inevitable. Any drift/sync detector that matches on `[ID]` tags from commit subjects MUST anchor in commit-graph state — pin the HEAD short-hash at capture time in the open bullet (`Since: <hash>`) and gate matches via `git rev-list <since>..HEAD`. Dates and counter values fail: dates collide within the same day; counters reset across clones. The commit-graph is the only globally-consistent observation point both sides of a sync share. See `bin/hv-todo-drift` and `bin/hv-append` for the reference implementation. <!-- 2026-05-16 -->

## Architecture: Skill authoring

- **Shorten skills structurally, not by rewording** — After one verbosity cut and moving conditional steps into per-skill files, `/concise-writing` passes on skills and references cut only 0.5-1.5% (round 5, #333-#335). The remaining length was duplicated rules and pointer-only sections; a structural dedup (one owner file per rule) cut the references by 10% (#342). <!-- 2026-10-06 -->
- **Codex drops skills whose unquoted description has ': ' or ' #'** — Codex parses SKILL.md frontmatter as strict YAML and silently drops a skill whose unquoted description contains ": " or " #". Claude Code tolerates it. validate-skills.py now rejects those values; use `description: >-` for long or punctuated text. <!-- 2026-10-04 -->
- **hv-complete callers own the exit-3 proof path** — Every skill that calls hv-complete needs a path for exit 3 (no proof): record an executed check with hv-proof-add, then retry. A /hv-review or second-opinion PASS reads the diff and runs nothing, so it is acceptance, never a proof row. Only the user may choose --no-proof; loop mode leaves the item open. test/sections/52_proof.sh fails any SKILL.md that calls hv-complete without mentioning hv-proof-add. <!-- 2026-10-01 -->
- **Backlog 'near-isomorphic CRUD' framing overstates uniformity — verify against helper code** — Backlog items tagged "near-isomorphic CRUD family" often overstate the foldability — show/list/rm helpers genuinely share shape, but *-add helpers diverge per-family on git-branch creation (hv-spike-add), ID minting + index updates (hv-vision-add), milestone+slice composite keys (hv-plan-add), or repo validation. F26's backlog described "16 helpers" but the surgical scope was 5 (2 *-rm already shared via hv-artifact-rm.sh + 3 *-show — design/plan retrofit, vision/spike new). Read 2 representative helpers per family during /hv-brainstorm Step 3 context-load before proposing approaches; the gap between backlog framing and code reality is where over-scoped Major items get born. <!-- 2026-05-18 -->
- **Composite-fold deletion scope: orphan helpers + public docs are the predictable miss** — Composite-fold scope undercounting is the predictable failure mode — the rename + link-sweep file list (T4-equivalent) almost always misses two adjacent categories the plan author forgets to enumerate: (1) orphan helpers whose only caller was the gone code (e.g. hv-context-index regenerated CLAUDE.md from .hv/CONTEXT.md, both gone after F18), and (2) public-facing docs about the gone artifact (docs/usage/<thing>.md user guide, docs/reference/<artifact>-md.md format reference). These are NOT "text references to update" — they are whole files to delete. Mitigation: when planning a composite fold, scope the T7 "remove" task with three explicit categories (a) skill folder, (b) plugin/manifest entries, (c) orphan helpers + public-docs deletions; let the T8 "final sweep" catch only TEXTUAL residue, not file deletions. The plan's 16-file rename list is correctly bounded; the deletion list is what gets underestimated. <!-- 2026-05-16 -->
- **Inline-fold drops slash-command surface; composite-fold preserves it as a flag mode** — When retiring a standalone skill, pick the destination shape deliberately. A composite-skill fold (e.g. `/hv-ship --undo` → `/hv-ship --undo`, `/hv-ship --docs` → `/hv-ship --docs`) keeps the slash-command surface as a flag mode and preserves both code paths. An inline fold (e.g. `/hv-map after-work` → `/hv-work` Step 13.7 prose) drops the user-invocable command entirely and embeds the logic at every former dispatch site. Inline folds need one MORE edit than composite folds: every SKILL.md that previously dispatched the gone skill via the `Skill` tool must inline equivalent prose instructions, and the bin helpers' placeholder text and nudge messages that referenced the now-defunct slash-command (empty-set bullets in index helpers, soft-cap-check nudges) need rewording too. Choose inline-fold when the gone skill's manual modes weren't being used; choose composite-fold when at least one manual entry-point still matters. <!-- 2026-05-16 -->
- **Skill folds need quadruple-update: SKILL.md, smoke assertions, references, plugin.json** — When folding standalone skill A into composite skill B as a flag-mode (e.g. `/hv-ship --undo` → `/hv-ship --undo`, `/hv-ship --docs` → `/hv-ship --docs`), four coordinated edits beyond porting the flow itself: (1) smoke-test assertions targeting `<A>/SKILL.md` must retarget to `<B>/SKILL.md` AND match any rewording the port introduced — F17's 'After-work flow' → 'After-work sub-flow' rename invalidated the F09 `grep -q 'Route to the After-work flow'` assertion until updated; (2) architectural reference docs naming the standalone skill (e.g. `references/three-mode-skill-shape.md` 'Used by /hv-ship --docs and /hv-map') need rewriting to describe mode-routed structure ('Used by /hv-ship Docs Mode and /hv-map'); (3) `references/README.md` Cited-by columns need a consumer-set refresh via grep; (4) `.claude-plugin/plugin.json` skill list drops the standalone entry. The fold isn't done until all four layers move together. <!-- 2026-05-16 -->
- **Multi-mode skill folds use prefixed step keys (R/I), not renumbering** — When folding N existing skills into modes on a single skill ( after F14/F16), prefix the new mode step numbers with an alphabetical key (R1-R5 for Remove Mode, I1-I7 for Import Mode) instead of renumbering the original capture flow. External references in other skills and reference files (e.g. `references/milestone-tagging.md` cites `/hv-capture` Step 4.5/4.6, `references/detail-files.md` cites Step 5/6) point at the original step numbers; renumbering forces a cross-cutting sweep that's easy to miss. Prefixed keys keep external Step-N references stable while the new modes get their own clean numbering. <!-- 2026-05-16 -->
- **Extend an existing reviewer brief instead of dispatching a parallel pass** — When augmenting `/hv-review` (or another single-pass reviewer skill) with a new check — silent-failure detection, security scanning, type-check parity — add a numbered rubric item to the existing reviewer brief instead of creating a separate dispatch step or `hv-<check>` helper. The reviewer already has the diff, intent, and conventions loaded; a parallel pass doubles model cost without changing the verdict shape. F08 is the canonical example: rubric item #5 in `/hv-review` Step 5, no separate helper. Reserve separate dispatch only for genuinely independent perspectives (e.g. `/hv-ship` Step 3.5 second-opinion gate, which deliberately omits shared context as the differentiator). <!-- 2026-05-15 -->

- **hv-migrate --apply bumps the version stamp on every path, including nothing_to_do** — B08 surfaced that the apply path was structured as `if nothing_to_do: sys.exit(0)` before any version-stamp write — meaning a project that was already v4-clean (no rewrites, no CONTEXT.md, no stale binaries) could never clear hv-preflight's drift nag. Mitigation in bin/hv-migrate: `stamp_version` runs both in the nothing_to_do branch AND in the normal apply tail, and returns False when the stamp is already canonical (`hvSkills.version` equals installed AND no legacy top-level `version` key) so repeated --apply runs stay silent. Pattern: post-cycle observable state must update on every user-invoked run, not only the runs that did 'interesting' work. <!-- 2026-05-17 -->
- **Bootstrap-stage helpers can't depend on hv-preamble.sh — keep the canonical exception list** — Some `bin/hv-*` helpers can't depend on `hv-preamble.sh` and must keep their custom bootstrap. Two reasons: (1) they operate before `.hv/` is resolvable (`hv-preflight`, `hv-bootstrap`, `hv-walk-up`, `hv-resolve-*`, `hv-umbrella-*`), or (2) they need graceful soft-fail and call `hv_self_locate || exit 0` to silently exit when `.hv/` isn't initialized (`hv-version-check`, which also captures `BIN_DIR` BEFORE any cd so post-locate commands can still reach sibling helpers). When adding new helpers in either category, do NOT source `hv-preamble.sh` — the preamble's strict invocation under `set -euo pipefail` defeats both intents. - **hv-preflight opens a smoke-failure window during major-version transitions** — `hv-preflight` compares the fixture's `.hv/bin/` against the resolved upstream plugin (via `hv-resolve-plugin-root --bin`). During a major-version transition where canonical `bin/` cut helpers (e.g. F18 removing `hv-context-*`) but the installed plugin cache at `~/.claude/plugins/cache/hv-skills/<ver>/bin/` still carries them, every smoke section that copies canonical `bin/` to `.hv/bin/` and then calls `hv-preflight` fails with "stale: missing helpers". - **Generic dispatchers accumulate dead-letter keys when typed wrappers grow own parsers** — Generic dispatcher helpers (e.g. bin/hv-section-query <key> <topic>...) often carry stale keys when their typed wrappers grow their own parsers. - **hv-append is the chokepoint for derived BACKLOG fields** — `bin/hv-append` is the single chokepoint that every capture flow walks through to write to `.hv/BACKLOG.md`. When a derived field needs to land on every new bullet (e.g. capture-time HEAD hash for `Since:`), inject it in `hv-append` rather than threading the value through every SKILL.md call-site. The pattern: detect the bullet shape (`- **[…] …`), check whether the field is already present, append it before the python write. Skip silently when context isn't available (no git HEAD, etc.) so smoke tests and greenfield repos don't break. <!-- 2026-05-16 -->
- **TODO field additions require three synchronized edits** — Adding a new optional field to a TODO bullet (e.g. `Since:`) requires three coordinated edits: (1) append the field name to `_TODO_FIELD_NAMES` in `bin/hvlib.py` — that tuple is the regex-builder source of truth; (2) add the lowercase key to the `fields` dict initializer inside `parse_todo_fields`; (3) add the same lowercase name to the valid-fields set in `bin/hv-todo-field`. Missing any of the three breaks silently — the parser may extract the value but `hv-todo-field` rejects it, or callers see an empty string when the field exists. Smoke covers all three via `05_reconcile.sh`. <!-- 2026-05-16 -->

- **Worktree .rota/ runtime is gitignored — run state helpers from main repo path** — When developing rota itself inside a worktree at `.claude/worktrees/<name>/`, the gitignored `.rota/` runtime doesn't exist in the worktree — only in the main repo path. Skill helpers (`hv-status-add`, `hv-complete`, `hv-merge`, etc.) read/write `./.rota/` relative to cwd, so calling them from the worktree fails with `no such file or directory`. Mitigation: `cd` to the main repo path before invoking helpers, or pass absolute worktree paths to helpers that accept them (e.g. `hv-status-add <branch> <ids> <abs-worktree-path>`). - **EnterWorktree branches from origin/main; rebase onto local main before editing** — The harness's `EnterWorktree` tool branches from `origin/<default-branch>` by default (governed by `worktree.baseRef: fresh`). When local main has commits that haven't been pushed to origin yet, the worktree's HEAD is stale — edits made there will conflict on merge. Rebase the worktree branch onto local main *before* making any edits (`git rebase main` from inside the worktree). The default `fresh` baseRef is intentional (clean origin-based isolation), but in a fast-moving repo where local commits queue up, the rebase-first flow is the correct mitigation. <!-- 2026-05-16 -->
- **`git branch -d` refuses on stale remote-tracking refs** — `hv-merge` uses `git branch -d <branch>` for cleanup. It only refuses when a `refs/remotes/origin/<branch>` upstream-tracking ref exists pointing at a different commit than the branch tip — even if the branch is fully merged to HEAD. Pure-local branches with no matching tracking ref delete cleanly. Cleanup for orphaned refs: `git update-ref -d refs/remotes/origin/<branch>` (after the upstream branch was deleted on the remote). Original framing "doesn't delete unpushed branches" was wrong — the failure mode is stale tracking refs, not lack-of-push. <!-- 2026-05-15 -->
- **git checkout -b inherits HEAD's lead over base** — When starting work, run `git log <base>..HEAD` before `git checkout -b` — commits ahead of base on the cut-from HEAD ride into the feature merge unchanged. Cherry-pick stray commits to base first, then rebase the feature branch so the merge body stays scoped to your work. <!-- 2026-05-15 -->
