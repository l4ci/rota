## Architecture: Helper conventions & invariants: Go verbs & fakes

- **Isolate the global config without a temp dir leak** — internal/testiso keeps test binaries off the developer's global rota config. An init that keeps an os.MkdirTemp dir leaks one dir per test binary (the gate's leak check fails), and a predictable path in shared /tmp lets another user plant a config. Use MkdirTemp, os.Remove it at once, and point XDG_CONFIG_HOME at a nonexistent child; also unset ROTA_CONFIG_DIR. <!-- 2026-10-21 sha:6b883b38 -->
- **A bigger timeout is not a flake fix** — Timing tests in internal/worker that flaked under gate load (#1266) were fixed by stubbing the slow call through the existing Env.Git seam and an injected clock, not by raising deadlines; a raised deadline only moves the flake. Prove a flake fix with go test -race -count=50 while another go test ./... runs as load. <!-- 2026-10-21 sha:6b883b38 -->
- **A config enum of harness kinds must be allowlisted in the kind-switch guard** — TestNoKindNamedOutsideHarness (internal/harness/kindswitch_test.go) fails on any claude/codex/opencode literal outside internal/harness. A config key whose enum lists harness kinds (config cannot import harness) must join the keys.go allowlist regex and be pinned equal to harness.Kinds in TestWorkerKindEnumIsKinds (round 27, #1001 plan.criticHarness). <!-- 2026-10-20 -->
- **The worker forge must not share the read cache** — `Deps.workerEnv` wires `worker.Env.Forge` with `d.TrackerOptions` only, never `trackerOptions()` with the `ReadCache`: the gate retries `PRMergeable` (`gh pr view`, a cached read) until GitHub computes it, the CI verifier polls `CommitChecks` (an `api` GET, cached) until checks settle, and PRView is re-read after a stale-merge push; nothing inside a gate run calls `freshReads`, so a cached first answer kills the retry and stalls CI mode to verify-timeout. `TestWorkerEnvForgeSkipsReadCache` pins it (#888, round 25). <!-- 2026-10-19 -->
- **The tracker REST layer never resends a POST after a 5xx** — internal/tracker/rest.go retries 429 for every method but 5xx only for GET/HEAD/PUT/DELETE, since a POST that hit a 5xx may already have created a comment or issue. Read-only GraphQL goes through REST.Query, which retries and refuses a mutation document (#809, #813). <!-- 2026-10-15 -->
- **Gate steps read the forge only after stepRemote** — A gate step that calls the forge must run after stepRemote and skip when the gate does not read origin refs: smoke 68(h) requires zero forge traffic for a recorded PR without an origin remote, and a gh pr view in an earlier step fails it (#817). <!-- 2026-10-15 -->
- **Gate target fields change mid-run** — Gate steps refine the target as they run: stepExternal replaces Branch with the forge's head and stepAdoptPR adopts a PR the slot never recorded. Anything derived from the target (issue via HeldID, approval thread via PR) must be recomputed where those inputs change; freezing it at resolution silently skipped closes/review-depth/best-of for external PRs and sent adopted-PR approvals to the issue thread (#795). <!-- 2026-10-12 -->

- **A per-invocation cache must reset per pass in long-running verbs** — The forge read cache (tracker.ReadCache, #547) lives for one rota invocation, but round watch and the autopilot are one invocation running for hours, and their forge polls only read, so nothing clears it. Any loop that re-reads the forge calls Deps.freshReads() at the start of each pass. A new long-running verb that polls the forge must do the same, or it serves its first answer forever. <!-- 2026-10-08 -->

- **Palette entries name the verb that registers the View** — Since #544 the palette opens a verb's Command.View in place. An entry must name that verb (config show, projects), not a verb that calls RunView itself (config edit) and not the verb plus --ui: both run through the cooked Run path and leave the user on 'press any key' after q. <!-- 2026-10-08 -->

- **Embedding host fakes must redeclare Capabilities** — Host.Capabilities() is promoted through struct embedding, so a test fake that embeds another fake and adds an optional method (Labeler, TabLister, ...) must define its own Capabilities() returning host.CapabilitiesOf(self); otherwise the promoted one describes the inner value and the new side is invisible to callers (#770). <!-- 2026-10-11 -->
## Architecture: Skill authoring

- **Shorten skills structurally, not by rewording** — After one verbosity cut and moving conditional steps into per-skill files, `/concise-writing` passes on skills and references cut only 0.5-1.5% (round 5, #333-#335). The remaining length was duplicated rules and pointer-only sections; a structural dedup (one owner file per rule) cut the references by 10% (#342). <!-- 2026-10-06 -->
- **Codex drops skills whose unquoted description has ': ' or ' #'** — Codex parses SKILL.md frontmatter as strict YAML and silently drops a skill whose unquoted description contains ": " or " #". Claude Code tolerates it. validate-skills.py now rejects those values; use `description: >-` for long or punctuated text. <!-- 2026-10-04 -->
- **Composite-fold deletion scope: orphan helpers + public docs are the predictable miss** — Composite-fold scope undercounting is the predictable failure mode — the rename + link-sweep file list (T4-equivalent) almost always misses two adjacent categories the plan author forgets to enumerate: (1) orphan helpers whose only caller was the gone code (e.g. hv-context-index regenerated CLAUDE.md from .hv/CONTEXT.md, both gone after F18), and (2) public-facing docs about the gone artifact (docs/usage/<thing>.md user guide, docs/reference/<artifact>-md.md format reference). These are NOT "text references to update" — they are whole files to delete. Mitigation: when planning a composite fold, scope the T7 "remove" task with three explicit categories (a) skill folder, (b) plugin/manifest entries, (c) orphan helpers + public-docs deletions; let the T8 "final sweep" catch only TEXTUAL residue, not file deletions. The plan's 16-file rename list is correctly bounded; the deletion list is what gets underestimated. <!-- 2026-05-16 -->
- **Inline-fold drops slash-command surface; composite-fold preserves it as a flag mode** — When retiring a standalone skill, pick the destination shape deliberately. A composite-skill fold (e.g. `/hv-ship --undo` → `/hv-ship --undo`, `/hv-ship --docs` → `/hv-ship --docs`) keeps the slash-command surface as a flag mode and preserves both code paths. An inline fold (e.g. `/hv-map after-work` → `/hv-work` Step 13.7 prose) drops the user-invocable command entirely and embeds the logic at every former dispatch site. Inline folds need one MORE edit than composite folds: every SKILL.md that previously dispatched the gone skill via the `Skill` tool must inline equivalent prose instructions, and the bin helpers' placeholder text and nudge messages that referenced the now-defunct slash-command (empty-set bullets in index helpers, soft-cap-check nudges) need rewording too. Choose inline-fold when the gone skill's manual modes weren't being used; choose composite-fold when at least one manual entry-point still matters. <!-- 2026-05-16 -->
- **Skill folds need quadruple-update: SKILL.md, smoke assertions, references, plugin.json** — When folding standalone skill A into composite skill B as a flag-mode (e.g. `/hv-ship --undo` → `/hv-ship --undo`, `/hv-ship --docs` → `/hv-ship --docs`), four coordinated edits beyond porting the flow itself: (1) smoke-test assertions targeting `<A>/SKILL.md` must retarget to `<B>/SKILL.md` AND match any rewording the port introduced — F17's 'After-work flow' → 'After-work sub-flow' rename invalidated the F09 `grep -q 'Route to the After-work flow'` assertion until updated; (2) architectural reference docs naming the standalone skill (e.g. `references/three-mode-skill-shape.md` 'Used by /hv-ship --docs and /hv-map') need rewriting to describe mode-routed structure ('Used by /hv-ship Docs Mode and /hv-map'); (3) `references/README.md` Cited-by columns need a consumer-set refresh via grep; (4) `.claude-plugin/plugin.json` skill list drops the standalone entry. The fold isn't done until all four layers move together. <!-- 2026-05-16 -->
- **Multi-mode skill folds use prefixed step keys (R/I), not renumbering** — When folding N existing skills into modes on a single skill ( after F14/F16), prefix the new mode step numbers with an alphabetical key (R1-R5 for Remove Mode, I1-I7 for Import Mode) instead of renumbering the original capture flow. External references in other skills and reference files (e.g. `references/milestone-tagging.md` cites `/hv-capture` Step 4.5/4.6, `references/detail-files.md` cites Step 5/6) point at the original step numbers; renumbering forces a cross-cutting sweep that's easy to miss. Prefixed keys keep external Step-N references stable while the new modes get their own clean numbering. <!-- 2026-05-16 -->
- **Extend an existing reviewer brief instead of dispatching a parallel pass** — When augmenting `/hv-review` (or another single-pass reviewer skill) with a new check — silent-failure detection, security scanning, type-check parity — add a numbered rubric item to the existing reviewer brief instead of creating a separate dispatch step or `hv-<check>` helper. The reviewer already has the diff, intent, and conventions loaded; a parallel pass doubles model cost without changing the verdict shape. F08 is the canonical example: rubric item #5 in `/hv-review` Step 5, no separate helper. Reserve separate dispatch only for genuinely independent perspectives (e.g. `/hv-ship` Step 3.5 second-opinion gate, which deliberately omits shared context as the differentiator). <!-- 2026-05-15 -->

## Build & Tooling: Smoke testing: Sections & fixtures

- **printf into head dies under pipefail** — `printf '%s\n' "$X" | head -1` in a section can exit 141 (SIGPIPE) under set -o pipefail when the payload is large, killing the shard with no OK or FAIL line (section 148, #1242). Use ${X%%$'\n'*} instead; test/sections/164 guards the pattern and test/gate.sh names a shard that dies without a summary. <!-- 2026-10-21 sha:6b883b38 -->
- **A new required config key goes into the F78 complete-config fixture** — test/sections/28_config_set.sh F78 builds a config it calls complete and expects config check to exit 0; a key registered with required=true makes it stale and fails the gate (round 27, #991 for ship.uat). Add the key to that fixture in the same PR; optional keys need nothing. <!-- 2026-10-20 -->

- **Failing-verify tests must own their TMPDIR** — A test that makes verify fail on purpose leaves runVerifyCmds' rota-gate-verify-* log behind by design (it is kept for the failure report), and test/gate.sh's no-leak check then fails the gate even though every suite passed. Point TMPDIR at t.TempDir() in such a test (#791). <!-- 2026-10-12 -->

- **Fixtures that expect issue or forge reads must pin the source and forge** — Since #797 a config with no issues.source resolves to the file source, and a local bare origin resolves forge.provider to local, so the gate reads no issue and calls no forge. A test or smoke fixture that expects either must set issues.source and forge.provider explicitly (smoke 146 broke this way on #802). <!-- 2026-10-15 -->

- **Smoke sections run only inside the runner; standalone needs an env-prep wrapper** — Smoke sections under test/sections/*.sh are SOURCED by test/runner.sh into a shared environment (($TMP, $BIN, $REPO, $TESTDIR plus pass/fail from test/lib.sh) — they are not executable standalone. To smoke-check a single retargeted section before running the full suite (which is intentionally slow and accumulates state across sections), use a one-shot wrapper that prepares the env then sources just the section file: bash -c 'set -euo pipefail; export REPO=$(pwd); export BIN="$REPO/bin"; export TESTDIR="$REPO/test"; export TMP="$(cd "$(mktemp -d)" && pwd -P)"; trap "rm -rf $TMP" EXIT; cd "$TMP"; git init -q && git config user.email t@t && git config user.name t && git add -A && git commit -q --allow-empty -m seed; source "$TESTDIR/lib.sh"; source "$TESTDIR/sections/NN_name.sh"'. Note $TMP must use pwd -P (macOS mktemp returns /var/folders/... while pwd -P returns /private/var/folders/...; helpers using pwd -P would otherwise mismatch). This pattern is per-task verification during /hv-work — the full smoke still runs at /hv-ship per the project's smoke-at-boundary rule. <!-- 2026-05-16 --> Only sections that build their own mktemp fixture (e.g. 52_proof, 55_backend, 54_tracker_call) or only read the repo (44_hvlib_exports) are safe this way: sections relying on state accumulated by earlier sections (01_status, 07_refactor, 35_undo) wrote into the dev tree's .hv/counters.json when run standalone in M07-S01. For those, run a scratch copy of test/runner.sh, then check `git status --short` on the real repo. (2026-10-01)

- **Inverted grep assertion (grep && fail) aborts the section under set -e** — In smoke sections (sourced under `set -euo pipefail`), an inverted assertion written as `grep -q PAT file && fail "..."` is a footgun: when PAT is absent (the PASS case) grep exits 1, the `&&` short-circuits to overall status 1, and set -e aborts the whole section before the next assertion. Use an explicit `if grep -q PAT file; then fail "..."; fi` for "must NOT contain" checks; the safe `|| fail` idiom only works for the "must contain" direction. <!-- 2026-05-19 -->

- **A verb captured in $(...) aborts the section silently when it exits non-zero** — Smoke sections run under `set -euo pipefail`, so `OUT=$( "$ROTA_BIN" ... )` aborts the whole section the moment that verb exits non-zero: no FAIL line, the shard log just stops after the last OK, and the gate reports FAILED. Section 49 broke main this way when #461 made `worker gate` refuse an empty `test.full`. When a change adds a refusal or a new exit code to a verb, grep `test/sections/` for every caller whose fixture hits the new rule and run those sections alone (`SECTION_LIST=test/sections/NN_x.sh bash test/runner.sh`); capture an expected failure with `|| true` and assert on the output. <!-- 2026-10-07 -->
## Build & Tooling: Smoke testing: Gate & frozen records

- **A new lock shows up as one line in every golden** — The internal/cli goldens record every file a verb changed, including empty lock sidecars, so adding an fsio.Locked call on a path adds `"<path>.lock": ""` to every golden of every verb that now takes it (30 one-line golden changes in #896 for KNOWLEDGE.md.lock). Regenerate with -update-golden and review the diff as the expected trace of the lock, not as drift. <!-- 2026-10-19 -->
- **Host CLI argv needs one real-host run** — herdr 0.9.3 rejects options before the positional ID (pane/workspace report-metadata: ID first, then --source), yet the argv goldens in internal/worker/testdata pinned the wrong order for a whole round (#537 to #552). A golden only proves what rota sends. When adding or changing a herdr or tmux call, run it once against a real host and paste the result in the PR. <!-- 2026-10-08 -->

- **Fakes hide real-host bugs: run one live check before a release** — A live round against real herdr 0.9.3 found l4ci/hv-skills#196 and l4ci/hv-skills#204-#213, and a live Codex 0.159.2 run found that Codex's `•` reply bullet hid every ROTA-DONE/ROTA-BLOCKED sentinel. All were green under test/fakes. Before a release, run one live check against the real host: a mktemp repo, one worker, a trivial task, the maintainer's own login. Never copy auth files. <!-- 2026-10-04 -->

- **Behavior-changing tasks must sweep smoke sections asserting the old behavior** — A task that intentionally changes behavior (e.g. F21-T7 lifting hv-migrate's umbrella refusal) must sweep the smoke sections that assert the OLD behavior — test/sections/37_migrate.sh still asserted "refuses umbrella project" and only failed on a targeted post-cycle re-run of the affected sections, never during per-task structural verification (which checks the diff, not orthogonal tests). Mitigation: after a behavior-changing wave, before declaring the cycle done, re-run the smoke sections whose subject the change touched (grep test/sections for the old behavior's keyword) — not the full suite, just the implicated sections in isolation against the runner contract. <!-- 2026-05-19 --> (Round-6 renumbering: 37_migrate.sh is now test/sections/39_migrate.sh.)

- **Shared-text changes need the full smoke run before merge** — A change to shared text (skill wording, help text, a path or name used by many sections) needs the full smoke run before merge, not only the touched sections. l4ci/hv-skills#176 broke section 08 that way. <!-- 2026-10-04 -->

- **A config key change regenerates the frozen config record** — Changing a config key's type, default or description changes rota config show output, and TestFrozenConfig then fails 30+ scenarios. Regenerate cmd/rota/testdata/frozen/config.jsonl with ROTA_FROZEN_DAY=2026-10-03,2026-10-03 and check the diff touches only that key (#808). <!-- 2026-10-15 -->

- **Pin ROTA_FROZEN_DAY when regenerating frozen records** — Each cmd/rota/testdata/frozen/*.jsonl carries a recording-day header, so go test ./cmd/rota -update-frozen on a later day rewrites every record. Regenerate with ROTA_FROZEN_DAY=<day>,<day> set to the file's recorded day (2026-10-03 in round 21) and only the records whose inputs changed move; a diff that touches every line means the day was not pinned (#848, 6884e3d). <!-- 2026-10-17 -->

## Build & Tooling: Git & isolation

- **Reviewer subagents export with git archive, never worktree add** — A reviewer subagent that runs git worktree add or remove while a gate runs changes git worktree list, and the gate fails FAIL worktree guard (#659, round 12; #607, round 11). Reviewer and fixer briefs export the branch with git archive <ref> | tar -x -C <scratch> and never touch worktrees. <!-- 2026-10-09 -->
- **Repo-wide renames: one sweep PR owns shared code, slices stack on it** — Run a repo-wide rename as one sweep PR that alone owns shared code. Other slices own disjoint files (front-door docs, release files) and stack on the sweep. Rename on top of the last merged stepping stone, never in parallel slices. Frozen records go through the same rename script; only content hashes may differ. <!-- 2026-10-04 -->
- **bg-isolation guard blocks main-thread Edits under /rota-work branch isolation** — Claude Code's bg-job harness defaults to a worktree-isolation guard that blocks orchestrator `Edit`/`Write` calls (subagent Edits pass — the guard fires main-thread-only). Conflicts with `/rota-work`'s `work.isolation: branch` pattern: edits are blocked even on a feature branch. Mitigation: write `"worktree": {"bgIsolation": "none"}` to `.claude/settings.local.json` (gitignored, per-project) — the documented escape hatch surfaced in the guard's stderr. The two isolations don't conflict architecturally: the guard protects parallel bg-jobs from clobbering each other, /rota-work's branch isolation protects main from feature work. Pre-set the flag in branch-isolation projects. <!-- 2026-05-16 -->
- **EnterWorktree branches from origin/main; rebase onto local main before editing** — The harness's `EnterWorktree` tool branches from `origin/<default-branch>` by default (governed by `worktree.baseRef: fresh`). When local main has commits that haven't been pushed to origin yet, the worktree's HEAD is stale — edits made there will conflict on merge. Rebase the worktree branch onto local main *before* making any edits (`git rebase main` from inside the worktree). The default `fresh` baseRef is intentional (clean origin-based isolation), but in a fast-moving repo where local commits queue up, the rebase-first flow is the correct mitigation. <!-- 2026-05-16 -->
- **git checkout -b inherits HEAD's lead over base** — When starting work, run `git log <base>..HEAD` before `git checkout -b` — commits ahead of base on the cut-from HEAD ride into the feature merge unchanged. Cherry-pick stray commits to base first, then rebase the feature branch so the merge body stays scoped to your work. <!-- 2026-05-15 -->

## Rounds: Orchestration: Reviews & verdicts

- **Record verdicts at review package data.head** — rota review package resolves the branch once and returns that sha as data.head; pass it to rota verdict add --sha so the verdict binds to exactly the commits the reviewer read. Without --sha, verdict add reads the branch again and a worker push in between binds the PASS to code nobody reviewed. <!-- 2026-10-21 sha:903ef239 -->
- **An orchestrator commit on a worker branch needs an independent reviewer** — When the orchestrator pushes a fix or a merge-with-regeneration to a worker's PR branch, the auto-mode classifier refuses the orchestrator's own PASS as self-approval. Dispatch a reviewer subagent on that commit and record its block; fix commits the worker authored can be re-reviewed inline. <!-- 2026-10-20 -->
- **A gate failure on a PASS-reviewed PR needs round bounce --force** — Since #963 round bounce refuses (exit 4, no blocking findings) when the PR's current review records hold no blocking finding. A merge-gate failure is not a review finding, so bouncing a PASS-reviewed PR for it takes --force; minor-only review findings go to the worker as an uncounted relay instead. <!-- 2026-10-20 -->
- **Verdict severities are blocker, major, minor and info** — rota verdict add rejects a finding whose severity is anything else (critical is refused) and a line below 1. Since #963 blocker/major are blocking by default and minor/info deferred; --file-deferred --pr files the deferred ones as items with an acceptance criterion. Give reviewer subagents this enum. <!-- 2026-10-20 -->
- **CONCERNS on a round PR is the orchestrator's call, not a picker** — The light-depth re-review after a bounce (`--since <sha>`) routes CONCERNS as ask in a solo ship, but in a round the orchestrator owns review: record the verdict, judge the open findings yourself (minor ones a Ruling already answers do not earn a third bounce), gate, and carry the findings into the round summary. The gate takes CONCERNS; only FAIL or a missing verdict blocks it. <!-- 2026-10-19 -->
- **Have the reviewer write its verdict JSON to a file** — A reviewer subagent report that ends with the verdict JSON block is cut off in the idle notification when it runs long (round 26, twice), so the block is lost; ask the agent to write the raw JSON to a scratch file and record from that. `rota verdict add` also rejects `"line": 0` anywhere in the body (exit 2, "declined[0].line must be 1 or more"): the brief should say to omit the key, never zero it. <!-- 2026-10-19 -->

- **Mutation-check source-grep guard tests** — A test that greps source for a forbidden pattern can pass while missing the case it exists for: #768's first guard exempted round_status.go, the file the issue named. Ask the reviewer to reintroduce the named regression in a scratch copy and confirm the guard goes red before accepting it. <!-- 2026-10-11 -->

- **Refactor reviews need an old-vs-new input table** — For a behavior-neutral refactor PR, brief the reviewer to build an input-by-input old-vs-new table from main and flag every changed row the PR body does not state. That caught silent regressions in #769 (PRRefNumber stopped parsing 12/ and started accepting #+5) that the worker's own tests missed. <!-- 2026-10-11 -->

- **A commit after the review makes its PASS stale, bookkeeping included** — rota verdict records bind to the head sha, so a chore commit landed after a PASS (a knowledge-hit sidecar sweep, #855) leaves rota verdict route stale and the queue re-reviews a JSON-only diff. Commit sidecars and other bookkeeping before dispatching the reviewers, and merge the reviewed sha as head; a post-review sweep goes in its own PR or is dropped. <!-- 2026-10-18 -->

- **A string ship.review fixes the depth for every branch, labels included** — With ship.review set to the plain string light, rota review depth reports 'default depth' light even for an issue labelled risk:high (round 23, #584, 58 files): only the policy-object form of ship.review consults labels and diff size. Adding a label to force a full review does nothing under the string form; change the config or dispatch the second reviewer by hand and say so in the verdict summary. <!-- 2026-10-19 -->

- **rota verdict add takes no extra top-level fields** — A reviewer block with a top-level key beyond verdict, summary, findings, items and declined (a re-review's deferred list, for instance) is refused with 'unknown field'. Fold the extra list into summary or file it as an issue before recording. <!-- 2026-10-19 -->

- **Re-reviews are one reviewer, majors only, fix range only** — After the maintainer's token-burn call in round 11, a bounced PR's re-review is one reviewer at the orchestrator model, majors only, the fix range only (--since); minors do not bounce and get a follow-up issue only when user-visible. A full two-reviewer pass is for the first review of a PR. <!-- 2026-10-09 -->

- **Renamed Go tests can silently stop running** — Go runs only functions named Test followed by a non-lowercase rune, so a rename like TestSlotWorktree to TestslotWorktree (from unexporting slotWorktree) drops the test with no error and the suite stays green (#745). Go 1.24+ vet (run by go test) rejects the name, but go.mod pins go 1.22, so this repo gets no warning. When a diff renames a Test func, check it still runs: go test -run '^TestName$' -v must list it. <!-- 2026-10-11 -->

- **A tiny fix range is re-reviewed by the orchestrator itself** — The one-reviewer, majors-only re-review of a bounced PR can be the orchestrator reading the fix range inline when it is a few dozen lines it already understands (round 25: #894 and #887 second fix); record the verdict with a summary that names the range and "re-review by the orchestrator" so the gate and the next reader see why only one record exists. Spawn a reviewer when the fix touches code the bounce did not name. <!-- 2026-10-19 -->
## Rounds: Orchestration: Gate, trains & bookkeeping

- **Until #1480: no assign or transfer while a gate runs** — Until #1480 lands: round assign and round transfer switch a slot worktree's branch, and a running gate or train's checkout guard sees it and reds the merge. Start gates and trains in the background, keep reviewing (verdict add touches only gitignored state), and assign freed slots once the gate exits. Remove this bullet when #1480 merges. <!-- 2026-10-21 -->

## Rounds: Orchestration: Workers & relays

- **A busy background shell reads as idle** — rota round watch reports a worker running a long command in a background shell as "idle, static pane, no sentinel". Read the pane before acting: the footer shows "1 shell, N monitors still running" and the worker is waiting on its own test run. <!-- 2026-10-21 -->
- **A bounce relay goes under Notes, not Approvals** — The gate's provenance check reads the slot's current relay log, and a new task dispatch resets it, so a PR whose slot moved on fails PROVENANCE-FAIL for a real relay (#1064). A bounce instruction is not an approval anyway: workers cite it in a Notes section and leave Approvals as None. <!-- 2026-10-20 -->
- **Worker context is mostly fixed preamble** — Round 25 worker sessions (Claude, 7 sessions, 145 turns): 60% of tokens entering context (380k of 638k) and 66% of cache-read is the first-turn preamble (~52-58k tokens, re-read every turn; sessions run only 13-40 turns). 43% of reads is Claude Code system prompt and tool schemas (untrimmable); 18% (17.97%) is the user-global skill, deferred-tool and agent listings (trimmable only if the harness can scope them per worker; unverified); CLAUDE.md+AGENTS.md+hook 6%. Brief 0.7%, KNOWLEDGE query output 1.3%, subagent reports 0% (none used), model prose 4.9%, so brief, KNOWLEDGE and output-style trims cannot beat pruning the listings, if that is possible. Method and table: .rota/spikes/worker-context-attribution.md (#907). <!-- 2026-10-19 -->  Saving if pruned: ~12-14k tokens per turn (listings are 27% of the preamble).
- **Claude Code echoes a brief as a ❯ header with a two-space body** — A dispatched brief or relay shows in a Claude Code pane as `❯ --- ORCHESTRATOR (round N) ---` with every further line indented two spaces, while codex and opencode panes show the bare header (opencode under a ┃ gutter) and only their payloads carry a `--- ROTA-SIG` trailer. - **No harness version pins; Codex uses the default account** — The maintainer ruled (round 5): never pin Codex or Claude CLI versions; check the flags the launch line needs in `--help` instead. - **Record maintainer answers by their real channel, never as a relay** — A maintainer answer given to the orchestrator in its own session is not an orchestrator relay: no relay is logged, so a PR that cites 'orchestrator relay round N' fails the gate with PROVENANCE-FAIL (round 4, #214). ## Rounds: Orchestration: Slate & issues

- **Sibling follow-ups from one review can contradict** — Deferred findings filed by one review can pin opposite behaviour: #1253 asked for a test pinning the symlink-to-dir error while #1254 asked to remove that error. - **Keep deferred findings out of the round that filed them** — Every --file-deferred review files two to five follow-ups on the file it just changed.
