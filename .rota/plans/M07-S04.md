# M07-S04 — Review queue merge flow and /hv-ship issue mode

## Goal

In issue mode, `/hv-review --queue` works through every `needs-review` issue's open PR/MR — PASS merges it and makes sure the issue closes, CONCERNS/FAIL posts findings and flips the issue to `changes-requested` — and `/hv-ship` opens a PR instead of merging.

## Approach

Tracker PR mechanics go into the adapters; two thin helpers expose them: `hv-review-queue` (what to review) and `hv-pr-merge` (merge + close fallback). The review itself stays `/hv-review`'s existing two-stage flow run against the PR branch; queue mode is a loop around it in the skill prose. The PR ↔ issue link is the closing keyword in the PR/MR body (`Closes #N` and GitHub/GitLab synonyms), which `hv-pr --closes` (S03 T4) writes — no extra state.

Decisions (auto, per the user's continue-automatically instruction):
- **Merge method:** merge commit (`gh pr merge --merge --delete-branch`, `glab mr merge --yes --remove-source-branch`), matching `hv-merge`'s `--no-ff` history.
- **Close fallback:** after a merge, any linked issue still open is closed through `IssueBackend.complete(..., reason="done", hash=<merge sha>)`, so the proof gate applies; an unproven item stays open with a `needs-review` → `changes-requested` flip and a comment naming the missing proof (never `--no-proof` automatically).
- **Verdict trail:** every verdict is posted as an `hv-item-comment --kind feedback` on each linked issue and as a PR/MR comment.
- **Loop autonomy:** queue mode merges PASS PRs unattended; interactive mode confirms each merge once (`AskUserQuestion`: merge / skip / stop).

## Assumptions

- PR bodies are authored by `hv-pr --closes` (S03 T4) so the closing keyword is present; PRs opened by hand without one are not in the queue's linkage (listed with `prs: []` so the reviewer sees them).
- `gh pr checkout` / `glab mr checkout` are acceptable side effects on the local repo during a queue run (the skill returns to the base branch afterwards).
