# M07-S07 — Migrate a file backlog to issues

## Goal

`/hv-migrate issues --dry-run|--apply` moves a file-backend project onto the issue backend: open items, their artifacts and milestones end up on the tracker, references are rewritten, and the switch is one config flip.

## Approach

A dedicated helper `bin/hv-migrate-issues` (the existing `hv-migrate` stays the v3→v4 codemod; its SKILL.md gains an `issues` target) drives `IssueBackend` directly regardless of the configured backend. Two passes: create everything, then rewrite references with the final old→new map. Writes are paced for GitHub's secondary limits and the run is resumable from the map.

Decisions (auto, per the user's continue-automatically instruction):
- **Map, not resolution:** `.hv/issue-map.json` (tracked) records old ID → new ID / issue URL. Helpers do **not** resolve old IDs through it (an old `F82` and a new issue `F82` can both exist); the migration rewrites `Related:` fields, design/plan bodies and milestone plans through it, and humans can read it.
- **Scope:** open items (Bugs/Features/Tasks) → issues with labels, native milestone, fields block, detail file → body; proof rows → proof note; `.hv/designs/<ID>.md` → design note; item plans → plan note; planned/active milestones → native milestone + tracking issue with the same `MNN` and status; slice plans → `plan:SNN` notes on the tracking issue. Completed/archived items are not migrated (history stays in `.hv/BACKLOG.md` / `ARCHIVE.md`).
- **Pacing / resume:** ≥1 s between writes (`issues.bulkPaceMs`, default 1000); items already in the map are skipped; a 4 (rate-limited) from the wrapper stops the run with the map saved — re-run continues.
- **Switch:** `--apply` does not flip `backlog.backend`; it prints the one-line `/hv-config backlog.backend=issues` to run after reviewing. `.hv/BACKLOG.md` gains a frozen-banner line at the top on apply.
- **Dry run** (default) prints every planned operation and the would-be map with placeholder numbers; no tracker calls beyond reads.

## Tasks

- **T1** — `bin/hv-migrate-issues [--dry-run|--apply] [--limit N]`: planning pass (collect items, artifacts, milestones), pass 1 creates (milestones first, then items, then notes), pass 2 rewrites references, map file, banner, pacing, resume; `issues.bulkPaceMs` config row.
  - Files: `bin/hv-migrate-issues`, `bin/hvlib_backend.py` (if create needs a body-with-notes path), `bin/hvlib_config.py`, docs config pages, new `test/sections/65_migrate_issues.sh`
  - Verify: 65 against both fakes with `issues.bulkPaceMs: 0` — dry run makes no writes; apply creates the expected issues/labels/milestones/notes; Related rewritten; re-run is a no-op; a rate-limit stop mid-run (`FAKE_TRACKER_FAIL` on the Nth create) then resume completes without duplicates; completed items untouched.

- **T2** — `/hv-migrate` SKILL.md `issues` target (dry-run review, apply, then the config flip and what to check), `docs/usage/` page for the issue backend (setup, config keys, label lifecycle, migration), README pointer.
  - Files: `hv-migrate/SKILL.md`, `docs/usage/issue-backend.md` (new), `README.md` (one line), `docs/reference/cli-helpers.md`
  - Verify: `validate-skills.py`; doc-home check passes.

Waves: T1 → T2. Full smoke at slice end; then the milestone acceptance pass (both fakes end-to-end + the manual real-repo check, which needs the user's go-ahead because it creates real issues).
