# M07-S06 — Umbrella: per-sub-repo trackers

## Goal

Under umbrella mode with `backlog.backend: "issues"`, each sub-repo's items live on that sub-repo's own tracker, and every backlog verb works across them as one backlog.

## Approach

`UmbrellaIssueBackend` holds one `IssueBackend` per registered sub-repo (adapter runs with cwd = the sub-repo path, so provider detection and CLI calls hit that repo's origin) and presents the backend interface: reads merge the per-repo renderings section by section, each bullet carrying `Repos: <name>`; every write is dispatched to the owning repo.

Decisions (auto, per the user's continue-automatically instruction):
- **Refs:** `<repo>#<n>` and `<repo>:<ID>` always resolve; a bare `F42` / `#42` resolves when exactly one sub-repo has it, else exit 1 listing the qualified candidates. Rendered bullets keep the plain `[F42]` grammar plus `Repos:`; `hv-backlog`'s existing Repo column disambiguates for humans.
- **Capture** needs a target repo: `--field Repos=<name>` (or cwd inside a sub-repo via `hv-resolve-repo`); multi-repo items are refused in issue mode — capture one item per repo and link them with `Related:` (qualified refs allowed in Related).
- **Milestones:** the tracking issue lives in a home repo (`issues.homeRepo`, default: first registered sub-repo); a sub-repo's native milestone `MNN — <title>` is created on first use when an item there is assigned to `MNN`. Release runs per sub-repo (as today) and closes that repo's native milestone; the tracking issue's status moves to shipped only when every sub-repo milestone is closed.
- **Review queue / PRs:** `hv-review-queue` iterates all sub-repos; `hv-pr --repo <name> --closes` and `hv-pr-merge --repo <name>` operate on that sub-repo (existing `--repo` convention).
