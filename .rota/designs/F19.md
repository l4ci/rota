# F19 — /hv-migrate v4 codemod (single helper, batch CONTEXT migration, removed_binaries pass)

## Goal

Ship `/hv-migrate v4` as the one-shot codemod that rewrites downstream projects' references to the 8 commands cut by M01, migrates `.hv/CONTEXT.md` content into KNOWLEDGE.md's Glossary topic via F18's batch API, and removes the stale `.hv/bin/` binaries left by the cuts. Upgrading from hv-skills v3.x to v4.0 is a single `/hv-migrate v4` invocation per project — not a manual hunt-and-replace exercise.

## Design

New skill at `hv-migrate/SKILL.md` dispatches a single `bin/hv-migrate` helper — bash wrapper plus Python core, matching the `bin/hv-knowledge-migrate` precedent.

Versioned arg required: `/hv-migrate v4`. Unknown version exits non-zero with helpful error. v4.0 supports `v4` only; future majors add their own arg.

`--dry-run` is default — runs the full migration in-memory and prints a per-file diff summary without writing. `--apply` writes; required for any disk mutation. Idempotent — re-running `--apply` after a clean first run rewrites zero files. `--verbose` adds per-file diffs to both modes.

Backup: every file the codemod touches gets copied to `.hv/migrate-backup/<ISO-timestamp>/<relative-path>` before any rewrite. CONTEXT.md gets backed up before migration; `.hv/bin/hv-*` binaries get backed up before removal. Refuses to re-run inside an existing backup directory.

**Three concerns, one helper:**

- **(a) regex sweep** — apply the 8 word-boundary rules from F19's detail-file table over `.hv/BACKLOG.md`, `.hv/plans/*`, `.hv/designs/*`, `.hv/handoffs/*`, `.hv/qa/*`, `.hv/MILESTONES.md`, `.hv/milestones/*`, `.hv/KNOWLEDGE.md`, `.hv/DECISIONS.md`, and project `CLAUDE.md`. Rewrites both prose AND fenced code blocks.
- **(b) CONTEXT migration** — parse `.hv/CONTEXT.md` with hvlib's `iter_topics` + `parse_term_entry`, build a term manifest, pipe to `hv-glossary-write --batch <manifest>` (**F18 dependency — see Assumptions**). Move `.hv/CONTEXT.md` to backup.
- **(c) removed_binaries pass** — hardcoded list of `.hv/bin/hv-*` files removed by M01 cuts (compiled at `/hv-plan F19` time from F11-F18 acceptance), `os.unlink` each present file with backup to `.hv/migrate-backup/<ts>/bin/`.

**Ambiguous-rewrite policy.** Two rules with ambiguous targets — `/hv-issues` → could be `--from-github` or `--from-gitlab`; `/hv-map` → could be `/hv-init --map` or delete-the-line — do NOT auto-rewrite. Each occurrence is recorded as `<file>:<line>: <reason>` in a `manual-review` summary printed at the end. User resolves by hand. The 6 unambiguous rules rewrite cleanly.

**Safety preconditions** (refuse on each, exit non-zero with clear message): (a) working tree has uncommitted changes outside `.hv/`; (b) running inside an existing backup directory; (c) `.hv/config.json`'s `hvSkills.version` is missing or pre-3.0 (point at `/hv-init` first); (d) umbrella project detected (`.hv/repos.json` + per-sub-repo CONTEXT.md present) — refuse with clear pointer at F21.

**Dogfooding.** Smoke-test section dogfoods against synthetic fixtures — a tmpdir scaffolded with placeholder CONTEXT.md, BACKLOG entries mentioning old commands, fake `.hv/bin/hv-learn --term-add`. Real-project dogfood happens during T8 of F18's plan, once the cumulative M01 cuts have landed.

## Approaches considered

- **A — Single helper, matches `hv-knowledge-migrate` precedent.** **Chosen.** One `bin/hv-migrate` Python core, single SKILL.md dispatch. Migrate runs once per major version; ship velocity wins over future-proofing. Pros: smaller `bin/` footprint, simplest ship, matches existing migration precedent. Cons: one Python module gets large (probably 200-400 lines); each concern shares scope with the others.
- **B — Composed orchestrator + 3 sub-helpers.** Rejected. `bin/hv-migrate-v4-rewrites`, `bin/hv-migrate-v4-context`, `bin/hv-migrate-v4-bins`, `bin/hv-migrate` (orchestrator). Better long-term separation of concerns and individually testable; cleaner partial-failure debugging. Higher file count in `bin/`; more inter-process plumbing; slower to ship for a tool that runs once per major version.

## Open questions

- **`removed_binaries` list construction** — hardcoded inline at `/hv-plan F19` time, read from a shared manifest file, or computed dynamically? *Working answer:* hardcoded inline, compiled from F11-F18 acceptance criteria during planning. If F22's brainstorm picks the manifest option (its Option C), share the manifest between F19 and F22. **Cross-feature coupling to resolve at F22 brainstorm.**
- **`--verbose` scope** — full per-file diff vs just the summary? *Working answer:* summary by default in both `--dry-run` and `--apply`; `--verbose` adds per-file unified diffs.
- **First-run confirmation prompt on `--apply`?** *Working answer:* no — `--apply` is the explicit confirmation. Adding a prompt is friction without protection.
- **Backup directory garbage-collection** — does `.hv/migrate-backup/` accumulate forever? *Working answer:* user owns cleanup. Add to v4.0 announcement notes; spike candidate if growth becomes a real problem.
- **v3.x specificity** — accept all 3.x versions or only the latest 3.x? *Working answer:* accept all 3.x. The 8 command names didn't change shape across 3.0 → 3.3.
- **Integration test against this very repo's `.hv/`** — *Spike candidate.* Run `/hv-migrate v4 --dry-run` against the live `.hv/` once F18 lands; surface anything weird before v4.0 GA.
- **Failure mode when `hv-glossary-write --batch` (F18 obligation) is missing or stale.** *Working answer:* `/hv-migrate v4` refuses with clear error citing the F18 sequencing dependency. F19 cannot ship before F18's batch API.

## Assumptions

- **F18 ships before F19.** `hv-glossary-write --batch <manifest>` exists and is callable. **This is a NEW obligation on F18's design** — was not in F18's original Approach C scope. Surface at report time so F18's plan absorbs it (likely as a new task or a T4 addition).
- **F22 ships in parallel.** Defense in depth for binary removal — F19's `removed_binaries` pass is the v4-specific safety net; F22's `/hv-init` mirror semantic is the class-of-bug fix.
- **Single-repo only at v4.0 GA.** Umbrella support deferred to F21; `/hv-migrate v4` refuses on umbrella projects with clear error.
- **Strict v3.x → v4 path.** Pre-3.0 projects must run `/hv-init` first to bring `hvSkills.version` current.
- **`.hv/config.json` carries `hvSkills.version`** (added in v3.x) — used as the migration trigger and as the "is this project recent enough" gate.
- **User commits or stashes non-`.hv/` uncommitted changes before running.** Refusal is the safety mechanism — F19 doesn't try to be clever about what's safe to leave dirty.
- **Regex rewrites are version-independent within the 3.x line** — the 8 command names didn't change shape across 3.0 → 3.3.
- **Backup directory is one-per-run** (`.hv/migrate-backup/<ISO-timestamp>/`) — never reused or merged. Re-running `--apply` creates a NEW timestamped backup; usually zero files to rewrite.
- **In-scope file set for the regex sweep:** `.hv/BACKLOG.md`, `.hv/plans/*`, `.hv/designs/*`, `.hv/handoffs/*`, `.hv/qa/*`, `.hv/MILESTONES.md`, `.hv/milestones/M*.md`, `.hv/KNOWLEDGE.md`, `.hv/DECISIONS.md`, project `CLAUDE.md`. Old command names appear in milestone prose, learnings, and decision rationale.
- **`removed_binaries` list compiled at `/hv-plan F19` time** from the F11-F18 individual plans. F19's plan cannot finalize this list until those plans surface which canonical `bin/hv-*` files each cut removes.
- **No user shell scripts / aliases / external scripts** — out of scope per F19's detail file. F20's announcement carries the *"check your .zshrc for aliases"* reminder.
