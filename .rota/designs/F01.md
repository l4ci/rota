# F01 — Browser-driven QA skill (/hv-qa)

## Goal

Ship a `/hv-qa <url>` skill that drives a real browser to surface behavioral, performance, and accessibility issues in a running app, with findings auto-captured into BACKLOG.md so the existing `/hv-next` loop picks them up.

## Design

**Skill body** (`hv-qa/SKILL.md`) orchestrates one Playwright session in sequential phases. Helpers live in `bin/`: `hv-qa-setup` (one-time Playwright browser install), `hv-qa-detect-target` (read explicit arg or scan `package.json` + ports 3000/5173/8080), `hv-qa-perf` (CDP trace + Lighthouse run, threshold-based findings), `hv-qa-a11y` (inject axe-core, collect violations), `hv-qa-ux-capture` (screenshot + DOM dump + console + network HAR), and `hv-qa-collate` (severity-floor filter + batched `/hv-capture` dispatch).

**Flow per invocation.** Preflight → resolve target (explicit > auto-detect > error) → launch single Chromium → navigate → phase 1 (`--perf`: CDP trace + Lighthouse) → phase 2 (`--a11y`: axe injection) → phase 3 (`--ux`: artifact capture) → close browser → LLM-as-judge subagent on `--ux` artifacts using the rubric (Nielsen 10, mobile reachability, contrast, target sizes) → collate findings across phases → severity-floor filter → batched capture into BACKLOG.md with `[B]`/`[F]` tagging by severity. Default is all three phases; flags subset them (`--perf`, `--a11y`, `--ux`, or any combination).

**Findings shape.** Each finding carries `{phase, severity, evidence (screenshot path or console line or trace metric), suggested fix, rule_id}`. Severity floor configured in `.hv/config.json` under `qa.minSeverity` (default `P2` so UX-mode spam is gated). Findings above `P0` are tagged `[B]`; everything else routes by `phase` (`--perf`/`--a11y` → `[B]`, `--ux` → `[F]` unless severity is P0/P1).

**LLM-as-judge subagent.** Dispatched via the `Agent` tool with `subagent_type: general-purpose`, model = orchestrator (Opus per `.hv/config.json`). Brief includes the rubric and the captured `--ux` artifacts. Returns structured findings JSON. Cost ceiling: one call per invocation (one rubric pass over batched artifacts), not one per finding.

**Headed default.** Headed in interactive sessions (visible signal during dev); add `--headless` flag for CI. Detection via `CI=true` env var or `--headless` arg auto-flips the default.

## Approaches considered

**A — Single Playwright session, sequential phases (chosen).** One browser, three phases share evidence, LLM-as-judge runs once. Pros: cheapest, simplest, consistent DOM snapshot. Cons: serial wall-clock; phase-1 crash kills the run. Why chosen: three modes share so much infra that splitting just duplicates setup cost.

**B — Three sub-mode code paths, shared Playwright helper.** Each flag is a distinct code path; no-flag invocation runs all three sequentially via the shared helper. Pros: modular, independently testable, matches `/hv-debug` shape. Cons: more code surface, subagent boundary friction for shared evidence. Why rejected: modularity wins are small when phases already share a browser and the artifact reuse pattern is straightforward inline.

**C — Parallel worker dispatch, three browsers.** Three workers in parallel via the `Agent` tool. Pros: fastest, strong isolation, mirrors `/hv-work` waves. Cons: 3× memory/CPU spike, three browser launches, LLM rate-limit risk. Why rejected: parallelism gains are small when individual phases are 5-20s, and three concurrent Playwright instances are heavy for a tool invoked occasionally rather than on every commit.

## Open questions

- **OQ1.** Lighthouse runner — call the npm CLI from `bin/hv-qa-perf` or invoke programmatically via the Lighthouse Node API inside the Playwright process? Spike candidate: `/hv-spike lighthouse-integration` to compare both for run time, error surface, and ease of threshold parsing.
- **OQ2.** Rubric format for `--ux` LLM-as-judge — inline markdown in the skill body, separate `hv-qa/rubric.md` reference, or pluggable via `.hv/qa/rubric.md` so each project can customize? Inline is fastest to ship; pluggable matches the hv-skills project-overrides pattern (e.g. `hv-context`, `hv-decisions`).
- **OQ3.** Dev-server auto-start vs. auto-detect-only when nothing is running — should `hv-qa-detect-target` spawn `npm run dev` (or framework-equivalent) and wait for the port, or fail loudly with "no dev server detected, start one and retry"? Auto-spawn is more convenient; auto-detect-only is more predictable (no orphaned background processes after the run).
- **OQ4.** Per-finding evidence storage — write screenshots/HARs to `.hv/qa/runs/<timestamp>/` and reference via path in BACKLOG entries, or inline base64 (small artifacts only) in the captured TODO? Persisted folder lasts across sessions and is greppable; inline keeps everything in BACKLOG.md but bloats the file.
- **OQ5.** Re-run determinism — phase 1 (perf) is non-deterministic (network, CPU jitter); two consecutive runs produce different findings. Should `hv-qa-collate` dedupe against the last run's findings, or always re-capture full set? Dedupe avoids "same finding three times in BACKLOG"; always-re-capture catches regressions that re-cross thresholds.

## Assumptions

- **A1.** Single-repo only in v1. Umbrella sub-repo orchestration deferred until `umbrella.enabled` lands as a stable feature; `/hv-qa` runs against one URL at a time.
- **A2.** Local dev environment only in v1. CI execution (headless + auth fixtures + secrets management) is explicitly out of scope; F01's detail file already flagged this. CI fitness is a follow-up captured item, not a v1 requirement.
- **A3.** Playwright is the only browser driver. No Cypress / Puppeteer / Selenium alternative; `hv-qa-setup` installs Chromium only (Firefox/WebKit deferred until a need surfaces).
- **A4.** LLM-as-judge for `--ux` uses the orchestrator model (Opus per `.hv/config.json` default). Rubric evaluation needs design judgment, not execution; running it on the worker model would degrade quality. Matches the `/hv-brainstorm --auto-loop` orchestrator-model contract.
- **A5.** Severity floor `qa.minSeverity` defaults to `P2` and is honored by `hv-qa-collate`. UX-mode "consider more whitespace"-class findings are filtered before reaching `/hv-capture` to prevent BACKLOG drowning.
- **A6.** Target URL must be reachable when `/hv-qa` runs. Skill does not retry network errors or wait for cold-start dev servers beyond a short bounded wait (10s) in `hv-qa-detect-target`.
- **A7.** Findings batch into a single `/hv-capture` Skill invocation with multiple items, not N independent invocations. Capture's existing batch shape supports this; per-finding invocation would spam BACKLOG.md timestamps.
