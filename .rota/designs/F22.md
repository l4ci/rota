# F22 — /hv-init mirror-cleanup (find -delete + cp) — class-of-bug fix for helper renames

## Goal

Fix `/hv-init` Step 2's helper-refresh semantic so stale `.hv/bin/hv-*` binaries left over from previous plugin versions are deleted on every `/hv-init` run, eliminating the silent-duplication risk that surfaces whenever M01 (or any future cycle) renames or removes helpers. Shipping this means `claude plugin update hv-skills && /hv-init` produces a `.hv/bin/` that exactly mirrors canonical `bin/` — no leftovers.

## Design

`/hv-init` Step 2's helper-install block changes from one line to two:

```bash
# Was:
cp "$SRC"/hv-* "$SRC"/hvlib.py .hv/bin/ && chmod +x .hv/bin/hv-*

# Becomes:
find .hv/bin/ -maxdepth 1 \( -name 'hv-*' -o -name 'hvlib.py' \) -type f -delete
cp "$SRC"/hv-* "$SRC"/hvlib.py .hv/bin/ && chmod +x .hv/bin/hv-*
```

Tools are POSIX-universal: `find -maxdepth 1 -type f -delete` works on BSD (macOS) and GNU (Linux). No new tool dependency over the current bash + cp.

`-maxdepth 1` prevents recursive descent into bin/ subdirs (none exist today, but defensive). `-type f` scopes to regular files. The OR clause matches both `hv-*` helpers and `hvlib.py` explicitly. `__pycache__` (a directory created by Python at runtime) is untouched — not in the include filter, not a regular file.

Two-step semantic: delete-then-copy. Brief window where `.hv/bin/` has no helpers — irrelevant since `/hv-init` is not concurrent-safe by design.

## Approaches considered

- **A — `rsync -a --delete` with include/exclude filter** (`--include='hv-*' --include='hvlib.py' --exclude='*'`). Rejected: filter syntax fiddly (order matters — `--exclude='*'` must come last), adds tool dependency the codebase doesn't use elsewhere. Universally available but stylistically inconsistent with the bash+cp shape used throughout `bin/`.
- **B — `find -delete` + existing `cp`.** **Chosen.** POSIX universal, no new tool dependency, explicit two-step, simple to test, minimal diff to the current code (one extra line). Matches the spirit of the existing helper.
- **C — Explicit `bin/MANIFEST.txt` listing every shipping helper.** Rejected: net-new file to maintain (must stay in sync with `ls bin/hv-*`); doesn't help F19 (F19 needs v3's REMOVED list, not v4's SHIPPING list); over-engineered for a single use case.

## Open questions

- **Smoke section slot number** — next available is likely 25 or 26 (verify with `ls test/sections/` at `/hv-plan` time). Trivial.
- **Wrap find+cp in a `mirror_helpers` function in SKILL.md, or inline?** *Working answer:* inline — two lines, no indirection needed.
- **Failure mode when a stale helper is read-only** — `find -delete` inherits rm semantics and exits non-zero. `/hv-init` exits non-zero too. *Working answer:* let it propagate. User intervenes manually. Rare case (`.hv/bin/` files are 755 by default).
- **Should `hv-init/SKILL.md` prose announce this as a "v4.0 behavior change"?** Yes — but the announcement copy lives in F20's marketing artifact. F22's SKILL.md updates are mechanical (describe the new behavior; cross-link to F20 for upgrade context).
- **`.hv/bin/__pycache__` handling** — Python creates it at runtime. Find filter excludes it (only matches `hv-*` and `hvlib.py`). *Working answer:* `__pycache__` is left alone by the mirror; Python regenerates it as needed.
- **Future-proofing — other patterns?** If future canonical `bin/` adds `bin/templates/` or similar, filter must update. *Working answer:* current design covers only `hv-*` and `hvlib.py`. Add a SKILL.md note: "if you add new bin/ patterns, update the find filter."

## Assumptions

- `.hv/bin/` is strictly canonical-mirrored. No user-customizable helpers belong there. The CLAUDE.md *"Never edit anything inside `.hv/`"* convention is the contract.
- `find -maxdepth 1 -type f -delete` works on BSD find (macOS) and GNU find (Linux). Both ship `find` with these flags.
- `/hv-init` is one-shot setup work, not concurrent-safe. Two simultaneous `/hv-init` runs on the same project can interleave — out of scope.
- The `cp "$SRC"/hv-* "$SRC"/hvlib.py .hv/bin/` line stays as-is. Only the delete step is added before it.
- `chmod +x .hv/bin/hv-*` line stays — `cp` doesn't preserve mode bits across all filesystems (notably network mounts and Windows-via-WSL).
- Existing test sections (`05_reconcile`, `09_review`) don't directly exercise the `.hv/bin/` install behavior. F22 ships a dedicated smoke section.
- F19 absorbs Change 2 (the explicit v3→v4 `removed_binaries` pass) in its own helper. F22's scope is only Change 1.
- The brief window between delete and copy where `.hv/bin/` has no helpers is acceptable. No skill expects `.hv/bin/` to always be populated mid-`/hv-init` run.
- The mirror behavior is BY DESIGN — users who customize `.hv/bin/` are doing something the existing convention forbids; v4.0 enforces the contract. F20's announcement carries the migration note.
- Future canonical `bin/` additions outside `hv-*` and `hvlib.py` patterns need filter updates. Not a v4.0 concern but flagged in SKILL.md prose.
