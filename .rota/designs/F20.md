# F20 — v4.0 marketing artifact bundle (ANNOUNCEMENT + CHANGELOG + README rewrite)

## Goal

Ship three coupled v4.0 marketing artifacts — `docs/announcements/v4-0.md`, the CHANGELOG v4.0 section, and a rewritten `README.md` — that frame v4.0's command cut as the act of clarifying around the *"Claude that doesn't forget"* wedge, written as an equal-weight two-part essay (~1800 words, DHH-declarative voice). Shipping this means the v4.0 release lands as project identity, not a version bump.

## Design

The announcement at `docs/announcements/v4-0.md` is an equal-weight two-part essay, ~1800 words, DHH-declarative voice (short paragraphs, confident, no hedging).

**Part 1 — the wedge (~900w).** Opens with a scenario the reader recognizes: you `/clear`, last session's gotcha is gone — except in hv-skills it isn't. Introduces `KNOWLEDGE.md` + `DECISIONS.md` + handoff-across-`/clear` as the project's memory layer. Names *"Claude that doesn't forget"* as the wedge. Frames v4 as the act of clarifying around the wedge, not introducing it — the wedge has been here since v1.

**Part 2 — the cut (~900w).** Opens with the complexity-budget framing (htmx essay pattern). Walks through what changed with a *"so you can…"* clause for each cut. Lands the receipts table near the close. Closes with the SCOPE section — 3-5 boundaries hv-skills will not become, esbuild-measured tone.

A short migration footer below Part 2 points v3 users to `/hv-migrate v4`. Not a recap of procedures — just the one command and a link.

The **CHANGELOG.md v4.0 section** lifts the receipts table verbatim, adds version metadata and date. It's the only place the cut is enumerated outside the announcement.

The **README rewrite** updates the five-lanes prose and feature table to the 20-command surface, adds *"Upgrading from v3? Run `/hv-migrate v4`"* as a banner above the Install section. FAQ stays intact (evergreen).

**Sequencing.** Part 1 + Part 2 outline + a 200-word voice sample drafted FIRST, before any cut lands — locks framing and voice. CHANGELOG built iteratively as cuts merge. README rewritten LAST when all 8 cuts are in. Final read-through across all three before `/hv-release` tags v4.0.

**Highest-risk piece:** the bridge paragraph between Part 1 and Part 2. It must connect *"the wedge has been here"* to *"so v4 cuts everything that wasn't it"* without sounding glib. Plan should call this out as a draft-and-redraft task, not a single-pass write.

## Approaches considered

- **A — Tight & matter-of-fact (~1200w, htmx voice, 30/70 split).** Wedge as preamble, cut as bulk. **Rejected:** the two-part framing decision implies equal weight, and demoting the wedge to preamble loses the strategic-positioning win that the two-part choice was made to capture.
- **B — Equal-weight essay (~1800w, DHH voice, 50/50 split).** **Chosen.** Wedge and cut get equal narrative weight; serves new readers (wedge half) and v3 users (cut half) in one document without forcing either audience; the wedge gets the room it needs to land. Cost: hardest authoring lift; voice must be tight or it sprawls; bridge between halves is non-trivial.
- **C — Worked examples (~1600w, demonstrative, 40/60 split).** Both halves anchored to specific project scenarios — show, don't tell. **Rejected:** examples date faster than principles, requires real dogfooding evidence to write authentically, and the harder authoring craft makes voice consistency riskier than B.

## Open questions

- **Voice sample first?** `/hv-plan` should produce a 200-word DHH-declarative voice sample as a Phase 0 task before the full draft — so the voice is locked, not discovered mid-draft.
- **Bridge paragraph craft.** Single sentence or full paragraph? Tone implications differ. Plan should treat this as 2-3 draft iterations, not a single pass.
- **Receipts table breadth.** Cuts only, or include cuts deliberately NOT made (e.g., kept `/hv-decide` and `/hv-learn` distinct despite overlap)? Adds depth at the cost of length. Spike candidate: try both versions, compare.
- **SCOPE section exact placement.** Near the close of Part 2 or the literal close (before migration footer)? Working answer: the literal close, so the reader leaves with the boundary statement, then the migration line as an actionable post-script.
- **Writer attribution.** Does Claude draft and the user edits, or does the user draft and Claude edits? Affects voice authenticity. Working answer: Claude drafts to outline, user owns voice pass on Part 1 (the wedge half), Claude finishes Part 2 (the cut half — more mechanical given the receipts).
- **Citation style.** Markdown footnotes vs inline citations for the research references (Tailwind v4, Rails, htmx, esbuild, etc.)? Inline reads tighter; footnotes preserve flow. Working answer: inline.
- **Banner placement in README.** Above Install heading, or inside the Install section as the first line? Working answer: above, so it's visible without scrolling.

## Assumptions

- Audience is mixed — existing v3 users (migration framing) AND new readers (intro framing). Two-part structure serves both without forcing either.
- Voice is DHH-declarative — not Apple-tense, not Vercel-corporate, not Stripe-clean. Reference touchstone: rubyonrails.org/doctrine.
- *"Claude that doesn't forget"* is the established wedge phrasing from this point forward; the announcement coins it, then it propagates to README and elsewhere.
- The announcement is NOT a migration guide — `/hv-migrate v4` is the one command pointed to; procedures live in the migrate skill's own output, not the post.
- The receipts table lives in two places (announcement + CHANGELOG) with identical content. Source of truth is the announcement.
- ~1800 words ±200 is acceptable. Below 1500 risks shallow; above 2200 risks tangents.
- External publishing (Mastodon, dev.to, Twitter) is out of scope for milestone completion — user's call post-merge.
- CHANGELOG and README artifacts are mechanical given the announcement. The announcement is the design challenge; the other two follow.
- The FAQ in the README (vs GSD, Octo, TODO.md) stays — evergreen comparisons, not v4-specific.
