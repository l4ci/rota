# F26 — design/plan/spike/vision CRUD triplet consolidation

## Goal

Bring all four artifact families (design, plan, spike, vision) to API parity for `show` by extracting a shared `bin/hv-artifact-show.sh` lib and filling the two missing show helpers.

## Design

Add `bin/hv-artifact-show.sh` mirroring the existing `bin/hv-artifact-rm.sh` precedent — a sourceable lib exposing `hv_artifact_show <kind> <id-or-key> <dir>` that owns the `[ ! -f "$path" ] && error >&2 && exit 1; cat "$path"` pattern. Update `bin/hv-design-show` and `bin/hv-plan-show` to source the lib and delegate (each shrinks 13 → ~5 lines). Add the two missing helpers `bin/hv-vision-show` (resolves `.hv/milestones/<MID>.md`) and `bin/hv-spike-show` (resolves `.hv/spikes/<name>.md`). Key validation stays in each calling helper where the family-specific regex lives (`M\d{2,}` for vision, slug-shape for spike); the lib accepts any string and only checks file existence — keeping the lib pattern-agnostic the way `hv-artifact-rm.sh` is today. List helpers are explicitly out of scope: their projections diverge per-family (git lookups, deps closures, milestone filters) and folding them would force per-kind branches inward. Skill callsites and docs are unaffected because helper names don't change. Smoke gains one new section per new helper.

## Approaches considered

- **A (chosen)** — show fold + parity-fill. *Shape:* `hv-artifact-show.sh` shared lib; two existing helpers shrunk; two missing helpers added. *Pros:* Matches existing precedent; zero callsite churn; closes API-parity gap; minimal risk. *Cons:* Modest LOC win (~26 lines); net file count grows. *Why this:* Surgical and honest about the actual code shape — the `*-add` helpers genuinely diverge so we don't pretend they don't.
- **B** — A plus list-helper extraction. *Pros:* Bigger LOC win (~60 lines). *Cons:* List projections genuinely differ (branchExists, ready, milestone filter); folding them inverts control and degrades readability. *Why not:* Forces a framework where straight-line code was clearer.
- **C** — Narrow F26 to Cosmetic, re-tag. *Pros:* Honest sizing; frees M01 capacity. *Cons:* Same code as A with a relabel. *Why not:* The work happens either way; A delivers it cleanly without bureaucratic reshuffling.

## Open questions

- Should `hv-vision-show` accept title fragments in addition to `M01`-style IDs? Recommend strict-ID for parity with `hv-plan-show`'s key-based input — titles can be looked up via `hv-vision-list`.
- Should the lib gain an `--fm` flag that prints frontmatter without the body? Out of scope for F26; capture as a follow-up if a caller needs it.
- One smoke section per new helper, or one combined section? Recommend one per helper to match existing per-helper smoke granularity.

## Assumptions

- The `hv-artifact-rm.sh` shape (source-after-preamble, single-function entry, `exit 0` success / `exit 1` not-found) is the canonical sourceable-lib pattern. `hv-artifact-show.sh` adopts it verbatim.
- All four families' detail-file paths are stable and bare: `.hv/designs/<ID>.md`, `.hv/plans/<key>.md`, `.hv/spikes/<name>.md`, `.hv/milestones/<MID>.md`. The lib takes `(dir, key)` and joins — no resolution logic.
- Missing `hv-vision-show` / `hv-spike-show` are oversight, not deliberate design — vision has `hv-vision-list` but no read-detail helper; same for spike. Both fill cleanly.
- Out-of-scope helpers (`hv-spike-finish`, `hv-vision-status`, `hv-plan-rename-check`, derived `hv-vision-active` / `-empty-active` / `-index`) stay family-specific by design and are not touched.
