# F25 — hvlib.py decomposition into flat hvlib_<name>.py modules

## Goal

Reduce `bin/hvlib.py` from 874 LoC to a thin ~50-LoC re-export shim by extracting the remaining ~9 logical concerns into flat `hvlib_<name>.py` modules. F25 completes M01's hvlib decomposition arc started in Rounds 1-3; future bootstrap-order changes become single-file edits.

## Design

F25 continues the flat-module pattern established by Rounds 1-3 (`hvlib_io.py`, `hvlib_version.py`). After F25, `bin/hvlib.py` becomes a pure re-export shim — every public name re-exported via explicit `from hvlib_<concern> import (...)` lists. No `__init__.py`, no PYTHONPATH changes, no caller migration.

Nine new flat modules planned: `hvlib_section`, `hvlib_bullet`, `hvlib_repos`, `hvlib_milestone`, `hvlib_crossref`, `hvlib_frontmatter`, `hvlib_glossary`, `hvlib_paths`, `hvlib_misc`. The 73 PYTHONPATH heredoc helpers see `from hvlib import X` continue to resolve via the shim — no behavior change for callers.

Verification rides on a new import sentinel (`test/sections/44_hvlib_exports.sh`, renumbered in round 6) that imports every public hvlib name and exits non-zero on `ImportError` / `AttributeError`. Per-commit sentinel pass is the cheap signal; full `bash test/smoke.sh` runs at ship time per project convention.

Sequencing: dependency-ordered, ~8-9 commits ("Round 4..N: extract hvlib_<name>"). Leaves first (section, bullet, frontmatter, paths, repos), then dependents (milestone, glossary, crossref), then misc-extract + final shim collapse. Each commit synchronizes the shim's re-export list — never a half-broken intermediate state.

Bootstrap exclusions from F24 (`hv-preflight`, `hv-bootstrap`, `hv-walk-up`, `hv-resolve-*`, `hv-umbrella-*`, `hv-version-check`) unchanged — they don't import hvlib. PYTHONPATH heredoc body rewrites (F24's deferred 14 helpers) are explicitly out of scope; captured as a follow-up `[F##]` post-M01.

## Approaches considered

**A. Big-bang single commit.** All ~9 modules in one PR; import sentinel + full smoke run once at the end.
- *Pros:* One review, one merge, one verification cycle. Smallest `git log` footprint.
- *Cons:* Failure surface is the whole change — hard to bisect which module's extraction broke a caller. Reviewer-hostile for 9 modules of mechanical moves.
- *Why this is not the right answer:* Throws away the bisection signal that incremental cuts give; breaks Rounds 1-3's per-round cadence.

**B. One module per commit, dependency-ordered (chosen).** ~8-9 commits with import sentinel after each. Leaves first (section, bullet, frontmatter, paths, repos), then dependents (milestone, glossary, crossref), then misc + shim collapse.
- *Pros:* Trivial bisection — a caller break names the offending commit. Reviewer-friendly per-commit diff. Continues Rounds 1-3 cadence. Pause/resume is cheap.
- *Cons:* 8-9 commits inflate PR commit count. Each commit must keep `hvlib.py` re-export list in sync — 9 small synchronization edits instead of 1.
- *Why this is the right answer:* Matches the established working pattern. Per-commit sentinel-pass is the strongest cheap "nothing broke" signal. The synchronization friction is intentional — it forces every extracted name to land in the shim's public surface.

**C. Layered batches (3 commits).** Leaves → dependents → shim. Sentinel runs after each batch.
- *Pros:* Reduces commit count to 3 reviewable chunks with coherent themes. Faster end-to-end than B.
- *Cons:* Within-batch bisection regresses — a sentinel failure pins the batch but not the module. Mid-size diffs (~5 file moves per batch) for reviewers.
- *Why this is not the right answer:* Bets that mechanical-move correctness needs no per-module checkpoint. The savings (3 vs 9 commits) don't pay back if anything breaks inside a batch.

## Open questions

1. **Module count exact.** Nine modules assumes one-concern-per-module. `hvlib_milestone` is only 2 functions (~50 LoC) and could fold into `hvlib_repos` (registry-shaped sibling). Decision deferred to `/hv-plan`'s per-batch task definition.
2. **Where does `find_item_ids` live?** Used by both bullet ops and section-scanning callers. Default: `hvlib_bullet` (ID-extraction is bullet-shaped); reconsider if it forces an awkward cross-module import during extraction.
3. **Constant placement.** `BACKLOG_FILE = "BACKLOG.md"` — keep in shim (constants stable, callers reference `hvlib.BACKLOG_FILE`) or extract to `hvlib_misc`. Default: keep in shim.
4. **Sentinel test enumeration strategy.** Sentinel needs exhaustive public-name list. Plan: grep `from hvlib import` across `bin/hv-*` and union symbols, then cross-check with `python3 -c "import hvlib; print([n for n in dir(hvlib) if not n.startswith('_')])"`. Diff catches missed names. Risk: a name imported only via heredoc-string concatenation evades the grep — manual spot-check on each heredoc helper during plan task.

## Assumptions

- Rounds 1-3 pattern continues unchanged (`hvlib_<name>.py` flat, explicit re-export, per-round commit).
- No package shape (`hvlib/` folder). Captured as out-of-scope; revisitable post-v4.
- 73 heredoc callers stay unmodified. Only `hvlib.py` and new `hvlib_<name>.py` files change.
- F24's bootstrap exclusion list applies unchanged. No hvlib import added to excluded helpers.
- PYTHONPATH heredoc body rewrites are out of scope. Future `[F##]` post-M01.
- Smoke runs at ship time, not per task. Per-commit verification = sentinel + targeted reproducer.
- No semantic changes during extraction. Function bodies move verbatim; refactoring inside a module is a separate concern.
