# F18 — Fold /hv-learn --term into /hv-learn --term (data-shape fold, single-repo)

## Goal

Ship the data-shape fold of `/hv-learn --term` into `/hv-learn --term` — terms migrate to a pinned `## Glossary` topic in `.hv/KNOWLEDGE.md` as nested-bullet entries, the `/hv-learn --term` skill is removed, and existing CONTEXT helpers are renamed and retargeted at the new storage. Shipping this means terms and learnings share one user-facing skill and one storage file for single-repo projects, while preserving Aliases, Not, alphabetical insertion, and cross-term alias-collision uniqueness.

## Design

Terms live in a pinned `## Glossary` topic at the top of `.hv/KNOWLEDGE.md` (alongside `## Architecture` and `## Build & Tooling`, which are the existing pinned topics).

Each term entry is a nested-bullet structure:

```
- **<term>** — <definition>
  - **Aliases:** X, Y
  - **Not:** Z
  <!-- YYYY-MM-DD -->
```

Date stamp lives as an HTML comment after the main bullet (existing KNOWLEDGE convention).

`/hv-learn --term` skill removed (folder, plugin.json, marketplace.json). Helpers `hv-context-add` and `hv-context-query` renamed via `git mv` to `hv-glossary-write` and `hv-glossary-read`. Existing logic preserved verbatim — alphabetical insertion, cross-term alias-collision refusal, structured field parsing.

The renamed helpers' write target changes from `.hv/CONTEXT.md` to the `## Glossary` section block inside `.hv/KNOWLEDGE.md`. Parsers extract the Glossary block, modify it in memory, write back. The rest of KNOWLEDGE.md is untouched.

`/hv-learn --term <name>` is a new flag on `/hv-learn` that exits the normal discovery flow and dispatches to `hv-glossary-write` directly. Same arg shape: `--def`, `--alias`, `--not`. Surface unifies on `/hv-learn`.

`hv-knowledge-merge` and `hv-knowledge-query` stay untouched and treat Glossary as not-their-business. `hv-knowledge-tier` learns a one-line skip for the Glossary topic (terms aren't tier-eligible).

`/hv-migrate v4` (F19) detects `.hv/CONTEXT.md`, parses its H2 term sections, writes each through `hv-glossary-write`. Idempotent, `--dry-run` default, backup to `.hv/migrate-backup/<timestamp>/`. Umbrella projects (`.hv/repos.json` present plus per-sub-repo CONTEXT.md files) trigger an explicit error pointing to F21.

CLAUDE.md managed-block: the `## Project Context` block is removed; terms surface via the existing `## Project Knowledge` index because Glossary is just a topic. `hv-knowledge-index` picks it up automatically with no change.

## Approaches considered

- **A — Extend `hv-knowledge-merge` with `--glossary` mode.** *Rejected:* spreads glossary-mode branching across 3-4 helpers (`merge`, `query`, `tier`); widens internal complexity to win user-surface consolidation. Worst of both architecturally — high internal cost for a marginal user-facing win over Approach C.
- **B — Dedicated `hv-glossary-*` helpers + skip-Glossary in knowledge helpers.** *Rejected:* cleanest long-term separation of concerns but slower to ship. Two complete write paths to maintain from scratch instead of recycling well-tested code. Better candidate for a v5 cleanup than for v4 first ship.
- **C — Retarget existing CONTEXT helpers (rename + new target file).** **Chosen.** Maximum logic reuse: the CONTEXT helpers were designed for this exact data shape (Aliases, Not, alphabetical insertion, collision-check). Recycle the tested code, change the target file. The two-write-paths-against-same-file risk is mitigated by a smoke-test pass and the fact that writes are sequential by usage.

## Open questions

- **Helper rename vs. delete-and-replace.** `git mv hv-context-add hv-glossary-write` preserves history but downstream projects with symlinks or custom wrappers break on `/hv-update`. Alternative: delete the old, create new. Decided in `/hv-plan`.
- **Glossary topic position in KNOWLEDGE.md.** Pinned at the top alongside Architecture/Build & Tooling, or alphabetical with the rest? Pinned-at-top feels right (terms are foundational); confirm in `/hv-plan`.
- **What does `/hv-migrate v4` do when KNOWLEDGE.md already has a `## Glossary` topic?** Working answer: merge into existing Glossary, refuse per-term on alias collision using the existing collision logic. Edge case for partial earlier migration runs.
- **Sub-bullets inside KNOWLEDGE.md — does `hv-knowledge-merge` see them in non-Glossary topics and misparse?** *Spike candidate.* Quick smoke test against the current parser to confirm it skips nested content correctly. If broken, parser hardening becomes part of F18.
- **Date-stamp placement on nested-bullet entries.** HTML comment after the closing nested bullet, or attached to the main bullet line? Working answer: main bullet (matches existing KNOWLEDGE convention).
- **`> from:` prefix on `hv-glossary-read` output.** In single-repo mode today it prints `> from: .hv/CONTEXT.md`; post-fold it should print `> from: .hv/KNOWLEDGE.md (## Glossary)`. Cosmetic but should be deliberate — confirm in `/hv-plan`.
- **Pre-fold smoke test of `hv-context-add`.** Recycling bets on the original being correct. Add a smoke-test pass against the un-renamed helper as the first task of F18 so any pre-existing bugs surface before they propagate.

## Assumptions

- **Single-repo only.** Umbrella support split to **F21** (captured this brainstorm). `/hv-migrate v4` errors on umbrella projects with explicit "wait for F21" guidance.
- The existing `hv-context-add` helper logic is correct enough to recycle. Bugs would propagate to the new path; pre-fold smoke test gates this.
- `.hv/KNOWLEDGE.md` will have `## Glossary` reserved at v4.0 ship — `/hv-init` writes it during new-project setup, and `/hv-migrate v4` writes it on existing projects before populating.
- F03 tier system applies to all topics by default; Glossary is the one special-case. The skip is a single-line check in `hv-knowledge-tier`.
- `hv-knowledge-index` (CLAUDE.md managed-block regenerator) needs no change — Glossary surfaces as a topic automatically through the existing topic-extraction code path.
- Two write paths against `KNOWLEDGE.md` (`hv-knowledge-merge` for learnings, `hv-glossary-write` for terms) are safe under sequential invocation. Concurrent writes are out of scope — no skill expects them.
- "Renamed in place" = `git mv` in canonical `bin/`; on user side, `/hv-update` re-runs `/hv-init` and replaces helper files. Custom symlinks/wrappers need user-side migration guidance in the v4.0 announcement.
- Alphabetical insertion semantic survives: alphabetical within the Glossary topic, not across all of KNOWLEDGE.md.
- `/hv-migrate v4` does NOT need to migrate the F03 tier sidecar (`.hv/knowledge-tier.json`) — Glossary entries don't appear in the sidecar by design.
- `/hv-learn --term-query` invoked at the CLI directly (not via /hv-learn) becomes `hv-glossary-read` post-rename; any documentation or skill references to `hv-context-query` need rewriting (handled by F19 migrate logic on user files; F18 handles canonical sources).
