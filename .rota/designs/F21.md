# F21 — Umbrella-aware KNOWLEDGE.md (hybrid umbrella + per-sub-repo storage)

## Goal

Ship F21 to enable umbrella users to scope `.hv/KNOWLEDGE.md` content to either umbrella (cross-repo) or per-sub-repo files via the same auto-resolve-or-ask UX `/hv-learn --term` uses today. Glossary topics from F18 follow the same hybrid model. Shipping this means umbrella users running `/hv-migrate v4` no longer hit F19's explicit refusal — they get coherent term and learning storage that respects repo locality, while DECISIONS.md stays permanently umbrella-shared by architectural commitment.

## Design

**Storage layout** — umbrella `.hv/KNOWLEDGE.md` (cross-repo learnings + umbrella-Glossary terms) AND per-sub-repo `.hv/knowledge/<repo>/KNOWLEDGE.md` (repo-local learnings + per-sub-repo Glossary terms). Mirrors CONTEXT.md's existing two-tier model exactly.

**Routing UX** — `/hv-learn` and `hv-glossary-write` (F18) auto-resolve sub-repo from cwd via `hv-resolve-repo`. At umbrella root: ask once via `AskUserQuestion` — *"Capture as umbrella-shared, or scoped to `<repo>`?"* with sub-repo options + *"Umbrella-shared (Recommended)"*. `--repo` flag overrides everything. Resolution logic lives in `bin/hv-knowledge-scope.sh` (`hv_resolve_knowledge_scope`); the `/hv-learn` Step 5 / `--term` UX provides the ask surface.

**Helper rewiring** — all 5 `hv-knowledge-*` helpers (merge, query, index, tier, amend) gain `--repo umbrella|<name>` handling with auto-resolve fallback. Target-file resolution lives in `hvlib` as a new `resolve_knowledge_target(repo)` function returning the right path.

**Reader semantic** — `hv-knowledge-query` reads BOTH umbrella and active-sub-repo files when called inside a sub-repo; emits `> from: <file>` prefix per existing convention so output remains traceable. At umbrella root, queries umbrella only unless `--repo` is specified.

**Tier sidecar split** — per-sub-repo `.hv/knowledge/<repo>/knowledge-tier.json` for the sub-repo file + umbrella `.hv/knowledge-tier.json` for the umbrella file. Each sidecar tracks its own file's bullets. Symmetric with the data-file split.

**CLAUDE.md managed-block** — each sub-repo's CLAUDE.md gets a `hv-knowledge-index`-generated block listing **umbrella topics + the sub-repo's own topics**. Reader scope = umbrella + active. Single-repo projects unchanged (umbrella file only).

**`/hv-migrate v4` umbrella branch** — for each existing `.hv/contexts/<repo>/CONTEXT.md`, parse with hvlib's `iter_topics` + `parse_term_entry`, write to `.hv/knowledge/<repo>/KNOWLEDGE.md`'s Glossary topic via `hv-glossary-write --batch`. Move CONTEXT.md to backup. Existing umbrella `.hv/KNOWLEDGE.md` left alone — those learnings were already umbrella-shared.

**DECISIONS.md UNCHANGED** — stays permanently umbrella-shared. Architectural rationale (hard boundaries are inherently cross-repo; repo-local commitments belong in KNOWLEDGE.md as learnings) documented in the `references/persistence-skills.md` update that's part of F21's acceptance.

## Approaches considered

- **A — Sidecar files** (`.hv/KNOWLEDGE.md` umbrella + `.hv/knowledge/<repo>/KNOWLEDGE.md` per sub-repo). **Chosen.** Mirrors CONTEXT.md's tested model. Clean separation; each file independently editable; target-path resolution in one helper.
- **B — Topic-suffix in single file** (`## Architecture` for umbrella, `## Architecture: web` for sub-repo, all in one .hv/KNOWLEDGE.md). *Rejected:* topic names get noisy in N-sub-repo projects, KNOWLEDGE.md grows large, cross-repo grep harder, asymmetric with how CONTEXT.md handles the same problem.
- **C — Per-bullet scope tag** (`- **Title** <repo: web> — body` inline in shared file). *Rejected:* loses topic-level grouping by scope, reader has to scan every bullet's tag to know its scope, hardest to read visually.

## Open questions

- **Ship in v4.0 GA or v4.1?** F21 currently untagged on milestone. `/hv-plan F21` decides. v4.0 grows M01 substantially. v4.1 means umbrella users bounce off `/hv-migrate v4`'s explicit refusal for one release cycle. *Working answer:* defer to `/hv-plan F21` as a milestone-tag decision; lean v4.1 unless dogfooding evidence on this very repo (no umbrella state) reveals it's small enough for v4.0.
- **`references/persistence-umbrella-scoping.md`** — resolved: created as a new canonical reference (not a rename of any prior file) covering the full hybrid model (KNOWLEDGE hybrid, DECISIONS umbrella-only, CONTEXT folded into hybrid Glossary). Ships as part of T8.
- **`hv-knowledge-amend` ambiguity** — when an entry with the same `(topic, title)` exists in BOTH umbrella and sub-repo files, which gets amended? *Resolved:* refuse with conflict error pointing to both files; user must pass `--repo` explicitly to disambiguate. Shipped in T4.
- **`/hv-init` umbrella-mode seeding** — pre-create `.hv/knowledge/<repo>/` for each registered sub-repo? *Working answer:* yes, mirrors today's `.hv/contexts/<repo>/` pre-creation in `hv-umbrella-init`.
- **Architectural commitment via `/hv-decide`** — capture the persistence-trio scoping rule (KNOWLEDGE hybrid, DECISIONS umbrella-only) as a hard boundary? *Working answer:* yes, manually invoke `/hv-decide` post-F21 ship with rule: *"persistence-trio scoping: KNOWLEDGE hybrid (umbrella + sub-repo), DECISIONS umbrella-only, CONTEXT folded into KNOWLEDGE Glossary."* Forbids future drift toward forcing all content into one scope.
- **CLAUDE.md at umbrella root** — does the umbrella root have its own CLAUDE.md, and if so what does its managed-block contain? *Working answer:* umbrella root may or may not be a git repo, may or may not have CLAUDE.md. When present, its block lists umbrella topics only — sub-repo-specific topics live in each sub-repo's own CLAUDE.md.
- **Test coverage** — new smoke section exercising hybrid storage end-to-end: write umbrella + sub-repo entries, query from inside sub-repo, query from umbrella root, migrate runs correctly. *Spike candidate* only if synthetic-umbrella-fixture authoring proves harder than expected; otherwise straightforward.

## Assumptions

- **F18 ships before F21.** `hv-glossary-write --batch <manifest>` (F18 T9) exists and is callable by `/hv-migrate v4`'s umbrella branch.
- **Existing umbrella `.hv/KNOWLEDGE.md` content stays umbrella-shared.** F21 doesn't retroactively split it — only new captures route per-sub-repo when the user wants them to.
- **DECISIONS.md is permanently umbrella-shared** by architectural commitment. The hybrid model is KNOWLEDGE-only. Captured via `/hv-decide` post-ship.
- **The hybrid model applies to learnings AND Glossary terms** — same routing UX, same storage shape, same query semantics. One mental model, two content types.
- **CONTEXT.md → KNOWLEDGE.md Glossary migration in `/hv-migrate v4`** writes to the **sub-repo's** KNOWLEDGE.md, not the umbrella file. CONTEXT.md was already per-sub-repo, so terms preserve their locality through the fold.
- **`/hv-init` pre-creates `.hv/knowledge/<repo>/`** during umbrella-mode setup. Mirrors today's `.hv/contexts/<repo>/` pre-creation in `hv-umbrella-init`.
- **`hv-knowledge-tier` sidecar splits** for symmetry with the data-file split. Each KNOWLEDGE file has its own tier sidecar. Could be reverted to single-composite-key shape later if symmetry proves cumbersome.
- **CLAUDE.md managed-block** in each sub-repo lists umbrella + own-sub-repo topics. Single-repo projects unchanged. Umbrella-root CLAUDE.md (if it exists) lists umbrella topics only.
- **`references/persistence-umbrella-scoping.md` created** as a new canonical reference covering the full hybrid model. Ships in T8; no prior file renamed.
- **F21 is currently untagged on milestone.** `/hv-plan F21` decides v4.0 GA vs v4.1.
