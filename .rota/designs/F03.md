# F03 — Knowledge promotion lifecycle in /hv-learn

## Goal

Ship a confidence-tiered `KNOWLEDGE.md` lifecycle — every bullet carries a tier (`provisional` / `confirmed` / `deprecated`) backed by automatic promotion via usage tracking and heuristic demotion via topic-overlap detection on user corrections, so consumers of `hv-knowledge-query` get a signal about which learnings have earned trust and which are still on probation.

## Design

State lives in a sidecar at `.hv/knowledge-stats.json`, keyed by `(topic, title)` → `{tier, hits, lastSeen, contradictions: []}`. `KNOWLEDGE.md` itself stays human-readable and authoritative for content; the sidecar carries only the lifecycle metadata. A new helper `bin/hv-knowledge-stats` (the writer; reuses the read-side function name for consumers) initializes new entries to `provisional` when `hv-knowledge-merge` lands a bullet, increments `hits` on consumer usage, auto-promotes to `confirmed` when `hits >= 3` without an outstanding contradiction, and demotes to `deprecated` on user-confirmed contradiction. `bin/hv-knowledge-query` reads the sidecar alongside the markdown, hides `deprecated` bullets from default output, and suffixes ` (provisional)` on bullets still on probation; `--include-deprecated` and `--tier <name>` flags let callers opt into the hidden set or filter explicitly. Cross-skill instrumentation: `/hv-work` and `/hv-review` call a new `bin/hv-knowledge-hit <topic> <title>` after consuming a queried bullet (no user correction = hit registered); they also log topic-overlap candidates to `.hv/knowledge-contradictions.json` when a user correction's text overlaps a queried bullet's body. `/hv-learn` Step 8 surfaces the pending contradictions list at session end and asks per-bullet whether to demote. `/hv-learn` gains three explicit flags — `--promote <topic> "<title>"`, `--deprecate <topic> "<title>"`, `--amend <topic> "<title>"` — for manual overrides; `--amend` preserves tier + hits, only rewrites the body via a controlled edit. A one-shot migration helper `bin/hv-knowledge-migrate` stamps every existing bullet as `provisional` on first F03-aware invocation so the rollout is observable rather than silently inherited.

## Approaches considered

**Full lifecycle (chosen).** Sidecar storage plus auto-promotion via hit-counter plus heuristic demotion via topic-overlap detection. Manual `--promote` / `--deprecate` / `--amend` overrides. **Pros:** delivers the durable-knowledge signal end-to-end; consumers immediately benefit from the `(provisional)` suffix without changing their code; manual overrides keep the user in control when heuristics misfire. **Cons:** larger surface — touches `/hv-work`, `/hv-review`, `/hv-learn`, plus 4-6 new helpers. Heuristic demotion has false-positive risk (mitigated by session-end user confirmation). **Why this is the right answer:** the V1 manual-only variant ships a sidecar that the cross-skill instrumentation never gets around to wiring, leaving the feature half-ported; full lifecycle ships the value the detail file promises.

**Manual V1 only (rejected).** Same sidecar storage, but no hit counter or contradiction tracker — every tier change requires explicit `/hv-learn --promote` / `--deprecate`. **Pros:** small surface (touches only `/hv-learn`); zero false-positive risk; ~3 helpers. **Cons:** the "promote after N successful applications" semantic from the detail file isn't actually realized — only the storage is; the lifecycle feels half-shipped because the autonomy story sits dormant until a follow-up captures the instrumentation. **Why this isn't right:** the value proposition is "skills get a confidence signal automatically"; gating it on manual user action erodes the win.

**Phased (rejected).** Manual V1 ships now plus a new backlog item `F0X` for the instrumentation. **Pros:** smallest ship surface; ship-it discipline. **Cons:** the instrumentation work is the harder half; capturing it as a separate item doesn't reduce its complexity, only its proximity to this ship. The sidecar schema with reserved fields silently encodes V2 assumptions without their validation. **Why this isn't right:** the user explicitly picked Full lifecycle in Step 5 — the project values the full feature now over the deferred ship.

## Open questions

- **Threshold tuning.** Default `N=3` hits before auto-promotion is a guess from the detail file. Surface as a config knob `learn.promoteThreshold` (default `3`) from day one so it's tunable per project? Or leave as a constant in the helper and revisit if drift surfaces? Lean toward config knob — costs nothing on ship and avoids re-litigating.
- **Topic-overlap heuristic implementation.** What counts as "overlap" between a user correction's text and a queried bullet's body? Token Jaccard? Specific-noun matching? Simple substring? Detail-file flags false-positive risk; the choice here drives precision/recall.
- **Hit-tracking event boundary.** `/hv-work` and `/hv-review` "consume" a bullet via the query brief — is the hit registered at query time (every consult counts) or only when the bullet appears in a worker brief that doesn't trigger a user correction? Latter is more meaningful but harder to instrument.
- **Migration UX.** `hv-knowledge-migrate` stamps everything `provisional` on first run — but should it run automatically on first F03-aware `/hv-learn` invocation, or require explicit user action? Auto-run trades zero-friction for surprise on the first post-F03 `hv-knowledge-query`.
- **Cross-cycle hit decay.** Should hits decay over time (e.g., halve every 90 days) so stale learnings naturally demote even without corrections? Or rely entirely on the contradiction signal? Decay is a third lifecycle dimension; defer unless we see actual drift in practice.
- **`(provisional)` suffix placement.** End of bullet body, beginning, or via leading emoji? Affects `hv-review` brief readability when bullets land verbatim in worker briefs.

## Assumptions

- **Sidecar is gitignored alongside `.hv/`.** Lifecycle state is local to the project; clones start fresh. (Validate during /hv-plan — if the team wants shared lifecycle state, the sidecar lives in a different place.)
- **Hit-tracking is opt-in per consumer skill.** `/hv-work` and `/hv-review` are the V1 consumers; future skills (`/hv-debug`, `/hv-go`) that pull `hv-knowledge-query` results gain hit-tracking only when explicitly wired.
- **Concurrent sidecar writes are rare.** Multiple parallel `/hv-work` waves consuming the same bullet would race on the JSON write; assume single-orchestrator-at-a-time for V1 and revisit if F05 (`/hv-freeze` scope lock) reveals concurrent-orchestrator patterns.
- **The query helper can read both sources.** `hv-knowledge-query` reads `KNOWLEDGE.md` for content and `.hv/knowledge-stats.json` for tier — the join cost is negligible at current corpus sizes (current corpus: 2 bullets across 2 topics).
- **Amend doesn't change topic or title.** `/hv-learn --amend` rewrites the body of a `(topic, title)` row in place; renaming the topic or title is a delete + re-merge flow, not an amend.
- **Migration is one-shot, not idempotent-replay.** `hv-knowledge-migrate` stamps anything currently in `KNOWLEDGE.md` that lacks a sidecar entry as `provisional`; running it again post-rollout is a no-op.
