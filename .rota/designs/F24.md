# F24 — hv-self-locate preamble consolidation across ~80 helpers

## Goal

Reduce the canonical helper preamble from a 3-line repeated boilerplate (`HERE=` / `. hv-self-locate.sh` / `hv_self_locate`) to a single source line by introducing `bin/hv-preamble.sh`. Bootstrap-order changes (PYTHONPATH default, error path, `HV_ORIG_PWD` semantics) become one-file edits instead of 66-file sweeps.

## Design

Add `bin/hv-preamble.sh`, a new sourceable file with intentional source-time side effects:

```sh
# bin/hv-preamble.sh
HERE="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
export HERE
. "$HERE/hv-self-locate.sh"
hv_self_locate
```

`hv-self-locate.sh` stays untouched — it remains a pure library (defines `hv_self_locate`, no auto-invocation). The new file is the only place that defines+invokes; the convention "sourceable files define, don't run" still holds for `hv-self-locate.sh`. `hv-preamble.sh` is explicitly named "preamble" to signal its side-effecting role.

Caller migration: replace the 3-line preamble in 66 helpers with a single line:

```sh
. "$(dirname "$0")/hv-preamble.sh"
```

`HERE` is exported by the preamble, so downstream `. "$HERE/hv-types.sh"` / `"$HERE/hv-walk-up"` references in caller bodies continue to work unchanged. The migration touches only the preamble block; nothing below it.

Bootstrap helpers that can't depend on the preamble (`hv-preflight` — must work pre-`.hv/`) are excluded explicitly. Sourceable helpers (e.g., `hv-design-list` which uses `${BASH_SOURCE[0]}`) need a slightly different caller shape and are deferred to a follow-up unless trivial.

## Approaches considered

**A. New `bin/hv-preamble.sh` (chosen).** Sourceable file that auto-invokes — exports `HERE`, sources `hv-self-locate.sh`, calls `hv_self_locate`. Caller becomes a single line. `hv-self-locate.sh` remains a pure library.
- *Pros:* Strongest separation — auto-invocation lives in a clearly named "preamble" file; library convention preserved. Single chokepoint for future bootstrap changes.
- *Cons:* One new file. Two related abstractions (`hv-preamble.sh` and `hv-self-locate.sh`) instead of one.
- *Why this is the right answer:* The cost (one new file) is paid once; the benefit (1-line preamble + clean library convention) is paid every time a helper is read, added, or modified.

**B. Two-line preamble (`hv_self_locate` exports HERE).** Modify `hv-self-locate.sh` so `hv_self_locate` derives and exports `HERE` from `BASH_SOURCE[1]`. Callers drop the `HERE=` line but keep `. self-locate` + `hv_self_locate`.
- *Pros:* No new file. Smallest diff. Saves 66 lines total.
- *Cons:* Saves the least — still 2 lines per caller, not 1. The bootstrap-change chokepoint argument weakens because callers still touch the file when, e.g., the locate invocation needs new arguments.
- *Why this is not the right answer:* Incrementalism — saves lines without solving the 66-file-sweep problem at root.

**C. Self-locate auto-invokes on source.** Modify `hv-self-locate.sh` itself to invoke `hv_self_locate` at source time. Caller becomes 1 line; no new file.
- *Pros:* Maximum compression with zero new files.
- *Cons:* Violates the "sourceable files define, don't run" convention this repo holds across `hv-self-locate.sh`, `hv-types.sh`, etc. Source-time side effects in a file named `*-locate.sh` (not `*-preamble.sh`) surprise future readers; the side-effect is hidden behind a name that suggests pure-library shape.
- *Why this is not the right answer:* The convention is load-bearing — breaking it for one file leaks into ambiguity across the rest.

## Open questions

1. **Migration scope for PYTHONPATH heredoc helpers (~14 files).** Helpers like `hv-todo-field` and `hv-archive-old` don't source `hv-self-locate.sh` today; they have a bare `HERE=` for PYTHONPATH. Should they migrate to `hv-preamble.sh` during F24 (consistency), or stay on bare `HERE=` until F25's caller sweep touches them anyway?
2. **Sourceable helpers using `${BASH_SOURCE[0]}` (small set; `hv-design-list` is one).** The `$(dirname "$0")` shape in the new preamble caller breaks when the helper itself is sourced rather than exec'd. Options: (a) provide a second caller pattern using `${BASH_SOURCE[0]:-$0}`, (b) leave these on the 3-line shape and document the exception, (c) audit and migrate them to exec-shape if possible.
3. **Bootstrap exclusion list.** `hv-preflight` must work before `.hv/` exists, so it can't depend on `hv-preamble.sh` (which sources `hv-self-locate.sh`, which expects to find or walk to `.hv/`). Are there other bootstrap-stage helpers with the same constraint? An audit pass — grep for helpers that legitimately operate outside an initialized umbrella — is part of `/hv-plan`.
4. **Verification strategy.** Each migrated helper must keep working under both fast-path (cwd has `.hv/`) and walk-up paths (cwd does not). Smoke section `40_init_mirror.sh` (renumbered in round 6) and friends exercise much of this, but full smoke is slow. Plan likely groups migrations into 5–10 batches and runs a targeted subset per batch.

## Assumptions

- **66 is the true count.** `grep -l "hv-self-locate" bin/hv-* | wc -l` returns 66; "~80" in BACKLOG is an estimate. F24's plan should hard-list the migration set from a fresh grep at plan time.
- **No caller body uses `$HERE` before the preamble runs.** Migration only rewrites the top-of-file 3-line block; bodies are untouched. Spot-checks (`bin/hv-backlog`, `bin/hv-archive-old`) confirm this; full audit is `/hv-plan`'s job.
- **`bin/` is the canonical source.** Per CLAUDE.md, `.hv/bin/` is regenerated on skill update — F24 edits live in `bin/` only.
- **Smoke `bash test/smoke.sh` runs at ship time, not per task.** Per-task verification is structural (grep + targeted reproducer).
- **F25 will refactor PYTHONPATH heredoc bodies regardless of F24's scope.** So leaving PYTHONPATH helpers out of F24's migration does not cost F25 anything material.
