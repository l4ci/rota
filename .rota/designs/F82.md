# F82 — Issue-tracker backend (backlog.backend: issues)

## Goal

Setting `backlog.backend: "issues"` makes GitHub/GitLab issues and native milestones the single source of truth for hv work items, with each item's running context (Q&A, feedback, per-item decisions, design, plan, proof) held in its comments; the default `"file"` backend stays byte-identical to today.

## Design

**Seam.** New `bin/hvlib_backend.py` with `FileBackend` (wraps today's `hvlib_section` / `hvlib_bullet` / `hvlib_paths` logic, no behaviour change) and `IssueBackend` with `GitHubAdapter` (gh; milestones and comment edits via `gh api`) and `GitLabAdapter` (glab; `glab milestone`, notes via `glab api`). Provider comes from `hv-issues-provider` unless `issues.provider` overrides. Existing helpers keep their CLI and select the backend through `load_config()`; skills change only where the issue flow adds steps (labels, comments, PRs).

**Identity.** An item is `#N`. Type = label `type:bug|feature|task`, priority = `p0`–`p3`. Commits and PRs reference `#N`; PR bodies carry `Closes #N`, so merge closes the issue (replaces `hv-todo-drift` in issue mode).

**Verb mapping.**
- capture (`hv-append` + `hv-next-id`) → `issue create` with labels and milestone; detail file content becomes the issue body.
- reads (`hv-todo-field`, `hv-summary`, `hv-backlog`, `hv-todo-by-milestone`, `hv-find-milestone-for-items`) → live `issue list/view --json`; no cache.
- `hv-complete` → close + comment. Reasons: `done` → completed; `dropped` / `handed-off` / `blocked` → GitHub `not planned`, GitLab close + `not-planned` label. `blocked` may instead stay open with a `blocked` label (plan decides). `hv-uncomplete` → reopen.
- proof / design / plan → one marker comment per kind (`<!-- rota:proof -->`, `<!-- rota:design -->`, `<!-- rota:plan -->`), edited in place; `hv-complete`'s proof gate reads the proof comment.
- new `hv-item-comment <#N> --kind question|answer|decision|feedback` → append-only comments for the item's running context.
- file-only verbs refuse with a pointer: `hv-next-id` (IDs are issue numbers), `hv-archive-old` (closed issues are the archive), `hv-rm` (use `hv-complete --reason dropped`).

**Lifecycle.**
- `/hv-next` ranks open issues (`changes-requested` first, then priority) and loads issue + comments as session context.
- `/hv-work` claims: add `in-progress` label + assign @me, re-read the issue, back off if another assignee won. Works on a branch, opens a PR/MR via `hv-pr` with `Closes #N`, swaps label to `needs-review`. Never merges directly in issue mode (`work.mergeStrategy` treated as `pr`).
- `/hv-review --queue` works every `needs-review` issue's PR: PASS → merge (closes issue) + verdict comment; CONCERNS / FAIL → findings comment + `changes-requested`. Unattended merge allowed under `autonomy.level: loop`; proof gate still applies and `--no-proof` is never auto-passed.
- `/hv-ship` in issue mode = open PR + `needs-review`, no direct merge.

**Milestones.** `/hv-vision` creates native milestones (description = milestone detail) plus one pinned tracking issue per milestone, labelled `milestone-tracker`; slice plans (`M01-S01`) and milestone-level designs live there as marker comments, milestone-level Q&A as its comments. `/hv-release`: (1) blocks while the milestone has issues labelled `in-progress` / `needs-review` / `changes-requested`; (2) builds notes from issues closed in the milestone, sectioned by type label; (3) after tagging, closes the milestone and labels shipped issues `released`.

**Umbrella.** Supported in V1: each sub-repo's items live on its own origin's tracker. `Repos:` routing resolves the sub-repo, and the adapter is picked per sub-repo origin. Multi-repo items get one issue per repo, cross-linked; the plan decides whether V1 permits them or restricts issue mode to single-repo items.

**Stays in files.** KNOWLEDGE, DECISIONS, Glossary, MAP, QA stay versioned in `.hv/`; `status.json` keeps the local branch ↔ item map.

**Config.** `backlog.backend` (`file` | `issues`, default `file`); `issues.provider` (`auto` | `github` | `gitlab`); `issues.labels.{inProgress, needsReview, changesRequested, released, notPlanned, milestoneTracker, types.{bug,feature,task}, priorityPrefix}`. Existing `issues.label` becomes an alias of `issues.labels.inProgress`. New rows go into `hvlib_config.CONFIG_KEYS` and surface in `hv-config show`.

**Migration.** `/hv-migrate issues --dry-run|--apply` exports open items (labels, milestone, detail file → body, proof/design/plan → marker comments), writes the old-ID → `#N` map to tracked `.hv/issue-map.json` (helpers resolve old IDs through it), and freezes BACKLOG.md with a header note. Switching back = flip the config.

**Tests.** Smoke gains a fake `gh` / `glab` on PATH that records argv and replays canned JSON; new sections cover each verb on both adapters. Existing sections run unchanged as the byte-identical regression for the file backend.

## Approaches considered

**A. Backend seam in hvlib (chosen).** One abstraction behind unchanged helper CLIs. Pros: one switch point, skills mostly untouched, file path byte-identical (KNOWLEDGE: scope-axis additions via literal legacy resolution), testable with a fake CLI. Cons: helpers accept two ID shapes; file-only verbs need defined issue-mode behaviour; adapter absorbs gh/glab differences. Why: keeps the backend check in one place.

**B. Parallel `hv-issue-*` helper family, skills branch.** Pros: zero risk to file helpers; explicit flows. Cons: 10+ skills carry two flows that drift; the backend check repeats at every call site. Why not: prose duplication is the failure mode this repo keeps paying for.

**C. Sync layer mirroring BACKLOG.md ↔ issues.** Rejected: user chose issues as the only source of truth, no cache, no sync.

## Open questions

- Latency with no cache: measure one `/hv-next` (list + view with comments) on a real GitHub and GitLab project; if too slow, revisit a request-scoped memo (not a persisted cache). Small spike / first plan task.
- Multi-repo items under umbrella + issues: one issue per repo cross-linked, or refuse multi-repo items in issue mode for V1?
- `blocked` close reason: close as not planned, or keep open with a `blocked` label?
- Parallel rounds (`orchestrate-herdr` / tmux dispatch): do workers claim via the same label+assignee path, with the orchestrator as assignee proxy, or does the orchestrator claim on their behalf?
- Comment size limits (GitHub 65,536 chars): large plans may need splitting across marker comments.

## Assumptions

- gh and glab are installed and authenticated; network is available (no offline mode in issue mode).
- One tracker per repo (per sub-repo under umbrella), inferred from origin unless `issues.provider` is set.
- Native milestones; no epic label. The tracking issue is the milestone's comment thread.
- Labels are auto-created on first use (existing `issues.autoCreateLabel`).
- Claim race window (label + assign, then re-read) is acceptable; no external lock.
- gh ≥ 2.45 (close `--reason`), glab ≥ 1.120 (`glab milestone`); comment edits go through the REST API on both.
