# B07 — `hv-migrate` reads top-level `version` while `/hv-init` writes nested `hvSkills.version`

## Symptom

Running the documented v3.x → v4 upgrade path dead-ends:

```
$ /hv-init           # bootstraps, writes hvSkills.version into .hv/config.json
$ /hv-migrate v4
error: refusing: .hv/config.json has no 'version' field — run /hv-init.
```

The refusal message tells the user to run `/hv-init` — which they already did. There is no path forward from inside the skill set without hand-editing config.

## Root cause

`.hv/bin/hv-migrate` line 154:

```python
version = cfg.get("version", "")
if not version:
    die("refusing: .hv/config.json has no 'version' field — run /hv-init.", 1)
```

The helper reads a top-level `version` key. But `/hv-init`'s FRESH write block (`hv-init/SKILL.md`, the `cfg = { ... }` literal) and the STALE write block (`hv-config-set hvSkills.version ...`) both put it under `hvSkills.version`. No code path in `/hv-init` ever writes a top-level `version`.

Hit on a real upgrade: `.hv/config.json` carried `hvSkills.version: "3.3.0"` from a prior bootstrap; no top-level `version`; `/hv-migrate v4` refused.

## Reproduction

```bash
# Fresh project, hv-skills 3.x install, then upgrade plugin to 4.x.
/hv-init                                      # writes hvSkills.version: "3.x.y"
/hv-migrate v4                                # ERROR: no 'version' field
python3 -c "import json; print(json.load(open('.hv/config.json')).get('version'))"
# → None
```

## Suggested fix

In `bin/hv-migrate`:

```python
version = cfg.get("hvSkills", {}).get("version", "") or cfg.get("version", "")
```

Nested-first read with legacy top-level fallback — keeps working for any pre-nesting project that still carries the old shape, and unblocks the canonical post-`/hv-init` shape.

Update the refusal message too — *"run `/hv-init`"* misdirects; the helper should say *"`.hv/config.json` missing version stamp — bug in `/hv-migrate`, see B07"* or similar until fixed.

## Workaround used in the wild

Hand-stamped a top-level `version` mirror via `hv-config-set version 3.3.0` before re-invoking `/hv-migrate v4`. That left the config carrying both keys; the migration helper itself doesn't clean up the temporary mirror.
