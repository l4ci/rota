# B05: `hv-update-check` trusts `CLAUDE_PLUGIN_ROOT` without verifying plugin name

> Related TODO entry: `[B05]` in `.hv/BACKLOG.md`

## Summary

`hvlib.resolve_plugin_root()` accepts `CLAUDE_PLUGIN_ROOT` as the install root as long as a `.claude-plugin/plugin.json` exists there — it never reads the `name` field. When another plugin (e.g. `context-mode`) is the active Claude Code context, `hv-update-check` reports that plugin's path and version as hv-skills's, and `/hv-update` would offer to update the wrong thing.

## Detail

### Root cause

`bin/hvlib.py` `resolve_plugin_root()`, step 2 (lines 714-717):

```python
cpr = os.environ.get("CLAUDE_PLUGIN_ROOT", "")
if cpr and os.path.isfile(os.path.join(cpr, ".claude-plugin", "plugin.json")):
    return (cpr, "plugin")
```

The branch checks file *existence* only. No check that the plugin's declared `name` equals `hv-skills`. Claude Code sets `CLAUDE_PLUGIN_ROOT` to whatever plugin is currently executing — so in a session where context-mode (or any other plugin) is active, hv-skills helpers happily resolve to that plugin's root.

### Reproducer

Smoke section 10 — `test/sections/10_update.sh` ("hv-update-check Claude Code plugin cache layout"). The fixture sets `HOME="$XX_TMP/fake-home"` and builds a fake cache with hv-skills 1.0.0 + 2.0.0, expecting the resolver to find 2.0.0. It fails on macOS in any session where `CLAUDE_PLUGIN_ROOT` is inherited from a non-hv-skills plugin context:

```
FAIL cache-layout: currentVersion != 2.0.0: {
  "installType": "plugin",
  "installRoot": "/Users/hellovolker/.claude/plugins/cache/context-mode/context-mode/1.0.89",
  "currentVersion": "1.0.89",
  ...
}
```

This failure was previously masked by an earlier `stat -c %Y` portability abort in section 01 (now fixed in `7125c52`).

### Real-world impact

Narrow but non-zero:

- The buggy code ships in `bin/hvlib.py` and propagates to every downstream project's `.hv/bin/hvlib.py` via `hv-bootstrap` — this is not a smoke-only artifact.
- In production, `hv-update-check` is virtually always invoked from within an hv-skills slash command (`/hv-update`, `/hv-preflight`, etc.) where Claude Code correctly sets `CLAUDE_PLUGIN_ROOT` to hv-skills. So the bug usually self-cancels.
- It bites when something *else* is the active plugin and a Bash invocation reaches an hv-skills helper, inheriting the wrong `CLAUDE_PLUGIN_ROOT` — cross-plugin sessions, agent harnesses, and the smoke suite itself.

### Fix shape

Guard the `CLAUDE_PLUGIN_ROOT` branch by reading `plugin.json` and confirming `name == "hv-skills"` before returning. On mismatch, fall through to steps 3+ (the `~/.claude/plugins/*/hv-skills` glob and cache walk that already filter by name correctly).

```python
cpr = os.environ.get("CLAUDE_PLUGIN_ROOT", "")
mf = os.path.join(cpr, ".claude-plugin", "plugin.json") if cpr else ""
if mf and os.path.isfile(mf):
    try:
        from hvlib import load_json  # already in module
        if load_json(mf, {}).get("name") == "hv-skills":
            return (cpr, "plugin")
    except Exception:
        pass
# fall through to step 3
```

### Verification

After the fix, section 10's `cache-layout` assertions must pass in a session where `CLAUDE_PLUGIN_ROOT` points at a non-hv-skills plugin (the current Claude Code session here is sufficient). The full smoke suite should run clean on macOS once this and `7125c52` are both in.

### Why P2

P0/P1 implies user-visible breakage. This is a misreport rather than a crash, and the production path that triggers it is rare. Promote to P1 if `/hv-update` is observed offering to update the wrong plugin in a real user environment.
