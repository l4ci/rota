# [F07] Two-stage `/hv-review` split (spec-compliance → code-quality)

Split `/hv-review` into two passes. First pass diffs the change against the active `PLAN.md` task outcomes — does the diff actually fulfill what the plan promised? Second pass runs code-quality/style/edge-case review only when the first pass passes. Short-circuit on plan-compliance failure (missing field, wrong file touched, outcome unmet) so we don't waste a full quality review on a diff that doesn't even match intent. Borrowed pattern from claude-spellbook's `code-reviewer-spec` → `code-reviewer-quality` decomposition.

## Why this is worth the split

- **Cheaper first pass.** Plan-compliance is a small focused diff scan; quality review is a deeper code read. Running quality only after compliance saves the expensive pass when intent is wrong.
- **Better failure messages.** "You promised X, the diff doesn't deliver X" is more actionable than a flat "review failed" with mixed reasons.
- **Leverages an artifact we already produce.** `/hv-plan` writes `PLAN.md` per slice/item. Today `/hv-review` doesn't differentiate plan-fulfillment from style — the artifact is underused.

## Proposed flow

1. **Stage 1 — spec compliance.** Inputs: current diff (or unstaged changes), the matching `PLAN.md` for the slice/item. Output: pass / fail + per-task verdict. Exit early on fail.
2. **Stage 2 — code quality.** Inputs: current diff, project conventions (KNOWLEDGE.md, DECISIONS.md). Output: per-file findings (style, edge cases, missing tests, security, perf).
3. **Combined report.** If both pass, print a green summary. If stage 1 fails, print fail summary + actionable diffs and do not run stage 2.

## Open questions

- Do we need separate sub-skills (`/hv-review-spec`, `/hv-review-quality`) or two phases inside `/hv-review`? Phases inside keep the user-facing surface stable; sub-skills make each stage independently invocable. Lean toward internal phases with a `--stage spec` / `--stage quality` opt-out for power users.
- When there is no `PLAN.md` (item went `/hv-go` straight from `/hv-capture` without `/hv-plan`), stage 1 has no spec to diff against. Fall back to stage 2 only with a one-line note in the report.
- Should plan-compliance check that *touched files* match the plan's declared `Files:` section if one exists? Useful but blocks legitimate scope creep — gate behind a config flag.
