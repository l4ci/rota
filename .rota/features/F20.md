# F20 — v4.0 marketing artifact bundle (ANNOUNCEMENT + CHANGELOG + README rewrite)

## Why

The strategic claim for v4.0 is "the cut IS the marketing." That claim is only true if there's actually a marketing artifact that carries it. Without an explicit deliverable for the announcement framing, the engineering ships and the positioning gets written as an afterthought — which is exactly the failure mode the v4.0 plan must prevent. This feature bundles the three artifacts that, together, make the release land as a story rather than a version bump.

## Three artifacts (all in repo, all merged before tag)

### 1. `docs/announcements/v4-0.md` — the long-form post

Structure (informed by Tailwind v4, Rails Doctrine, Next.js 13, htmx Complexity Budget research):

- **Lead with user experience, NOT the count.** Open: *"You open hv-skills and there are 20 commands. You know what they all do."* Not: *"We cut 8 commands."* (Rails omakase.)
- **State the trade as a complexity budget decision.** One paragraph: *"28 commands meant 8 we maintained, documented, and carried in every user's mental model. That's a tax we kept collecting. We stopped."* Matter-of-fact, no apology. (htmx essay.)
- **Every cut gets a "so you can…" clause.** No bare-courage claims. Example: *"We folded /hv-brainstorm and /hv-spike into /hv-work --preview — so you stop choosing between them when starting something new."* (Apple "courage" cautionary tale.)
- **Receipts table near the bottom.** Two columns: `removed | replaced by`. Enumerate cuts exactly once. Not the headline. (Next.js 13.)
- **Migration footer.** One paragraph: `npx skills add l4ci/hv-skills` to upgrade, then `/hv-migrate v4` to rewrite project state. Link to migration guide.
- **What hv-skills v4.0 will not become.** Optional section (esbuild trust-signal pattern). Names the boundary so users know what to expect.

### 2. `CHANGELOG.md` v4.0 section

- Lead line: matches the announcement's outcome framing, not the count.
- Two-column `removed | replaced by` table — non-negotiable. Every removal has a named successor. Where no replacement exists (`/hv-c`), say *"removed — use /hv-capture (no alias)."* (React 19 discipline.)
- Migration callout: `/hv-migrate v4` is the one command.
- Date stamp, version tag.
- Linkable from the announcement.

### 3. `README.md` rewrite

- "Five lanes" prose reflects the new surface (drop hv-c, hv-assume, hv-rm, hv-undo, hv-issues, hv-context, hv-map, hv-docs from the prose).
- Feature table trimmed to the 20-command surface. Cut the rows describing removed commands; consolidate their successor's row to mention the new flags.
- Add a single banner-style line at the top of "Install" pointing v3 users to the migration: *"Upgrading from v3? Run `/hv-migrate v4` after install."*
- FAQ unchanged (hv-skills vs GSD vs Octo vs TODO.md) — those comparisons are evergreen.

## Sequencing

**Critical:** the announcement must be drafted *first*, before any cut lands. Writing it after invites compromise — the framing softens to fit what shipped instead of what was intended.

1. Draft `docs/announcements/v4-0.md` (this feature, early). Locks the framing.
2. As cuts land (F11–F18), update CHANGELOG.md incrementally with each merge.
3. README.md rewrite is **last**. It can only fully reflect the surface once cuts are in.
4. Final pass: re-read all three together for voice consistency before `/hv-release` tags v4.0.

## Open questions

- Optional `SCOPE.md` ("what hv-skills will not become") — in scope for v4.0 or defer to a later adoption milestone? Lightweight version in the announcement first; standalone doc later.
