# F03 — Knowledge promotion lifecycle in `/hv-learn`

## Why

`/hv-learn` currently writes durable entries to KNOWLEDGE.md on first capture. Two failure modes:

1. **Noise accumulation.** A learning captured in one session may turn out wrong, context-specific, or superseded — but it stays in KNOWLEDGE.md, gets pulled by `hv-knowledge-query`, and pollutes future work.
2. **No confidence signal.** Skills reading KNOWLEDGE.md treat all entries as equally authoritative. A learning that's been validated across 10 sessions reads the same as one captured 5 minutes ago and never re-tested.

Gstack's domain-skills pattern (per-hostname browser learnings) handles this with a quarantine → active → optional-global promotion lifecycle. Adapt to KNOWLEDGE.md entries.

## Shape

Tier each entry:

- **`provisional`** — newly captured. Visible to `hv-knowledge-query` but flagged. Skills surface "(provisional)" suffix when echoing back to the user.
- **`confirmed`** — promoted after N successful applications (default N=3) without contradiction.
- **`deprecated`** — demoted on contradiction signal. Hidden from default query results, kept for audit.

## Signals

- **Usage counter.** Skills that pull an entry via `hv-knowledge-query` and act on it without immediate user correction increment the entry's hit count. Threshold reached → auto-promote to `confirmed`.
- **Contradiction signal.** When `/hv-work` receives a user correction that mentions or implicates a queried learning, demote it. Heuristic: if the user's correction text overlaps with the learning's topic, flag it for review at session end.
- **Manual override.** `/hv-learn --promote <topic>` and `/hv-learn --deprecate <topic>` for explicit user control.

## Open questions

- Where does the hit counter live? Per-entry frontmatter in KNOWLEDGE.md, or a sidecar `.hv/knowledge-stats.json`?
- N for promotion — fixed at 3, or configurable per-tier?
- How is "without contradiction" detected reliably? Heuristic risk: false-positive demotion on noisy user corrections.
- Migration: existing KNOWLEDGE.md entries default to `confirmed` (grandfathered) or `provisional` (re-validate)?
