# F22 — /hv-init mirror-cleanup + /hv-migrate v4 explicit-removal pass

## Why

`/hv-init` Step 2 currently refreshes `.hv/bin/` via `cp "$SRC"/hv-* "$SRC"/hvlib.py .hv/bin/`. `cp` writes the files that exist in canonical source bin/ but **does not remove files that are in `.hv/bin/` but no longer in canonical bin/**. After F18 ships, downstream users running `claude plugin update hv-skills` followed by `/hv-init` end up with BOTH `.hv/bin/hv-glossary-write` (new) AND `.hv/bin/hv-context-add` (stale leftover). The stale binaries still execute as standalone scripts and write to `.hv/CONTEXT.md` which `/hv-migrate v4` has already moved or removed — subtle corruption surface.

Same problem applies to every command cut in M01 (hv-c, hv-assume, hv-rm, hv-undo, hv-issues, hv-context, hv-map, hv-docs) and to every helper rename in the future. Without this fix, the hard-cut promise doesn't actually hold on user disks — only in canonical source.

## Shape — defense in depth

Two complementary changes:

### Change 1: `/hv-init` Step 2 mirrors instead of copies

Replace:

```bash
cp "$SRC"/hv-* "$SRC"/hvlib.py .hv/bin/ && chmod +x .hv/bin/hv-*
```

with a mirror operation that removes stale `.hv/bin/hv-*` files no longer present in canonical bin/. Options to weigh in `/hv-brainstorm`:

- **A. `rsync -a --delete "$SRC/" .hv/bin/` filtered to `hv-*` + hvlib.py.** Cleanest. Requires rsync (universally available on macOS and Linux; Windows users via WSL/git-bash should have it). One-line change.
- **B. Pre-cp cleanup with find:** `find .hv/bin/ -maxdepth 1 -name 'hv-*' -type f -delete` then the existing cp. No rsync dependency. Two-step but explicit.
- **C. Explicit allowlist from a manifest file** (`bin/MANIFEST.txt` lists every shipping helper; `/hv-init` removes any `.hv/bin/hv-*` not in the manifest). Most precise; adds a maintenance burden on the manifest.

Brainstorm decides A vs B vs C. A and B both blast through any user-dropped `.hv/bin/hv-<custom>` helpers — by design, since `.hv/bin/` is canonical-mirrored, not user-customizable.

### Change 2: `/hv-migrate v4` (F19) explicit-removal pass

`/hv-migrate v4` already scans and rewrites references. Add an explicit `removed_binaries` list to its pass — for each v4 cut, name the canonical bin/ binaries that no longer exist:

```
removed_binaries:
  - .hv/bin/hv-context-add        # F18: renamed to hv-glossary-write
  - .hv/bin/hv-context-query      # F18: renamed to hv-glossary-read
  - .hv/bin/hv-map-add            # F12: hv-map auto-only
  - .hv/bin/hv-map-first-run      # F12
  - .hv/bin/hv-undo               # F13: folded to /hv-ship --undo
  - .hv/bin/hv-issues-pull        # F16: folded to /hv-capture --from-github
  - .hv/bin/hv-docs-sync          # F17: folded to /hv-ship --docs
  - …
```

`/hv-migrate v4 --apply` removes each listed file from `.hv/bin/` if present, backing up to `.hv/migrate-backup/<timestamp>/bin/<filename>`.

The actual binary names need verification (`ls bin/hv-*` to enumerate which helpers each cut removes from canonical source). Done in `/hv-plan F22`.

### Why both

- Change 1 fixes the class of bug for **all future renames/removals**, not just v4.0. Future cycles inherit the cleanup automatically.
- Change 2 catches the v4.0 case **even for users who skip `/hv-init` post-plugin-update** — a real path, given hv-update SKILL.md offers a "skip — I'll run /hv-init later" option.

Either alone leaves a real gap. Together they're complete.

## Acceptance

- `/hv-init` Step 2 mirrors canonical `bin/` into `.hv/bin/` (stale binaries removed), per the option chosen in F22's brainstorm.
- `/hv-migrate v4` carries a tested `removed_binaries` list covering every binary removed by M01 cuts (cross-reference F11–F18 acceptance to compile the list).
- Smoke-test section: stage a `.hv/bin/hv-context-add` (stale-from-v3) in a tmpdir, run `/hv-init` with canonical source pointing at v4 bin/, assert `.hv/bin/hv-context-add` is gone post-init.
- Smoke-test section: stage same scenario, but run `/hv-migrate v4 --apply` instead of `/hv-init`, assert removal + backup at `.hv/migrate-backup/<ts>/bin/hv-context-add`.
- Documentation: hv-init SKILL.md Step 2 prose notes that `.hv/bin/` is now canonical-mirrored; any user-dropped helpers in `.hv/bin/` will be removed on next `/hv-init`. Guidance points users to place custom helpers outside `.hv/`.

## Open questions

- Option A (rsync) vs B (find -delete + cp) vs C (manifest). Decided in `/hv-brainstorm F22`.
- For users with custom `.hv/bin/hv-<x>` helpers (anyone?): announce as breaking change, or assume nobody does this? Worth grepping social signal before deciding.
- Should Change 1 also mirror `bin/hvlib.py` and any other non-`hv-*` files in canonical bin/? Currently the cp explicitly names `hvlib.py`; what's the broader rule?
- Should `/hv-migrate v4`'s `removed_binaries` list also apply to projects whose hvSkills.version is v2.x or earlier (not just v3 → v4)? Likely yes; flag in F19's plan.
- Order between F22's two changes — do they need to ship together, or can Change 1 land first (it fixes the class of bug) and Change 2 follow? Working answer: ship together so M01 is coherent.

## Risk

This is a load-bearing change. `/hv-init` is the most-run skill across the user base. A bug here breaks installs. Smoke coverage and a manual dogfood pass on hv-skills's own .hv/bin/ are non-negotiable acceptance.
