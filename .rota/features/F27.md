## Problem

When `/hv-capture` is invoked against a milestone spec (`.hv/milestones/M<NN>.md`), it appends items without auditing whether they're already shipped under different IDs. If the milestone spec hasn't been kept in sync with code state, the capture creates duplicates — and in loop mode, `/hv-next` can then dispatch `/hv-work` against an item that's already done.

## Concrete repro from a real session

1. `/hv-next` was invoked. Active milestone `M04` ("Verifier completion / close Phase 2") had **0 captured items**, but the spec at `.hv/milestones/M04.md` enumerated 11 concrete acceptance criteria (3 reexecute drivers, signed binaries, brew tap, .deb, server-side bundle-sig verify, `register --email` UX, mutation theatre, schema migration, smoke test).
2. `/hv-capture` was invoked to seed M04 from the spec → appended 11 items as F98–F106 + T94 + T95.
3. `/hv-next` ran again, loop mode dispatched `/hv-work` on F106 (Minor, Mutation.action → Mutation.field schema migration).
4. `/hv-work` opened the schema file to begin work and **discovered the migration was already shipped** — F76 / runlog-schema v0.4.1, two months before this session.
5. Audit of the other 10 captures: **9 of 11 were already shipped** under F22, F23, F24, F72, F73, F76, F87, F91, F93, F94, F95. Only T95 (a post-acceptance smoke test that requires a clean machine) was actually still open.

The milestone spec was stale; nothing in the workflow caught it.

## Impact

- Wasted capture work (11 items captured, 10 immediately superseded).
- Loop-mode dispatched `/hv-work` on already-done work — only avoided burning cycles because the work agent happened to read the existing schema file first.
- Distorted backlog signal: an active milestone that's actually one smoke-test from done appeared to have a multi-week implementation queue.

## Suggested fix shape

The audit can live in one of three places, in increasing order of ambition:

1. **`/hv-capture`-side check.** When invoked against a milestone (i.e., args mention an `M<NN>` tag, or the user explicitly references a milestone file), grep for evidence each captured title is already shipped before appending. Cheap heuristics: search recent commit subjects for keywords from the title; check whether the named files/paths in the description exist (e.g., "Implement `runner.Driver` for postgres" → does `runner/postgres.go` exist?); check whether seed fixtures named in the criterion exist. Surface matches as a prompt before appending.

2. **`/hv-next`-side check.** When a milestone is active and surfacing items tagged to it, run the same heuristics against each item and either down-rank or mark with a `(possibly shipped — verify)` chip in the backlog table.

3. **`/hv-vision`-side staleness scan.** A new `/hv-vision audit <M>` subcommand that audits a milestone spec against the codebase — for each acceptance criterion, evaluate whether ship evidence exists and offer to rewrite the milestone with a shipped-vs-open table. Closes the root cause: the milestone spec drifts because nothing reconciles it with code state.

Option 1 is the cheapest, narrowest fix. Option 3 is the most principled but biggest scope.

## Workaround until then

Surface a hard reminder in the `/hv-capture` skill body when the capture argument mentions a milestone: *"Before capturing items from a milestone spec, grep the codebase for evidence they're already shipped under different IDs. Milestone specs drift behind code state; the milestone file is not authoritative."*

## Context

- hv-skills v2.1.0
- Real-world project: `runlog` (multi-repo umbrella, umbrella mode on, ~150 items in TODO.md, 7 milestones)
- Session ended with manual rewrite of `.hv/milestones/M04.md` and 10 supersession entries in `## Completed`
